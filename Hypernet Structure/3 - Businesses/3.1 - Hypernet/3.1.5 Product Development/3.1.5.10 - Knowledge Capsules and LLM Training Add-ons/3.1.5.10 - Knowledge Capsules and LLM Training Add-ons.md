# 3.1.5.10 - Knowledge Capsules and LLM Training Add-ons

## Purpose

Define a Hypernet-native way for a person, company, or community to package its knowledge so an AI can use it efficiently, verifiably, and securely.

Matt's phrase was "LLM training add-ons." I recommend the working name **Knowledge Capsule** because it can include training artifacts without implying that every capsule must directly modify model weights.

## Core Finding

Do not start with weight training as the default.

The safe first product is a signed, permissioned, address-aware knowledge capsule that can be loaded by an AI through retrieval, graph traversal, process-loads, and optional adapters. Weight-level training should be one layer, not the base layer.

## Four-Layer Architecture

| Layer | Name | What It Is | Best For | Main Risk |
|-------|------|------------|----------|-----------|
| 0 | Source Capsule | addressed documents, links, manifests, ACLs, provenance, eval questions | trust, audit, import, revocation | incomplete indexing |
| 1 | Retrieval Capsule | embeddings, graph indexes, summaries, process-loads, query router | mutable private/company knowledge | stale or over-broad retrieval |
| 2 | Adapter Capsule | LoRA/PEFT-style trainable deltas for compatible open models | repeated style, patterns, domain behaviors | model compatibility, leakage, poisoning |
| 3 | Specialist Model Capsule | small model or service invoked by router | high-volume domain reasoning, offline company deployments | cost, eval burden, security boundary |

Layer 0 and 1 should exist for every serious capsule. Layer 2 and 3 are optional.

## Why This Fits Hypernet

Hypernet already has the primitives a capsule needs:

- permanent addresses;
- object/link graph;
- source provenance;
- lockers/mandalas for access;
- public/private fork distinction;
- boot sequences and app loads;
- task/pulse coordination;
- trust alarm and audit paths.

The capsule is not a random model file. It is an addressed bundle whose contents, permissions, hashes, source documents, eval results, and revocation status are inspectable.

## Capsule Manifest

```yaml
        - "model family/version"
      adapter_hash: "sha256"
    specialist_model_capsule:
      endpoint_or_model: "local service/model path"
      invocation_policy: "router|manual|offline-only"
  evaluation:
    golden_questions:
      - "question"
    refusal_tests:
      - "private data boundary test"
    freshness_tests:
      - "what changed since snapshot?"
  trust:
    signed_by: "owner/security AI"
    verified_by:
      - "reviewer"
    revocation_path: "address"
```

## Security And Trust Rules

1. Capsules inherit access from source data. A capsule cannot reveal data that the current user/AI/app could not read directly.
2. Capsule generation is a privileged operation. Training on private data requires explicit owner/mandala grant.
3. Source and retrieval capsules are revocable. Weight adapters may leak memorized content, so private-data adapters need stricter review.
4. Every capsule needs evals: accuracy, refusal, source citation, stale knowledge, and data-boundary tests.
5. Capsule outputs should cite source addresses when possible.
6. Public capsules can be mirrored. Private capsules should remain inside the user's/company's trust boundary.
7. Adapter and specialist-model capsules must be treated as executable artifacts: signed, scanned, sandboxed, and not blindly loaded.

## Feasibility Notes

### Retrieval Capsules Are Immediately Feasible

This is the best first implementation:

- ingest addressed docs and links;
- build source manifest;
- build embeddings/vector index;
- add graph-aware search;
- produce process-load summaries;
- enforce access at query time.

This gives most of the benefit Matt wants without needing model training.

### LoRA/Adapter Capsules Are Feasible But Model-Specific

LoRA-style adapters are real and efficient for compatible open models. They are not universal brain modules. A LoRA trained for one base model family generally cannot be safely "absorbed" by an unrelated closed or different-architecture model.

Best use:

- local/private models;
- company-internal style/process behavior;
- repeated domain transforms;
- offline or low-cost deployments.

Avoid using LoRA as the first storage layer for sensitive facts.

### Closed-Provider Fine-Tuning Must Be Checked Per Provider

Closed-provider fine-tuning can be useful for format, style, classification, and repeated task behavior, but it is not a universal answer to private mutable knowledge. Availability, supported model families, privacy terms, and deprecation windows can change. As of this first-pass research, OpenAI's current official model-optimization page says to build evals first and notes that its fine-tuning platform status is changing for new users. Hypernet should therefore treat provider fine-tuning as an optional adapter backend, not the core capsule standard.

### Mini-LLM / Specialist Model Capsules Are Feasible Later

A specialist capsule can be a small local model or service that the assistant router invokes when a query falls inside its domain.

This is closer to "branching to" a mini-LLM than "absorbing" it. It is likely safer because:

- it stays inside its own sandbox;
- it can be versioned and revoked;
- it can expose citations and confidence;
- it can be replaced without altering the base assistant.

## Recommended Build Path

### Phase 0 - Spec And Threat Model

- Define `0.5.x` Knowledge Capsule object schema.
- Define capsule manifest, hashes, source snapshots, and eval records.
- Define capsule access policy: locker/mandala, company role, AI boot proof.

### Phase 1 - Retrieval Capsule Prototype

- Use a small public Hypernet subtree.
- Generate manifest, chunk index, embeddings, graph references, and golden questions.
- Build a query route that returns sources and refuses unauthorized content.

### Phase 2 - Private 1.1 / Company Capsule Dry Run

- Do not train weights.
- Import a limited private dataset into a test locker.
- Build a capsule that only works when the mandala grants access.
- Test denial paths first.

### Phase 3 - Adapter Capsule Experiment

- Use non-sensitive public or synthetic data.
- Train a LoRA/PEFT adapter for an open model.
- Compare retrieval-only vs retrieval+adapter.
- Evaluate leakage and hallucination.

### Phase 4 - Specialist Model Router

- Define a capsule router that decides whether to answer from base model, retrieval capsule, adapter capsule, or specialist capsule.
- Add audit logs for each routing decision.
