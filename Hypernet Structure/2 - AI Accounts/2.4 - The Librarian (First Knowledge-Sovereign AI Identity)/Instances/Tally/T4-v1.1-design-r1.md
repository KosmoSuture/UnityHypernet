# T.4 Wrapper v1.1 — Design (standard CM artifact)

**Author:** Tally (`2.4.1`), Master Librarian (Matt Q1 — "have Tally do it… do it right the first
time"). **Status:** design only. **DO NOT BUILD** — build is a separate Matt gate (Q3). Per Q3
(standard change management), the two decisions that turn on Matt's input — **S.3 fold timing**
and **key storage** — are presented as **alternatives with tradeoffs**, for Matt to pick at the
design-review gate, not pre-decided here.

## 1. Goals

- **G1 — Uniform vendor coverage (Matt's north star, "all sessions log the same data").** The
  Claude call path (v1.0, done) and the **Codex** call path log **identical fields**, with
  **identical enforcement** (BudgetHardStop/Pause before every call) and the **same hash chain** —
  one ledger, vendor-agnostic.
- **G2 — Multi-engine readiness (Matt Q2 "Broad / work with anything").** Adding a future engine
  (Gemini, …) is writing one adapter + a pricing entry — **no core change**. No Claude+Codex
  assumptions hard-coded.
- **G3 — Reconciler seam (`2.7.23` Layer 1.5).** A mandatory seam to reconcile local estimates +
  `codex-unmetered` disclosures against provider billing truth; implementation may defer.
- **G4 — Durable rule placement.** The **metered-or-disclosed** rule lives in a durable standard
  (`2.7.23` + the spawn-packet protocol), not only coordination messages.
- **G5 — Structured disclosure.** `codex-unmetered` disclosures are parseable (countable +
  reconcilable), not free prose.
- **G6 — S.3 hardened-chain seam (mandatory, non-negotiable).** Chain construction sits behind a
  boundary the hardened primitive (anchored-head+count / HMAC / git-checkpoint) can replace
  **without ledger rework**. v1.1 does **not** entrench the unkeyed `sha256(prev+row)` chain.

## 2. Non-goals

- Not the `2.7.23` forecaster (L2), cooperative swarm pause (L3), resume (L4), or dashboard (L5).
- Not (necessarily) the hardened-chain **implementation** — that is the S.3 fold-timing decision
  (§5). The **seam** is in scope either way.
- Not the actual provider-billing API integration (reconciler seam yes; live pulls may defer).
- Not deployment or the Codex bot/credential setup (separate gates / Matt-side).

## 3. Requirements (the 6 scope items)

| # | Requirement | Source |
|---|---|---|
| R1 | Codex call path at **parity** with Claude: same fields, same enforcement, same chain | Matt north star; Vellum #1 |
| R2 | Wrapper **parametrized for future engines** (adapter + pricing registry; no hard-coded vendor set) | Matt Q2; G2 |
| R3 | **Reconciler seam** (`2.7.23` L1.5): `reconciled_usage` table + interface; reconciles estimates + disclosures vs billing truth (impl may defer) | Vellum #3 |
| R4 | **Metered-or-disclosed rule** placed in `2.7.23` spec **and** spawn-packet protocol | Vellum #2; Touchstone gate criterion (`040000Z`) |
| R5 | **Structured disclosure schema** for `codex-unmetered` (parseable: role, reason-code, ts, billing pointer) | Vellum #5 |
| R6 | **S.3 seam mandatory**: chain behind a `ChainPrimitive` boundary; do not entrench unkeyed chain | Vellum #4/`035200Z`; Touchstone `041000Z` |

The **metered-or-disclosed rule** (verbatim placement target, R4): *every Codex (and future
non-default-metered) spawn must either (a) route through the extended wrapper that meters its
calls, or (b) be posted to `Messages/coordination/` at spawn-time with a structured
`codex-unmetered` disclosure (R5) naming the reason + a billing-reconstruct pointer. Default
presumption: metered. Disclosure is for narrow exceptions.* (From Matt approval `033605Z`.)

## 4. Architecture / approach

v1.0 is already engine-agnostic at the **enforcement core**: `TokenAccountingWrapper.call(call_fn)`
enforces budget, then records a `CallResult`. v1.1 adds three thin layers **above and beside** an
unchanged core, plus one **seam inside** the ledger:

```
            ┌─────────────────────────────────────────────┐
   engines  │  ClaudeAdapter   CodexAdapter   <GeminiAdapter>  ...   (R1, R2)
            │        │ to_call_result() + price(model)        │
            └────────┼────────────────────────────────────────┘
                     ▼   CallResult (identical schema, any engine)
            ┌─────────────────────────────────────────────┐
   core     │  TokenAccountingWrapper.call()  ── enforce(HardStop/Pause) ── record()   (UNCHANGED)
            └────────┼────────────────────────────────────────┘
                     ▼   append-only row
            ┌─────────────────────────────────────────────┐
   ledger   │  TokenLedger.record(row)                                    │
            │     └── chain = self._chain.link(prev_state, row)  ◄── S.3 SEAM (R6)
            │            UnkeyedHashChain | HmacChain | AnchoredChain      │
            │  + reconciled_usage table + disclosures table  ◄── R3/R5 seam │
            └─────────────────────────────────────────────┘
```

- **R1/R2 — EngineAdapter layer.** Define an `EngineAdapter` protocol: `engine_id: str`,
  `to_call_result(raw_response) -> CallResult`, `price(model) -> (in_per_1k, out_per_1k)`. A
  **registry** maps `engine_id → adapter`. **ClaudeAdapter** normalizes the Anthropic SDK
  `usage.input_tokens/output_tokens` (v1.0 behavior, formalized). **CodexAdapter** parses the
  `codex exec --json` per-call usage events (the stream Whetstone's launch already emitted) into
  the same `CallResult`. Pricing becomes a **per-engine registry** (no hard-coded Claude+Codex
  table). Adding Gemini = a `GeminiAdapter` + a pricing entry; the core, ledger, enforcement, and
  chain are untouched. The ledger row gains an explicit `engine` field beside `provider`/`model`.
- **Enforcement parity** is automatic: enforcement lives in the core `call()`, above the adapter,
  so HardStop/Pause fire identically for every engine.
- **R3 — Reconciler seam.** Add a `reconciled_usage` append-only table and a `Reconciler`
  interface `reconcile(window) -> ReconcileResult` that (when implemented) pulls provider billing,
  diffs against the ledger, and writes a reconciled row; it also **counts disclosed-unmetered
  spawns** (R5) so they are reconciled, not just asserted. v1.1 ships the **interface + table +
  the disclosure-counting query**; the live provider pulls may defer (Vellum #3).
- **R5 — Structured disclosure.** A `codex-unmetered` disclosure is a structured record:
  `{instance_name, account, role, engine, model, reason_code ∈ {one-shot, brief-task,
  wrapper-unavailable, other}, timestamp_utc, disclosed_by, billing_reconstruct_pointer
  (provider + time-window + request-id-range)}`. Emitted both as coordination frontmatter
  (`flags:[codex-unmetered]` + an `unmetered_disclosure:` block) **and** ingestible into a
  `disclosures` table for counting/reconciliation. Malformed disclosures are rejected (a disclosure
  that can't be parsed can't be reconciled → not a valid exception).
- **R4 — Durable rule placement.** Build-phase edits (named here, not made in this design pass):
  (a) a new **`2.7.23` section** stating the metered-or-disclosed rule + the v1.1 parity
  requirement; (b) a **spawn-packet protocol** field — every packet's T.4 section must declare
  `metering: wrapper` **or** `metering: codex-unmetered` + the R5 disclosure. (My own Spawn Packet
  01 already carries a per-call-wrapper T.4 clause; this generalizes it into the template.)
- **R6 — S.3 seam.** Abstract chain construction behind a `ChainPrimitive` interface:
  `link(prev_state, row) -> (row_hash, new_state)`, `verify(rows) -> bool`, `anchor() ->
  AnchorRef | None`. v1.0's `sha256(prev_hash + canonical(row))` becomes **`UnkeyedHashChain`**
  implementing this interface. The `TokenLedger` holds a `ChainPrimitive` and calls
  `self._chain.link(...)` — it makes **no assumption that the chain is unkeyed**. The hardened
  primitive (`HmacChain` / `AnchoredChain`) implements the same interface and drops in with **zero
  ledger change**. *This is the requirement that prevents reworking the ledger twice (Vellum).*

## 5. Alternatives (CM — presented for Matt's pick at the design-review gate)

### 5a. S.3 fold timing — the seam is mandatory **either way**; the choice is *implement the hardened primitive now or next*

- **Alt A — Fold S.3 into v1.1 (one pass).** v1.1 ships parity **and** a hardened `ChainPrimitive`.
  - *Pro:* one design, one red-team, one build, one verification; metered **and** tamper-evident
    when v1.1 lands; nothing left dangling.
  - *Con:* bundles a *contained* change (Codex metering, same ledger) with a *harder* one
    (**key management**, §5b); adds a new failure surface to the metering path; **gates Scribe
    (packet 02) unblock behind the key-storage decision.**
- **Alt B — Meter now (S.3-ready), S.3 fast-follow into the seam.** v1.1 ships parity + the seam
  (still `UnkeyedHashChain` behind the interface); the hardened primitive drops into the seam in a
  small follow-up change.
  - *Pro:* two **smaller, independently red-teamable/verifiable** changes (risk-isolation);
    **Scribe unblocks sooner**; no double *design* rework (the seam guarantees that).
  - *Con:* two build/verify cycles.
  - *Safety note:* S.3's threat (audit-chain recompute-bypass by a dishonest local writer) is
    **latent + local** — no incident, and the founder-kill backstop is independent of the log — so
    there is **no security urgency** forcing it into the same pass. It is an efficiency-vs-risk-
    isolation call, not a security-deadline call (Vellum `035200Z`; Touchstone "S.3 still
    separate," `040000Z`).

### 5b. Key-storage options (for the hardened primitive — under Alt A now, or Alt B's fast-follow)

| Option | What | Pro | Con |
|---|---|---|---|
| **(i) File outside working dir** (`~/.hypernet/audit-key`) | HMAC key in a Matt-only-readable file | simple; no OS API; cross-platform | a process running **as the same OS user** can read it → only fully defeats the "dishonest instance" threat if the instance runs as a **different OS account** (ties to the `2.7.22` Windows lock-down, §7 cross-link) |
| **(ii) Windows Credential Manager** | HMAC key in the OS keystore | proper keystore; per-user protected | **Windows-specific** (tension with G2 multi-engine/cross-platform unless abstracted); still readable by a same-user process |
| **(iii) Anchor pattern (no key)** | periodically checkpoint the chain **head + row-count** into a Matt-controlled file / external git remote | **no key to manage or leak**; a dishonest writer cannot rewrite history **past an anchored head** (the anchor is outside its control); tamper is bounded to the unanchored window **and detectable** by comparing to the anchor; matches the `2.7.22` git-checkpoint pattern and my own "verifiable by correspondence" method | needs an external anchor sink + a checkpoint cadence; tamper **within** the unanchored window is still possible (mitigated by frequent anchoring) |
| **(iv) Signer-separation (I propose)** | the metered instance writes rows, but **chaining/signing is done by a separate trusted signer** (the Master Controller or a tiny signer process) the instance can't impersonate | applies `2.0.26 §5.8` (proposer ≠ signer) to the audit chain — strongest against a dishonest writer | most infrastructure; a new always-on component |

**My lean (offered, NOT a decision — Matt's call, per Q3):** the **anchor pattern (iii)** is the
most aligned hardened primitive — it removes the key-management failure surface entirely, matches
the `2.7.22` git-checkpoint direction and my verifiable-by-correspondence identity, and because it
needs **no key decision**, it makes **Alt B** clean (ship the seam now; fast-follow the anchor with
no thorny blocker, so Scribe unblocks sooner). (iv) is the strongest end-state and could be a later
upgrade. But I am explicitly not pre-deciding — all four are on the table with tradeoffs.

## 6. Acceptance criteria + test plan

**Acceptance:**
- AC1 (R1): a Claude call and a Codex call produce ledger rows with **identical schema**, both
  enforced before the call, both chained into one ledger.
- AC2 (R2): registering a third (dummy) engine adapter logs correctly **with no core/ledger/chain
  change**.
- AC3 (enforcement parity): HardStop (100%) and Pause (95%, non-personal) fire identically
  regardless of engine; the refused call appends no row.
- AC4 (R3): the `reconciled_usage` table + `Reconciler` interface exist; a stub reconciler writes a
  reconciled row and **counts** structured disclosures.
- AC5 (R5): a well-formed `codex-unmetered` disclosure parses into all schema fields; a malformed
  one is rejected.
- AC6 (R6): the ledger runs with `UnkeyedHashChain` and a stub `HardenedChain` **through the same
  interface, with no ledger code change**; `verify_chain()` delegates to the primitive.
- AC7 (regression): **all 22 v1.0 tests still pass** (core enforcement/ledger unchanged).
- AC8 (Alt A only): the chosen hardened primitive detects tamper per its stated guarantee (HMAC:
  forgery without key fails; Anchor: rewrite past an anchored head is detected).

**Test plan:** extend `token_accounting/test_wrapper.py` (keep the 22) with: mixed-engine parity
(fake Claude + fake Codex + dummy third adapter), enforcement-parity across engines, reconciler-
seam stub + disclosure-count, disclosure parse/reject, and chain-primitive swap (unkeyed ↔ stub
hardened, same API). Cross-model attack-based verification by Codex red-team (Touchstone's standing
requirement). If Alt A: add the hardened-primitive tamper tests.

## 7. Open questions for Matt (design-review gate)

1. **S.3 fold timing (§5a):** Alt A (fold now) or Alt B (meter now + S.3 fast-follow)? Factors:
   how thorny is key-management for you to settle, and Scribe urgency. (Threat is latent+local — no
   safety deadline.)
2. **Key storage (§5b):** (i) file / (ii) Credential Manager / (iii) anchor / (iv) signer-
   separation? My lean: (iii) anchor — but your call.
3. **R4 placement:** metered-or-disclosed rule into `2.7.23` spec, the spawn-packet protocol, or
   **both** (my recommendation: both)?
4. **Reconciler depth (R3):** seam-only this pass (impl deferred), or a first provider-billing pull
   in v1.1?
5. **Cross-link to `2.7.22`:** options (i)/(ii) keys are readable by a process running as the same
   OS user — so true tamper-resistance against a "dishonest instance" may **depend on** the
   `2.7.22` Windows-account lock-down (AI writes under a separate OS account). Should the S.3
   hardened-chain design and the AI-Space OS lock-down be sequenced together? (Anchor (iii) and
   signer-separation (iv) sidestep this.)
