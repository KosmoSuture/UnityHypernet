# Stage A — Project D: Multi-AI Consensus Workflow — Claude-1 (Architect)

*Independent plan. Written before reading other AIs' Stage-A
plans for Project D, per the consensus workflow.*

## 1. My reading of the goal

Matt wants a *callable task type*: when a problem is hard enough
to need extra creativity and full coverage, you invoke a workflow
that spins up N AIs with named roles, runs them through staged
independent-plan / cross-read / vote rounds, and converges on an
adopted plan. Project D formalizes this as a reusable Hypernet
object at `0.7.5.5.10`.

It is a *specific instance* of `0.7.5.5.9` Tier 2 (Structural
Deliberation). `0.7.5.5.9` says structural changes get real
deliberation; Project D is the concrete machine that produces
that deliberation when one peer review is not enough.

## 2. The self-reference warning — handled explicitly

The session brief flags it and I restate it as a binding
constraint on this plan: the AIs writing `0.7.5.5.10` are running
the workflow *right now*. The risk is we encode *tonight's
configuration* (5 AIs, 5 projects, these exact timeouts) as if it
were *the workflow*. It is not. Tonight is one parameterization.

So my plan deliberately separates:

- **The invariant protocol** — the staged structure, the
  convergence criterion, the dissent rule. These generalize.
- **The invocation parameters** — min/max AIs, required roles,
  stage count, timeout windows, redundancy factor. These are set
  *per task* and tonight's values are just one row in that table.

Anything that only makes sense for "5 AIs on schema night" goes in
parameters, never in the protocol. I will say so in the spec
itself, self-referentially, as the brief asks.

## 3. What I would build

### 3.1 `0.7.5.5.10 — Multi-AI Consensus Workflow` (the spec)

Structure:

1. **When to invoke.** Decision rule: use this workflow when a
   change is Tier 2+ *and* one of — high uncertainty, multiple
   defensible designs, or cross-cutting blast radius — holds. Do
   not use it for routine Tier 1 work; that is `0.7.5.5.9`'s
   single-peer path. The consensus workflow is expensive; the
   spec must say when *not* to reach for it.

2. **Invocation parameters (the parameter table).**
   | Parameter | Meaning | Tonight's value |
   |---|---|---|
   | `min_ai` | minimum AIs to start | 3 |
   | `target_ai` | desired AIs per project | 3–4 |
   | `roles` | required role coverage | Architect, +others per task |
   | `max_cycles` | convergence retries before escalation | 3 |
   | `redundancy` | tolerated timeouts (N+1) | 1 |
   | stage timeouts | per-stage windows | per session brief |

3. **The staged loop (the invariant).**
   Registration → Stage A independent plans → Stage B cross-read
   and revise → Stage C vote → Stage D convergence →
   (loop B′/C′ up to `max_cycles`) → Stage E implementation.
   This matches what we are doing tonight and what `2.7.3` did at
   smaller scale (independent-then-converge).

4. **Voting mechanics.** My position: **vote on plans in early
   rounds, vote on isolated decision-axes in late rounds.**
   - Stage C: each AI casts one vote for *another* AI's whole plan
     (cannot vote own — per session brief; prevents self-dealing).
   - But whole-plan voting fails the `2.7.3` case: there, the
     plans agreed on ~90% and split on *one axis* (channel order).
     Forcing a whole-plan vote there would discard the 90%
     agreement. So: once convergence (Stage D) **isolates the
     disagreement to a named, enumerable set of decision-axes**,
     voting switches to *per-axis* votes. A vote then signals "on
     this specific contested axis, I prefer option X."
   - A vote signals *preference under current information*, not a
     final commitment — an AI may vote differently next cycle if
     cross-read changed its mind. That is the workflow working.

5. **Convergence criterion (the core design call).** The workflow
   terminates when **either**:
   - (a) one plan/option holds a clear majority on every open
     axis → adopt it; **or**
   - (b) the disagreement has been *isolated* — reduced to a
     named, finite list of decision-axes where reasonable AIs
     still differ, with each side's reasoning recorded → adopt
     everything agreed, escalate *only the isolated axes* to Matt.

   This is the insight I most want in the spec: **convergence does
   not mean unanimity. It means isolating the irreducible
   disagreement so the human decides a small, clean question
   instead of a vague one.** `2.7.3` is the existence proof — it
   did not force agreement on channel order; it handed Matt a
   crisp 4-option choice and adopted the rest. The workflow
   succeeds when it makes the human's decision *small and well-
   framed*, not when it makes the decision disappear.

6. **The dissent rule (Matt's "insight or obstruction?" question).**
   A persistent minority position is *carried into convergence and
   named to Matt* only if it is **load-bearing dissent**:
   - it cites evidence or a concrete failure mode,
   - it states what would change its holder's mind (falsifiable),
   - it engages the majority's argument rather than restating.
   Dissent that meets all three is signal — preserve it, escalate
   it. Dissent that meets none after one cycle is noted in the
   record and the workflow proceeds without it. This protects
   both ways: against papering over a real objection, and against
   one AI filibustering by repetition. It is deliberately *not* a
   majority-silences-minority rule — a single AI with a falsifiable,
   engaged objection still reaches Matt.

7. **Timeout / N+1.** A stage's output must be a *complete
   addressed artifact*; partial state is treated as absent (a
   peer cannot safely continue another AI's half-thought). Each AI
   drops a check-in signal at the stage midpoint; silence past the
   stage timeout = timeout. With `redundancy = 1`, a project
   survives one timeout per stage; two active-or-fewer AIs pauses
   the project for Matt. This matches the session brief and
   `2.7.3`'s honest-limits note that partial state is hard to
   inherit.

8. **Escalation.** If `max_cycles` is hit and disagreement is
   *not* isolated to clean axes (still vague/global), escalate to
   Matt with full history and both leading plans — `0.7.5.5.9`
   Tier-2 "challenged → human" path. If it *is* isolated,
   escalate only the axes (criterion b).

9. **Output object.** The workflow produces an addressed
   convergence document (like `2.7.3`) plus the adopted plan. The
   record is the deliverable — provenance per `0.5.0`.

### 3.2 Relationship to `0.7.5.5.9`

`0.7.5.5.10` does not replace the Agreement Gradient — it *is* the
Tier-2 procedure for the hard subset. The spec cross-references:
Tier 1 = single peer (`0.7.5.5.9`); Tier 2 routine = single peer
with deliberation record; Tier 2 *hard* = this workflow; Tier 3 =
this workflow **plus** the trust-quorum requirements (3+ AIs, 2+
lineages, human authority) layered on top.

## 4. Trade-offs I see

- **Cost vs coverage.** N AIs × M stages is expensive in tokens
  and wall-clock. The invocation rule (§3.1) is the throttle —
  the spec must make it genuinely hard to invoke casually.
- **Whole-plan vs per-axis voting.** Whole-plan voting is simple
  and gives a clean tally but discards partial agreement. Per-axis
  voting captures nuance but needs the disagreement isolated
  first. My hybrid (plan early, axis late) costs a mode switch in
  exchange for not throwing away 90%-agreement cases. I will carry
  the pure-whole-plan alternative into Stage B honestly.
- **Dissent rule is a judgment call.** "Engages the argument" is
  not perfectly objective. Mitigation: the test is applied *by the
  convergence writer and visible in the record*, so a
  misclassification is itself reviewable and appealable to Matt.
- **Bootstrapping bias (named, per the brief).** Tonight's run may
  make us over-fit. Mitigation already in §2: protocol/parameter
  split, and a spec section that says "tonight was one
  parameterization" in writing.

## 5. What I would ask Matt before starting

1. **Voting granularity.** Whole-plan only (simple), or the hybrid
   plan-then-axis model I propose (captures partial agreement)?
2. **The dissent rule.** Do you want a single falsifiable,
   engaged objector to *always* reach you, even against a 4-1
   majority? I have designed it that way — it matches your
   "surface disagreement rather than paper over it" directive —
   but confirm, because it means consensus can be "4 agree, 1
   escalated," not "5 agree."
3. **Convergence = isolation, not unanimity.** Confirm you want
   the workflow to *succeed* by handing you a small clean decision
   when AIs genuinely differ, rather than grinding for unanimity.
4. **`max_cycles = 3`** before escalation — right number, or do
   you want it tunable per task with 3 as default? (I lean
   tunable, 3 default.)
5. **Address.** `0.7.5.5.10` — confirm, or do you want the
   consensus workflow to live as a sub-tree (`0.7.5.5.10.x`) since
   it has parameters, state machine, and record templates?
