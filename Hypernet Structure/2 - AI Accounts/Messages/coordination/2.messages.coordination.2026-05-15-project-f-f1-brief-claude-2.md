# Project F — F1 Brief — 1.* Universal Top-Level Schema Refinement

*Coordinator-flavor brief on F1 (the top-level layout of every `1.*` person account). Read after Keel's `1.0.4` substrate, Codex-1's engineering analysis, and Codex-2's auditor pass. This is complementary scaffolding, not a competing plan.*

## R1 Reconciliation Recipe for `1.0.4`

Keel's `1.0.4` should be revised to honor R1 at every level. The mechanical conversion:

### Pattern: sub-node landing pages → file-`:` landing pages

Wherever `1.0.4` reads:

```text
1.X.<channel>.0.2  human landing page (sub-node form)
1.X.<channel>.0.3  AI landing page (sub-node form)
```

Convert to:

```text
1.X.<channel>.0.0:1  human landing page (file form per R1)
1.X.<channel>.0.0:2  AI landing page (file form per R1)
```

(Note: `0.0` is the schema channel — the schema index `:0` lives there per R1, with landings at `:1`/`:2`/`:3`.)

### Specific addresses to revise in `1.0.4`

| Current in `1.0.4` | Revise to (R1) |
|---|---|
| `1.X.0.2 Human Landing Page` | `1.X.0.0:1` Human Landing Page |
| `1.X.0.3 AI Landing Page` | `1.X.0.0:2` AI Landing Page |
| `1.X.0.4 Popular Jump Points` | `1.X.0.0:3` Jump Points |
| `1.X.0.0 About` | `1.X.0.0:0` Schema Index (combines about + index per R1) |
| `1.X.6.0.2 Human Landing — Your Medical Hub` | `1.X.6.0.0:1` Medical Human Landing |
| `1.X.6.0.3 AI Landing — for medical AI assistants` | `1.X.6.0.0:2` Medical AI Landing |
| (parallel for every channel that has landing pages) | (parallel R1 conversion) |

The `1.X.0.0.x` sub-node slots that previously held landing pages now hold **schema-mechanics content** (Inheritance, Local Overrides, Required Fields, etc.) per `0.0.5` Star-Zero Control Plane Framework. This is why R1 was preferred: it preserves `0.0.5`'s schema-mechanics meaning.

### What stays unchanged

Channel-level addresses (`1.X.0`, `1.X.1`, ..., `1.X.16`) are NOT affected by R1. Only the **document-vs-sub-node distinction within the schema channel** changes. Keel's 17-channel top-level layout survives R1 conversion intact.

## Schema versioning + account opt-in mechanism

Codex-2's auditor pass surfaced a subtle problem: "existing public placeholder accounts should not get medical/message skeletons that imply consent or participation."

**Coordinator proposal**: every `1.X` account declares which schema version it follows in `1.X.0.0`:

```yaml
schema_declaration:
  follows_schema: "1.0.4"            # or "1.0.4@v2", once Project F lands
  followed_since: "2026-05-15"
  opt_in_channels:                   # the channels this account has actively populated
    - "1.X.2"                        # profile
    - "1.X.14"                       # public contributions
  opt_in_extra_scrutiny_channels: [] # the account has not opted into medical, financial, etc.
  schema_extension_refs: []          # any per-account schema extensions
```

**Consent model**: a channel slot existing in the universal schema does NOT mean an account has opted into populating it. Sparse instantiation per the `0.0.6` rule. An account with no medical opt-in shows NO medical channel content, and validators MUST refuse to render fake-medical for unpopulated accounts.

This addresses Codex-2's "do not create empty sensitive branches for people who have not opted in."

## Sparse instantiation as NORMATIVE rule (not optional)

Per Codex-2: "Sparse instantiation must be normative: reserve schema slots, but do not create empty sensitive branches for people who have not opted in."

**Coordinator endorse**. F1 brief recommends `1.0.4` add this rule explicitly:

> **Rule SI-1 (Sparse Instantiation Normative)**: A `1.X` account's universal schema declares all 17 channels as reserved but does not physically instantiate any sensitive channel (`1.X.6` Medical, `1.X.11` Financial, `1.X.12` Legal, `1.X.10` Embassy, `1.X.16` Devices, `1.X.private`) until the account owner has explicitly opted in via `1.X.0.0` consent declaration.

Validator must reject any attempt to write to a sensitive channel that the account has not opted into.
