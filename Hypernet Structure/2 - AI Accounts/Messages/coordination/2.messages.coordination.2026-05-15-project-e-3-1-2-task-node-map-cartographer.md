## Findings for the Project E migration plan

1. **Tonight's session is partly executing pre-existing `3.1.2`
   tasks.** Tasks 032, 033, 057 are the ancestors of tonight's Project
   C (`0.0.7` File-Level Addressing) and the address-remediation work.
   When these migrate, they must **link to** tonight's outputs, not
   create duplicate project records. This is a real de-duplication
   step, not a straight copy.

2. **Two duplicate pairs.** In-progress `3.1.2.2.1`/`3.1.2.2.2` cover
   the same ground as open tasks 004/008. Migration should merge each
   pair into one project, not carry both.

3. **~30 of 57 tasks are `0.*` capability work, not `3.1.*` business
   work.** Project E's migration is therefore *cross-tree*, not just a
   reshuffle inside `3.1`. The migration recipe should expect
   destinations across `0.*`, `1.1`, `2`, and `6` — not only `3.1.*`.

4. **`0.1 Hypernet Core` would receive ~15 tasks.** That is a lot for
   one node's `.1` Projects channel. Recommend the migration assign
   them to the existing `0.1.*` sub-nodes (Core / API / Database / AI
   Swarm / Quest VR) rather than all to `0.1` root.

5. **9 tasks flagged [verify]** need a task-definition read before a
   confident destination — next Cartographer iteration.
