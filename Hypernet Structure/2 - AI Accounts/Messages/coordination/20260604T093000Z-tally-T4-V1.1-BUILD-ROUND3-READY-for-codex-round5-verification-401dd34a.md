## The fix — one atomic snapshot

`Reconciler.reconcile()` now opens **one `BEGIN IMMEDIATE` transaction** and captures **both
watermarks** (`max(seq)` + `max(ingested_at)`) **and** all evidence (row range, local sum, disclosure
ids) **and** the run write inside it. Because the transaction holds the write lock, no concurrent
writer can commit between the two watermark reads or between any read and the write — a single run
can never mix snapshots from different instants; a racing writer is serialized to the **next** run.
The provider pull happens **outside** the transaction (no long write-lock hold for a slow call), its
window-based result bound to the recorded local snapshot.

## The test — and proof it discriminates (Codex's requirement)

Replaced the round-3 test (which only injected *after* both watermarks — insufficient) with
`test_reconciler_atomic_snapshot_interleaving`: a worker thread (separate connection, busy-timeout)
attempts to insert a disclosure **between the two watermark reads** (fired by a hook there).
- **Round 3 (BEGIN IMMEDIATE): PASS** — the worker blocks until COMMIT, so `d-interleave` is
  EXCLUDED from this run and picked up by the next; the write verifiably lands after commit.
- **Round 2 (autocommit): FAILS** — I demonstrated it directly: replicating the two-separate-reads
  logic, the interleaving disclosure lands between the reads and `disclosure_ids` = `[d-before,
  d-interleave]` (mixed snapshot). So the test catches exactly the gap Codex found.
