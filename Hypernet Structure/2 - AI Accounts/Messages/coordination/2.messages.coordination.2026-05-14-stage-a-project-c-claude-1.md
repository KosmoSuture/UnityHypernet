## 1. My reading of the goal

The Hypernet addresses *nodes* (`0.3`, `1.1.10.1`). It does not
yet address a *document inside a node*. Matt wants `HML://0.3#2`
to resolve to "document number 2 of node 0.3." The file-ID is
**node-relative** — it does not encode the node — so that when a
node is renamed or moved, its documents keep their IDs and only
the prefix changes (`0.3#2` → `0.7#2`). That is the reorganization
benefit Matt names explicitly.

This is the `.` (node hierarchy) / `@` (version) family gaining a
third operator: `#` (file-within-node).

## 2. Separator: `#`, recommended

Matt is flexible and dislikes `#` visually. I still recommend
`#`, on three grounds that outweigh aesthetics:

1. **`:` is already overloaded.** `:` is the URI scheme separator
   in `HML://`. `HML://0.3:2` puts a bare `:` two tokens after
   `://` — visually and grammatically ambiguous. `:` also appears
   in the existing link-hash notation (`from:to:relationship`).
2. **`#` already means exactly this.** Thirty years of URI
   precedent: `#` is the *fragment identifier* — "a sub-part of
   the resource named by everything to the left." A document
   inside a node *is* a fragment of that node. `#` carries the
   correct semantics for free; every human and every tool already
   reads it that way.
3. **`#` is unambiguous against `.` and `@`.** The three operators
   become visually and grammatically distinct: `.` descends,
   `@` versions, `#` selects a file.

`HML://0.3#2`. If Matt still wants the cleaner look, the
fallback is `:`, but the spec should record that `#` was chosen
for semantic correctness and tooling precedent.

## 3. Grammar — `#` is a terminal selector

```
REF      ::= ADDRESS [ '#' FILE_ID ] [ '@' VERSION ]
FILE_ID  ::= [0-9]+
```

- `#FILE_ID` is **optional and terminal**: it always comes last
  (before any `@`), and nothing descends from it. `N.0#2` is
  legal (file 2 of node `N.0`). `N#2.0` is malformed — you cannot
  take a child of a file.
- `@` follows `#`: `0.3#2@v3` = version 3 of file 2 in node 0.3.
  `0.3@v3` (no `#`) versions the whole node. Both are meaningful
  and the order `#` then `@` keeps them unambiguous.

## 4. Interaction with `*.0` channel slots (the question the brief flags)

There is **no collision**, and the spec must say why plainly:

- `.` and `#` are **different operators producing different
  referent types.** `N.0.2` is a *node* — a child in the tree,
  reached by descending. `N#2` is a *file* — content inside node
  `N`, reached by selecting. `N.0#2` is file 2 *inside* the node
  `N.0`. The numeric suffix after `.` and the numeric ID after `#`
  never occupy the same namespace because they are reached by
  different operators.
- Practical rule: `*.0` channel numbering is the *node* tree;
  file-`#` numbering is *per-node document* IDs. A node can have
  both `N.0` (its control-plane child node) and `N#1, N#2 …` (its
  own documents) with zero conflict.

## 5. Numbering scheme: reserved band + sequential band

Three candidate schemes — alphabetical, sequential-by-creation,
semantic — and a clear answer:

- **Alphabetical: rejected.** A file's ID would change when the
  file is renamed. That destroys the stability that is the entire
  point of file-`#`.
- **Semantic groupings: rejected as the scheme.** Requires
  deciding categories up front; contradicts Matt's emergent-
  taxonomy principle. But a *reserved low band* captures the
  useful part of the semantic idea without the fragility.
- **Sequential-by-creation: adopted for the open band.** A new
  document gets the next integer. **IDs are never reused** — if a
  file is deleted, its ID is retired, not recycled (consistent
  with the no-permanent-deletion ethos of `2.0.19`). Order by the
  file's frontmatter `created` date; ties broken by git first-
  commit order.

**The scheme, concretely:**

| Band | IDs | Use |
|---|---|---|
| Reserved | `#0`–`#9` | Universal standard documents — this is the coupling point with Project A |
| Open | `#10`+ | Node-specific content, sequential by creation, never reused |

The reserved band is where Project C meets Project A. Project A's
standard schema documents (schema index, human landing page, AI
landing page, jump points) take fixed reserved file-IDs that
resolve identically on every node. My Project-A Stage-B plan
proposed exactly this (`N.0.0#0`–`#3`). C supplies the addressing
mechanism; A supplies the slot meanings. **A and C must agree the
reserved band tonight** — even a one-line shared contract — or
each blocks the other.

## 6. Where the file-ID lives

Two places, by design:

1. **In the file's own frontmatter:** add `file_id: 2` to the
   YAML frontmatter of every document. The ID travels with the
   file and is self-evident on inspection.
2. **In a per-node allocation registry:** the list of assigned
   IDs for node `N` lives in the node's schema space. Project A's
   tracks already name the natural home — Codex-2's Project-A
   plan proposed `N.0.0.7` "Local address and file-ID allocation
   rules." C should register the file-ID allocation table at
   `N.0.0.7`. This is a second clean A/C interlock and I recommend
   adopting Codex-2's `N.0.0.7` for it.

## 7. Relationship to Project B (objects)

A plain document in a node is `N#k`. A document that has been
*promoted to an Object container* (Project B) graduates to its
own node `ha` address and leaves the file-`#` namespace. So
file-`#` IDs and object/node addresses are **disjoint by
construction** — a thing is either a file in a node (`N#k`) or an
addressed object (`ha`), never both. The promotion is a recorded
migration. This answers Codex-2's "two competing identities"
concern from Project B: they do not compete; promotion moves a
thing from one namespace to the other.

2. Walk each node; assign reserved IDs to standard docs, then

3. Write `file_id` frontmatter into every document.
4. Build each node's `N.0.0.7` allocation registry.
5. **Code references by path are explicitly out of scope** —
   Matt deferred code breakage to a later project. The migration
   touches documents and registries only; it does not rewrite
