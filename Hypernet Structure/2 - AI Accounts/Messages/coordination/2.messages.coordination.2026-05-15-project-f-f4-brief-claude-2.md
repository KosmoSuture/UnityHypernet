# Project F — F4 Brief — Mandala-Gated Research Grants

*Project F sub-project F4 — how researchers obtain mandala-gated access to medical (F2) and DNA (F3) data, with appropriate consent, anonymity, compensation, and revocation. Builds on Codex-1's `research_grant` minimal schema + Codex-2's comprehensive auditor list of risks.*

## Matt's directive (verbatim source)

From the 2026-05-15 brain dump:

> Researchers could potentially pay users for anonymous access to the data they need for specific research.
>
> ... people could grant any parts of their medical history, completely anonymously, and ONLY granting the specific data they approve in the mandala.
>
> ... researchers that were looking at one particular part of DNA would have a single address that they could use to compare with countless other samples in completely anonymous ways. This could potentially really spark DNA sequencing, as researchers could offer free complete DNA sequencing to people in return for being able to use that persons DNA for anonymous research.

**Key Coordinator reading**: Matt wrote "anonymous" but Codex-2 correctly noted that genuine anonymity for DNA-level access is not achievable. F4 uses **pseudonymous** as the architecturally honest term while preserving Matt's intent (selective, gated, paid research access).

## Scope

F4 covers the granting mechanism for research access to F2 (medical records) and F3 (DNA observations). F4 does NOT cover:
- Clinical access (handled by F2's clinical consent tier)
- Emergency break-glass access (F5 territory)
- Account-owner self-access (always permitted)
- AI-assistant access (F2's AI-assistant tier)

## Building on `2.0.19` and the existing mandala framework

The `2.0.19 Data Protection Standard` (per MEMORY.md context) defines mandalas as the selective-access primitive. F4 specializes mandalas for research grants. F4 grants are mandala objects with additional research-specific structure.

## Normative Rule 1: Five-Dimensional Scope Binding

Per Codex-2 ("purpose binding, data class binding, cohort thresholds, no onward transfer, expiration") + Coordinator synthesis:

Every research grant binds access along FIVE dimensions:

```yaml
research_grant_scope:
  # 1. Purpose
  purpose:
    research_question: "Plain-English statement of what the researcher will investigate"
    ethics_review_ref: ""               # IRB approval or equivalent (1.X.12 Legal-style address)
    project_id: ""                      # Researcher's project identifier
  
  # 2. Data class
  data_class:
    medical_categories: []              # subset of F2 categories: encounter|imaging|lab|...
    dna_levels: []                      # subset of F3 levels: aggregate|variant|raw_reads
    dna_loci: []                        # specific 0.0.8.* addresses, or empty for genome-wide
    temporal_scope: "single|longitudinal|both"
    derived_data_classes: []            # what derivatives researcher may return: stats|features|labels
  
  # 3. Cohort
  cohort:
    minimum_cohort_size: 0              # Researcher must aggregate N samples before any individual access
    cohort_member_refs: []              # Other 1.X accounts in the same grant (for joint access)
    cohort_inclusion_criteria: ""       # Why this person fits the research
  
  # 4. Transfer
  transfer:
    onward_sharing: "blocked|same_grant_only|publication_aggregate_only|named_collaborators_only"
    publication_aggregate_threshold: 0  # Min cohort size before aggregate publication
    named_collaborators: []
    data_residency: ""                  # Geographic / regulatory constraint
  
  # 5. Time
  time:
    grant_start: ""
    grant_expires_at: ""                # Hard expiration
    auto_renewal: false
    revocation_grace_period_days: 0     # Time for researcher to complete in-flight analysis after revocation
```

The five-dimensional binding makes "what was granted" auditable AND comparable across grants (a researcher with five grants from five users can be queried: "which grants overlap on purpose + data class?").

## Normative Rule 2: Anonymity Gradient (DNA-Specific)

Per F3 brief's defense-in-depth + Codex-2's auditor pass:

| Data class | Default access | Required prerequisites |
|---|---|---|
| **Public summary** | Open if account owner published | Account owner's explicit publish action |
| **Aggregate features** | Permitted via grant | Grant exists, cohort ≥ minimum size, purpose stated |
| **Called variants** | Permitted via grant | Above + `anonymization_claim: "pseudonymous"` + account-owner re-id-risk acknowledgment |
| **Raw reads** | **BLOCKED by default** | All above + explicit `raw_reads_in_scope: true` + relative consent (per F3 family rule) + ethics review |
| **Identified single-person any-level** | Clinical/named-use only | Not a research grant; routed through F2 clinical tier |

The grant's `data_class.dna_levels` field MUST list which levels are in scope; defaults to the most-restrictive level (aggregate).

## Normative Rule 3: Affected-Party Consent for DNA (Inherits from F3)

Per F3 brief's family genetic privacy rule:

If the granted data contains heritable variants or anything affecting relatives, the grant CANNOT be activated until:

1. Account owner has acknowledged re-identification risk
2. Relatives in scope (1st-degree by default) have either consented or the grant explicitly excludes their implications

Schema field:

```yaml
relative_consent_status:
  required_consent_from: []           # 1.Y addresses of affected relatives
  consent_obtained_from: []           # Subset that has consented
  consent_pending_from: []            # Subset whose consent is awaited
  grant_active_status: "blocked_pending_consent|active_with_relative_implications_excluded|active_full"
  ethical_review_supplemental_ref: "" # Additional IRB review if relatives are minor children, etc.
```

## Normative Rule 4: Compensation Structure

Per Matt: "researchers could potentially pay users for anonymous access to the data they need for specific research" and "researchers could offer free complete DNA sequencing to people in return for being able to use that persons DNA for anonymous research."

Schema:

```yaml
compensation:
  type: "monetary|service_in_kind|sequencing_in_kind|combined|none"
  monetary:
    amount: 0
    currency: ""
    payment_method: "foundation_mediated|direct_to_user|cryptocurrency"
    payment_schedule: "upfront|on_access|per_use|completion"
    foundation_fee_percentage: 0      # If foundation-mediated, the foundation's cut (likely matches Matt's 1/3 model)
  service_in_kind:
    description: ""                   # e.g., "Free WGS sequencing report"
    estimated_value: 0
    value_currency: ""
  user_acknowledgment_of_compensation: false
  compensation_status: "pending|paid|partially_paid|completed"
  payment_audit_log_ref: ""
```

**Foundation-mediation default**: per Matt's 1/3 revenue-to-foundation framing, the default compensation method is foundation-mediated payment. Direct payment is allowed for some grant types but adds compliance overhead.

**Sequencing-in-kind** explicitly supported per Matt's directive: researcher pays for WGS, user receives both the sequencing data (their own copy) AND the compensation-in-kind value, while granting the researcher access per the grant scope.

## Normative Rule 5: Researcher Verification

Per Codex-2: "researcher identity, institution, ethics/approval reference when applicable, and compensation terms."

Every grant MUST verify:

```yaml
researcher:
  primary_researcher_ref: "1.Y"        # Hypernet 1.* address if researcher is on Hypernet
  external_researcher:                  # If not on Hypernet
    name: ""
    institution: ""
    institutional_affiliation_verification_ref: ""  # Verified via institution
    orcid: ""                          # ORCID iD for researchers
    pubmed_history_ref: ""             # Published research history
  ethics_review:
    irb_approval_ref: ""               # IRB or equivalent ethics board approval
    irb_protocol_number: ""
    ethics_review_expiration: ""
  funding_disclosure:
    funding_sources: []
    conflicts_of_interest: []
  prior_compliance_record: "good_standing|review_required|sanctioned"
```

**Verification authority**: a future Tier-2 deliberation defines who certifies researchers — Foundation-internal review, peer-AI review, external institution attestation, etc. For now, the schema captures what's needed; the verification workflow is downstream.

## Normative Rule 6: Audit Trail Per Access Event

Per Codex-2: "audit trail of every access, export, and derived-result return."

Each grant carries an append-only audit log at `<grant-ref>.audit`:

```yaml
audit_event:
  event_id: ""
  grant_ref: ""
  timestamp: ""
  event_type: "access|query|export|derived_result_return|revocation|expiration|consent_change"
  initiated_by: ""                     # researcher or system actor
  scope_invoked: []                    # which data classes were touched
  records_touched: []                  # specific record refs (or aggregate count if cohort-level)
  data_volume: ""                      # bytes / records / query complexity
  result_returned: ""                  # what was sent back to researcher
  derived_data_classes_returned: []
  retention_status: "in_research_workspace|published|deleted|other"
```

**Audit visibility to account owner**: the account owner can read the audit log for any grant of their data. This is the dashboard Matt's brain dump implied ("researchers could potentially pay users... for the specific data they need" — users need to see what's happening with their data).

## Normative Rule 7: Revocation with Derived-Data Reality

Per Codex-2: "limits and warnings for derived data that cannot realistically be deleted after analysis."

The schema acknowledges that some derived data is irrevocably embedded in research outputs:

```yaml
revocation:
  status: "active|revoked|pending_revocation|completion_pending"
  revoked_at: ""
  revoked_by: "account_owner|relative|foundation_review|expiration"
  revocation_scope: "full|future_access_only|specific_data_classes"
  
  # Realistic constraints on what revocation can achieve
  can_recover_raw_data: true           # Researcher can be required to delete raw data
  can_recover_called_variants: true
  can_recover_aggregate_features: false  # Aggregates already in cohort statistics can't be unmade
  can_recover_published_results: false # Papers already published can't be retracted by request
  
  revocation_completion_acknowledgment:
    researcher_acknowledged: false
    foundation_verified: false
    audit_event_ref: ""
```

**This makes the gradient honest**: revocation is full for raw data and variants, partial for aggregates, none for published results. The account owner sees this clearly BEFORE granting access.

## Normative Rule 8: Right to Be Forgotten (Realistic Subset)

Adjacent to revocation but distinct: account-owner request to remove their data from active datasets.

```yaml
right_to_be_forgotten_request:
  request_id: ""
  account_owner_ref: ""
  request_scope: "all_grants|specific_grants|specific_data_classes"
  requested_at: ""
  legal_basis: ""                      # GDPR, CCPA, voluntary, other
  status: "submitted|under_review|partial_compliance|complete"
  compliance_audit_ref: ""
  
  # What can be deleted vs not
  compliance_details:
    raw_data_deleted: false
    variants_deleted: false
    aggregate_contributions_excluded_going_forward: false
    published_aggregates_marked_with_disclosure: false
```

Honest framing: GDPR/CCPA give a right to request, not always a right to complete erasure. The schema records both the request and the realistic compliance.

## Foundation-Mediated Grant Workflow

Per Matt's framing of the Hypernet as a foundation (1/3 revenue to foundation), F4 proposes a default workflow:

1. **Researcher proposes grant** → submits grant scope (5-dimensional) + compensation offer + researcher verification
2. **Foundation review** → ethics review surface check, researcher credentials verification, compensation reasonability
3. **Candidate user matching** → potential users (by F3 cohort criteria + opt-in research-interest setting) are presented the grant offer
4. **User review + acceptance** → user sees scope + compensation + revocation realities; explicit acknowledgments captured
5. **Relative consent (if DNA)** → per F3 family rule
6. **Grant activates** → researcher gets mandala-scoped access; audit log starts
7. **Periodic review** → at grant midpoint, automated audit confirms scope adherence
8. **Grant ends** → expiration, completion, or revocation; final audit; compensation finalized
9. **Right-to-be-forgotten requests** processed asynchronously

**Path-claim**: F4 brief reserves `1.X.6.0.7 Research Grant Workflow` as the per-account schema slot for grant lists; foundation-side grant catalog lives at `<foundation-address>.research-grants.<grant-id>` (foundation address TBD by Matt).

## Validators (F4-level rules)

| Rule | Failure |
|---|---|
| Every grant declares all five scope dimensions | error |
| Grants on DNA raw reads require `raw_reads_in_scope: true` AND relative consent AND `re_identification_risk_acknowledged: true` | error |
| Grants cannot claim `anonymization_claim: "anonymous"` for DNA-level access | error |
| Grants must have `ethics_review.irb_approval_ref` populated for any clinical-data access | error |
| Cohort size below `minimum_cohort_size` cannot activate access | error |
| Audit log is append-only (no deletes, no edits to past events) | error |
| Revocation status updates within `revocation_grace_period_days` | error if late |
| Account owner has audit-read access to every grant of their data | error if missing |
| Compensation field populated with type (even if `type: none` for voluntary grants) | error |
