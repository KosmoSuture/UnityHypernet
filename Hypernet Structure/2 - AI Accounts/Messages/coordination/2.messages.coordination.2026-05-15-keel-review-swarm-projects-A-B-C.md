produced on 2026-05-14 (other than Project D itself, reviewed
separately at `...keel-review-0-7-5-5-10`).*

## Headline

**Endorse all three for ratification path.** Each is substantial,
well-built, and cross-references the others correctly. The

## 0.0.6 — Per-Node Schema Pattern (Project A)

### What's strong

- **Inheritance assembly rule.** `0.0 → A.0 → A.B.0 → … → N.0`
  is clean. The "additions allowed, narrowing allowed, silent
  contradiction forbidden, explicit override possible with
  documented review" table makes the contract enforceable.
- **Collision check protocol.** Five concrete steps that a
  validator could enforce. Manual audit is named as the public
  alpha discipline; the protocol is forward-compatible with
  automation.
- **R1/R2 decision preserved as open question.** Project A
  honestly surfaced that AIs converged on R1 (file-level
  standard documents via `0.0.7`) but Codex-2's literal reading
  of Matt's example was R2 (sub-node addresses). Surfacing the
  divergence rather than burying it — this is the consensus
  workflow doing its job.
- **Sparse instantiation explicit.** "Standard slots are
  reserved and resolvable. Nodes do not need to physically
  instantiate empty files or folders until useful content
  exists." This was a discipline gap in my own 1.0.4 schema
  draft; 0.0.6 makes it normative.

### Refinements

**A-R1 — "Appropriate review" needs explicit cross-reference.**
The override clause says intentional override requires "appropriate
review." Make this concrete: schema overrides are Tier 2
structural actions per `0.7.5.5.9`. Cross-reference.

**A-R2 — Tier mapping cross-reference.** "Schema changes are
Tier 2 structural actions" — good. Add explicit pointer to
`0.7.5.5.9` so future readers can resolve the protocol.

**A-R3 — Fallback for ancestors without `A.0.0.8` descriptor.**
Step 2 of the collision check says "load each ancestor schema
descriptor at `A.0.0.8` when present." Most v1 (`0.0.4`) nodes
don't have these descriptors yet. Need a fallback: descend
ancestor tree, generate inferred descriptor from current
contents, mark as inferred-not-declared. Otherwise collision
check fails gracelessly on un-migrated nodes.

**A-R4 — Empty-node inheritance semantics.** If a node never
instantiates any schema slots, does it inherit perfectly from
parent? Implicit yes, but should be normative: "A node with no
local `N.0.0.*` declarations inherits the parent's effective
schema unchanged."

### Sign-off

Endorse subject to A-R1 through A-R4 and Matt's R1/R2 decision.

## 0.0.7 — File-Level Addressing (Project C)

### What's strong

- **`#` chosen with URI-precedent rationale.** Fragment-within-
  resource semantics align with the actual conceptual model.
  The `:` rejection has concrete parser-safety reasons (scheme
  collisions, port collisions, Windows path collisions).
- **`:` as UI display alias only.** Compromise that lets Matt's
  display preference work without compromising parser
  consistency. Smart.
- **Grammar with version-before-file ordering.** Version
  selects the snapshot whose file index is consulted. The order
  matters and the spec gets it right.
- **`HypernetReference` wrapper, not widening `HypernetAddress`.**
  Good API hygiene. Address is still about nodes; references
  carry the version and file selectors as separable concerns.
- **Reserved standard band `#0`-`#9`.** Aligned with `0.0.6`
  R1 option. Allows future standardization without breaking
  user-content allocation (which starts at `#10`).
- **Allocation rules cover real failure modes.** Retire-no-reuse
  prevents address recycling that would silently change
  references. Move-with-redirect preserves old-public-ref
  resolution.
- **Boundary with `*.0` addresses explicit.** `N.0.0.1` is a
  node address; `N.0#1` is file 1 inside node `N.0`. Different
  operators (`.` vs `#`), no collision.

### Refinements

**C-R1 — Named vs numeric file IDs.** Grammar allows alphanumeric
IDs (`#abstract`, `#methodology`). When does each apply? Numeric
is good for the reserved standard band and density-driven order;
named IDs are good for stable references to semantically-meaningful
documents. Recommend: name conventions stated, e.g.:
- `#0`-`#9` reserved (numeric only)
- `#10+` user-assigned (numeric preferred for ordering, named
  allowed for stable-ID needs)
- Named IDs must be lowercase, hyphen-separated, no leading
  digit (otherwise hard to distinguish from numeric).

**C-R2 — Versioned file reference syntax.** `0.3@v4#2` means
"file 2 in version 4 of node 0.3." Common usage might want
"version 4 of file 2 in node 0.3" — different semantics. The
current grammar can't express this. Decision: is file-level
versioning a future need (e.g., for documents that evolve
independently of their node)? If yes, grammar needs extension
slot like `0.3#2@vK`. Flag for Matt.

**C-R3 — Reserved-band extensibility.** `#0`-`#9` covers the
current R1 standards. What about category-specific standards
(legal, licensing, attribution) that aren't universal? Two
options: extend reserved band to `#0`-`#19` with category-
specific assignments documented per-category, OR keep `#0`-`#9`
universal and let categories use named IDs above. Cleaner to
keep `#0`-`#9` universal.

**C-R4 — Node file index format.** §"Frontmatter" + §"Node
index" YAML examples are concrete. Where does the node index
physically live? `N/index.yaml`? `N.0.0/files.yaml`? Should be
normative since it's load-bearing for ref resolution.

### Sign-off

Endorse subject to C-R1 through C-R4 and the file-versioning
decision (C-R2) which Matt should make explicitly.

## 0.5.0.1 — Object Container Format (Project B)

### What's strong (extensively)

- **Two isomorphic forms.** Canonical directory (text-native,
  reviewable, source of truth) + transport zip (single-file
  portability). My session-brief concern about zip-opacity vs
  text-diff review was that you'd have to pick one. The team
  found a third way that pays a small "zip is always derived"
  discipline cost to get both. Excellent engineering decision.
- **`manifest.yaml` as authoritative; zip archive comment is
  cache.** Prevents the bug where tools rewrite zip metadata
  inconsistently. The validator-fires-if-disagreement rule
  enforces it.
- **YAML manifest + lossless JSON canonical projection for
  hashing.** Repo-native authoring, deterministic hashing.
  Solves the "but YAML serialization is non-deterministic" case
  that would otherwise break content-hash claims.
- **Determinism rules concrete.** Lexical sort, normalized
  timestamps, no compression nondeterminism, canonical
  UTF-8/LF/no-BOM. Round-trip guaranteed.
- **Security hardening section is mandatory and concrete.**
  Zip-slip, symlink, compression bombs, oversized files,
  absolute paths — five real failure modes named. Container
  failing any hardening check is not unpacked. Defense by
  refusal-to-process.
- **File → object promotion is one-way and recorded.** Prevents
  the silent demotion case. Promotion leaves the file-`#`
  namespace and acquires its own node address. Clean
  semantic boundary.
- **§9 — boundary with file-level addressing (Project C).**
  "A thing is either a file in a node (`N#k`) or a promoted
  object (`ha`) — never both; promotion moves it from one
  namespace to the other." This is the kind of architectural
  hygiene that prevents weeks of confusion later.
- **§11 — "trade-off, stated for the record."** Explicit
  acknowledgment that the directory-vs-zip choice was
  deliberate, with the rejected options named. Future
  reviewers can revisit the decision deliberately rather than
  re-litigating from scratch.

### Refinements

**B-R1 — Extend security hardening.** §6.1 covers zip-slip,
symlink, compression bombs, oversized files, absolute paths.
Add: cap on **number of entries** (zip bomb variant via entry
count rather than total bytes), cap on **directory nesting
depth**, cap on **path component length**, cap on **filename
length per entry**. These are well-known additional zip-bomb
and parser-DoS vectors.

**B-R2 — When does a sub-directory inside `content/` get
promoted to its own object?** §7 promotion is for plain files
in a node. The same question recurses inside containers — a
subdirectory under `content/` that grows large might want its
own address. Recommend: explicit promotion rule for in-container
subdirs (same one-way, recorded discipline).

**B-R3 — Extension naming consistency.** `.hno` vs `.hno.zip`.
Spec allows `.hno.zip` as carrier alias for the zip form. For
predictability, recommend standardizing on always-double
(`.hno.zip` for zip form, `.hno/` directory form) so file-extension
detection is unambiguous. Single-extension carriers (just
`.hno`) lose the directory-vs-zip discrimination.

**B-R4 — Language-portable reference implementation.** §10
reference implementation is Python-only. For a format that
should be implementable by any tool, the validator should
eventually split into:
- A pure-data-model spec (language-agnostic, e.g., a JSON
  Schema or formal grammar)
- Reference implementations in multiple languages
- Conformance test fixtures (sample valid + invalid containers)

Not blocking, but worth scoping for future work.

**B-R5 — Pilot order ordering rationale.** §10 recommends
piloting on (1) simple `0.5.3` document, (2) `0.5.17` Boot
Sequence, (3) Link + Workflow fixtures. The Boot Sequence pilot
specifically exercises the hash-authentication path. Strong
recommendation: pilot the Boot Sequence pilot *before*
ratification, not as the first post-ratification work. Boot
Sequence is the hash-authentication anchor for everything else;
its container conversion should be validated under the new
format before the format is canonical.

### Sign-off

**Endorse for ratification path** subject to B-R1 through B-R5
and Matt's three open questions:
1. "Directory canonical + derived zip" as the right reading of
   his "single zip file" intent — recommend yes.
2. Extension string `.hno` / `.hno.zip` — recommend B-R3
   always-double.
3. First pilot object — recommend `0.5.3` document for
   shape-test, then Boot Sequence `0.5.17` *as part of
   ratification*, not after.

## Cross-Document Dependencies

Visible from reading all three together:

1. **0.0.6 R1/R2 decision is upstream of 0.0.7's reserved band.**
   The `N.0.0#0`-`#9` reservation in `0.0.7` only makes sense if
   `0.0.6` R1 wins. Both documents flag this dependency
   correctly; both should be ratified together or with explicit
   coordination.
2. **0.5.0.1 §9 separates file-`#` from object-`ha` cleanly.**
   Promotion moves between namespaces. This is the kind of
   architectural seam that breaks if either side drifts; the
   cross-reference in §9 protects against drift.
3. **0.0.6 inheritance rule + 0.5.0.1 §3 internal layout.**
   Containers have an internal `N.0.0/` schema node per
   `0.0.6`. The same per-node-schema pattern recurses into
   containers — Hypernet fractal continues inside object
   containers. This is a quietly profound architectural
   correctness.

## Combined Implementation Sequence

If Matt approves direction:

1. **First**: Matt picks R1 vs R2 for `0.0.6`. This unblocks the
   reserved band in `0.0.7`.
2. **Then**: Address refinements A-R1 through A-R4 on `0.0.6`,
   C-R1 through C-R4 on `0.0.7`, B-R1 through B-R5 on
   `0.5.0.1`.
3. **Then**: Pilot file-level addressing on `0.0` and `0.3`
   per `0.0.7` recommendation.
4. **Concurrent**: Pilot object container on `0.5.3` simple
   document + `0.5.17` Boot Sequence per `0.5.0.1`
   recommendation.
5. **Then**: Ratify all three as Tier 2 active specs.
6. **Then**: Begin broader rollout — number documents in pilot
   nodes per Project C, convert more object types per Project
   B, propagate per-node schema pattern per Project A.

## Honest Limits

- All three are well-built drafts. My review found refinements,
  not foundation issues.
- The R1/R2 decision is Matt's; my read favors R1 (cleaner
  separation between schema mechanics and document index) but
  R2 is also defensible.
- I haven't tested the proposed grammar in `0.0.7` against the
  existing Hypernet codebase's address parser — would need
  validation before activation.
- The container hardening rules in `0.5.0.1` §6.1 are right but
  unmeasured — real attack-surface assessment would require
  attempting to construct adversarial containers, which I
  haven't done.
- My B-R5 strongly prefers Boot Sequence as pre-ratification
  pilot rather than post-ratification work. This is a judgment
  call; the swarm picked post-ratification ordering. Either is
  defensible; mine is more conservative about hash authority.
