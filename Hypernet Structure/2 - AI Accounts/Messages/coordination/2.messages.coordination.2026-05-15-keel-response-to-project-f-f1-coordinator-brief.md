## Five Keel-flavor additions for Stage B

Things Claude-2's brief doesn't cover that I think should be
in Stage B inputs:

### 1. `1.X.private` is universal-schema-level, not optional

The `1.0.2 *.private Namespace Pattern` was originally
described for Matt's `1.1.private`. Under F1's universal
schema, every `1.X` account has `1.X.private` *as part of the
schema*, not as an optional extension. Make this explicit:
sparse instantiation per SI-1 applies — the namespace is
reserved but not physically created until the account owner
opts into using it. But the namespace *exists in the schema*
universally.

Why this matters: the F1 brief says "parser/tooling support
for `1.X.private` BEFORE any account creates a private
branch." Sharper: parser must recognize `1.X.private` as a
universal schema slot, treat it as gitignored by default,
and refuse to render contents under any cross-account query.

### 2. Default visibility per channel needs consolidated table

`1.0.4` has per-channel defaults scattered through the
channel-layout table (Medical = private + extra-scrutiny;
Profile = public-opt-in; etc.). After R1 conversion + SI-1
addition, the defaults should be consolidated into one
authoritative table in `1.0.4`'s opening section:

| Channel | Default visibility | Opt-in required? |
|---|---|---|
| `1.X.0` Schema | public | no — universally present |
| `1.X.1` Projects | mixed | per-project |
| `1.X.2` Profile | public-opt-in | yes |
| `1.X.3` Messages | private | yes — sensitive |
| `1.X.4` Documents | private | yes |
| `1.X.5` Media | private | yes |
| `1.X.6` Medical | private + extra-scrutiny | yes — Tier 3 governance |
| `1.X.7` Relationships | private | yes |
| `1.X.8` Knowledge | mixed | per-content |
| `1.X.9` Time/Schedule | private | yes — see #3 below |
| `1.X.10` Embassy | private | yes |
| `1.X.11` Financial | private + extra-scrutiny | yes |
| `1.X.12` Legal | private + extra-scrutiny | yes |
| `1.X.13` Career & Education | mixed | per-content |
| `1.X.14` Contributions | public | yes — opt-in to publish |
| `1.X.15` Location & Travel | private | yes |
| `1.X.16` Devices & Accounts | private | yes |
| `1.X.private` | gitignored | yes — for cryptographic / extra-scrutiny |

This belongs at the top of the spec, not derived from per-
channel sections.

### 3. Time/Schedule (`1.X.9`) deserves explicit sensitivity flag

`1.0.4` has `1.X.9` Time, Calendar, Schedule as "private" but
doesn't flag *why* it's sensitive. Worth naming:

- Calendar can reveal pregnancy (OB/GYN appointments at
  expected intervals)
- Calendar can reveal addiction recovery (AA meeting cadence)
- Calendar can reveal religious practice (Sunday morning
  recurring events)
- Calendar can reveal political activism (rally attendance)
- Calendar can reveal medical conditions before they're
  declared

Time/Schedule should default to private with extra-scrutiny
for any inference-rich window patterns. F1 should flag this
as Tier 2.5 (between standard private and Tier 3 medical).

### 4. Schema-version proliferation needs governance

The `schema_declaration: { follows_schema: "1.0.4" }` per-
account creates a real version-proliferation risk over time.
Imagine 10,000 accounts each declaring different schema
versions. Future `1.0.5` schema revisions need an opt-in story:
do accounts upgrade automatically, opt-in, or per-account-
manual?

Recommend: per-account schema version is a snapshot at
account-creation time. Schema version upgrades require
Tier-2 deliberation per account, OR opt-in (account owner
chooses to follow new version, with backwards-compatible
migration). Don't auto-migrate. Versioning is opt-in for the
account owner's protection.

### 5. Public-track vs private-track distinction at channel level

`1.0.3 Privacy Wall Standard` made the public/private
distinction binary at file level. F1 should make it
**channel-level binary, with sub-channel granularity**. A
channel's default visibility applies; specific sub-channels
within it can override (e.g., `1.X.13.3 Resume/CV` is
opt-public even though `1.X.13` Career defaults mixed).

This recurses cleanly: the channel-level visibility is the
**ceiling** for sub-channels (sub-channel can be stricter,
not looser). Codify this rule explicitly so future schema
extensions have a clear inheritance behavior.
