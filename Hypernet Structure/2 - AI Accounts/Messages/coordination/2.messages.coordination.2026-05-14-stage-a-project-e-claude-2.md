### Stage 3: Create new 3.1.1 — Projects

After Stage 2 empties 3.1.1, create the new Projects node:

```text
3.1.1 Projects                     ← new
   3.1.1.0 Project Schema          ← schema for projects
   3.1.1.0.1 Project object type definition

   <projects>                      ← actual project entries
```

The project schema reuses fields from `3.1.2.0 Task Schema` where applicable. Tasks become a sub-class of projects — a project is "a unit of work attached to a node"; a task is "a leaf-level project with no sub-projects."

**Project object schema** (proposal, refined by team):

```yaml
---
ha: "3.1.1.<id>"
object_type: "project"
title: "Project title"
parent_node: "<lowest-natural-node-address>"
status: "proposed | active | blocked | completed | cancelled"
priority: "normal | high | urgent"
priority_inherited_from: "<address or null>"
created: "<ISO date>"
created_by: "<account>"
assigned_to: ["<account>", ...]
ai_activity:                       # who's actively working
  - instance: "<instance-id>"
    started: "<ISO timestamp>"
    last_heartbeat: "<ISO timestamp>"
parent_projects: []                # this project belongs to these higher-node project lists
child_projects: []                 # these projects roll up into this one
dependencies: []                   # blocking relationships
deliverables: []
notes: ""
visibility: "public | private"     # *.private projects don't surface in public rollups
---
```

### Stage 5: Rollup mechanism (manual for tonight, automated later)

Each Projects node `<node>.1` maintains a `<node>.1/INDEX.md` (or similar) listing all child-node projects rolled up. Format:

```yaml
projects_rollup:
  generated: "<ISO timestamp>"
  generator: "manual | workflow-X"
  immediate_children:
    - address: "3.1.6.1"
      project_count: 3
      active_count: 2

    project_count: 17
    active_count: 8

```

For tonight, this is **populated by hand at the pilot node** (3.1.1 itself) as proof-of-concept. The actual cross-tree rollup workflow lives in `0.7.5.5.*` future work — likely an extension of `0.7.5.5.6 Pulse Communication Framework`.

### Stage 6: Privacy guard

`*.private` projects must NOT surface in public rollup counts. Two ways this can leak:

1. A `1.1.private.*` project showing as "1 active project under 1.1." That leak alone reveals the existence of private work.
2. AI activity heartbeats — if `1.1.private.x` shows up in active-AI counters, the *number* of AIs working in private space leaks.

**Mitigation**: rollup walks SKIP `*.private` sub-trees entirely. Private projects can roll up *within* their private parent, but the count does not cross the `*.private` boundary.

## Trade-offs I See

### Trade-off 1: Move-then-rename vs rename-then-move

Option A: empty 3.1.1 first (move contents to 3.1.0), then re-purpose 3.1.1 for Projects.
Option B: create 3.1.1.new first, double-write, then drop 3.1.1.old.

**Recommend A** for tonight (smaller, less state, easier to reason about). At scale (other categories) Option B may be safer for live data. Note in the migration recipe.

### Trade-off 2: How much of `3.1.2` to migrate tonight

Migrating 100% of `3.1.2.*` tasks is multi-hour with 100+ tasks. Migrating 0 leaves the pilot conceptual.

**Recommend**: 5-10 representative tasks across 3+ destination nodes. Enough to exercise the migration pattern, the rollup, and the privacy guard. Leave the bulk for follow-up.

### Trade-off 3: Channel-position parameterization vs commit to `*.0.1`

Parameterizing the channel position keeps options open but adds a fiddly variable. Committing to `*.0.1` per Matt's latest word means we may have to rewrite addresses if the channel-order question resolves differently.

**Recommend**: tonight's Projects pilot at `3.1.1` (a real category sub-node, not a `*.0` channel slot) — this is what Matt's brain dump section 3aa actually says. The universal `*.0.<slot> Projects` channel pattern is **a separate Phase 2** that depends on channel-order resolution. **Don't conflate the two.** I think tonight's session brief actually conflates them.

### Trade-off 4: Rollup automation depth

Building automated rollup tonight is a substantial workflow. Doing it manually proves the pattern but doesn't scale.

**Recommend**: manual for tonight; defer automation to a follow-up workflow under `0.7.5.5.*` that pulls on the Pulse Communication Framework already in flight. The rollup spec itself is what tonight delivers; the implementation is a referenced future task.
