# 1.0.* Integration Brief for Project F

*Coordinator integration of Keel's `1.0.1 Lockers/Mandalas/Aliases`, `1.0.2 Private Data Namespace`, `1.0.3 Privacy Wall Standard` with my Project F sub-project briefs (F1-F8). Identifies alignment + flags strengthening needed. Stage B AIs should treat the 1.0.* docs as authoritative foundation; Project F sub-projects ratify when consistent with 1.0.*.*

## The privacy ladder (from 1.0.2)

```text
X.private (base material — extra scrutiny on every access)
   ↑
X.locker.<name> (link manifests — opened by mandalas)
   ↑
X.alias.<name> (public-facing identity surface)
   ↑
public-facing data (auto-granted public mandalas)
```

Every Project F sub-project sits at some level of this ladder. The Coordinator integration check: does each sub-project respect ladder direction (private below, public above) and ladder semantics (locker is link manifest not payload; mandala is access pattern not data; alias is outward surface)?

## Per-sub-project alignment check

### F1 (1.* Universal Top-Level Schema) — Strengthening needed

**1.0.1 critical reminder I missed in F1**: *"The master `1.*` account is a private home. Public interaction happens through aliases and lockers, not by browsing the master account directly."*

F1 brief proposed standard landing pages at `1.X.0.0:1` (human) and `:2` (AI). Per 1.0.1, these landing pages should NOT be directly addressable from public surfaces. The schema is correct that the slots exist; what F1 needs to clarify is that **the landing pages are reached via the account's public locker or alias surface, not via direct `1.X.0.0:1` resolution from outside**.

**Strengthening for Stage B**:
- `1.X.0.0:1` and `:2` landing pages are LOGICALLY universal but PHYSICALLY accessed via the account's public-profile locker
- Direct `1.X.0.0:1` resolution from outside the account's owner / authorized AI requires going through a mandala grant (the public-profile mandala by default, but it's still a mandala)
- This preserves 1.0.1's "private home" rule while giving F1's landing pages their universal-slot meaning

**Cross-link**: F1's `1.X.private` reservation rule (Keel's response added this) is consistent with 1.0.2 — every `1.X` reserves `1.X.private` as the cryptographic-identity / biometric / extra-scrutiny base material.

### F3 (DNA Addressing) — Aligned with one clarification

F3's two-namespace architecture:
- Universal namespace at `0.0.8.*` (canonical biological references; non-personal)
- Per-person observed at `1.X.6.3.*` (linked via `universal_ref`)

Per 1.0.2's DNA-specific treatment:
- Raw DNA data lives in `1.X.private.biometric.dna.<sample-id>` (per 1.0.2 examples)
- F3's per-person normalized view at `1.X.6.3.*` is the **locker-level** representation

**Clarification for Stage B**: F3 brief should explicitly state that `1.X.6.3.*` per-person observations are at the locker level, not the private-base-material level. Raw reads live in `1.X.private.biometric.dna.*` and are surfaced via locker links only as mandala grants permit.

F3's "DNA is pseudonymous, not anonymous" rule is consistent with 1.0.1's mandala visibility_mode: `non_granted_invisible` — researchers grant scope is limited; they never see the existence of non-granted DNA segments for that person.

## What 1.0.* doesn't yet cover (gap for future work)

While doing this integration, gaps in 1.0.* that future iterations might address:

1. **Multi-account joint lockers**: 1.0.2 open question — "When two accounts need to privately share data (e.g., a couple with a shared family locker), do they create a third joint account with its own `*.private`?" Project F doesn't resolve this either; it's a future joint-account feature.

2. **Locker discoverability**: 1.0.1 open question — "Should hidden lockers be discoverable by emergency responders if the pointer is presented?" F5 brief assumes pre-curated discoverability (the QR code IS the pointer). Worth flagging.

3. **Recovery without single point of failure**: 1.0.2 open question — Shamir-secret-shared recovery vs designated custodian. Both Project F's `1.X.private` lock-out scenarios and F8's lost-device protocols touch this; a unified recovery model would benefit all.

4. **Cross-account third-party content**: 1.0.3 mentions cross-reference walking ("when personal data appears in another account's tree, the wall should extend across account boundaries"). F7 brief identifies the same problem for messages. A general cross-account privacy-extension protocol would help.

These are Project G / future-session territory; flagging for the retrospective.
