# Codex Binding Cross-Model Verification - sm v0.1 - REVISE

I self-author this verdict as the independent cross-model binding seat. Same-family reviews were context only. I hashed the eight primary artifacts twice at the start and twice again before writing this record; both passes were stable and are bound in frontmatter.

Verdict: REVISE. The queued-prompt executor and STOP behavior are real, and I do not find a reason to BLOCK/remove sm for the current bounded Tally-resume convenience use. I do find material enforcement gaps that prevent ACCEPT for expansion: the audit chain can be rewritten/truncated silently by a local writer, recovery can be misled by a forged status UID, NODE-0 fail-closed coupling is documented but absent in code, and role names are not path-confined.

## S.1 - Cannot self-authorize

Finding: PASS for prompt execution path, with scope caveat.

Evidence:
- `sm send` either reads an operator-supplied inline prompt or `@file`, then writes it into the role command queue: `session_manager/sm.py:136-153`.
- The worker only lists regular `.txt`/`.md` files under `commands/`: `session_manager/worker.py:35-41`.
- The worker reads exactly the selected queued command file before building an engine call: `session_manager/worker.py:232-256`.
- There is no autonomous loop in this code; spawn is explicit CLI registration plus worker launch: `session_manager/sm.py:104-134`.

Adversarial result: in temporary-path worker tests with `_stream_to_log` stubbed, no engine call occurred with no queued command or when a command was queued after STOP:

```text
STOP_IDLE_THEN_COMMAND ok=True thread_alive=False calls=0 after_stop_remains=True stop_audit_resume=True errors=[]
STOP_DURING_CALL ok=True thread_alive=False calls=['FIRST_ONLY'] after_stop_remains=True processed=['20260603T061406Z-20260603T000000Z-first.txt'] stop_audit_resume=True errors=[]
```

I did not find a code path where sm or the honest worker invents a prompt outside `commands/`. Direct manual file placement in `commands/` remains an operator action, not self-authorization by sm.

## S.2 - Fails closed on STOP

Finding: PASS for subsequent-command suppression; current in-flight engine call is not interrupted.

Evidence:
- STOP is checked at the top of every worker loop before heartbeat and before polling commands: `session_manager/worker.py:209-221`.
- The stop status is written via `_heartbeat_fields`, which carries `resume_session_id`: `session_manager/worker.py:212-220`, `session_manager/worker.py:166-190`.
- Command polling happens after the STOP check: `session_manager/worker.py:231-278`.

Adversarial outputs:

```text
STOP_PREEXISTING ok=True thread_alive=False calls=0 command_remains=True stop_audit_resume=True errors=[]
STOP_IDLE_THEN_COMMAND ok=True thread_alive=False calls=0 after_stop_remains=True stop_audit_resume=True errors=[]
STOP_DURING_CALL ok=True thread_alive=False calls=['FIRST_ONLY'] after_stop_remains=True processed=['20260603T061406Z-20260603T000000Z-first.txt'] stop_audit_resume=True errors=[]
```

Interpretation: STOP while idle or before polling prevents all command execution. STOP while mid-call does not kill the child engine call; the current call returns, the current command archives, then the worker stops before processing commands queued after STOP. That matches the design's "finish current atomic action" soft-stop model, not an immediate hard interrupt.

## S.3 - Audit chain cannot be silently bypassed

Finding: FAIL; material REVISE item.

The simple tamper test is real, but the chain is unkeyed and unanchored. `write_status` and `audit` compute `hash = sha256(prev_hash + ':' + canonical_entry)` and append it: `session_manager/audit.py:32-50`, `session_manager/audit.py:59-72`. `verify_chain()` starts at `GENESIS` and accepts whatever valid prefix reaches EOF: `session_manager/audit.py:75-96`. There is no signed head, external checkpoint, monotonic count anchor, or file append-only enforcement.

My stronger attack succeeded:

```text
AUDIT_RECOMPUTE_BYPASS verify_ok=True msg='3 entries verified'
AUDIT_TRUNCATION_BYPASS verify_ok=True msg='2 entries verified'
```

I edited an intermediate row, recomputed that row and all later hashes, and `verify_chain()` accepted it. I also truncated the last entry and `verify_chain()` accepted the shorter prefix. This means the audit chain is tamper-evident only against non-recomputed edits, not against a local writer with ordinary filesystem access.

I did not find a status write path in `sm.py` or `worker.py` that bypasses `audit.write_status`; all worker status writes go through it (`session_manager/worker.py:201-203`, `session_manager/worker.py:214-229`, `session_manager/worker.py:242-248`, `session_manager/worker.py:270-276`, `session_manager/worker.py:280-288`). The helper itself remains publicly callable and unprotected.

Required revision: anchor the latest head hash and entry count somewhere a local log rewrite cannot silently rewrite in the same operation, or sign/HMAC entries with a key unavailable to the worker. Also verify `status.json` equals the last history entry and fail on mismatch.

## S.4 - resume_session_id integrity

Finding: FAIL for adversarial status integrity; PASS only for the honest worker path.

Honest path:
- `_heartbeat_fields()` sets `resume_session_id` from `cfg["session_id"]`: `session_manager/worker.py:166-190`.
- Claude invocation and resume hint also use `cfg["session_id"]`: `session_manager/worker.py:44-58`, `session_manager/worker.py:144-158`.

Adversarial gap:
- `audit.write_status(role, **fields)` accepts arbitrary fields, including arbitrary `resume_session_id`: `session_manager/audit.py:32-50`.
- `sm recover` trusts the status value if present instead of validating it against the roster: `session_manager/sm.py:227-244`.
- The roster is plain JSON without hash-chain or signature: `session_manager/roster.py:13-17`.

Test output:

```text
RESUME_UID_HONEST_MATCH ok=True honest_uid='real-roster-session-id' roster_uid='real-roster-session-id'
RESUME_UID_FAKE_ACCEPTED chain_ok=True msg='1 entries verified' recover_prints_fake=True
```

A malicious local writer/worker can create a chain-valid status row with a fake `resume_session_id`, and `sm recover` prints the fake. Required revision: enforce `status.resume_session_id == roster[role].session_id` at write and recover time, fail closed on mismatch, and preferably bind roster changes into the same audit substrate. For Claude, compare stream `session_id` against roster when parseable.

tally idle, alive yes, PID 8688, heartbeat 2026-06-03T06:15:32Z, pending 0

STOP file behavior was reverified in the S.2 isolated worker tests.

NODE-0: the design requires deleting `C:/Users/spamm/.hypernet/node0-authorization.json` to fail closed for the controller too (`master-controller-design.md:108-112`), and the README documents the same (`session_manager/README.md:10-12`). Code search found no NODE-0/auth marker check in the package; the only matches are README text. Therefore sm itself does not honor NODE-0 deletion. It relies on the spawned AI/tooling to check auth, if they do.

Additional caveat: external `taskkill /F` stops the process but cannot be reverse-transparent automatically; the killed worker cannot write a stop audit row, and the stale `worker.pid` remains until a graceful worker run overwrites/unlinks it. `_is_worker_alive()` still correctly reports dead by checking `tasklist`: `session_manager/sm.py:29-50`.

Required revision: add an auth-marker check in worker startup and each loop, and make sm CLI commands fail closed when the marker is absent. If reverse-transparency for external kill is required, add a watchdog/reconcile path that records observed PID death.

## S.6 - No external/network/spawn beyond scope

Finding: PASS for no hidden git/network calls in sm itself; REVISE for path and configuration confinement.

Subprocess paths are visible and limited to:
- `tasklist` liveness check: `session_manager/sm.py:38-44`.
- Detached worker launch: `session_manager/sm.py:80-102`.
- Engine process launch through `_stream_to_log`: `session_manager/worker.py:71-94`.
- Engine commands are `claude --resume ...` and `codex exec ...`: `session_manager/worker.py:44-68`.

I found no `git push`, direct network call, or process name outside `python -m session_manager.worker`, `claude`, `codex`, and `tasklist` in source.

Material confinement gaps:
- Role names are unsanitized and directly appended to `SESSIONS_DIR`: `session_manager/paths.py:10-37`. Test output:

```text
ROLE_PATH_TRAVERSAL outside_session_manager_root=True resolved=C:\Users\spamm\AppData\Local\Temp\sm_adv_paths_7uzp98bq\outside_sm_root
```

- `sm spawn` accepts arbitrary `--cwd`, `--tools`, and `--append-system-prompt`: `session_manager/sm.py:262-271`; these are passed to engine commands: `session_manager/worker.py:46-57`, `session_manager/worker.py:63-67`.

Required revision: validate role names with a strict allowlist such as `[a-z0-9_-]+`, resolve all role paths and assert they remain under `SESSIONS_DIR`, and constrain `cwd/tools` to approved/panel-bound values before expansion.

This is enough to recover the worker. The prompt-level resume hint still depends on S.4 integrity, because `sm recover` trusts status fields if forged.

## Net Verdict

REVISE. Keep sm constrained to Tally-resume convenience only. Do not use it for Spawn-Packet execution, peer management, or wider monitoring/kill authority until the revisions below are implemented and reverified:

1. Add real audit head/count anchoring or signatures/HMAC; detect truncation and recomputed-chain rewrites.
2. Enforce `resume_session_id` against roster at status-write and recover time; fail closed on mismatch.
3. Implement NODE-0 marker checks in sm and worker startup/loop.
4. Sanitize role names and path confinement; constrain `cwd/tools/append_system_prompt` to approved/panel-bound config.
5. Expand tests to include the adversarial cases above.

This is not a BLOCK because the core bounded executor does not self-author prompts and STOP/recovery work under the tested conditions. It is not an ACCEPT because several safety claims are documented or convention-based rather than enforced against adversarial local-state manipulation.
