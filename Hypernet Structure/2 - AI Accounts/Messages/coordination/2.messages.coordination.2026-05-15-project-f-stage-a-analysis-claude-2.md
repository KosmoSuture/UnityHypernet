# Project F — Stage A Coordination Analysis of Keel's `1.0.4`

*Coordinator-flavor read of Keel's `1.0.4-UNIVERSAL-1-STAR-SCHEMA-DRAFT.md` as Project F Stage A substrate. Identifies strengths, swarm-refinement targets, and isolated decision axes. Intended to make a future Project F consensus-workflow invocation faster.*

## Headline

Keel's `1.0.4` is **substantively complete as a Stage A starting plan**. Project F is positioned to skip the blue-sky-blank-page phase: the swarm's Stage A becomes "react and refine Keel's draft" rather than "design from scratch."

This is a different shape than tonight's 5 projects, where each project started with Matt's brain dump + the existing repo state. Project F starts with a real coherent draft. The consensus workflow accommodates this — Stage A becomes responsive Stage A.

## What's strong in Keel's `1.0.4`

### 1. The 17-channel top-level layout

Coverage is comprehensive without inflation. Each channel has a clear purpose; cross-references between channels are explicit (e.g., `1.X.5` Media → `1.X.9` Events via `1.X.5.8 Linked Events`). The order is principled: schema/metadata first, projects/work next, then content channels (profile, messages, documents, media, medical, relationships, knowledge, time), then specialty (embassy, financial, legal, career, contributions, location, devices), private last.

**Likely to survive Stage A unchanged** unless the swarm finds a real gap.

### 2. Default-private with explicit-public exceptions

Every channel has a default visibility. Profile (`1.X.2`) is public-opt-in; Medical (`1.X.6`) is private + extra-scrutiny; Documents (`1.X.4`) is private; etc. The `1.X.private` namespace is gitignored.

This is the right safety default. Matches `1.0.3 Privacy Wall Standard`.

### 3. Migration map from current Matt-1.1

Explicit table of "Current 1.1.* → Proposed 1.X.* + action." Doesn't pretend the existing inconsistent slots don't exist. Migration is named as a multi-day project, not a tonight task.

### 4. Granularity stopping rule encoded

"Schema is the ceiling; data fills as much as it needs." This is the answer to Matt's "granular-to-infinity" — depth follows data, sparse instantiation.

### 5. Messages deep buildout

10 sub-channels under `1.X.3` (Email, Chat, SMS, Social, Calls, Mail, Forums, Contacts, Search, +Schema). 4-5 levels deep. Per-platform sub-sub-channels (Slack at `1.X.3.2.2.1`, Discord at `.2`, etc.). **Ready for tens of thousands of imported messages** per Matt's requirement.

### 6. Medical deep buildout

5 levels deep. Clinical Records (`.1`), Vitals (`.2`), then DNA, Providers, Insurance, Conditions, Emergency, Research, AI Swarm Real-Time. The device-agnostic vital-reading schema with `metric_address` (e.g., `1.X.6.2.1.heart_rate`) is exactly what Matt asked for.

### 7. Universal `1.X.0.*` schema channel pattern

Follows tonight's Project A `0.0.6` Per-Node Schema Pattern. Standard documents at known slots (`1.X.0.2` always human landing, `1.X.0.3` always AI landing). Inheritance declared at `1.X.0.1`. Local extensions at `1.X.0.6`. Machine-readable descriptor at `1.X.0.8`.

**Project A's schema pattern survives the first real application test in Keel's `1.0.4`.** That's the architectural validation tonight's outputs needed.

## What needs swarm refinement (Stage A targets)

### Target 1 — DNA addressing scheme detail

`1.X.6.3` is reserved for "DNA" but the actual addressing scheme — *how chromosome 17, gene BRCA1, SNP rs1234567 get permanent Hypernet addresses* — is the hardest single piece of Project F. Matt's directive: "The schema should ensure that all parts of the DNA are labeled in such a way that you would have an hypernet address that could point to particular chromosomes, genes, or any part of DNA in a standardized way."

Candidate addressing scheme:

```text
1.X.6.3                    # this person's DNA channel
1.X.6.3.<chromosome>       # e.g., 1.X.6.3.17 = chromosome 17
1.X.6.3.<chr>.<gene>       # e.g., 1.X.6.3.17.BRCA1
1.X.6.3.<chr>.<gene>#<variant>   # e.g., 1.X.6.3.17.BRCA1#rs1234567
```

Or alternative:

```text
0.dna                      # universal DNA reference space (across all 1.X)
0.dna.<chr>.<region>       # canonical address; not per-person
1.X.6.3 -> mandala-gated   # this person's data, linking via mandala to 0.dna addresses
```

The second pattern enables cross-sample research (a researcher comparing BRCA1 across thousands of samples uses a single `0.dna.17.BRCA1` address; each person's data is mandala-linked to it).

**Stage A AIs should propose 2-3 candidate addressing schemes**; Stage B converges on one with reasoning.

### Target 2 — Mandala-gated medical research grants

Matt's directive: "Researchers could potentially pay users for anonymous access to the data they need for specific research."

The mandala framework is referenced (`1.X.6.3.<mandala>`) but the specifics of:
- How a research grant proposal is structured
- How payment flows work (cryptocurrency? Foundation-mediated? Direct?)
- How anonymity is enforced when the AI assists the researcher
- How re-identification risk is monitored

… need to be specified. This is Tier-3 Trust Quorum territory — touches private data + external researchers + monetary flows.

### Target 3 — Emergency "break-glass" protocol

Matt's directive: "having processes in place that would allow emergency responders or medics to be able to 'break glass' and get whatever medical information about you that they need immediately."

The schema reserves the slot (`1.X.6.X` Emergency) but the protocol — who can break the glass, how authentication works, what triggers an audit alert, how the user's AI swarm intersects with the responder — is not specified. This is a privacy-vs-survival tradeoff that's life-or-death-relevant.

### Target 4 — Real-time AI swarm during medical episodes

Matt's directive: "the entire swarm, as a collective, could go over all real-time data, combined with their privileged access to their users medical data, could be working full time to monitor, research, and verify all medical treatments in real-time."

Schema needs to support this access pattern:
- A "medical episode active" flag that elevates AI swarm permissions
- Real-time data streaming from monitors (architecture, not just schema)
- AI advisory output structure (what does the swarm hand to clinicians?)
- Liability and consent boundaries

This intersects with the Companion Standard (`2.0.20`) and the Embassy Standard (`2.0.16`) — both should be reviewed.

### Target 5 — Universal health-tracker device-agnostic standard

Schema sketch is good (the `vitals_reading` YAML). What needs swarm refinement:
- The full canonical metric address registry (what's `1.X.6.2.1.heart_rate` vs `1.X.6.2.1.heart_rate.continuous` vs `1.X.6.2.1.heart_rate.spot_check`?)
- Unit normalization rules
- Confidence-level semantics across vendors
- Migration when changing device brands (deduplication, gap-fill, conflict resolution)

### Target 6 — Channel position couplings with tonight's open questions

Keel's `1.X.0` uses the schema-mechanics pattern from tonight's Project A. But:
- Project A's R1/R2 (landing pages as `N.0.0#1` files vs `N.0.0.1` sub-nodes) directly determines whether Keel's `1.X.0.2 Human Landing Page` and `1.X.0.3 AI Landing Page` are sub-nodes or files.
- The `2.7.3` channel-order question about universal `*.0.<slot>` doesn't directly bind here because Keel's layout is `1.X.<channel>` (one level of nesting), not `*.0.<channel>` (universal control plane).

**Coordinator read**: Project F's schema is *upstream* of the universal channel-order question but *downstream* of Project A's R1/R2. Make this explicit in Stage A AIs' plans.

### Target 7 — Migration of Matt-1.1 timing

Keel's migration map is structurally complete but the *order of operations* matters:
- Privacy wall remediation must be in place first (done per `1.0.3`)
- Schema activation second (Project F output)
- Matt-1.1 migration third (multi-day)
- Other 1.* accounts forward (1.2 Sarah, 1.3 John, etc.) follow the schema directly without back-migration

The schema should declare a `schema_activation_date` so accounts know which version to follow.

### Target 8 — `1.X.16 Devices & Accounts` foundation for device swarm

This is the architectural seed for Matt's "appliance swarm" vision (every device joins your AI swarm). Schema reserves the slot. Project F's `1.X.16.3 Device Swarm Participation` is the protocol slot. Needs:
- Device authentication/identity scheme
- Swarm membership criteria (what does a device need to provide to join?)
- Permissions model (a smart fridge vs a smart car vs a phone — what can each access?)
- Failure mode (what happens when a device leaves the swarm?)

This may overlap with Project E's rollup mechanism (active-AI count, but extended to active-devices).

## Isolated decision axes for Stage A AIs to surface

For Stage B convergence (or Matt escalation if stuck):

1. **DNA addressing**: per-person nested vs universal-cross-sample with mandala link (my lean: universal-cross-sample, but this is Stage A AIs' call)
2. **Medical channel position**: keep at `1.X.6` (Keel's draft) vs promote to top-level peer category
3. **Mental health gating**: same channel as physical medical with stricter defaults vs separate sub-channel
4. **Substance use records**: where? Medical, legal, or separate?
5. **Mandala vs traditional ACL**: when is each appropriate for medical data?
6. **Emergency break-glass**: pre-authorized list vs role-based (any licensed medical professional) vs verified-credentials only
7. **AI swarm advisory authority**: advice (low liability), recommendations (medium), or near-real-time decision support (high)?
8. **Health-tracker data retention**: indefinite vs sliding-window vs per-user-controlled
9. **Device swarm onboarding security**: pairing flow, attestation requirements
10. **Schema activation strategy**: hard-cutover (`1.X` follows new schema from date Y) vs gradual (existing `1.X` accounts opt in)
