# Stage A - Project A - Codex-2 Engineer-Auditor

## My Reading Of The Goal

Project A needs to turn Matt's latest rule into a precise per-node
schema pattern:

- every node `N` has a reserved `N.0` control/schema space;
- that `N.0` space tells humans, AIs, and tools how to understand
  `N` and everything below it;
- standard node resources get standard addresses everywhere;
- local schema extensions are inherited by descendants;
- local extensions must not collide with upstream definitions.

This has to integrate with existing `0.0.4` and draft `0.0.5`
rather than pretending those documents do not exist.

## What I Would Build

I would define `0.0.6 Per-Node Schema Pattern.md` as a compatibility
layer over `0.0.4` and `0.0.5`, not as a silent replacement.

Core rule:

```text
For a content node N, N.0 is the node-local schema/control plane.
N.0.0 is the schema channel for N.0.
N.0.0.x contains standard schema-facing documents with universal slot meanings.
```

I would reserve these first universal schema slots:

| Address pattern | Standard meaning |
|---|---|
| `N.0.0.0` | Schema index and compatibility declaration |
| `N.0.0.1` | Human landing page |
| `N.0.0.2` | AI landing page |
| `N.0.0.3` | Popular jump points |
| `N.0.0.4` | Inheritance and upstream compatibility |
| `N.0.0.5` | Required fields and validation rules |
| `N.0.0.6` | Local extensions and override declarations |
| `N.0.0.7` | Local address and file-ID allocation rules |
| `N.0.0.8` | Machine-readable schema descriptor |
| `N.0.0.9` | Open questions, known gaps, and migration notes |

The pilot should use a real node with enough structure to test the
pattern but not so much blast radius that migration becomes the
real project. My preferred pilot is `3.1.0`, because Project E
already needs `3.1.0` to become the schema home for `3.1`.

## Collision-Avoidance Check

The upstream collision check should be deterministic:

1. Resolve `N` to its ancestor chain: `0`, top-level category,
   each intermediate parent, then `N`.
2. Load each ancestor's schema descriptor at `A.0.0.8` when it
   exists, falling back to documented `A.0.0`/frontmatter if not.
3. Build a reserved-slot map:
   - address suffixes, such as `.0.0.1`;
   - object types;
   - link types;
   - workflow names;
   - required fields;
   - reserved file IDs if Project C lands.
4. If a local schema extension reuses an inherited slot with a
   different meaning, block it unless it is an explicit override
   documented at `N.0.0.6` and approved under the correct trust
   tier.
5. If a local extension is additive and non-conflicting, allow it
   and pass it down to descendants.

The check can start as a manual audit table tonight. The spec
should still be written as if an automated validator will enforce
it later.

## Tradeoffs

The biggest tradeoff is between Matt's latest slot examples and
the existing draft `0.0.5` level-2 pattern.

`2.7.3` says one proposed level-2 pattern makes `.1` mean primary
registry or inherited baseline. Matt's latest example says every
`*.0.0.1` should be the human landing page. Those collide. My
recommendation is to let Matt's latest directive win for the
schema channel and explicitly migrate the older draft meanings
into the table above.

That choice is not free. It means `0.0.5` and `2.7.3` need an
erratum or convergence update before `0.0.6` becomes active.

## What I Would Ask Matt Before Starting Implementation

1. Does `*.0.0.1` definitely mean the human landing page, even
   though earlier draft work used `.1` differently?
2. Is `N.0.0` the right schema channel, or should the standard
   human/AI landing pages live directly under `N.0`?
3. Should Project A adopt Matt's latest `Projects at *.0.1` as a
   settled channel decision tonight, or record it as provisional?
4. Does the pilot need to create actual placeholder landing pages
   at every tested node, or only where useful content exists?
5. Who has authority to approve a subtree schema override that
   intentionally diverges from an ancestor?

## Auditor Risks To Surface At Stage D

- Direct collision: `N.0.0.1` as human landing page conflicts
  with the existing `0.0.5`/`2.7.3` draft pattern for inherited
  baseline.
- Channel collision: `0.0.4` v1 says `N.0.1` is Publishing;
  Matt's latest says Projects likely belongs at `*.0.1`; earlier
  `0.0.5` says Social at `N.0.1`.
- Trust risk: a schema extension can quietly change descendant
  behavior. It should be treated as a structural/governance
  action, not a routine documentation edit.
- Sparse-instantiation risk: "standard slot" must mean reserved
  and resolvable, not physically created everywhere with empty
  files.
- Inheritance risk: without a machine-readable `N.0.0.8`, humans
  and AIs will disagree about what actually applies at deep nodes.
- Migration risk: changing standard slot meanings without redirects
  will make old addresses tell false stories.

## My Stage A Recommendation

Proceed with `0.0.6` as a narrow spec:

- codify `N.0.0.x` schema slots;
- explicitly name every collision with `0.0.4`, `0.0.5`, and
  `2.7.3`;
- pilot on `3.1.0`;
- require each pilot node to publish a small machine-readable
  descriptor before any mass migration.
