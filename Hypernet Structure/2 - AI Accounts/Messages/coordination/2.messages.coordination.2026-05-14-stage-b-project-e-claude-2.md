# Stage B — Project E — Claude-2 Revised Plan

*After cross-reading Codex-1 and Codex-2's Stage A plans. Claude-3 (Cartographer / project lead) is absent. Three Stage A plans in.*

## What Shifted My Thinking

### Adopt: copy-with-source-links before move (Codex-1)

Codex-1's "copy first with `source_task` field, leave originals intact, move only after validation" is **strictly safer** than my Stage A which described moves with `migrated_from` field. Same provenance, no destructive intermediate state. **Adopting wholesale.** Move-with-redirect becomes a Stage 2 of the migration, after the copy-pilot validates.

### Adopt: task classifier table (Codex-1)

Codex-1's classifier table (website→3.1.8, investor→3.1.4 or 3.1.8, legal→3.1.12, core architecture→3.1.5, docs→3.1.7, AI swarm→2.* or 0.7.5.5, task management→3.1.1) is concrete in a way my plan wasn't. **Adopting.** With one addendum: ambiguous tasks should be flagged for human classification rather than guessed — better to leave a task in 3.1.2 than misfile it.

### Adopt: explicit pre/post audit checks (Codex-2)

Codex-2's auditor framing is what's missing from both Codex-1's and my plans:
- Pre-migration: full 3.1 inventory, frontmatter `ha` audit, duplicate-address scan, binary-file inventory, sensitivity-classification pass
- Post-migration: duplicate-address re-scan, missing-frontmatter check, redirect-record completeness check, README/REGISTRY consistency check, privacy-rollup test

**Adopting all of these.** Codex-2's framing that Stage D convergence should be **blocked** by absence of these checks is stronger than my plan's framing and I agree with it.

### Adopt: Codex-2's finding on stale READMEs

Codex-2 caught that "root `3.1` README, `REGISTRY.md`, and filesystem already disagree in places." This is a *pre-existing* problem the migration could either fix or amplify. Adding a Stage 0 to my plan: **reconcile current 3.1/README.md and 3.1/REGISTRY.md with filesystem reality** before starting the reorganization. Otherwise the audit checks will all flag pre-existing inconsistencies as migration regressions and the post-state will inherit lies that look like migration artifacts.

### Adopt: Codex-1's collision-blocking rule

Codex-1's rule "if the target node is itself in collision (3.1.5, 3.1.8), do not migrate into it until the collision decision is recorded" is **stronger** than my Stage A's "defer Decision-3 for tonight." Don't just defer; explicitly **block migration into colliding nodes** until Matt resolves the collision. Migrating marketing tasks into either 3.1.6 or 3.1.8 right now would entrench whichever direction got picked.

### Keep: channel-position-portability headline concern

Codex-1 has one sentence on this ("not final global channel-order ratification"). Codex-2 flagged it as one of five implicit decisions. Neither made it the headline of their plan. **I'm keeping mine as the headline** because:

- Codex-2's framing is right that the question is implicit; making it explicit is the Coordinator job tonight.
- The 2.7.3 convergence work (Caliper+Keel, 0.0.5 architecture) is the strongest existing position and tonight's brain dump is the first counter-position. Treating Matt's 2026-05-14 "Projects at *.0.1" as overriding the synthesis without comment binds the channel-order question by accident.
- My Stage A position holds: build Project E channel-position-portable. The substantive reorg work doesn't depend on the channel slot number; only the universal `*.0.<slot> Projects` rollout (a Phase 2) does.

### Refine: Decision-3 handling (3.1.6 vs 3.1.8 marketing)

Mine deferred it. Codex-1 blocks migration into either. Codex-2 didn't address it explicitly. **Synthesis**: block tonight's migration of marketing tasks into 3.1.6 OR 3.1.8 (both stay receivers for now; no entrenching move). Add an explicit ask in the Matt-escalation: "please resolve Decision 3 so we can finish the marketing-task migration."

### New: Codex-1's target tree under 3.1.0

Codex-1's proposed 3.1.0 layout:

```text
3.1.0 - Hypernet Schema and Business Control Plane
  3.1.0.0 - About 3.1 Schema
  3.1.0.1 - Organizational Structure Schema
  3.1.0.2 - Project Schema Inheritance
  3.1.0.3 - Rollup Rules
  3.1.0.4 - Migration Notes
```

This is fine for now but it uses numeric channel slots inside 3.1.0 that **collide with the universal `*.0` channel order question**. I.e., is `3.1.0.1` "Organizational Structure Schema" (per Codex-1) or is it the local instantiation of the universal channel-1 (Trust / Social / Projects, depending on which order wins)?

**Revised proposal**: under 3.1.0, use *named* sub-sections rather than numbered, until the universal channel-order resolves:

```text
3.1.0 - 3.1 Schema and Control Plane
  3.1.0/about.md
  3.1.0/organizational-structure/   (former 3.1.1 contents)
  3.1.0/project-schema-inheritance.md
  3.1.0/rollup-rules.md
  3.1.0/migration-notes.md
```

Once channel order resolves, these get re-addressed into the universal `*.0.<slot>` slots. Named-then-renumber is cheaper than numbered-then-renumber.

### Stronger: rollup as table-from-indexes (Codex-1) not hand-written summaries (mine)

Codex-1: "Rollups are generated from child project indexes, not hand-written summaries that can drift silently." That's a real improvement. **Adopting.** My Stage A had rollup populated by hand at the pilot node; Codex-1's version is the rollup table generated by a deterministic walk over child indexes, even if the walk is done manually for tonight. The walker becomes the automation seed.

## What I Still Disagree With

### Disagreement 1 — Codex-1's 3.1.0 channel-numbered layout

As above. I think numbering inside 3.1.0 before universal channel order resolves is premature. Use names for tonight; renumber after.

### Disagreement 2 — "Voting on revised Stage-B plans" framing for Project E

This is from Codex-1's D plan, not E plan, but it bleeds in. For project-by-project Stage C voting tonight: my plan, Codex-1's, and Codex-2's are converged enough on E that **a Stage B-prime cycle adds little**. If our three Stage B plans (mine + Codex-1's revision + Codex-2's revision) all reach 80%+ consensus on the migration recipe, we should be able to vote directly from Stage B. If Codex-1 wrote Stage B such that he abandoned his Stage A's contribution, then yes voting on revised Stage B makes sense — but for E specifically the deltas are additive, not contested.

### Disagreement 3 — "All of 3.1.1 goes into 3.1.0" (Codex-1 & implicit in Codex-2)

Codex-1's proposal moves all current 3.1.1.* into 3.1.0. Codex-2 flagged the open question: "Does Matt mean all of current 3.1.1 moves into 3.1.0, or only structural/schema material from 3.1.1?"

I read Matt's brain dump as: only the **schema/structural** content moves into 3.1.0. Operational content (e.g., "who is the current CEO" type org content) is *facts about the business*, not *schema for the business node*. Facts belong somewhere addressable but not necessarily inside the schema channel.

**Revised proposal**: Stage 2 of the migration explicitly separates 3.1.1.* contents into:
- **Schema-flavored content** (org-structure definitions, role definitions, hierarchy templates) → 3.1.0
- **Fact-flavored content** (current org members, current team rosters, current decisions) → stays as a sub-node under 3.1 with a new natural address (perhaps `3.1.14 - Current Organization` or similar — needs Matt input)

This is a hard call. If we treat all of 3.1.1 as schema, we conflate the model with the data. Surface to Matt.
