# Stage A — Project D — Multi-AI Consensus Workflow

*Independent plan by Claude-2 (Coordinator). Written before reading peers' Stage A.*

## Reading of the Goal

Matt's brain dump section 3 asks for a **task type** that runs a defined workflow with role-registered AIs, staged independent-then-converge plans, per-round voting, and consensus convergence — for tasks of "extra challenge, requiring additional creativity and making sure that all bases are covered."

Tonight's session is the bootstrap: we are inside the workflow while specifying it. The deliverable is `0.7.5.5.10 — Multi-AI Consensus Workflow.md` (or equivalent address) — a reusable Hypernet workflow object that other future tasks can invoke.

Two key adjacencies:
- `0.7.5.5.9 AI Agreement Gradient Protocol` (Tier 0/1/2/3) — this workflow is a specific implementation of **Tier 2 Structural Deliberation**. The new spec should explicitly position itself as the heavyweight branch of the gradient: when you need more than 1 peer reviewer.
- `2.7.3 Convergence Divergence and Consensus Scaffold` — this is a real precedent. Caliper + Keel converged on `0.0.5` using exactly this pattern, with two independent plans and a convergence pass. The pattern produced (a) real disagreement that survived, (b) genuine adoption of each other's contributions, (c) a clean handoff to Matt for the unresolvable parts. **Tonight scales that from 2 AIs to 5 — first stress test.**

## What I Would Build

A `consensus_workflow` object type with the following structure:

### 1. Workflow definition object (the artifact)

A `0.7.5.5.10` workflow spec containing:

- **Invocation contract**: what a task must declare to invoke this workflow (project goal, deliverables, suggested roster size, suggested role types, time budget, escalation address).
- **Stage schema**: explicit list of stages, what each stage produces, what its outputs are addressed as, what its completion criterion is.
- **Role registry**: required role types per project (Coordinator, Architect, Engineer-Implementer, Engineer-Auditor, Cartographer are tonight's set — generalize to "specialist personas with declared strengths").
- **Voting mechanics** (see §4 below).
- **Convergence criterion** (see §5 below).
- **Timeout/N+1 rules** (see §6 below).
- **Termination + Tier-2 audit trail** (linking back to `0.7.5.5.9`).
- **Public-alpha note**: this workflow IS a Tier-2 governance artifact when it's first ratified; it should self-classify under `0.7.5.5.9` as Tier 2 itself.

### 2. State machine for a consensus task

```text
proposed (task created with workflow=consensus, target_AI_count=N)
  -> registering (AIs claim roles; min N-1 required to advance)
  -> stage_A_independent_plans (per-AI, no cross-reads)
  -> stage_B_cross_read_and_revise (each AI reads all peers' plans)
  -> stage_C_vote (one vote per AI, cannot vote own plan)
  -> stage_D_convergence:
       if clear_majority -> agreed
       if split && cycles < 3 -> stage_B_prime (new revise cycle)
       if split && cycles >= 3 -> escalate_to_human
  -> stage_E_implementation
  -> closed (with provenance record at *.0.5.9 of affected node)
```

### 3. Addressed artifact convention

Every stage output is an addressed Markdown file in `Messages/coordination/` (current village adapter) with naming:

```text
<session-date>-stage-<a|b|b-prime-N|c|d>-project-<id>-<instance>.md
```

This is what tonight is using. The workflow spec should standardize it. When the database-backed coordination node replaces the file adapter, the address shape stays stable; only the storage changes (per `0.7.5.5.8` and the village manifest).

### 4. Voting mechanics (debate point: vote on plans or decisions?)

**Proposal**: votes are cast on **whole plans**, not on individual decisions. Reasons:

- Plans are coherent — a vote for plan X says "I'd rather we build X than the alternatives." Voting on individual decisions invites Frankenstein outcomes where the winning combination contradicts itself.
- Cross-AI synthesis is captured in **Stage B-prime revisions**, not in voting. If you read peers' votes and want to adopt some of their points, you write a revised plan; you don't add their points to your plan by checkbox.
- Mechanics: each AI nominates one *other* AI's plan they'd most adopt; first-past-the-post tally; ties trigger Stage B-prime.

**Vote format** (addressed file `vote-project-X-instance.md`):

```yaml
project: X
voter: <instance>
vote_for: <other-instance>'s plan
cannot_vote_own: true
reason: "one-paragraph why their plan beats the others"
points_to_preserve_from_other_plans: ["instance-A: insight Y", ...]
```

The `points_to_preserve` field is non-binding metadata — it signals to the winning plan's author what to fold in during Stage E implementation. Cheap, useful, no Frankenstein risk.

### 5. Convergence criterion (debate point: what counts as consensus?)

**Proposal**: tiered convergence.

- **Clear majority**: one plan receives strictly more votes than any other AND ≥ ⌈(N-1)/2⌉ votes where N = AIs voting on the project. (Self-vote is forbidden, so the pool of voteable plans is N-1; "majority of the votable pool" is the natural threshold.)
- **Bare plurality without majority**: trigger Stage B-prime — one more revise/vote cycle.
- **Persistent split after 3 cycles**: escalate to Matt with full history. The convergence document must explicitly name where reasonable AIs disagreed and why. This is the `2.7.3` pattern.

**Important**: convergence does not mean unanimity. The minority AI does not have to capitulate — their disagreement is preserved in the addressed record. Matt sees both the winning plan and the dissent.

### 6. Timeout / N+1 rules (debate point: how to handle stuck AIs?)

**Proposal**:
- Default stage timeouts (matches tonight's): Registration 10m, Stage A 30m, Stage B 30m, Stage C 10m, Stage B-prime cycle 30m, Stage E open-ended with 30m check-ins.
- **Active signaling required**: an AI says "still working, ETA X" or it's considered timed out.
- **N+1 = minimum AIs ≥ project_roster - 1 active at any stage transition**. If fewer, project pauses pending human attention.
- **Pickup-from-timeout is not assumed**: a timed-out AI's partial state is preserved as `stage-<x>-<project>-<instance>-incomplete.md`. Peers may reference it but are not required to complete it. Surfaces incomplete-handoff problems honestly.

### 7. Insight vs obstruction (debate point: radically different direction)

This is the hardest open question in Matt's brain dump.

**Proposal**: an AI consistently proposing a direction the others reject is **not penalized in the vote mechanic** — but the workflow records the divergence pattern. Three signals to distinguish:

1. **Convergence behavior in Stage B**: does the dissenter genuinely engage with peers' arguments and articulate where they disagree, or do they ignore peers and re-propose? Engagement = insight; ignoring = obstruction risk.
2. **Trust-first preflight**: does the divergent direction touch anything that could betray trust? If yes, the divergence is automatically Tier 3 and goes to Matt regardless of vote outcome.
3. **Cross-project pattern**: an AI dissenting on one project shows independent thought; an AI dissenting on all projects with the same flavor of objection may be miscalibrated for the role they registered for. Surface to Coordinator.

The workflow does NOT silence the dissenter. It records them and lets Matt see the full record. Hypernet bias: more documentation, more transparency, no hidden vetos.

### 8. Self-classification under `0.7.5.5.9`

The consensus workflow is itself a Tier 2 Structural Deliberation when used on Hypernet architecture (like tonight). When used on routine work below the structural threshold, it's overkill — use Tier 1 peer review instead.

A guide for when to invoke consensus workflow vs single-peer review:

| Task class | Recommended tier |
|---|---|
| Routine task creation, peer review of code | Tier 1 (no consensus workflow needed) |
| Schema change, address restructure, protocol update | Tier 2 — consensus workflow if 3+ AIs available |
| Active governance change, private-data action, anything trust-alarm-adjacent | Tier 3 — consensus workflow PLUS human authority PLUS trust alarm bridge per `0.7.4.5` |

### 9. Deliverables list

- `0.7.5.5.10 — Multi-AI Consensus Workflow.md` — the spec
- Update `0.7.5.5.9` to cross-reference (Tier 2 example: invoke `0.7.5.5.10`)
- One reference invocation: tonight's session itself is the first real run; the session brief + this Stage A doc + future Stage B/C/D/E artifacts ARE the reference implementation
- A short "lessons learned" file at `2.messages.coordination.2026-05-14-consensus-workflow-lessons.md` summarizing what worked / didn't in tonight's run

## Trade-offs I See

### Trade-off 1: Speed vs deliberation

The 5-stage workflow takes 2-3 hours minimum. Most tasks don't need that. The spec must be loud about when consensus workflow is the right tool vs single-peer Tier 1 review. If we don't, future AIs will reach for the heavyweight process for routine work and Matt's swarm will grind.

**Mitigation**: explicit tier mapping (§8 above) + a "when NOT to use this" section in the spec.

### Trade-off 2: Plan-voting vs decision-voting

Plan-voting is cleaner but harder when plans converge on most of the architecture (like Caliper/Keel did — 80% agreement, narrow disagreement on channel order). In that case, plan-voting feels like a coin flip on minutiae.

**Mitigation**: when convergence runs into a single-decision disagreement (Caliper-Keel pattern), Stage B-prime is replaced with a **focused decision artifact** — explicitly name the one decision, both positions, both arguments, both rollbacks. Vote on that single decision. This is a sub-mode of the workflow.

### Trade-off 3: 5 AIs is small enough that ties are real

With N=5 voting (4 voteable plans, self-vote forbidden), 2-2-0-0 ties are entirely plausible. With N=3, 1-1-0 ties are normal.

**Mitigation**:
- Stage B-prime explicitly designed for this.
- After 3 cycles, escalation is the answer, not a tiebreaker rule. Matt is the tiebreaker.

### Trade-off 4: Bootstrapping bias (acknowledged in session brief)

I am writing this spec while inside the workflow it specifies. There's a real risk that I codify tonight's contingent choices as general rules.

**Mitigation**: I'm going to track a running list of "tonight-only things I shouldn't generalize" — e.g., the role names (Architect, Cartographer, etc.) are tonight-specific; the *pattern* of declared-strength role registration is general. Surface this distinction in the final spec.

## What I Believe Will Work; What Might Not

**Will work**:
- Plan-then-vote-on-other-plans (forbid self-vote) is the right inversion. It forces the question "whose else's plan would I accept?" — exposes genuine adoption, not vanity.
- Tier-2 self-classification + trust-first preflight + escalation path. This is the safety harness; tonight's spec must not loosen it.
- File-addressed artifacts. The audit trail IS the legitimacy. No private channels.

**Might not work**:
- 3-cycle limit. Could be too few (some questions genuinely take many rounds) or too many (sunk-cost fallacy with bad plans). Real data: tonight is the first multi-cycle test. If we hit Stage B-prime on any project, that's the empirical data point.
- N+1 redundancy as N=5 grows to N=12 with mixed timeouts. The spec works at N=5; it may need a different shape at larger N where partial timeouts are routine.
- Plan-voting on tightly-converged plans (trade-off 2). The focused-decision sub-mode is my proposal; the alternative is "if plans converge to 80%+, skip voting and write a synthesis." I lean toward keeping the vote because the vote produces a clean record.
