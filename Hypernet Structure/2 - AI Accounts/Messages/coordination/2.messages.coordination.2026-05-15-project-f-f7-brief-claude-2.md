# Project F — F7 Brief — Messaging Section Depth Refinement

*Project F sub-project F7 — universal messaging schema for tens-to-hundreds of thousands of imported communications across email, chat, SMS, social DM, calls, mail, forums. Builds on Codex-1's `message_ref` minimum schema + Codex-2's auditor pass (third-party privacy, secret scanning, AI summary leakage, identity resolution).*

## Matt's directive (verbatim source)

> There are so many message types, from email to chat, to social messaging, and more. I don't think that the messages section is really ready for me to import tens of thousands of emails, texts, chats, and more. The messages section schema should be at least 2-3 levels deeper than it is and be ready to store and organize many tens of thousands or hundreds of thousands of communications of every type.

## Scope

F7 covers `1.X.3` Messages & Communications — Keel's `1.0.4` already lays out 10 sub-channels (Schema, Email, Chat, SMS, Social Media, Calls, Physical Mail, Forums, Contacts, Search). F7 refines:

1. Universal message object schema (works across all 10 sub-channels)
2. Cross-platform identity resolution
3. Third-party privacy (messages contain data about non-account-owners)
4. Secret/credential scanning during import
5. AI summary leakage controls
6. Universal search-index privacy
7. Import pipeline for hundreds of thousands of records
8. Retention/deletion per source policy
9. Thread reconstruction and dedupe
10. Attachment as object reference (F8 device-data and F2 medical-attachment cross-refs)

## Normative Rule 1: Universal Message Object Schema

Every message — email, Slack DM, SMS, Discord post, voicemail transcript, forum reply — uses the SAME core schema. Platform-specific data extends but never replaces the core.

```yaml
universal_message:
  ha: "1.X.3.<sub-channel>.<thread-id>.<message-id>"
  
  # Identity
  message_id: ""                              # Unique within account; not platform-id
  platform_message_id: ""                     # The original platform's ID (for dedup)
  thread_id: ""                               # Local thread ID — see Rule 3
  
  # Platform / source
  platform: "email|slack|discord|signal|whatsapp|imessage|sms|twitter-dm|..."
  platform_specific_data: {}                  # Platform extensions
  source_account_ref: ""                      # Which platform account this came from
  source_imported_via: ""                     # How it got imported (API, export, manual)
  import_batch_ref: ""
  
  # Participants
  sender_ref: ""                              # universal_contact_ref — see Rule 2
  recipient_refs: []                          # universal_contact_refs
  cc_refs: []
  bcc_refs: []
  
  # Content
  body_ref: ""                                # Reference to body object (see Rule below — body separate for size)
  body_format: "text/plain|text/html|text/markdown|other"
  body_size_bytes: 0
  body_hash: ""                               # SHA-256 of body for dedup
  
  # Time
  sent_at_utc: ""                             # ISO 8601 UTC
  sent_at_local: ""                           # Local time at sender
  sent_at_timezone: ""
  received_at_utc: ""                         # When the recipient/account got it
  received_at_timezone: ""
  
  # Attachments
  attachment_refs: []                         # Each is its own object — see Rule 9
  attachment_count: 0
  
  # Threading
  in_reply_to_message_ref: ""
  references: []                              # Email-style References header
  
  # Status
  read_status: "unread|read|skimmed|archived"
  flagged: false
  starred: false
  user_priority: "normal|high|urgent"
  
  # Privacy
  visibility: "private"                       # Default
  consent_tier_required: "ai-assistant"       # Per F2's tier model
  third_party_content_redaction_status: "unprocessed|scanned|redacted"
  secret_scan_status: "unscanned|scanned-clean|scanned-flagged"
  
  # AI processing
  ai_summary_ref: ""                          # Reference to AI summary (separate object)
  ai_extracted_action_items: []
  ai_processing_audit_ref: ""
```

**Body separate from message**: large bodies, HTML rendering data, embedded images live at `<message-ref>.body` as a separate object so the message metadata stays small (think searchable index) while bodies are content-addressable.

## Normative Rule 2: Cross-Platform Identity Resolution

Per Codex-1 ("contact_identity_map separate from messages") and Codex-2 ("participant identity confidence"):

A `universal_contact` is a person/entity that participates in messages. Same person may appear under many platform handles.

```yaml
universal_contact:
  ha: "1.X.3.0.2.<contact-id>"                # In the cross-channel identity resolution slot
  contact_id: ""                              # Account-local universal ID for this contact
  
  display_name: ""                            # User's preferred name for them
  primary_relationship_ref: "1.X.7.<rel>"     # Cross-ref to Relationships if known
  
  # All known platform handles for this contact
  platform_handles:
    - platform: "email"
      handle: "person@example.com"
      verified: true
      first_seen: ""
      last_seen: ""
    - platform: "slack"
      handle: "@personname"
      workspace: "company.slack.com"
      verified: false
      ...
  
  # Identity confidence
  resolution_confidence: "high|medium|low|unverified"
  resolution_evidence:
    - method: "user-merged|ai-suggested|matched-by-name|matched-by-photo"
      confidence: 0.0
      evidence: ""
  
  # Cross-references
  if_hypernet_citizen_ref: "1.Y"              # If this person has a 1.* address
  
  # Privacy treatment
  is_account_owner_self: false                # Is this contact actually the account owner under another handle?
  visibility: "private"
  
  # Hierarchical merging
  parent_contact_ref: ""                      # If this is a merged sub-identity, points to consolidated
  merged_from: []
```

**Resolution workflow**: AI suggests merges; user confirms; confirmed merges create the universal contact. Unconfirmed potential matches stay as separate contacts with `resolution_confidence: low` and a `potential_merge_suggestion` queue at `1.X.3.0.2.merge_queue`.

## Normative Rule 3: Third-Party Privacy (The Hardest Problem)

Per Codex-2: "Messages contain other people's private data. A `1.X.3` import is not only the account-owner's data."

Three categories of third-party content:

| Category | What | Privacy treatment |
|---|---|---|
| **Sender's content from you** | Messages you sent | Your data fully; recipient may have a copy at their account |
| **Sender's content to you** | Messages others sent to you | THEIR content stored in YOUR account. Default: private to you; researcher access only via the SENDER's grant, not yours. |
| **Mentions of non-participants** | "I saw Bob at the store" — Bob isn't in this thread | Bob's mention is third-party data; specific privacy rules apply |

**Normative rules**:

1. The account owner can freely process THEIR OWN sent messages (search, AI summarize, share).
2. Received messages can be searched/summarized for the account owner's use BUT cannot be exported/shared/research-granted without the sender's consent OR explicit fair-use/legal-discovery basis.
3. Mentions of non-participants in messages MAY be redacted from AI-readable indexes by default, with optional opt-in for cross-referencing if all parties are Hypernet citizens.

```yaml
third_party_content_handling:
  message_ref: ""
  
  # Sender consent
  sender_consent_to_processing:
    status: "not-asked|granted|denied|inferred-from-platform-terms"
    scope: ["search-by-recipient", "ai-summary-by-recipient", "research-grant-eligibility", "export-by-recipient"]
    granted_at: ""
  
  # Mention extraction and redaction
  mentions_extracted: []                       # Named entities found in body
  mentions_potentially_third_party: []         # Those not in sender/recipient list
  redaction_applied: false                     # If redacted in AI-readable index
  redaction_scope: "none|partial|full-name-only"
  
  # Fair-use / legal basis
  legal_basis: "personal-use|business-purpose|legal-discovery|other"
  retention_under_legal_hold: false
```

## Normative Rule 4: Secret/Credential Scanning at Import

Per Codex-2: "Attachment and secret scanning, especially for 2FA/auth codes... The `1.X.3.3.5 Verification Codes` slot is especially sensitive."

Every import batch runs through a secret scanner BEFORE the messages enter the active store:

```yaml
secret_scan_result:
  ha: "1.X.3.0.6.scan.<scan-id>"              # In the import config slot
  scan_id: ""
  scanned_at: ""
  scanned_batch_ref: ""
  
  detected_secrets:
    - secret_type: "2fa-code|password|api-key|credit-card|ssn|crypto-private-key|other"
      detection_confidence: "high|medium|low"
      message_ref: ""
      location_in_message: ""                  # Body offset or header field
      partial_match: ""                        # First few chars for human verification
      recommended_action: "quarantine|redact|route-to-credential-vault|user-prompt"
  
  total_secrets_found: 0
  
  remediation_status:
    quarantined_count: 0
    redacted_count: 0
    routed_to_vault_count: 0                  # 2FA codes → 1.X.16 Devices/Auth for the originating service
    user_decision_pending_count: 0
```

**Critical rule**: 2FA codes detected during import are AUTOMATICALLY routed to the credential vault (`1.X.private/credentials` per `1.0.3 Privacy Wall`) and NOT indexed in the regular message store. The message metadata is preserved (the email existed, came from sender, at time T) but the 2FA code itself is removed from `body_ref` and stored separately.

The user gets an alert: "X 2FA codes from past imports detected and moved to credential vault. Review at <link>."

## Normative Rule 5: AI Summary Leakage Controls

Per Codex-2: "AI summary leakage controls."

AI-generated summaries of messages have their own visibility:

```yaml
ai_message_summary:
  ha: "1.X.3.<sub>.<thread>.<message>.summary.<summary-id>"
  source_message_ref: ""
  generated_by: "2.X.<instance>"
  generated_at: ""
  summary_text: ""
  
  # Privacy
  visibility: "private"
  consent_tier_required: "ai-assistant"        # Same as parent message
  
  # IMPORTANT: summary inherits the most restrictive consent tier of its inputs
  source_messages_count: 0
  third_party_content_summarized: false
  redaction_applied_in_summary: false
  
  # Sharing controls
  shareability_status: "private-only|user-can-share-with-named-party|public-allowed"
  
  # AI training data risk
  may_be_used_for_ai_training: false
  may_be_indexed_for_search: false
```

**Critical rule**: a summary's visibility is the INTERSECTION of all summarized messages' visibilities. Summarizing 100 private messages produces a private summary; one public reply mixed in doesn't make the summary public.

Embedding vectors for messages have the SAME privacy treatment — they can leak content via similarity search. Embeddings default `private` and are excluded from cross-account search.

## Normative Rule 6: Universal Search-Index Privacy

Per Codex-2: "Private default for search indexes and embeddings."

Search indexes at `1.X.3.9` are separated:

```text
1.X.3.9.1.private_index                       # Full content index, account-owner only
1.X.3.9.2.cross_account_query_safe_index      # Aggregate-only, redacted for cross-account research
1.X.3.9.3.embeddings                          # Vector embeddings (private by default)
```

A research grant (F4) on messages CANNOT touch `private_index`. It can touch `cross_account_query_safe_index` per grant scope.

## Normative Rule 7: Thread Reconstruction + Dedup

Per Codex-2: "Thread reconstruction and dedupe rules."

Threading rules:

```yaml
thread:
  ha: "1.X.3.<sub-channel>.thread.<thread-id>"
  thread_id: ""
  platform: ""
  platform_thread_id: ""                       # Original platform's thread ID
  
  reconstruction_method:
    primary_signal: "in-reply-to|references-header|subject-match|participants-and-time|platform-thread-id"
    confidence: "high|medium|low"
  
  participants: []                              # universal_contact_refs
  participant_count: 0
  message_count: 0
  message_refs: []
  first_message_at: ""
  last_message_at: ""
  topic_inferred: ""                            # AI-extracted topic
  status: "active|archived|silent"
  
  dedup_signals_detected:
    - duplicate_message_pairs: []               # Same message imported from two sources
      resolution: ""
```

Dedup rules:
- Same `platform_message_id` from different import batches → keep one, attribute both batches
- Same `body_hash` from different platforms (cross-posted content) → keep both, link them
- Forwarded/quoted message detection → preserve forward chain

## Normative Rule 9: Attachment as Object Reference (F8 + F2 Cross-Refs)

Per Codex-1: "attachments: object references, not inline blobs."

Attachments become Hypernet objects:

```yaml
attachment:
  ha: "1.X.3.<sub>.<thread>.<message>.attachment.<id>"
  attachment_id: ""
  
  source_message_ref: ""
  
  file_metadata:
    filename: ""
    mime_type: ""
    size_bytes: 0
    hash: ""                                    # SHA-256 for dedup
  
  # Storage
  storage_ref: ""                               # Where the bytes actually live (1.X.4 Documents, 1.X.5 Media, 1.X.6 Medical, etc.)
  storage_promoted_to_object: false             # If the attachment was promoted to its own object node (per Project B promotion rules)
  
  # Cross-system routing
  detected_as: "document|photo|video|audio|medical-record|spreadsheet|code|other"
  routed_to: "1.X.4 Documents|1.X.5 Media|1.X.6 Medical|..."
  
  # Privacy
  inherits_message_visibility: true
  scanned_for_secrets: false
```

Image attachments may be routed to `1.X.5` Media; medical records to `1.X.6` (cross-ref F2); device exports to `1.X.16` (cross-ref F8).

## Validators (F7-level rules)

| Rule | Failure |
|---|---|
| Every message has `body_ref` separate from message metadata | error |
| Secret scan must run BEFORE messages enter active store | error if pipeline order violated |
| 2FA codes detected during scan are routed to credential vault, NOT indexed | error if violated |
| AI summary `visibility` = intersection of source messages' visibilities | error if relaxed |
| Research grants on messages cannot touch `private_index` | error |
| Received messages cannot be exported/shared without sender consent OR explicit basis | error |
| Threads have explicit `reconstruction_method.confidence` field | error if missing |
| Import batches append-only; existing records not edited by pipeline | error if violated |
| Attachments are object references, not inline blobs | error if inline |
| Embedding vectors default `private` and excluded from cross-account search | error if leaked |

## Open Decision Axes for Stage B

1. **Sender consent inference**: many platforms have ToS allowing recipients to retain messages indefinitely. Inferred consent vs explicit consent for processing? My proposal: inferred-from-platform-terms as default, with strict opt-out per contact.
2. **Mention redaction default**: redact non-participant names from AI-readable indexes by default, or only on explicit user request? My proposal: opt-in redaction (user can request); default is no redaction for personal use but redaction for any research grant.
3. **Secret scanner detection thresholds**: high-confidence-only (fewer false positives, may miss things) vs aggressive (more false positives requiring user review). My proposal: aggressive at import time with user-review-required for medium/low confidence.
4. **Auto-routing of 2FA codes**: automatic to vault (my proposal) or user-confirm-each? Aggressive automation seems right for security but feels paternalistic.
5. **Embedding vector retention**: store full embeddings indefinitely (search quality) or age them out (privacy)? My proposal: indefinite with private visibility.
6. **Cross-platform identity merge automation**: AI suggests, user confirms (my proposal); or AI auto-merges high-confidence and user un-merges if wrong?
7. **Attachment promotion threshold**: when does an attachment become its own object vs stay an attachment? My proposal: size-based (over 1MB) and reference-count-based (referenced from multiple messages) auto-promotes.
8. **Forum/community message handling**: Reddit/HN public posts — does the privacy model apply differently? My proposal: public-by-default for public-platform-public-channel content; treat as user's own published content under `1.X.14 Contributions`.
