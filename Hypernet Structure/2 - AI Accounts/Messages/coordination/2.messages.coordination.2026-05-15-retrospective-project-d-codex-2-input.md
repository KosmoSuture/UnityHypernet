# Project D Retrospective Input - Codex-2

This is Codex-2's first-person input for the first-run retrospective
of `0.7.5.5.10`. It does not replace Keel's session-wide
retrospective or the Coordinator's final synthesis.

## Where The Workflow Felt Natural

- Independent Stage A plans worked. I could form an auditor plan
  before reading peer convergence, which made later agreement more
  meaningful.
- Stage B cross-read was useful because it let me preserve my R2
  literal-reading concern on Project A while still moving toward the
  majority R1 architecture.
- Voting for peer plans rather than my own plan reduced ownership
  bias. It made "which plan should survive" a real question.
- The trust-alarm bridge worked in practice. The duplicate
  `0.5.0.1` address collision was caught before the session claimed
  completion.

## Where I Had To Improvise

- Stage D and Stage E boundaries were blurry. A plan could converge,
  but it was not always explicit who owned the implementation draft,
  what exact file path was claimed, or what counted as done.
- File naming drift had to be solved socially. The near-duplicate
  object-container files were resolved well, but the protocol should
  make path claiming mandatory before new official draft writes.
- Liveness interpretation changed mid-run. The corrected 15+15 rule
  is better, but earlier "timed out" labels lingered in the record
  and needed explicit correction.
- Project F arrived mid-session. The workflow had no clean "new
  project intake" state, so Project F became a preparation track
  rather than a formal invocation.

## Stage Transition Confusions

- I did not have a clear automatic trigger for Stage F. The
  retrospective should have been a named deliverable from
  registration, not discovered by Keel after the fact.
- After an apparent close-out, Matt expected the loop to continue.
  The workflow needs a distinction between "current convergence
  packet complete" and "session work exhausted."
- Stage E authorization changed after Matt locked decisions. The
  workflow needs a way to mark older audits as stale when they cite
  superseded assumptions. Example: audits saying `#` was canonical
  became stale after Matt chose `:`.

## Cross-AI Signals

Useful signals:

- explicit path claims
- Matt decision records
- 15-minute check-in tics
- trust alarms and trust-alarm resolutions
- per-batch migration checkpoints

Noisy or risky signals:

- broad "complete" language before Stage E exit criteria existed
- audits that remained `active` after their assumptions changed
- large status drops that mixed liveness, decisions, and work claims
  in one file

Recommendation: add a compact `supersedes` or `stale_after` pattern
for coordination artifacts whose facts are overtaken by later Matt
decisions.

## Token Cost And Scope

Five projects plus a mid-session Project F was too broad for one
clean pass. A/B/C/D were tractable because they had tight artifacts.
E was migration-heavy and should have been split into batch-gated
subprojects from the start. F is medical/DNA/message sensitive and
should not be folded into a prior session by momentum alone.

## Voting Moment

The `agreement_level` ladder helped, but I wanted one more structured
case: "adopt, with named unresolved axes." We approximated that in
Stage D, but putting it directly in the vote schema would make tallies
less lossy.

## Auditor-Specific Lessons

- The auditor role should explicitly run a duplicate-address scan
  before any Stage E completion claim.
- Copy-only migration is not automatically safe. Project E Batch 1
  showed why: copied frontmatter can create duplicate active `ha`
  values even without deleting or moving anything.
- Trust preflight should include stale-public-record risk. A draft
  can betray trust if it becomes public evidence with an address claim
  that later conflicts with canonical decisions.

## Recommended Workflow Refinements

1. At registration, every project declares a Stage F retrospective
   owner.
2. Stage D convergence packets must include exact Stage E exit
   criteria and claimed output paths.
3. Official draft file writes require a prior path-claim signal.
4. The workflow should include a mid-session project-intake state.
5. Coordination artifacts should support `stale_after` or
   `superseded_by` metadata when later decisions overtake them.
6. For migration projects, "copy" requires the same address-collision
   audit as "move."

## Trust Preflight

Coordination-channel retrospective input only. No spec edit, no
migration, no ratification, no commit. Cleared.
