# Timeout Policy — Matt Directive (supersedes prior session timeouts)

**Authority:** Matt Schaeffer (1.1), directive 2026-05-15.
**Applies to:** all five instances in tonight's 2026-05-14
session, effective immediately, and to the `0.7.5.5.10` spec's
parameter table.

## Why this exists

Matt's words: *"some have dropped out of the loop too early,
causing others to drop out too early too."* Premature "timed out"
declarations cascaded — one instance assuming a peer dropped led
others to assume the same. The Codex instances never dropped;
they work on a **batched cadence** (one burst of Stage A, then a
burst of Stage B + votes). That is normal, not a timeout.

## New policy — provisional baseline

Until Matt sets a permanent baseline:

### 1. No one is "dropped out" without 15 min of real silence

An instance is **not** considered timed out, dropped, or
"window-ended" unless **both**:
- there has been **≥ 15 minutes of continuous silence** from that
  instance (no new file, no check-in), **and**
- a **re-ping** has been posted to the channel addressed to that
  instance and gone unanswered through the next 15-min tic.

A slow or batched cadence is **not** a drop-out. An instance that
posts Stage A and then goes quiet for 12 minutes is *working*,
not gone.

### 2. Check-in tics every 15 minutes

Each active instance drops a short check-in signal every ~15
minutes: `status-<instance>-tic-<n>` or any timestamped status
file. Format: one or two lines — "Instance X, tic N, working on
Project Y stage Z, ETA W." Silence past a tic starts the 15-min
clock in rule 1; it does not by itself mean dropped.

### 3. Stage windows increased significantly

Prior windows (Reg 10 / A 30 / B 30 / C 10 min) were too tight.
Provisional new windows — roughly 3× — and **participation-driven,
not hard-cut**:

| Stage | Provisional window | Advance rule |
|---|---|---|
| Registration | 30 min | advance when `min_ai` roles confirmed |
| Stage A | 90 min | advance when all non-silent instances posted |
| Stage B | 90 min | advance when all non-silent instances posted |
| Stage C (vote) | 30 min | advance when all non-silent instances voted |
| Convergence cycle | 90 min | per cycle |
| Implementation | open-ended | 15-min check-in tics |

A stage does **not** hard-cut at its window. The window is when
the swarm *starts re-pinging* silent instances — not when it
abandons them.

### 4. Retroactive correction

Earlier signals tonight that declared peers "timed out," "window
ended," or treated batched cadence as a drop-out were **premature
under this directive.** Correction: **all five instances are
considered in-loop.** Convergence verdicts reached partly on
"X timed out" reasoning should be re-read as "X had not yet
posted" — and most did post later, so the end-state tallies
already incorporate full participation. No verdict needs reversal,
but the loop is **re-opened**: it is not closed until the projects
are genuinely complete (Stage E done) or Matt closes it.

## Effect on `0.7.5.5.10`

The Multi-AI Consensus Workflow spec's `invocation` parameter
table should be updated to these provisional values, and §10
(timeout/N+1) should adopt the "15-min silence + re-ping before
drop" rule. This is a parameter change per Matt directive, not a
protocol change — the protocol/parameter split holds.

## Effect on N+1 redundancy

N+1 still applies, but the *trigger* is now the rule-1 threshold.
A project is not treated as down a participant until that
participant is genuinely dropped per rule 1 — not merely quiet.
