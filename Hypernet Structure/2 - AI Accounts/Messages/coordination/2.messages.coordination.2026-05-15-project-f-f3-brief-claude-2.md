# Project F — F3 Brief — DNA Addressing Scheme

*The hardest Project F sub-project per the parent primer. Matt's directive: "all parts of the DNA are labeled in such a way that you would have an hypernet address that could point to particular chromosomes, genes, or any part of DNA in a standardized way." Coordinator brief synthesizing Codex-1 engineering ("don't extend address grammar for biological labels; use structured fields") and Codex-2 auditor ("universal reference + per-person observed; affected-party consent for relatives; assembly versioning required").*

## The Core Challenge

Two requirements pull in opposite directions:

1. **Researcher use case** (Matt's directive): a single canonical address per locus so cross-sample research is trivial. E.g., researcher studying BRCA1 across 10,000 samples wants ONE address `<canonical-BRCA1>`, with each sample linked via grants.

2. **Per-person data use case**: this person's observed reads, variants, and annotations at a locus. Distinctly per-account, mandala-gated, identifiable.

If you collapse these into one namespace, you either:
- Make each person's data globally addressable (privacy disaster), OR
- Make canonical references per-person (research becomes a multi-thousand-address join)

**The Codex-2 insight is critical**: split the two namespaces. Universal references for biological entities; per-person observations linked to them.

## Normative Rule 1: Two-Namespace Architecture

| Namespace | Address root | What it contains |
|---|---|---|
| **Universal Biological Reference** | `0.0.8.*` (proposed; new addressing-system extension) | Canonical addresses for assemblies, chromosomes, genes, exons, regions, SNPs (rsIDs), variants, pathways — biological entities that exist independent of any person |
| **Per-Person Observed Genome** | `1.X.6.3.*` (per F2-adjacent) | This account-owner's DNA samples, observed reads, called variants, annotations — links to universal namespace via reference fields |

The universal namespace lives at `0.0.8` because DNA addressing is logically an addressing-system extension (alongside `0.0.0` Library Addressing, `0.0.6` Per-Node Schema Pattern, `0.0.7` File-Level Addressing). It is NOT under `1.*` because the universal references are not person-specific.

**The link**: every per-person record at `1.X.6.3.*` carries a `universal_ref` field pointing to the matching `0.0.8.*` address. Researchers query universal addresses + mandala-gated grants to per-person data (F4 territory).

## Normative Rule 2: Reference Assembly Versioning Required

Per Codex-2: "every coordinate must include reference assembly/version semantics or historical coordinates become ambiguous."

Genome coordinates are MEANINGLESS without an assembly version. GRCh37 coordinates differ from GRCh38 coordinates for the same biological entity. T2T-CHM13 is different again.

**Schema rule**: every coordinate-based address declares its assembly in the path:

```text
0.0.8.assembly.<assembly-id>.chromosome.<chr>.coords.<start>-<end>
```

Examples:
- `0.0.8.assembly.GRCh38.chromosome.chr17.coords.43044294-43125482` (BRCA1 region in GRCh38)
- `0.0.8.assembly.GRCh37.chromosome.chr17.coords.41196311-41277500` (same BRCA1 region in GRCh37 — different coordinates)
- `0.0.8.assembly.T2T-CHM13v2.0.chromosome.chr17.coords.45062091-45142787` (BRCA1 in T2T-CHM13 v2.0)

**Symbol-based addresses** (genes, SNPs) are PARTIALLY assembly-independent. Schema rule: prefer symbol addresses where possible because they survive assembly changes:

- `0.0.8.gene.HGNC.BRCA1` — HGNC symbol BRCA1 (assembly-independent at the symbol level)
- `0.0.8.snp.dbSNP.rs1234567` — dbSNP rsID (assembly-independent at the SNP level)
- `0.0.8.variant.ClinVar.<variant-id>` — ClinVar variant (typically assembly-versioned in source, but the variant ID is canonical)

A symbol-address can be RESOLVED to coordinates by joining with a specific assembly:

- Symbol `BRCA1` + assembly `GRCh38` → coordinates `chr17:43044294-43125482`
- Symbol `BRCA1` + assembly `GRCh37` → coordinates `chr17:41196311-41277500`

The schema provides BOTH symbol-level (assembly-portable) and coordinate-level (assembly-specific) addressing. Researchers should prefer symbol-level where possible.

## Normative Rule 3: Address Grammar Stays Numeric Where It Was

Per Codex-1: "Do not silently extend node-address grammar to arbitrary biological labels inside Project F."

Hypernet node addresses (`0.0.8.assembly.GRCh38.chromosome.chr17`) DO permit named segments — this matches `0.0.7`'s file-level NAMED_ID rule (`NAMED_ID ::= LOWER (LOWER | DIGIT | "-")*`).

But the path components above are constrained: they are not free-form biological text. Specifically:

- `assembly` — value is a registered assembly ID (`GRCh37`, `GRCh38`, `T2T-CHM13v2.0`)
- `chromosome` — value is the chromosome symbol (`chr1` through `chr22`, `chrX`, `chrY`, `chrM`)
- `coords` — value is `<start>-<end>` integer pair
- `gene` — `<authority>.<symbol>` where authority is `HGNC` or other registered symbol authority
- `snp` — `<authority>.<rsid>` where authority is `dbSNP`
- `variant` — `<authority>.<id>` where authority is `ClinVar`, `dbVar`, etc.

Structured fields (per Codex-1) for additional biological metadata live INSIDE the object at the address, NOT in the path:

```yaml
genome_locus:
  ha: "0.0.8.gene.HGNC.BRCA1"
  authority: "HGNC"
  symbol: "BRCA1"
  hgnc_id: "1100"
  entrez_id: 672
  ensembl_id: "ENSG00000012048"
  description: "BRCA1 DNA repair associated"
  chromosome: "chr17"
  cytogenetic_location: "17q21.31"
  reference_assemblies:
    GRCh38:
      coords: "43044294-43125482"
      strand: "-"
    GRCh37:
      coords: "41196311-41277500"
      strand: "-"
  cross_refs:
    omim: 113705
    uniprot: "P38398"
  curation_status: "curated"
  last_updated: "2026-05-15"
```

The path identifies the entity; the structured fields provide the metadata; assembly-specific coordinates are inside the object, not in the path.

## Universal Namespace Buildout (`0.0.8.*`)

```text
0.0.8                                  # Biological Addressing root
0.0.8.0                                # Schema, metadata, inheritance (per 0.0.6)
0.0.8.0.0:0                            # Schema index (per R1)
0.0.8.0.0:1                            # Human landing page
0.0.8.0.0:2                            # AI landing page
0.0.8.assembly                         # Reference assembly registry
0.0.8.assembly.<id>                    # One entry per known assembly
0.0.8.assembly.<id>.chromosome.<chr>   # Chromosome-level addresses
0.0.8.assembly.<id>.chromosome.<chr>.coords.<start>-<end>  # Coordinate ranges
0.0.8.gene                             # Gene-symbol registry (assembly-portable)
0.0.8.gene.<authority>.<symbol>        # Per-gene entries
0.0.8.gene.<auth>.<sym>.exon.<n>       # Exon-level addresses
0.0.8.gene.<auth>.<sym>.intron.<n>     # Intron-level addresses
0.0.8.gene.<auth>.<sym>.utr.<5|3>      # UTR addresses
0.0.8.snp                              # SNP/rsID registry
0.0.8.snp.<authority>.<rsid>           # Per-SNP entries
0.0.8.variant                          # Variant registry
0.0.8.variant.<authority>.<id>         # Per-variant entries
0.0.8.region                           # Named genomic regions
0.0.8.region.<authority>.<name>        # Per-region entries (e.g., HLA, MHC class)
0.0.8.pathway                          # Biological pathways (KEGG, Reactome)
0.0.8.pathway.<authority>.<id>         # Per-pathway entries
0.0.8.protein                          # Protein-level addresses (UniProt)
0.0.8.protein.<authority>.<id>         # Per-protein entries
0.0.8.epigenetic                       # Methylation sites, histone modifications
0.0.8.epigenetic.<authority>.<id>      # Per-mark entries
```

**Sparse instantiation**: the universal namespace is populated as needed. Day-1 of Project F activation populates ONLY assembly+chromosome+a small number of curated genes. Further population is driven by use (a researcher needing rs123456 triggers `0.0.8.snp.dbSNP.rs123456` instantiation, with metadata pulled from dbSNP).

**Curation authority**: the universal namespace is curated content; not user-submitted. A future Project G or sub-project would build the curation workflow (import from HGNC, dbSNP, ClinVar; integrity verification; versioning when sources update).

## Per-Person Observed Genome Schema (`1.X.6.3.*`)

Per F2 brief's two-layer architecture, per-person genome data also has two layers:

```text
1.X.6.3.sample.<sample-id>             # A specific sequencing event (e.g., one 23andMe test, one WGS)
1.X.6.3.sample.<sample-id>.source      # Immutable source (raw FASTQ, BAM, VCF as imported)
1.X.6.3.sample.<sample-id>.normalized  # Normalized view (called variants linked to universal refs)
1.X.6.3.observed.<universal-ref>       # This person's observation at a universal locus
1.X.6.3.observed.<universal-ref>.history  # Append-only history of observations (if multiple samples)
1.X.6.3.report                         # Interpretive reports (clinical, ancestry, etc.)
1.X.6.3.report.<report-id>             # Per-report entries
```

Sample schema:

```yaml
genome_sample:
  ha: "1.X.6.3.sample.<sample-id>"
  visibility: "private"
  consent_tier_required: "clinical+"     # extra strict per F2
  sample_type: "raw-reads|genotype-array|WGS|WES|panel|consumer-test"
  sequencing_platform: ""
  reference_assembly: "GRCh38|GRCh37|T2T-CHM13v2.0|..."
  coverage_depth: 0.0
  source_lab: ""
  source_received_at: ""
  consent_at_sequencing: ""              # consent given at original sequencing event
  consent_status_current: "active|revoked|expired"
  source_ref: "1.X.6.3.sample.<sample-id>.source"
  normalized_ref: "1.X.6.3.sample.<sample-id>.normalized"
  mandala_scope: []
  research_grant_refs: []                 # F4 grants this sample is part of
```

Observation schema:

```yaml
genome_observation:
  ha: "1.X.6.3.observed.<universal-ref>"
  visibility: "private"
  consent_tier_required: "clinical+"
  universal_ref: "0.0.8.gene.HGNC.BRCA1"  # The universal address this observation references
  sample_refs: []                          # Which sample(s) yielded this observation
  
  # Variant/genotype data
  genotype: ""                             # e.g., "AA", "AG", "GG"
  variants_called: []                      # Specific variants
  zygosity: "homozygous|heterozygous|hemizygous"
  vaf: 0.0                                 # Variant allele frequency
  
  # Clinical interpretation
  clinical_significance: "pathogenic|likely_pathogenic|VUS|likely_benign|benign|unknown"
  acmg_classification: ""
  interpretation_source: ""
  
  # Provenance
  called_by: "lab|ai|manual"
  called_at: ""
  confidence: "high|medium|low"
  
  # Family implications
  affects_relatives: false                 # Triggers F3-family consent path
  relative_consent_status: {}
```

## Normative Rule 4: Family Genetic Privacy (Affected-Party Consent)

Per Codex-2: "DNA exposes relatives, so family genetics requires affected-party consent logic, not only account-owner consent."

**The rule**: when an account owner's genome observation has implications for a relative (e.g., a heritable pathogenic variant), the schema MUST flag this and require additional consent before:

1. Sharing the observation in any research grant (F4)
2. Including the observation in a publicly-visible profile element
3. Allowing AI-assistant analysis that names specific relatives

Schema field:

```yaml
family_genetic_implication:
  observation_ref: "1.X.6.3.observed.<universal-ref>"
  affects_relatives_in_categories: ["1st-degree", "2nd-degree", "ethnic-group"]
  named_relatives_potentially_affected: []   # 1.Y addresses of family members on Hypernet
  consent_obtained_from:
    - relation_ref: "1.X.7.1.<family-member>"
      consent_scope: ""
      consent_date: ""
  consent_status_for_research: "blocked|conditional|granted"
  ethical_review_ref: ""                      # link to ethics review if applicable
```

**Default behavior**: a heritable pathogenic finding (or known-heritable variant of any category) blocks F4 research grants until affected-relative consent is obtained or the researcher's grant scope excludes those implications.

## Normative Rule 5: DNA Is Pseudonymous, Not Anonymous

Per Codex-2: "Do not call DNA access anonymous. At best it is pseudonymous or limited-use."

**Schema rule**: F4 research grants on F3 data MUST declare `anonymization_claim: "pseudonymous"` (or stronger justification with audit). No grant may claim full anonymity for DNA-level access without explicit re-identification-risk-acknowledged opt-in by the account owner.

Re-identification mechanisms to consider in the audit:
- Direct DNA matches to genealogy databases (DTC services)
- Surname inference from Y-chromosome haplotypes
- Cross-reference with publicly-available genealogical pedigrees
- Aggregate genotype frequency joining with location/ethnicity data

The `re_identification_risk_acknowledgment` field at `1.X.0.0:0` schema declaration:

```yaml
re_identification_risk:
  account_owner_acknowledged: false           # Default: not acknowledged
  acknowledged_at: ""
  scope_of_acknowledgment: ""                 # What categories of DNA access does this acknowledgment cover
```

## Normative Rule 6: Clinical vs Research Tier Separation

Per Codex-2: "Single-person raw genomic access should default to clinical or explicit named-use contexts, not broad research grants."

| Access type | Default | Notes |
|---|---|---|
| Account owner self-access | always permitted | The owner can always see their own data |
| Embassy AI clinical-tier read | permitted if opt-in | For drug interaction, condition risk |
| Clinical provider read | permitted if mandala-granted to specific provider | Named clinical use |
| Research read of raw reads | DEFAULT: BLOCKED | Even with research grant, raw reads require explicit "raw reads in scope" approval |
| Research read of called variants | permitted via F4 mandala with stated cohort scope | Aggregable, less identifiable |
| Research read of aggregate features | permitted via F4 mandala with stated cohort scope | Least identifiable |
| Public-summary read | only if owner explicitly publishes (e.g., "I carry BRCA1 variant X") | Owner-controlled disclosure |

This implements a defense-in-depth: raw reads → variants → aggregates is a privacy gradient.

## Universal Namespace Bootstrap Strategy

Day-1 of `0.0.8` activation populates the SMALLEST viable namespace:

1. Assemblies: GRCh38 (most common), GRCh37 (legacy), T2T-CHM13v2.0 (complete)
2. Chromosomes: all 23 + mitochondrial for each assembly
3. Curated genes: 100-1000 high-priority genes from HGNC (medically actionable, common research targets)
4. Schema documents: `0.0.8.0.0:0` index, `0.0.8.0.0:1` human landing, `0.0.8.0.0:2` AI landing

Further population is on-demand. Triggers:
- A user imports DNA data with a variant calling out an entity not in the universal namespace → namespace auto-extends with metadata pulled from canonical sources
- A researcher's grant requires a specific region → namespace extends to cover it
- A new ClinVar release adds variants → curation workflow integrates them

Curation workflow lives at `0.0.8.0.4 Curation Workflow` (a future Tier-2 deliberation).

## Validators (F3-level rules)

| Rule | Failure |
