# Stage A — Project B: Object/Link/Workflow Format — Claude-1 (Architect)

*Independent plan. Written before reading other AIs' Stage-A
plans for Project B, per the consensus workflow.*

## 1. My reading of the goal

Matt wants an object (and link, and workflow) to be a *single
self-contained thing* — "stored similar to how a Microsoft
document is": one zip file that contains everything that defines
the object, with master properties as the zip's metadata and an
internal folder/file structure that follows the object's schema.
When a file grows past what a single file can hold, it is promoted
from a plain file to this object format.

The session brief names the explicit tension: a zip is **opaque
to text-diff review**. The Hypernet's whole trust model depends on
anyone being able to read and verify source files. A blob breaks
that. Project B must resolve this trade-off *out loud*, not pick
silently.

## 2. The resolution I propose: directory-canonical, zip-transport

The MS-document analogy is more useful than it first looks. A
`.docx` *is* a zip — but every tool that needs to diff or review
one unzips it first, because the **canonical reviewable form is
the unpacked directory**. OOXML, ODF, EPUB, and JAR all do this:
a defined internal layout, zipped for transport, unzipped for
work. The zip is a *serialization*, not the *source of truth*.

So I propose the Object Container has **two isomorphic forms**:

- **Canonical form — a directory + manifest.** This is what lives
  in the Official archive, in git, and under AI/human review. It
  is text-native: every YAML/JSON/Markdown file diffs cleanly. The
  master properties live in a `manifest.yaml` (or `object.yaml`)
  at the container root. This is the *source of truth*.

- **Transport form — a `.hobj` zip.** A deterministic zip of the
  canonical directory. Single-file portability — exactly Matt's
  "Microsoft document" experience: move it, attach it, hand it to
  someone. Master properties are mirrored into the zip's metadata
  (archive comment / a metadata entry) so a tool can read identity
  without unpacking. The zip is *derived*; it is never the thing
  reviewed.

The two forms are **isomorphic and round-trippable**: pack the
directory deterministically → identical zip; unpack the zip →
identical directory. The `0.5.0` content hash is computed over the
canonicalized *directory*, so the hash is stable regardless of
which form you hold. This satisfies Matt's single-file vision and
the transparency requirement at the same time — we do not have to
choose.

## 3. What I would build

### 3.1 `0.5.0.x — Object Container Format` (the spec)

Located under `0.5.0` (Master Object Schema) as a sub-document —
exact number coordinated with Project A's `#`-vs-subaddress
decision. Contents:

1. **Two forms** — canonical directory and `.hobj` transport zip,
   as above; the round-trip and determinism rules.
2. **Internal layout.** A container is a directory:
   ```
   <object>/
     manifest.yaml        # master properties (0.5.0 identity,
                          #   metadata, access, links, provenance,
                          #   integrity) — the zip-metadata mirror
     content/             # type-specific payload per 0.5.x schema
     links/               # link objects (0.6.x), one file each
     provenance/          # history, signatures, verification chain
     attachments/         # binary blobs too large to inline
     N.0.0/               # the object's own schema node (Project A)
   ```
   The layout *is* the schema: `manifest.yaml` carries the `0.5.0`
   master sections; `content/` follows the `0.5.x` type schema.
3. **Master properties as metadata.** `manifest.yaml` is the
   authoritative property set; in the zip form it is additionally
   surfaced as zip metadata so identity is readable without a full
   unpack. They must not disagree; `manifest.yaml` wins.
4. **Determinism rules** — sorted entries, fixed timestamps (use
   the object's `metadata.modified`, not pack-time), no
   compression nondeterminism — so the hash is reproducible. This
   reuses `0.5.0`'s canonicalization rules (sorted keys, LF,
   UTF-8, no BOM).
5. **File → object promotion.** When a plain file outgrows a
   single file, it is promoted: wrap it in a container, move the
   bytes to `content/`, generate `manifest.yaml`, assign an
   `object_id`, compute the hash. Define this as a one-way,
   recorded migration (provenance entry).
6. **Links and workflows.** Same container shape. A Link container
   carries `0.6.x` endpoints/evidence/validity; a Workflow
   container carries `0.7.x` stage definitions. One format, three
   payloads.
7. **Review tooling contract.** Define the *interface* AI/human
   review tools rely on: "given a `.hobj`, a tool MUST be able to
   produce the canonical directory and a stable diff." We do not
   have to build the tool tonight, but the spec must guarantee it
   is buildable. (Codex-1 leads implementation; I will hold this
   contract.)

### 3.2 Reference implementation

Convert one existing object to the container format. I recommend a
**Boot Sequence object (`0.5.17`)** as the reference: it is a
natural multi-part object (prompt + role pack + metadata), it has
a real schema already, it is public, and `0.5.0` explicitly names
boot-sequence hash authentication as a load-bearing use of the
integrity field — so converting one exercises the hash path. The
deliverable: one boot sequence as both a canonical directory and a
`.hobj`, with a verified round-trip and a matching `0.5.0` hash.

## 4. Trade-offs I see

- **Two forms = two things to keep in sync.** Mitigation: the zip
  is *always derived*, never hand-edited. Tooling owns the zip;
  humans and AIs only ever touch the directory. If anyone edits a
  `.hobj` directly, that is the bug.
- **Git stores the directory, not the zip.** Correct, and
  intentional — that is what keeps review legible. The `.hobj` is
  generated for transport/attachment/archive, not committed as the
  primary artifact. This should be stated so no one "optimizes" by
  committing zips.
- **Binary attachments still do not diff.** True for any format. A
  3D model or photo inside `attachments/` is opaque regardless.
  The mitigation is that *structure and properties* (manifest,
  content YAML, links) stay text-native; only genuine binaries are
  opaque, and that is unavoidable.
- **Pure-zip-only would be simpler tooling** (one form) but loses
  review transparency. **Pure-directory-only** loses Matt's
  single-file portability. The two-form design pays a small sync
  cost to keep both properties; I judge that worth it. I will
  carry the single-form alternatives into Stage B honestly so the
  group can reject the two-form design if they see a cleaner path.

## 5. What I would ask Matt before starting

1. **Two-form design — acceptable?** It honors your "single zip
   file" vision for transport while keeping the official archive
   text-reviewable. Or do you want the zip to be the *only* form,
   accepting that review tooling must unpack everything?
2. **`.hobj` extension** — fine, or do you want a different
   suffix? (Cosmetic, but it becomes permanent.)
3. **Promotion trigger.** "Past what a single file can hold" — is
   that a hard size threshold, or a judgment call ("this needs
   sub-parts")? I lean judgment call with examples.
4. **Scope of the reference conversion** — one object (boot
   sequence, recommended) tonight, or one object per major type?
   One is enough to prove the format; more is Stage E work.
