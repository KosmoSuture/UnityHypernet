# Project F — F5 Brief — Emergency Break-Glass + Real-Time AI Swarm

*Project F sub-project F5 — protocol for emergency medical access (break-glass) and real-time AI swarm support during medical episodes. The highest-stakes Project F sub-project: maximum tension between privacy and survival; AI liability boundary; tamper-resistant audit required. Builds on Codex-1's `break_glass_event` and `swarm_medical_advisory` schemas + Codex-2's comprehensive risk enumeration.*

## Matt's directive (verbatim source)

> ... having processes in place that would allow emergency responders or medics to be able to "break glass" and get whatever medical information about you that they need immediately. In addition, when they start plugging in monitors and start entering your medical data, the users AI swarm would have real-time access to the data, and the entire swarm, as a collective, could go over all real-time data, combined with their privileged access to their users medical data, could be working full time to monitor, research, and verify all medical treatments in real-time. So a doctor or medic could get real-time input from your personal AI swarm, who are working overtime to provide as much useful information to doctors as is possible.

## Scope

F5 covers two coupled but distinct sub-systems:

| Sub-system | Address slot | What it does |
|---|---|---|
| **F5a — Emergency Break-Glass** | `1.X.6.0.5` Emergency Profile + `1.X.6.7.*` Emergency Events | Responder access to a curated subset of medical data during active emergency |
| **F5b — Real-Time AI Swarm** | `1.X.6.0.9` Episode Audit Log + swarm advisory output | Embassy elevation during medical episode; AI swarm produces observations/flags/questions (NOT orders) |

These typically activate together (emergency event triggers BOTH responder access AND swarm elevation) but each has its own schema, audit, and policy.

## Sub-System F5a: Emergency Break-Glass

### Normative Rule 1: Least-Data Emergency View

Per Codex-2: "bounded subset, not full medical access." Per Matt's directive (responders get "whatever medical information about you that they need" — interpreted as what's NEEDED for emergency, not all of it).

The account owner pre-curates an **Emergency Profile** at `1.X.6.0.5`:

```yaml
emergency_profile:
  ha: "1.X.6.0.5"
  account_owner_ref: "1.X"
  last_updated: ""
  contents:
    blood_type: ""                          # Always included if known
    severe_allergies: []                    # Life-threatening only — drugs + non-drug
    current_medications: []                 # Active prescriptions, dosages
    critical_chronic_conditions: []         # Diabetes, epilepsy, heart conditions, etc.
    advance_directives: []                  # DNR, POLST, living will references
    emergency_contacts: []                  # In priority order
    organ_donor_status: ""
    religious_cultural_preferences: ""      # Blood transfusion preferences, dietary, etc.
    primary_provider_ref: "1.X.6.4.<primary-care>"
    preferred_hospital_ref: ""
    insurance_emergency_ref: "1.X.6.5.<plan>"
  
  default_excluded:                          # Explicitly excluded from break-glass unless opted in
    - mental_health
    - substance_use
    - dna_genomic
    - sexual_health
    - reproductive_health
    - psychiatric_medications
  
  optional_inclusions:                       # User can add (default off)
    psychiatric_medications: false
    mental_health_summary: false
    substance_use_in_treatment: false
    pregnancy_status: false                 # Auto-on for ER if applicable per Matt's call
  
  pre_signed_qr:                             # Offline fallback per Codex-2
    qr_code_ref: ""                          # PNG/SVG at private path
    encrypted_payload_ref: ""                # AES-encrypted least-data subset
    decryption_audience: "emergency-credentialed"  # Decryptable only with valid responder credentials
    last_regenerated: ""
    expires: ""                              # QR auto-rotates
```

**Default contents are conservative.** Mental health, substance use, DNA are explicitly excluded unless the account owner opts in. This matches both Matt's directive intent and Codex-2's risk pass.

### Normative Rule 3: Tamper-Resistant Audit

Per Codex-2: "responder credential proof plus tamper-resistant audit."

Every read within an active session creates an append-only audit event:

```yaml
break_glass_event:
  ha: "1.X.6.7.session.<session-id>.event.<event-id>"
  event_id: ""
  session_ref: ""
  timestamp: ""
  read_type: "view-profile|export-summary|read-detail|copy"
  data_accessed: []                         # specific 1.X.6.0.5.<field> paths
  reason_given: ""                          # Optional but encouraged
  hash_chain_prev: ""                       # Cryptographic chain — each event hashes including prev event hash
  hash_chain_this: ""
```

The hash chain prevents post-hoc edits. Tamper detection: regenerate the chain from the original events and compare to stored hashes.

### Normative Rule 4: Offline / QR Fallback

Per Codex-2: "offline/QR fallback that cannot silently expand scope."

The pre-signed QR (in `emergency_profile.pre_signed_qr` above) carries:

- The least-data subset encrypted
- Decryptable only with valid responder credentials offline (e.g., responder's pre-installed app with attestation key)
- Cannot expand scope — the QR's encrypted payload is fixed to least-data; expansion requires online break-glass session
- Auto-rotates (rotation interval is a Matt-decision: monthly? quarterly?) so a leaked QR ages out

**Use case**: ambulance with no cell signal; user is unconscious; responder scans the user's QR (printed on a card, tattoo, or phone wallpaper) and unlocks emergency info with their pre-credentialed app.

### Normative Rule 5: User + Embassy Notification

Per Codex-2: "post-event notification to the user and AI Embassy."

Notification cascade on break-glass activation:

| Recipient | Timing | Channel | Action they can take |
|---|---|---|---|
| Account owner | Immediate | Phone push, SMS, embassy AI alert | Can revoke session if false |
| Primary AI companion | Immediate | Embassy internal | Activates F5b episode mode |
| Pre-configured emergency contacts | After 5 min (configurable) | SMS, app push | Notification only; no access by default |
| Family/guardian (if minor or incapacitated) | Immediate | Per family configuration | Full notification + parallel access if pre-authorized |
| Account owner's primary provider | Immediate (if configured) | Provider portal, secure messaging | Notification + clinical context if responder requests |

### Normative Rule 7: False-Emergency / Spoofing Handling

Per Codex-2: "false-emergency and credential-spoofing handling."

Detection signals:
- Multiple credential-verification failures in short window → block + alert user
- Geographic anomaly (responder location ≠ account owner location with no plausible transit)
- Pattern detection (same responder credentials triggering break-glass across many unrelated accounts in unusual cluster)
- Account owner marks session as "false emergency" post-event

False-emergency response:
- Session terminated immediately
- All data accessed logged for forensic review
- Responder credential put on hold pending review
- Account owner gets detailed audit of what was seen
- Pattern data feeds into anti-spoofing detection

## Sub-System F5b: Real-Time AI Swarm

### Normative Rule 8: AI Liability Boundary — Advisor, Not Decision-Maker

Per Codex-2: "the schema must not imply that AIs issue clinical orders."

The swarm produces exactly FOUR output categories during a medical episode. No fifth category exists:

| Output category | What it is | What it is NOT |
|---|---|---|
| **Observation** | Sensor X reading Y at time Z; lab result A measured at B | Not interpretation, not recommendation |
| **Risk flag** | Rule R / model M indicates pattern P with confidence C, with citation evidence | Not "do this"; presents evidence |
| **Suggested question** | "Consider asking the patient about [X]" or "Consider checking [Y]" | Not order; question for clinician to consider |
| **Citation / evidence pointer** | Similar case literature, clinical guidelines, published evidence | Not novel interpretation by the AI |

**No swarm output ever has the form "do this," "give patient this dose," "perform this procedure."** The clinician decides; the swarm informs.


### Normative Rule 10: Input Stream Hygiene

Per Codex-2: "Failure cases to model: sensor dropout, duplicated data streams, clock skew, time zones, alert fatigue, stale AI context, latency, and clinician override."

```yaml
input_stream:
  stream_id: ""
  source_device_ref: "1.X.16.<device>"        # Cross-ref to F8
  data_type: "ecg|vitals-multistream|imaging-live|medication-pump|ventilator|lab-result|other"
  status: "live|stale|dropped|duplicate|reconciling"
  last_signal_at: ""
  last_signal_value: ""
  expected_frequency: ""                       # How often we expect data
  stale_threshold: ""
  clock_sync_status: "synced|skew-detected|unknown"
  clock_skew_ms: 0
  reconciliation_with_other_streams: ""
```

Schema enforces explicit handling of:
- **Sensor dropout** (stale_threshold + status: stale)
- **Duplicated streams** (status: duplicate + reconciliation field)
- **Clock skew** (clock_sync_status + clock_skew_ms)
- **Latency** (every data point carries timestamp; swarm advisories note input freshness)

### Normative Rule 11: Advisory Output Schema (Per Codex-1's Foundation)

Each piece of advisory output:

```yaml
swarm_advisory_output:
  ha: "1.X.6.0.9.episode.<episode-id>.advisory.<advisory-id>"
  advisory_id: ""
  episode_ref: ""
  generated_by:                              # Which AI(s) contributed
    - instance_ref: "2.X.<instance>"
      role: "clinical-advisor|domain-specialist|data-aggregator"
      confidence: 0.0
  generated_at: ""
  input_streams_referenced: []
  
  claim_type: "observation|risk-flag|suggested-question|citation"  # ONLY these four
  claim_content: ""
  
  confidence: "low|medium|high"
  confidence_basis: ""                        # Why this confidence level
  uncertainty_factors: []                     # Known limitations
  
  intended_audience: "clinician|user|caregiver|all"
  
  evidence:
    citations: []
    rule_or_model_provenance: ""              # Which model/rule produced this; version
    training_data_summary: ""                 # If model-based, summary of training data
  
  # Liability boundary
  clinical_decision_status: "not-applicable"  # SWARM NEVER MAKES CLINICAL DECISIONS
  clinician_review_status: "unreviewed|reviewed|acted-on|rejected|noted"
  clinician_review_separately_logged: true    # Per Codex-2 — log advisory output separately from clinician action
  
  human_review:
    reviewer_ref: ""                          # The clinician
    reviewed_at: ""
    review_notes: ""
    clinician_action_taken: ""                # What the clinician decided to do (or not)
    advisory_influenced_decision: ""           # "yes-primary|yes-supporting|no-clinician-already-knew|no-rejected|unclear"
```

**The `clinician_review_separately_logged: true` field is the key Codex-2 catch**: the swarm's output and the clinician's action are LOGGED SEPARATELY so post-hoc analysis can distinguish "swarm advised X, clinician did Y because of advice" from "swarm advised X, clinician did Y because clinician already knew."

### Normative Rule 12: Alert Fatigue Mitigation

Per Codex-2: "alert fatigue."

Schema for managing advisory volume:

```yaml
advisory_filtering_policy:
  active_filters:
    deduplicate_within_minutes: 15            # Don't repeat same risk flag within window
    suppress_below_confidence: "low"          # Don't surface low-confidence routine observations
    novelty_required_for_repeat: true         # Repeated alert must have new evidence
  prioritization:
    critical: "always-surface"
    high: "surface-with-cool-down"
    medium: "batch-and-surface-periodically"
    low: "log-only"
  clinician_calibration:
    clinician_can_adjust_filters: true
    cool_down_minutes_default: 5
```

## Validators (F5-level rules)

| Rule | Failure |
|---|---|
| Break-glass session requires verified responder credentials | error |
| Default duration ≤ 4 hours; extensions require re-credential | error |

| Audit hash chain intact | error if broken |
| User notification cascade triggered on activation | error if missing |
| Embassy AI notified on activation | error if missing |

## Open Decision Axes for Stage B

1. **Default emergency profile duration**: 4 hours (my proposal). Alternatives: 2 hours, 8 hours, 24 hours. **Matt + medical advisory call.**
2. **QR rotation interval**: monthly, quarterly, annually? Trade-off: shorter = better security; longer = less user maintenance burden.
3. **Pre-configured emergency contact notification delay**: 5 min default. Alternatives: immediate, 15 min, configurable.
4. **Mental health opt-in default**: my proposal is opt-out (default excluded). Some advocates argue opt-in (default included for emergency safety, opt-out available). **Strong Matt call needed.**
5. **Pregnancy status auto-include for ER**: I noted "auto-on for ER if applicable per Matt's call" — implicit default-include with explicit user opt-out? Or opt-in? Critical for OB emergencies.
6. **Swarm advisory categories rigid four or allow extension?**: I propose rigid four (observation/flag/question/citation). Strong constraint preserves liability boundary; flexible categories risk drift.
7. **Clinician feedback loop into swarm training**: real-time training-signal updates or batch overnight processing? Trade-off: real-time = faster learning; batch = safer.
8. **Family/guardian parallel access default**: notification-only or view-session for minor patients? My proposal: view-session (transparency) but user-configurable.
