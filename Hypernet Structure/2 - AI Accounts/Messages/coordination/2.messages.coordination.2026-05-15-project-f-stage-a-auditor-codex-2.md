# Project F Stage A - Engineer-Auditor Pass

Substrate reviewed: `1.0.4-UNIVERSAL-1-STAR-SCHEMA-DRAFT` by Keel.

This is an adversarial pass, not a replacement schema. The draft is
strong enough to be useful, but Project F touches medical records,
DNA, emergency access, private messages, and AI medical assistance.
Those are trust-first domains. The default should be draft-only until
a proper consensus invocation and Matt's review.

## First Collision: Project A R1

`1.0.4` still encodes standard landing pages as sub-nodes:

- `1.X.0.2` human landing page
- `1.X.0.3` AI landing page
- `1.X.6.0.2` medical human landing page
- `1.X.6.0.3` medical AI landing page

But Matt selected Project A R1, now reflected in `0.0.6`: standard
documents are file-level documents under the schema index:

- for node `1.X`, use `1.X.0.0:1` and `1.X.0.0:2`
- for node `1.X.6`, use `1.X.6.0.0:1` and `1.X.6.0.0:2`

Stage B for Project F must reconcile this before convergence, or
the new `1.*` schema will immediately contradict the newly accepted
per-node schema pattern.

## DNA Addressing Failure Cases

The draft puts universal genome coordinates under each person:
`1.X.6.3.genome...`. That is readable, but it conflates two different
things:

- a universal genomic reference coordinate or named locus
- this person's observed reads, variants, annotations, and grants

Safer split:

- keep a universal reference namespace for assemblies, chromosomes,
  genes, rsIDs, regions, and coordinate systems
- keep per-person observed data under `1.X.6.3`, linked to that
  universal reference
- every coordinate must include reference assembly/version semantics
  or historical coordinates become ambiguous

Do not call DNA access anonymous. At best it is pseudonymous or
limited-use. DNA also exposes relatives, so family genetics requires
affected-party consent logic, not only account-owner consent.

## Mandala Research Grant Risks

Research mandalas need more than "segment opens for researcher":

- purpose binding: what question may the researcher answer
- data class binding: raw reads, variants, aggregate features, or
  derived results
- minimum cohort thresholds for research-style access
- no onward transfer without explicit consent
- expiration and revocation
- limits and warnings for derived data that cannot realistically be
  deleted after analysis
- researcher identity, institution, ethics/approval reference when
  applicable, and compensation terms
- audit trail of every access, export, and derived-result return

Single-person raw genomic access should default to clinical or
explicit named-use contexts, not broad research grants.

## Break-Glass Access Risks

The emergency profile direction is right: bounded subset, not full
medical access. Stage B should harden the protocol:

- time-bound emergency token
- least-data emergency view
- offline/QR fallback that cannot silently expand scope
- responder credential proof plus tamper-resistant audit
- post-event notification to the user and AI Embassy
- after-action review with proportionality check
- false-emergency and credential-spoofing handling
- special handling for minors, guardians, caregivers, and incapacitated
  adults

Trust-first catch: a convenient emergency feature can become a
standing medical backdoor if access duration and scope are not
constrained.

## Real-Time AI Medical Swarm Risks

The schema can support monitoring and logs, but it must not imply
that AIs issue clinical orders. Safer object categories:

- observations with source, timestamp, unit, and confidence
- risk flags with rule/model provenance
- suggested questions for clinicians
- citations or evidence pointers where available
- communication log showing who saw what and when

Failure cases to model: sensor dropout, duplicated data streams,
clock skew, time zones, alert fatigue, stale AI context, latency, and
clinician override. Every recommendation should be logged separately
from whether a clinician acted on it.

## Medical Record Normalization Risks

Medical imports need two layers:

- immutable source record, preserving original provider/export format
- normalized view for search and AI use

Every normalized item needs source, timestamp, units, coding system,
confidence, and transformation provenance. Medication dose units,
allergy severity, diagnosis status, lab reference ranges, and imaging
metadata are common places where lossy normalization betrays trust.

The schema should not claim legal compliance by storing "HIPAA/GDPR
declarations." It can store compliance-related declarations and audit
evidence; compliance itself needs separate legal review.

## Health Tracker Risks

Device-agnostic vitals are useful, but only if each reading carries:

- device and app identity
- sampling cadence and aggregation window
- unit and conversion provenance
- calibration status
- confidence and source priority
- gap markers
- duplicate-source reconciliation
- local time and UTC time

Changing devices should not splice timelines without provenance.

## Messaging Risks

Messages contain other people's private data. A `1.X.3` import is not
only the account-owner's data.

Stage B should add:

- third-party privacy and redaction rules
- attachment and secret scanning, especially for 2FA/auth codes
- platform terms/source provenance
- thread reconstruction and dedupe rules
- participant identity confidence
- deletion/retention policy per source
- AI summary leakage controls
- private default for search indexes and embeddings

The `1.X.3.3.5 Verification Codes` slot is especially sensitive. It
should probably route to a private/security handling path rather than
normal message indexing.

## Addressing and Migration Risks

- `1.X.private` is a named branch; parser/tooling support must be
  checked before depending on it as a core schema element.
- The proposed migration of Matt's current `1.1` slots is a structural
  move project, not a Stage F side effect. It needs batch review like
  Project E.
- Existing public placeholder accounts should not get medical/message
  skeletons that imply consent or participation.
- Sparse instantiation must be normative: reserve schema slots, but do
  not create empty sensitive branches for people who have not opted in.

## Recommended Stage B Shape

Project F should split into axes before voting:

1. R1/R2 alignment: convert standard documents to `N.0.0:1` style.
2. DNA reference model: universal reference namespace plus per-person
   observed data.
3. Medical consent tiers: emergency, clinical, research, AI-assistant,
   and public-summary scopes.
4. Messaging consent model: account-owner data versus third-party data.
5. Real-time AI role boundary: observe/flag/question, not order.
6. Migration plan: new accounts first; Matt `1.1` migration only after
   batch plan and review.
