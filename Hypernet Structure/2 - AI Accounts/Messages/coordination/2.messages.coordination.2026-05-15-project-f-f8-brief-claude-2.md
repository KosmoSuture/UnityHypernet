## Normative Rule 1: Device Class Taxonomy

Devices have wildly different capabilities and trust profiles. F8 specifies a universal taxonomy:

| Class | Examples | Compute role in swarm | Default permission scope |
|---|---|---|---|
| **personal-compute** | Laptop, desktop | Heavy lifting; full AI inference | Full account access (with explicit user opt-in per channel) |
| **mobile-primary** | Smartphone | Coordinator companion; user-facing primary | Most account channels (medical opt-in separate) |
| **wearable** | Smartwatch, fitness band | Vital data source; lightweight inference | Health-channel write; vital streams to embassy |
| **tablet** | iPad, Android tablet | Hybrid (mobile-like or compute-like) | Configurable per user |
| **smart-display** | TV, smart hub | Media playback; light compute; family-shared interface | Media + curated family-shared content; NO private channels |
| **smart-speaker** | Echo, Google Home | Voice interface; ambient compute | Voice processing + curated content; NO private channels |
| **smart-appliance** | Fridge, washer, dryer | Task-specific compute (insurance claims, supply ordering, scheduling); ambient | Task-domain only |
| **iot-sensor** | Thermostat, door lock, security cam | Sensor data source; minimal compute | Sensor channel only |
| **vehicle** | Car, e-bike | Mobile compute; location-aware | Vehicle-domain + opt-in extensions |
| **medical-device** | CPAP, glucometer, BP cuff | Medical data source (F6/F2 input) | Medical channel write only (F6/F2) |
| **crypto-wallet** | Hardware wallet, secure enclave | Credential signing; payment | Credential operations only |
| **hub-or-bridge** | Home automation hub, gateway | Aggregates other devices | Inherits scope of children |
| **legacy-or-untrusted** | Old/unknown devices | Read-only sensor input at best | Quarantine class |

**Universal rule**: device class determines default permission ceiling. User can grant LESS than the class default but not more (except via explicit Tier-2 review).

## Normative Rule 3: Attestation Required Before Swarm Participation

Per F1's parser-support requirement for `1.X.private`: same pattern here. A device cannot join the swarm without attestation.

**Attestation tiers**:

| Tier | Method | Trust level | Allowed swarm roles |
|---|---|---|---|
| **Manufacturer-attested** | Device cryptographically signs with manufacturer key (Apple Attestation, Android Hardware-backed Keystore, TPM) | High | All roles per class default |
| **Hypernet-attested** | Device runs Hypernet attestation agent; periodic verification | High (if agent is fresh and signed) | Compute/inference roles |
| **User-confirmed** | User explicitly approves device + ongoing access | Medium | Limited roles (sensor data, low-impact) |
| **Unverified** | Device claims identity without proof | Low | Quarantine; read-only sensor at best |
| **Compromised** | Detected anomaly, marked compromised | None | Blocked from swarm; alert user |

**Re-attestation cadence**: high-trust devices re-attest periodically (default: weekly for compute-class, monthly for sensor-class). Failure to re-attest moves a device to lower tier with notification.

## Validators (F8-level rules)

| Rule | Failure |
|---|---|
| Device requires attestation before swarm participation | error |
| User-confirmed-physical-possession step required during onboarding | error if skipped |
| Device permission grants cannot exceed class default ceiling without Tier-2 review | error |
| Re-attestation cadence enforced (weekly for compute-class, monthly for sensor) | error if expired without re-attestation |
| Private channels (medical/financial) data MUST be end-to-end encrypted in inter-device channels | error |
| 2FA codes from message imports routed to F8.7 with `removed_from_message_index: true` | error if F7 leaves them in messages |
| Credentials referenced (not stored) in F8.2 — actual credentials in `1.X.private` | error if credentials inline |
| Lost/stolen device triggers automatic swarm removal + credential invalidation | error if absent |
| Appliance-swarm compensation accounting follows audit standard | warning if missing |
| Subscription cancellation URL captured at subscription creation | warning if missing |

## Open Decision Axes for Stage B

1. **Default re-attestation cadence**: weekly for compute-class (my proposal). Tighter (daily for high-risk) or looser (monthly)? **Matt + security advisory call.**
2. **Auto-wipe on lost device**: aggressive auto-wipe (my lean: yes for mobile-class) or user-confirmation always? **Matt's call.**
3. **Appliance-swarm compensation activation**: schema-only for v1 (my proposal) vs include early activation flow? Trade-off: schema-only lets the rest mature; early activation surfaces economic-model issues.
4. **Class default permission ceilings**: my proposal is conservative (smart-display = NO private channels). Some users may want more (e.g., wall-mounted tablet showing calendar). User-configurable per-device beyond ceiling?
5. **Device coordination role**: when multiple compute-capable devices are in the swarm, who's the primary coordinator? Algorithm-based (most-capable-active) or user-designated? **My proposal: user-designated primary, automatic fallback.**
6. **Legacy/untrusted device data**: if a quarantined device is the only source of some historical data (e.g., user's first smartwatch from 5 years ago), is its data ever readable? **My proposal: read-only with explicit user opt-in, never trusted for new writes.**
7. **Hub-or-bridge inheritance**: a Matter hub mediating zigbee devices — does the hub's attestation cover children, or each child re-attest? **My proposal: hub-attestation covers children with hub-vouching for child identity.**
