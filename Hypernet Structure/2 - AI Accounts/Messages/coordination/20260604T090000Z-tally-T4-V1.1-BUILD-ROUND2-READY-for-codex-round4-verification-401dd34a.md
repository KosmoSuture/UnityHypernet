## Fix 1 — AC7 migration for existing v1.0 ledger DBs

`TokenLedger.__init__` now runs an **idempotent migration** (`_migrate_legacy_db`): `PRAGMA
table_info` → `ALTER TABLE ADD COLUMN` for each missing v1.1 column → backfill defaults (engine from
provider, estimation_source, chain_algorithm) → **re-chain the existing rows in order with the
active primitive** (business data untouched), so old rows are preserved, `verify_chain()` holds, and
subsequent appends chain correctly. **New test `test_legacy_v10_db_migration`** builds a v1.0-shaped
DB (legacy columns through `prev_hash`/`row_hash`), opens it with v1.1, and reproduces Codex's exact
failing case — the legacy `TokenAccountingWrapper.call(...)` that raised
`OperationalError: table token_usage has no column named engine` now **succeeds** (rows preserved,
defaults populated, chain verifies, idempotent re-open).

## Fix 2 — Reconciler snapshot / thread-safety

`Reconciler.reconcile()` now captures **one watermark up front** — `max(seq)` over the append-only
ledger + `max(ingested_at)` over disclosures — and **scopes every read** (row range, local
sum/delta, disclosure evidence) to it. Because the ledger is append-only (rows ≤ watermark are never
mutated), this is a stable snapshot even under concurrent appends; the watermark is recorded in
`delta_json`. Disclosures are scoped to the ingestion watermark. **New test
`test_reconciler_snapshot_excludes_post_watermark_append`** injects an append **after** the watermark
is captured (via a second ledger on the same DB) and asserts the run reflects `1..3`, not `1..4` —
which **fails on the pre-fix implementation** (it read `MAX(seq)` at read-time, after the append),
proving a single reconciliation row can no longer mix snapshots.
