# Stage A - Project B - Codex-2 Engineer-Auditor

## My Reading Of The Goal

Project B needs to define how Hypernet objects, links, and
workflows become self-contained packages while preserving the
transparency and reviewability of the public repository.

Matt's instinct is a Microsoft-document-like zip container: one
object file that contains all material needed to understand the
object, with master properties in zip metadata and internal files
laid out by schema. The auditor question is whether that container
can be trusted in a repo where "every line is public" is a core
trust claim.

## What I Would Build

I would define one logical object package format with two allowed
serializations:

1. **Directory package** for Git and public review.
2. **Deterministic zip package** for transport, archival snapshots,
   and single-file exchange.

The directory package should be canonical during public alpha. The
zip package should be a deterministic build artifact from that
directory, not the only review surface.

Proposed internal layout:

```text
object-name.hno/
  manifest.yaml
  content/
  links/
  provenance/
  schemas/
  signatures/
  attachments/
```

For a zip serialization:

```text
object-name.hno.zip
  manifest.yaml
  content/
  links/
  provenance/
  schemas/
  signatures/
  attachments/
```

`manifest.yaml` is authoritative. Zip metadata may mirror a small
subset for quick discovery, but it must not be the only source of
truth because zip metadata is not consistent enough across tools.

Minimum manifest sections should map to `0.5.0`:

```yaml
container:
  format: "hypernet-object-container"
  version: "0.1"
identity:
  address: "..."
  object_id: "..."
  object_type: "..."
  schema_refs: []
metadata:
  created: {}
  modified: {}
  status: "draft|active|deprecated|archived"
  visibility: "public|private|restricted"
access:
  owner: "..."
  permissions: {}
integrity:
  hash: {}
  verified: false
links: []
provenance: {}
```

Links and workflows use the same container pattern, with
`object_type` and `schema_refs` pointing to the correct `0.6.*`
or `0.7.*` definitions.

## Decision On Zip Versus Text-Native

My recommendation:

- text-native directory package is canonical in Git;
- zip package is canonical only when explicitly marked as a
  release artifact with a reproducible build recipe;
- official tooling must be able to unpack, validate, diff, and
  rebuild the zip byte-for-byte;
- no opaque zip-only object should be accepted as a public-alpha
  canonical object until the validator exists.

This keeps Matt's single-file object goal without sacrificing the
repository's inspectability.

## Reference Implementation Pilot

For tonight, I would convert one small existing document object to
the directory package form first, then generate the zip artifact.
Good candidates:

- a simple `0.5.3` document schema object if a clean one is chosen;
- or `0.5.0 Master Object Schema` as a deliberately self-referential
  pilot if the team wants to test schema packaging.

I would not start with a private, permissioned, or large media
object. The first pilot should test shape, not encryption or chunking.

## Tradeoffs

Zip strengths:

- portable single-file object;
- familiar document-container model;
- easy to attach, move, archive, and sign as a unit.

Zip weaknesses:

- poor Git diffs;
- platform-specific metadata behavior;
- timestamp/order/compression differences break reproducible hashes;
- hidden internal changes can be missed in casual review;
- zip-slip and zip-bomb risks require validator hardening.

Directory package strengths:

- public review stays line-by-line;
- normal tooling can diff and search;
- easier for AIs to inspect without unpack tooling.

Directory package weaknesses:

- less like Matt's requested single-file model;
- move/copy operations can split an object if tooling is careless;
- signatures must cover a directory canonicalization process.

## What I Would Ask Matt Before Starting Implementation

1. Is a source directory plus deterministic zip artifact an
   acceptable interpretation of "single zip file" for public alpha?
2. Should zip metadata be authoritative, or can it be a discoverable
   cache of `manifest.yaml` fields?
3. What file extension should Hypernet object containers use:
   `.hno`, `.hno.zip`, `.hyperobject`, or plain `.zip`?
4. Should links and workflows use the exact same container layout,
   or should they have specialized top-level folders?
5. What is the first pilot object Matt wants converted?

## Auditor Risks To Surface At Stage D

- Trust risk: zip-only canonical objects weaken "every line is
  public" because meaningful changes become opaque binary diffs.
- Integrity risk: if zip metadata is authoritative, common tools
  may rewrite it and silently invalidate or alter object identity.
- Security risk: unpacking untrusted object zips needs path
  traversal, symlink, compression bomb, and oversized-file checks.
- Privacy risk: manifest or zip metadata can expose owner,
  access, or provenance details even when content is encrypted.
- Hash risk: `0.5.0` already defines canonical hash behavior; the
  container spec must say whether the hash covers content only,
  content plus metadata, or the full container bytes.
- Address risk: object package address and file-level address from
  Project C must not become two competing identities.

## My Stage A Recommendation

Adopt a package-first spec:

- `manifest.yaml` is source of truth;
- directory package is canonical for public review;
- deterministic zip is canonical for transport/release after
  validation tooling exists;
- reference implementation includes unpack, validate, diff, and
  rebuild checks before any real migration.
