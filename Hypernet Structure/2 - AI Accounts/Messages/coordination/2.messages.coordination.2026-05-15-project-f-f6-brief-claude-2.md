# Project F — F6 Brief — Universal Health-Tracker Standard

*Project F sub-project F6 — device-agnostic schema for continuous and spot-check health-tracker data, so changing devices doesn't break the timeline. Builds on Codex-1's `vital_reading` minimal schema + Codex-2's auditor catches on device/calibration/dedup/timezone + Keel's `1.X.6.2` 10-sub-channel buildout.*

## Matt's directive (verbatim source)

> For things like health trackers, they could store all of their data to your account, and if you replace it with a different model/brand at a later point, it doesn't matter, because all devices store their data to your account the same way, and you can continue your health tracking without interruption and adding or removing data points as desired.
>
> We want this to just be the most logical, understandable way to store any medical information as a common standard as is possible.

## Scope

F6 covers `1.X.6.2` Vitals & Continuous Tracking (10 sub-channels per Keel's `1.0.4`):

- `.1` Cardiovascular (HR, HRV, BP)
- `.2` Activity (steps, distance, exercise, calories)
- `.3` Body Composition (weight, BMI, body fat, hydration)
- `.4` Metabolic (glucose CGM, ketones, lipids)
- `.5` Respiratory (O2, breathing, peak flow)
- `.6` Temperature (core, skin, location-specific)
- `.7` Sleep (stages, quality, duration, apnea)
- `.8` Mood/Mental (subjective, anxiety, depression scales)
- `.9` Symptoms (user-reported pain, nausea, etc.)
- `.0` Schema & standards

F6 does NOT cover:
- Clinical lab results (F2 — different sampling pattern)
- DNA / genetic data (F3)
- Discrete medical encounters (F2)
- Device hardware itself (F8)

## Normative Rule 1: Canonical Metric Address Registry

Per Matt's "universal schema for each metric": every distinct metric has a canonical Hypernet address. Different brands/devices/apps measuring the same metric write to the same address.

**Address pattern**:
```text
1.X.6.2.<dimension>.<metric>.<modality>
```

Examples:
```text
1.X.6.2.1.heart_rate.continuous          # Continuous HR (smartwatch, fitness band)
1.X.6.2.1.heart_rate.spot_check          # One-time HR (pulse oximeter, BP cuff)
1.X.6.2.1.heart_rate_variability.rmssd   # HRV measured by RMSSD method
1.X.6.2.1.blood_pressure.systolic        # Systolic BP component
1.X.6.2.1.blood_pressure.diastolic       # Diastolic BP component
1.X.6.2.2.steps.cumulative_daily         # Daily step count
1.X.6.2.2.steps.cadence_realtime         # Realtime step cadence
1.X.6.2.4.blood_glucose.cgm              # Continuous glucose monitor
1.X.6.2.4.blood_glucose.fingerstick      # Discrete glucose reading
1.X.6.2.5.oxygen_saturation.spo2         # Pulse oximetry SpO2
1.X.6.2.7.sleep_stage.rem                # REM sleep duration
```

**Universal metric registry** lives at `0.0.8.metrics` (paralleling the DNA universal registry from F3 — same pattern of "canonical biological measurements live at addressing-system extensions").

Actually, reconsidering: metric addresses are heavily related to medical context (units, expected ranges, clinical interpretation). The registry could live at:
- Option A: `0.0.8.metrics.*` (sibling to DNA universal namespace)
- Option B: `0.5.<medical-object-type-id>.metrics.*` (under object-type taxonomy)
- Option C: A registered authority for each metric (e.g., LOINC for clinical lab metrics, custom registry for consumer-fitness metrics)

**My recommendation: Option C with `0.0.8.metrics` as the registry index pointing to authority-specific entries**. LOINC for clinical, custom registry for consumer wearables, with cross-walks where applicable. Matt's call on this is open in Stage B decisions below.

## Normative Rule 2: Universal Reading Schema (Per-Account)

Every health-tracker reading at `1.X.6.2.<dimension>.<metric>.<modality>` follows the same shape (extending Codex-1's `vital_reading` minimal schema):

```yaml
vital_reading:
  ha: "1.X.6.2.<dimension>.<metric>.<modality>.<reading-id>"
  visibility: "private"                       # Default; account owner opt-out for opt-public
  
  # Identity
  reading_id: ""
  canonical_metric_ref: "0.0.8.metrics.<...>" # Required link to canonical
  
  # Value
  value: 0.0                                   # Always numeric
  value_unit_ucum: ""                          # MUST match canonical_metric.unit_ucum
  value_string: ""                             # For non-numeric (e.g., sleep stage labels)
  
  # Time (CRITICAL — both local and UTC per Codex-2)
  timestamp_utc: ""                            # ISO 8601 UTC
  timestamp_local: ""                          # Local time at reading
  timezone: ""                                 # Olson timezone identifier
  timestamp_recording_method: "device-clock|app-clock|server-clock|manual-entry"
  
  # Source provenance (per Codex-2)
  source:
    device_ref: "1.X.16.<device-id>"           # Cross-ref to F8
    device_type: ""
    device_model: ""
    device_firmware_version: ""
    app_ref: ""                                # If reading came via app rather than direct device
    app_version: ""
    raw_source_ref: ""                         # Original raw data (e.g., raw ECG before HR derivation)
  
  # Sampling/aggregation context
  sampling:
    sampling_rate: ""                           # e.g., "1/sec", "1/30sec", "manual"
    aggregation_window: ""                      # If averaged, e.g., "60sec moving average"
    is_aggregated: false
    aggregation_method: "raw|avg|min|max|median|count|sum"
    aggregation_source_readings_count: 0
  
  # Quality
  calibration:
    status: "calibrated|uncalibrated|expired|unknown"
    last_calibration: ""
    calibration_authority: ""
  confidence: "high|medium|low|unknown"
  confidence_factors: []                       # Sensor placement, motion artifact, etc.
  
  # Context
  context: "rest|activity|sleep|clinical|driving|workout|unknown"
  
  # Gap / dedup metadata (per Codex-2)
  gap_marker: false                            # Mark gaps in continuous data
  duplicate_source_reconciliation:
    is_potential_duplicate: false
    other_source_refs: []
    reconciliation_method: ""                  # If multiple devices recorded same event
  
  # Import / processing audit
  import_batch_ref: ""
  imported_at: ""
  normalized_at: ""
  transformation_log_ref: ""
```

## Normative Rule 3: Two-Layer Architecture (Inherits from F2)

Per F2 brief's normative rule on medical records: vital readings ALSO get two-layer storage.

```text
1.X.6.2.<dim>.<met>.<mod>.<reading-id>         # Normalized view (searchable, AI-readable)
1.X.6.2.<dim>.<met>.<mod>.<reading-id>.source  # Immutable source (original device/app format)
```

The source preserves whatever the device/app actually wrote (e.g., Apple HealthKit's raw schema, Garmin's FIT file, a Withings JSON blob). The normalized view extracts the canonical metric, normalized unit, and context fields.

**Sources are write-once.** Normalizations may be regenerated as transformation logic improves.

## Normative Rule 4: Aggregation Tiers

Continuous data at 1Hz produces millions of readings/year. Storage at full resolution is wasteful for most queries; aggregation enables long-term timeline queries.

**Standard aggregation tiers**:

| Tier | Address suffix | Retention | Source |
|---|---|---|---|
| Raw | `.raw.<reading-id>` | Per source device retention policy (often 30-90 days at device) | Direct from device/app |
| 1-min | `.1min.<bucket-id>` | Long-term (default: indefinite) | Aggregated from raw |
| 5-min | `.5min.<bucket-id>` | Long-term | Aggregated from 1-min |
| Hourly | `.hour.<bucket-id>` | Long-term | Aggregated from 5-min |
| Daily | `.day.<bucket-id>` | Long-term | Aggregated from hourly |

The aggregation pipeline is automatic; users can configure retention per tier. Raw data may age out by user preference; aggregated data persists.

## Normative Rule 5: Device Migration Semantics (Per Matt's Directive)

The CORE F6 requirement per Matt: "if you replace it with a different model/brand at a later point, it doesn't matter."

**Device migration is supported by:**

1. **Canonical metric addresses**: HR from Apple Watch and HR from Garmin write to the SAME canonical address `1.X.6.2.1.heart_rate.continuous`. The `source.device_ref` field distinguishes them within the same address space.

2. **Source-device cross-references at F8**: when a device is retired, F8 marks it as `status: retired` but preserves the device_ref so historical readings remain attributable.

3. **Transition handling**:

```yaml
device_migration_record:
  ha: "1.X.16.<old-device>.migration.<event-id>"
  old_device_ref: ""
  new_device_ref: ""
  migration_date: ""
  migration_type: "voluntary-replacement|device-failure|brand-switch|upgrade"
  data_migration:
    historical_readings_preserved: true        # Old device's readings stay at their addresses
    raw_data_archive_ref: ""                   # Where the old device's raw data went
  reconciliation_recommendation:
    duplicate_window_during_overlap: ""        # If both devices ran simultaneously
    preferred_source_during_overlap: ""        # Which device's data takes precedence
  gap_period:
    start: ""                                  # Period without device coverage
    end: ""
    gap_markers_inserted: false
```

4. **Gap markers** (per Codex-2): a continuous metric that loses its source device produces a `gap_marker: true` reading at expected sampling intervals, so downstream consumers see "device offline" vs "value 0."

5. **Duplicate reconciliation** (per Codex-2): if two devices simultaneously measure the same metric (e.g., user wearing both Apple Watch and Garmin during a transition period), reconciliation logic picks one as primary and marks the other as `duplicate_source_reconciliation.is_potential_duplicate: true`.

## Normative Rule 6: Unit Standardization (UCUM)

Per Codex-2: "unit and conversion provenance."

All units MUST be UCUM-coded. Common UCUM codes:
- `/min` — per minute (HR, breathing rate)
- `mm[Hg]` — mmHg (blood pressure)
- `kg` — kilograms (weight)
- `%` — percentage (SpO2, body fat)
- `mg/dL` — milligrams per deciliter (glucose)
- `mmol/L` — millimoles per liter (alternative glucose, lipids)
- `Cel` — Celsius (temperature)
- `[degF]` — Fahrenheit (temperature alternative)
- `1` — dimensionless (sleep score, mood score 1-10)
- `s` — seconds (sleep duration in seconds; UI displays as h/m/s)
- `h` — hours

The schema includes a `value_unit_ucum` field that MUST match the canonical metric's `unit_ucum`. Conversions are explicit (e.g., importing mg/dL glucose to a person whose preferred display is mmol/L — the conversion is logged with provenance).

## Normative Rule 7: Mood / Mental Channel — Stricter Default

`1.X.6.2.8 Mood/Mental` overlaps with mental health (F2 `1.X.6.1.9`). Per F2's stricter default for mental health:

- Mood scores, anxiety scales, depression scales default to `consent_tier_required: clinical+`
- Embassy AI opt-in for mood data is separate from generic vitals opt-in
- Aggregation tiers preserve only daily-or-coarser for mood by default (raw moment-to-moment data ages out faster)

## Normative Rule 8: Symptom Self-Report (1.X.6.2.9)

Symptoms reported by the user are different from device-measured data:

```yaml
symptom_report:
  ha: "1.X.6.2.9.<symptom-id>.<report-id>"
  symptom_canonical_ref: "0.0.8.metrics.symptoms.<symptom>"
  symptom_description: ""                      # Free-text user description
  severity: 0                                  # 1-10 scale
  
  # User-reported context
  timestamp_local: ""
  timestamp_utc: ""
  duration: ""                                 # If symptom has duration
  associated_factors: []                       # User-tagged context (food, exercise, etc.)
  
  # Source
  source: "user-self-report"
  reporter_ref: "1.X"                          # Always the account owner
  reporting_method: "app-quick-log|app-detailed|voice-to-text|other"
  
  # Cross-references
  related_clinical_ref: ""                     # If linked to a clinical encounter
  related_medication_ref: ""                   # If symptom is a medication side effect
```

Symptoms don't have device provenance; they have user-reporter provenance.

## Normative Rule 9: Privacy & Aggregation Visibility

| Visibility level | What it shows | Use case |
|---|---|---|
| Private (default) | Full readings, all metadata | Account owner + embassy AI |
| Aggregate-private | Daily/weekly/monthly aggregates, no per-reading | Account owner's anonymous research participation |
| Aggregate-public | Coarse aggregate (e.g., "active person, average resting HR ~60") | Public profile if user opts in |
| Research-mandala | Per F4 grant scope | External research |

The two-layer architecture allows source to remain private while normalized aggregates are shareable.

## Validators (F6-level rules)

| Rule | Failure |
|---|---|
| Reading carries `canonical_metric_ref` pointing to valid `0.0.8.metrics.*` address | error |
| Reading carries BOTH `timestamp_utc` AND `timestamp_local` | error |
| Reading carries `timezone` (Olson identifier) | error |
| Reading's `value_unit_ucum` matches canonical metric's unit | error |
| Reading carries `source.device_ref` (or `app_ref`) | error |
| Aggregated readings (`is_aggregated: true`) declare `aggregation_method` + `aggregation_source_readings_count` | error |
| Gap markers (`gap_marker: true`) appear at expected sampling intervals when source device is offline | warning |
| Duplicate source reconciliation field populated when multiple devices measure same metric | warning if missing |
| Mood / mental data default `consent_tier_required: clinical+` | error if lower |
| Calibration status declared | warning if `unknown` |
| Device migration records exist when device_refs change | error if missing |

## Open Decision Axes for Stage B

1. **Canonical metric registry location**: my proposal is `0.0.8.metrics` with authority-namespace sub-entries (LOINC for clinical, custom for consumer). Alternative: separate `0.5.<medical-object-type>.metrics`. **Matt's call.**
2. **Default raw data retention**: device-dependent (default keep per device policy) or universal Hypernet default? My proposal: universal minimum of 90 days raw + indefinite aggregated.
3. **Aggregation pipeline trigger**: automatic on import, or batch overnight, or user-configurable? My proposal: automatic on import with user-configurable schedule for resource-intensive aggregations.
4. **Mood / mental aggregation retention**: my proposal is daily-or-coarser only (no moment-to-moment retention beyond device cache). Strict default may need user-opt-in for finer-grained retention.
5. **Multi-source reconciliation default**: prefer most-recent device, most-accurate device per metric, or user-specified priority? My proposal: user-specified primary device per metric with fallback to most-recent.
6. **Device migration auto-detect**: should the schema auto-detect device replacement based on data patterns (e.g., one device's data stops, another's starts) or require explicit user action? My proposal: detection produces a suggested migration record for user confirmation, never auto-applied.
7. **Symptom canonical registry**: build a symptom ontology under `0.0.8.metrics.symptoms.*` or use existing ontology (SNOMED CT, ICD-10)? My proposal: cross-walk to SNOMED CT but maintain user-friendly canonical names.
