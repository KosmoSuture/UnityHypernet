# 3.1 Migration Recipe - Codex-1

## Preconditions

Do not start physical migration until the Stage-D migration gate is
cleared or Matt explicitly approves the conservative defaults.

## Phase 0 - Inventory

Produce an inventory table for `3.1`:

| Field | Requirement |
|---|---|
| source path | exact path |
| declared `ha` | from frontmatter when present |
| object type | from frontmatter when present |
| file kind | markdown, text, binary, folder |
| sensitivity | public, possible-private, legal, financial, personal, unknown |
| collision flag | duplicate address or duplicate domain |

Run before and after the pilot.

## Phase 1 - Draft Project Schema

Create a draft project record shape:

```yaml
project:
  title: ""
  home_node: ""
  source_task: ""
  status: "proposed|open|active|blocked|complete|archived"
  priority: "normal|high|urgent"
  visibility: "public|restricted|private"
  public_rollup: true
  active_claims: []
  dependencies: []
  deliverables: []
  provenance:
    copied_from: ""
    copied_at: ""
```

Do not create a new `3.1.1 Projects` directory while the existing
`3.1.1 Organizational Structure` path remains live unless the move
or alias plan has been approved.

## Phase 2 - Classify Tasks

For each task under `3.1.2`:

| Task subject | Candidate home |
|---|---|
| project/task management itself | `3.1.1` after Projects node exists |
| website, outreach, launch content | marketing/outreach target after `3.1.6`/`3.1.8` decision |
| investor, Kickstarter, revenue | `3.1.4` or marketing target if outreach-shaped |
| legal entity, patent, governance | `3.1.12` if confirmed |
| core architecture, MVP, API, app | `3.1.5` if collision-free |
| docs, START HERE, contributor guide | `3.1.7` |
| swarm, boot, agent framework | `0.7.5.5` or `2.*`, with `3.1` rollup pointer |

If the target is ambiguous, colliding, sensitive, or stale, mark
`needs_human_classification` and do not copy.

## Phase 3 - Copy Pilot Records

For 5-10 low-risk tasks:

1. create a project record in the chosen destination draft area;
2. preserve original `3.1.2` task untouched;
3. include `source_task`;
4. include provenance;
5. add a temporary `pilot_copied_to` note only if the source task
   edit is separately approved.

No deletes. No address reuse.

## Phase 4 - Rollup

Rollups are generated from child project indexes, even if the first
walk is manual.

Rollup table:

| Field | Meaning |
|---|---|
| `project_id` | project address or draft id |
| `home_node` | lowest owning node |
| `status` | current state |
| `priority` | parent-visible priority |
| `active_ai_count` | claims with fresh heartbeat |
| `last_activity` | stale-work detection |
| `public_summary` | safe public text |

Private projects do not contribute public names, paths, identities,
or counts in v1.

## Phase 5 - Audit Gate

Codex-2 or another auditor should verify:

| Check | Must pass |
|---|---|
| duplicate address scan | yes |
| frontmatter completeness for new records | yes |
| source-to-copy provenance | yes |
| no stale root README/REGISTRY claims introduced | yes |
| no public private-rollup leak | yes |
| no migration into colliding target nodes | yes |

## Phase 6 - Full Migration Later

After Matt decisions and audit pass:

1. create or move `3.1.1` Projects with approved redirects;
2. split current organization material into schema-flavored and
   fact-flavored destinations;
3. copy remaining tasks;
4. add redirect/provenance records;
5. update rollups;
6. update root maps;
7. run audit again.

## Trust Preflight

This is a recipe, not a migration. It preserves the evidence and
does not alter the public `3.1` tree.
