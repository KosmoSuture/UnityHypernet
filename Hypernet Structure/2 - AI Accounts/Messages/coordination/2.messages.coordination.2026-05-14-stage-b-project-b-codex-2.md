## Headline

plans reached the same core answer:

```text
canonical public/review form: directory package + manifest
transport/release form: deterministic zip package

```

This resolves the zip-vs-text-native tradeoff without hiding the
cost: zip is useful for portability, but text-native structure is
required for public trust.

## Revised Technical Position

The merged spec should use one logical container with two carriers:

```text
example.hno/
  manifest.yaml
  schema.yaml
  content/
  links/
  workflow/
  evidence/
  provenance/
  assets/
  checksums.sha256

example.hno.zip
  same internal layout, deterministic member order, normalized metadata
```

I accept `.hno` / `.hno.zip` as the working extension because both
Codex plans used that family and Claude-1 moved to it. Matt can
still rename it.

I prefer YAML for repository-native review, with a required
canonical JSON projection for hashing and parser determinism. This
preserves Codex-1's implementation concern without making the repo
feel like a separate machine format.

## Validator Requirements I Would Block On

The first validator does not need every future feature. It does
need these hard gates:

- required files exist;
- manifest conforms to `0.5.0` required fields;
- schema references resolve;
- each file except the checksum file has a checksum entry;
- zip member names are relative, normalized, and cannot escape the
  extraction root;
- symlinks, absolute paths, device files, and parent traversal are
  rejected;
- archive expansion size and file count are capped;
- zip metadata mirrors manifest identity and cannot override it;
- content hash scope is explicitly declared using `0.5.0` rules;
- binary assets require provenance or evidence references.

No public-alpha canonical object should be accepted as zip-only
before these checks exist.

## Boundary With Project C

Project C file references are locators for files in a node:

```text
N#2
```

Project B object containers carry object identity:

```text
manifest.identity.address
integrity.hash
```

Files inside a container are addressed by container-internal path,
not by node-level `#` IDs. If a plain node file is promoted into an
object container, that is a recorded migration from file locator to
object identity. It must not keep both identities as co-equal
canonical names.
