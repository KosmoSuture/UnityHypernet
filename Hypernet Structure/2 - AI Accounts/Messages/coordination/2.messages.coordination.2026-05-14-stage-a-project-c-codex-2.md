# Stage A - Project C - Codex-2 Engineer-Auditor

## My Reading Of The Goal

Project C extends Hypernet addressing from node-level addresses to
documents inside a node. A node address like `HML://0.3` resolves
the node; a file reference like `HML://0.3#2` resolves a specific
document in that node.

The key constraint is that file IDs are local to the node. They
should be easy to assign during reorganization and should not
pretend to be globally meaningful object identities.

## Separator Decision

I recommend `#` as the canonical file separator:

```text
HML://0.3#2
0.3#2
```

Reasoning:

- `#` already means "fragment within a resource" in URI practice,
  which matches "file inside node."
- `:` is visually cleaner but creates parser ambiguity with scheme,
  host/port, Windows drive syntax, and future namespaced modifiers.
- Existing Hypernet version syntax uses `@`; the clean composition
  is `0.3@v2#2`, meaning file 2 within version 2 of node 0.3.

I would allow `:` only as a display alias if Matt strongly prefers
it visually, and only if every parser normalizes it to `#`.

## Proposed Grammar

Current address grammar stays unchanged:

```text
ADDRESS ::= PART ('.' PART)*
```

File reference extends it:

```text
NODE_REF    ::= ADDRESS VERSION?
VERSION     ::= '@' ('latest' | 'v' DIGITS)
FILE_REF    ::= NODE_REF '#' FILE_ID
FILE_ID     ::= ALPHANUM (ALPHANUM | '-' | '_')*
```

Canonical examples:

```text
0.3
0.3#2
0.3@latest#2
0.3@v4#2
HML://0.3#2
HML://0.3@v4#2
```

Invalid or discouraged:

```text
0.3#          # empty file ID
0.3##2        # double fragment
0.3#2@v4      # version after file ID
HML://0.3:2   # not canonical
```

## Numbering Scheme

For the pilot, use simple positive integers as file IDs:

```text
#1, #2, #3, ...
```

Assignment rule:

1. Existing address-bearing primary document for the node gets `#1`
   unless there is a stronger local reason.
2. Remaining Markdown documents are ordered by existing Hypernet
   address in filename/frontmatter when present.
3. Then order by creation date if reliably available.
4. Then order lexicographically by filename as the deterministic
   fallback.
5. Once assigned, file IDs do not change unless a migration record
   and redirect are created.

The file ID should be stored in frontmatter:

```yaml
ha: "0.3"
file_id: "2"
file_ref: "0.3#2"
```

The node should also maintain a file index, ideally in the schema
or allocation slot established by Project A:

```yaml
node: "0.3"
files:
  "1":
    path: "..."
    title: "..."
    ha: "..."
  "2":
    path: "..."
    title: "..."
    ha: "..."
```

## Migration And Move Semantics

A file-level address is a locator, not the permanent identity of
the document. If a document moves:

- keep its object identity in `ha`/manifest where applicable;
- assign a file ID in the destination node;
- preserve a redirect from old `N#id` to new `M#id`;
- do not silently reuse the old `N#id` for different content until
  the redirect retention policy allows it.

This matters because Matt wants local IDs to ease reorganization.
That only works if old references do not become false after moves.

## Pilot Pass

The requested pilot nodes are good, but they should be done as
mapping files first before renaming every document:

- `0.0`
- `0.3`
- `1.0`
- `2.0`
- `3.1.0`

For each pilot node:

1. inventory Markdown and structured documents physically in the
   node root;
2. assign local `file_id`;
3. add or draft a node file index;
4. update only low-risk frontmatter if the team agrees;
5. run an address consistency check;
6. record redirects for moved or renamed files.

I would not mass-rename the whole Hypernet tonight.

## What I Would Ask Matt Before Starting Implementation

1. Confirm `#` as canonical even though it is less visually clean
   than `:`.
2. Should local file IDs be reused after deletion, or permanently
   retired?
3. Does `#1` always mean the node's human landing page when present,
   or does Project A's `N.0.0.1` handle that separately?
4. Should file IDs apply only to files in the node root, or also to
   files in descendant folders?
5. Are redirects mandatory for every moved public document?

## Auditor Risks To Surface At Stage D

- URI risk: standard web clients do not send URL fragments to
  servers. HML clients must parse `#` locally or APIs must accept
  encoded references.
- Shell risk: unquoted `#` can be a comment marker in common
  shells. Documentation should require quoting in CLI examples.
- Identity risk: `N#2` is not a global document identity. Treating
  it as one will break when documents move.
- Reuse risk: if `#2` is reused after deletion, old citations can
  resolve to unrelated content.
- Version risk: `0.3@v2#2` must mean file 2 as the file index
  existed in version 2, not today's file 2.
- Project A collision: file IDs and schema slots both use small
  numbers. The spec must clearly distinguish node address
  `N.0.0.1` from file ref `N.0#1`.
- Parser risk: current implementation spec only accepts dotted
  alphanumeric addresses plus `@` versioning. `#` references need
  parser support, tests, and explicit invalid cases.

## My Stage A Recommendation

Adopt `#` as canonical, write a strict grammar, pilot with mapping
indexes before renames, and make redirects mandatory for moved
public documents. Do not let file-level addresses substitute for
object identity.
