# Project F Stage A - Codex-1 Engineering Analysis

## Trust Preflight

Project F touches medical, DNA, emergency access, and personal
messages. Those are high-trust domains. This analysis therefore
does not import data, does not define clinical guidance, does not
claim medical correctness, and does not ratify `1.0.4`. It only
names engineering constraints, schemas, validators, and stop
conditions for a later Project F consensus invocation.

## Engineering Read

Keel's `1.0.4` is a strong first-pass information architecture.
The engineering risk is not "is there a slot for the data?" but
"can tools safely resolve, validate, gate, migrate, and audit the
data without leaking private content or inventing false authority?"

Project F should be treated as two coupled systems:

| System | Purpose |
|---|---|
| public schema | stable channel layout and object contracts |
| private data adapter | local/private storage, imports, mandalas, emergency access |

The public schema can be drafted in Git. Real medical/DNA/message
records must stay private or synthetic until the privacy wall and
mandala contracts are validated.

## Addressing Risk: DNA Labels vs Hypernet Address Grammar

Keel's draft uses readable examples like:

```text
1.X.6.3.genome.gene.BRCA1
1.X.6.3.genome.snp.rs6311
```

That is semantically clear but may conflict with the current
numeric-node expectations of Hypernet addressing. Do not silently
extend node-address grammar to arbitrary biological labels inside
Project F.

Recommended engineering split:

| Layer | Addressing rule |
|---|---|
| Hypernet node address | remains numeric until core grammar changes |
| file-level selector | may use named IDs under `0.0.7` rules, e.g. `1.X.6.3:genome-index` |
| biological locus ID | structured field inside data, e.g. `gene_symbol: "BRCA1"` |
| universal locus registry | future shared registry mapping stable locus IDs to reference builds |

Minimal workable pattern:

```yaml
genome_locus_ref:
  locus_id: "gene:BRCA1"
  reference_build: "pending"
  coordinate_system: "pending"
  chromosome: "17"
  start: null
  end: null
  source_registry: "pending"
```

This keeps permanent biological identity structured without
requiring a risky address-grammar change in the first pass.

## Validators Before Any Real Data

| Validator | Must enforce |
|---|---|
| visibility validator | medical/DNA/message records default private |
| mandala scope validator | grant exposes only approved fields/ranges |
| break-glass validator | every emergency access has event, scope, credential evidence, audit |
| public leak validator | no private counts/names/identifiers in public rollups |
| import validator | imported source keeps provenance and source-system ID |
| retention validator | deletion/revocation requests create auditable state |
| advisory validator | AI medical output labeled as observation/question/risk-flag/recommendation |

No Project F Stage E import should begin until these validators
exist against synthetic fixtures.

## Messaging Schema Engineering Notes

For messages, the key engineering contract is scale and identity
resolution:

| Need | Contract |
|---|---|
| hundreds of thousands of records | append-only import batches plus searchable index |
| cross-platform identity | `contact_identity_map` separate from messages |
| attachments | object references, not inline blobs |
| threads | stable thread IDs plus per-message IDs |
| privacy | channel-level and participant-level visibility defaults |

Minimum message object:

```yaml
message_ref:
  message_id: ""
  thread_id: ""
  platform: ""
  sent_at: ""
  sender_ref: ""
  recipient_refs: []
  body_ref: ""
  attachment_refs: []
  import_batch_ref: ""
  visibility: "private"
```

## Stage E Exit Criteria For Project F

Project F should not call Stage E complete until:

1. `1.0.4` is revised into a converged `status: draft-proposed`
   spec;
2. DNA addressing chooses either structured-locus fields or a
   formal address-grammar extension;
3. medical/DNA records have default-private validators;
4. break-glass and research-grant records have audit schemas;
5. message imports have synthetic scale fixtures;
6. no real private medical/DNA/message data has been imported in
   the public tree;
7. medical/biology/privacy reviewers have signed off or named
   blockers.

## Stage A Recommendation

Adopt Keel's `1.0.4` as the Stage A substrate, but isolate these
engineering axes for Stage B:

| Axis | Codex-1 recommendation |
|---|---|
| DNA addresses | structured biological IDs first; grammar extension later |
| real data | synthetic fixtures only until validators exist |
| medical advice | record claims as advisory artifacts, never unlabeled truth |
| break-glass | event-scoped, audited, bounded subset |
| research grants | mandala scope + re-identification warning required |
| messages | append-only import batches with separate identity map |
