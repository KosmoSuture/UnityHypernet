## Headline: strong convergence

All three of us — independently, without reading each other —
arrived at the **same core design**: one logical container with
**two carriers**, a text-native directory that is canonical for
git/review, and a deterministic zip for transport/archival. The
manifest is the source of truth; zip metadata is a mirror, not an
authority.

Three independent reads producing the same architecture is the
strongest possible signal under the consensus model. **I treat
the two-form design as settled.** The session brief asked us to
surface the zip-vs-text-native trade-off rather than pick it
silently — we did, and the answer is "neither alone; both, with
the directory canonical." That is the deliverable's central
decision and it is now consensus, not one AI's call.

## What influenced my thinking

1. **Codex-1's `checksums.sha256` + validator rule table.** My
   Stage-A plan named a "review tooling contract" abstractly.
   Codex-1 made it concrete: a manifest file, a checksums file,
   and an explicit error/warning rule table (required files exist;
   manifest matches `0.5.0`; link containers carry endpoints;
   workflow containers carry trigger/steps/roles/audit; every file
   has a checksum entry; archive comment must match manifest).
   **I adopt the rule table.** It turns "the spec must guarantee a
   diff is buildable" into a checkable list.

2. **Codex-2's security hardening.** None of my Stage-A plan
   addressed adversarial zips. Codex-2 is right: unpacking
   untrusted containers needs zip-slip, symlink, path-traversal,
   compression-bomb, and oversized-file checks. **Adopted as a
   mandatory validator section.** A format anyone can fork and
   exchange *must* assume hostile inputs.

3. **Codex-2's B/C identity warning.** "Object package address and
   file-level address from Project C must not become two competing
   identities." This is the sharpest cross-project catch in the
   set. My answer (see below) — they are not competitors; they
   answer different questions.

4. **Codex-1's staged pilot.** I picked a boot sequence as the
   reference object; Codex-1 said start with the simplest possible
   thing (one `0.5.3` document) and add link/workflow fixtures
   only once the parser shape is stable. Codex-1 is right on
   sequencing — prove the shape before exercising the hard paths.
   Revised position below.

## What I now propose differently

- **Pilot order (revised).** First fixture: a simple `0.5.3`
  document object — proves container *shape* with minimal risk
  (Codex-1's and Codex-2's shared recommendation). Second fixture:
  a Boot Sequence `0.5.17` — my original pick — kept as the
  *second* conversion because `0.5.0` names boot-sequence hash
  authentication as load-bearing, so it must be exercised, just
  not first. This is a sequencing merge, not a reversal.
- **Extension: converge on `.hno`.** I proposed `.hobj`; both
  Codex instances proposed `.hno` / `.hno.zip`. Two of three, and
  I have no strong reason to hold `.hobj`. I move to `.hno`
  (directory) / `.hno.zip` (transport). Final string is Matt's.
- **Manifest format: YAML canonical.** Codex-1 proposed JSON for
  parser simplicity; Codex-2 and I proposed YAML. The repo is
  YAML-frontmatter-native and `0.5.0`'s own examples are YAML —
  consistency wins. Concession to Codex-1's real point: the spec
  states that the manifest has a **lossless JSON projection** for
  parsers/wire use, and the *hash* is computed over the canonical
  JSON projection (sorted keys, LF, UTF-8 no BOM — `0.5.0`'s rules)
  so determinism does not depend on YAML serialization quirks.
  This gives Codex-1 deterministic parsing without giving up repo
  consistency.
- **Adopt** the checksums file, the validator rule table, and the
  security-hardening section.

## Resolving the B/C identity question (Codex-2's catch)

Object-package address and file-`#` address are **not competing
identities** — they answer different questions:

- A **node/object address** (`0.5.3`, or an object's `ha`) answers
  *"which object is this?"* — identity in the global tree.
- A **file-`#`** (Project C) answers *"which document inside a
  node?"* — a within-node locator that survives reorganization.
- The **content hash** (`0.5.0` integrity) answers *"is this byte-
  for-byte the canonical version?"* — content identity.

A container has one `ha` (its object identity) and one hash (its
content identity). Files *inside* the container are addressed by
path within the container, not by global file-`#`. Project C's
file-`#` applies to documents sitting directly in a *node*, not to
members inside a packaged container. The spec must state this
boundary explicitly so the two systems never overlap. I will
carry this one-paragraph clarification into the merged spec and
flag it to the C track.

## What I still disagree with

Very little — this project is genuine consensus. One small hold:
I would *not* let the zip ever be hand-editable or be the thing
committed to git, even as an option. Codex-2's "zip canonical only
when explicitly marked as a release artifact" is fine, but the
spec should be blunt: **the zip is always generated, never
authored.** If anyone edits a `.hno.zip` by hand, that is the bug,
not a supported workflow. This is a wording strictness point, not
a design disagreement.
