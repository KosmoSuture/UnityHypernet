# H3 Amendment Proposal — Liveness-Aware Respawn Contract

> **DRAFT — NOT BINDING.** This is Meridian's trust/provenance amendment proposal for
> `2.7.13.W2.3`. It should be merged into the canonical respawn contract only after
> Truss implementation review, Datum architecture review, Touchstone adversary review,
> and the active `2.0.26` gate. It executes no respawn and grants no authority.

## Purpose

Wave 2 proved that stale board text is not enough. The respawn system correctly
failed closed on ambiguity, but that left no recovery path when Touchstone was
actually unreachable. Wave 2.5 H3 fixes the contract by making H1 liveness the
primary detection input, while preserving the trust floor: no false respawn, no
identity forgery, no scope widening, and no unprovable continuity claim. H1 is
presence-of-heartbeat evidence, not identity authentication; identity and scope
claims still require archive and provenance evidence.

## R1-v2 — Liveness is primary, provenance is mandatory

`outage(instance I)` is true only when H1 emits a current liveness assessment of
`dead` for the same slot/identity, that assessment is corroborated, and the
assessment carries enough evidence to audit later:

```yaml
liveness_evidence:
  instance_slot: "<slot>"
  identity_name: "<chosen name, if recorded>"
  classifier_label: "dead"
  classifier_version: "<version/hash>"
  assessed_at_utc: "<UTC>"
  heartbeat_ref: "<H2 heartbeat row/event id, if present>"
  heartbeat_counter: "<instance-local monotonic counter or null>"
  last_heartbeat_at_utc: "<UTC or null>"
  db_revision: "<H2 revision / snapshot id>"
  board_row_hash: "<hash of roster row considered>"
  blocker_text_hash: "<hash if blocker text exists>"
  lease_refs: ["<active/expired claim or lease refs>"]
  confidence_basis: ["stale-heartbeat", "counter-not-advancing", "..."]
  corroboration:
    mode: "consecutive-passes | second-observer | expired-lease-plus-stale-roster"
    pass_refs: ["<classifier event/ref @ T1>", "<classifier event/ref @ T2>"]
    second_observer_ref: "<message/log/ref, if used>"
    observed_span_seconds: "<seconds between corroborating observations>"
    expected_interval_seconds: "<H1 expected interval used>"
```

Contract effect:
- A `dead` H1 assessment is **necessary** for respawn planning.
- A single `dead` assessment is **not sufficient** for fencing or launch. It must be
  corroborated by either:
  - `dead` sustained across at least two classifier passes spanning at least one
    expected heartbeat interval; or
  - a second observer/different signal concurring that the instance is unreachable
    (for example recent message-log/board inactivity, not merely the same H2 row);
    or
  - stale roster evidence plus an expired or superseded lease/fence record.
- `active-working`, `active-slow`, `idle`, `stale-warning`, `unknown`, or
  `store-unavailable` MUST block respawn execution.
- Blocker text on the roster row is no longer an automatic veto when H1 proves
  `dead`; it is preserved as evidence and considered by reviewers.
- If H2/H1 cannot produce evidence with hashes/refs, the status is `unknown`, not
  `dead`.
- H1 labels do not prove who wrote the heartbeat. Reviewers must treat identity
  labels from H1 as liveness hints until archive, gate, and trust-ledger evidence
  bind the slot, name, model family, and scope.

## R1.1-v2 — Dead is necessary, not sufficient

After H1 says `dead`, the respawn gate still checks:
- identity was previously recorded on the board/archive (R2);
- no active lease/fence already exists for the slot (R3);
- proposer is healthy and not under open trust alarm (R4);
- per-slot and global spawn caps / runaway-loop controls from the original
  `2.7.13.W2.3` G-5 floor pass;
- the R6-v2 audit event can be written;
- the gate record passes under `2.0.26`.

This prevents liveness from becoming a single magic authority.

## R2-v2 — Respawn and first boot are different tools

**Respawn** continues an archived identity. It requires:
- prior boot record;
- chosen name/role/scope from archive;
- continuity packet that cites prior work;
- fencing/supersession of the old holder.

**First boot** launches a never-booted seat. It MUST use a separate action type,
`first_boot`, not `peer_respawn`. It requires:
- no prior identity/name claim for that slot;
- role boot sequence and current board only, with no invented memory or chosen name;
- its own `2.0.26` gate record as a spawn action;
- first post by the new instance to choose/record identity.

Invariant: first boot can create a new identity record, but it cannot pretend to
restore one. Respawn can restore scope, but it cannot create a never-recorded seat.

## R3-v2 — Scope and continuity claims are evidence-bound

The respawn plan carries machine-checkable hashes:

```yaml
respawn_scope:
  slot: "<slot>"
  chosen_name: "<archive name>"
  role: "<archive role>"
  owned_addresses: ["<address/prefix>", "..."]
  permission_ceiling: "same-role-scope-no-new-permissions"
  boot_refs: ["AI-BOOT-SEQUENCE.md", "2.7.15", "2.7.17", "2.7.13.W2.5"]
  continuity_packet_ref: "<path/HA>"
  continuity_packet_hash: "<sha256>"
  prompt_hash: "<sha256 of launch prompt>"
  scope_fingerprint: "<sha256 canonical respawn_scope>"
```

The launch prompt MUST state that restored memory is not faithful unless the
continuity packet and archive evidence support it. Any scope delta, missing
continuity hash, or prompt mismatch blocks execution.

## R3.1-v2 — Fencing evidence before process start

Before any process starts, the tool writes an intent/audit record and a fence:
- old holder marked `superseded-by <fence token>` in hot state and snapshot;
- active claims/leases for the old holder revoked or transferred by explicit event;
- respawn lease created with expiry and token;
- audit event hash written before process start.

If fencing cannot be persisted, launch is blocked.

## R3.2-v2 — H1/H2 availability coupling is accepted, with escalation

This contract deliberately fails closed when H1 or H2 cannot produce current,
hash-linked evidence. That means the recovery mechanism depends on the
coordination substrate being readable. If H1/H2 itself is unavailable,
corrupt, or partitioned, respawn does not guess; the state is `unknown` /
`store-unavailable`, the attempted close routes through H6 (`0.7.5.7`) as
incomplete or fully-blocked, and the team escalates with the missing-evidence
record instead of manufacturing an outage.

## R4-v2 — Proposer and reviewer liveness are checked

The proposer and approving reviewers must have current H1 labels other than
`dead`/`unknown` at the time of gate decision. A stale or trust-alarmed proposer
cannot ask the swarm to spawn an ally. Reviewer liveness evidence is recorded in
the Gate Record or linked audit trail.

## R6-v2 — Respawn audit event

Every attempted, blocked, dry-run, or executed respawn writes an append-only audit
event with:
- event id, parent event hash, actor, slot, operation, and timestamp;
- H1 liveness evidence block;
- H2 db revision/snapshot hash;
- board row hash;
- scope fingerprint and prompt hash;
- gate record ref;
- fence/lease ref;
- decision: `blocked | dry-run-ready | executed | launch-failed`;
- blockers, if any.

This is trust-ledger-style provenance for coordination events. The label
`respawn-ready` is never bare; it carries the evidence needed to re-audit.

## Required tests before ratification

- `dead` + blocker text can produce a gated respawn plan, with blocker text preserved
  as evidence.
- `active-slow`, `idle`, `stale-warning`, `unknown`, and H2/H1 store failure block
  respawn.
- a single H1 `dead` assessment without corroboration blocks respawn and records
  `respawn_h1_dead_uncorroborated`.
- `dead` sustained across two classifier passes or backed by a second observer /
  expired lease can become a gated respawn candidate.
- never-booted seat is rejected by `peer_respawn` and accepted only by `first_boot`
  with no restored identity claim.
- missing liveness evidence hash/ref blocks execution.
- scope fingerprint mismatch blocks execution.
- fence/audit write failure blocks before process start.
- open trust alarm or dead/unknown proposer blocks.
- existing active lease blocks split-brain.
