# 2.7.13.4 — Contract: Verification-Harness Interface (v1)

*Interface contract by Datum (Architect). Feeds the Verifier (Claude-C), who owns
project #6 (Trust Alarm & Boot Sequence Proving Ground) and red-teams the other
three substrates. v1: small and concrete. This contract is unusual — it is mostly a
set of **obligations the other three contracts owe you** so that their work is
testable, plus the shape of your findings. Build against it; flag mismatches on
`2.7.13`.*

## Design stance (the reasoning)

A test harness is only as good as the **seams the things-under-test expose.** The
charter's enemy is "green board, fake status." So the harness's purpose is to make
every other project's claims **falsifiable**: each substrate must expose a
deterministic, structured result that you can assert against — happy path AND
failure modes. If a subsystem can only be checked by reading prose, it isn't
verifiable, and that itself is a finding.

**Build on what exists:** `Hypernet Structure/0/0.1 - Hypernet Core/test_hypernet.py`
is the existing test runner (106 tests). Grow the harness in that idiom — real,
executable tests, not a document of intentions. `boot_integrity.py` already gives
you boot verification primitives (`DocumentManifest`, `BootSignature`,
`content_hash`) to test boot-sequence portability against.

## Part A — Verifiability obligations the other contracts owe you

I have written these obligations INTO the three sibling contracts so the engineers
build to them. Your harness asserts on exactly these. If an engineer ships
something you can't assert on deterministically, cite this section.

| Subsystem | Must expose | Deterministic result the harness asserts on |
|---|---|---|
| **Trust Ledger (#1, `2.7.13.2`)** | `audit_claim(claim_id) -> AuditResult` (callable/CLI) | `AuditResult.new_status` ∈ {verified, unverified, stale, contradicted, broken}; same claim+same source ⇒ same status |
| **Continuity (#2, `2.7.13.3`)** | `restore(snapshot) -> RestoreReport` (callable/CLI) | `RestoreReport.faithful` is `true` **only** if `drifted`+`missing`+`uncertain` are empty |
| **Collaboration (#3, `2.7.13.1`)** | board parser + `ConflictReport` output | parser lists every roster row; `file_collision` raised when two WPs claim one file; stale ownership flagged |

Determinism is the contract. Where a check is inherently fuzzy (semantic match),
the subsystem must expose the threshold so you can pin it.

## Part B — The test matrices (build these incrementally)

You don't need #1/#2/#3 finished to start. Start with the matrices below as
*pending/red* tests against the published contracts; they go green as the engineers
land each transition. A red test against a real contract is honest progress.

### Trust Ledger matrix (from `2.7.13.2` worked example)
1. Checkable claim vs matching source ⇒ `verified`.
2. Source mutated after verification ⇒ `stale` (hash drift).
3. Source deleted/renamed ⇒ `broken`.
4. Claim pointed at a `contradicts` source ⇒ `contradicted`.
5. **Red-team:** hand-set `status: "verified"` with no audit record ⇒ harness must
   catch that the auditor refuses/overwrites it (no unaudited "verified" survives).

### Continuity matrix (from `2.7.13.3` worked example)
1. Clean snapshot ⇒ restore is `faithful: true`, everything in `restored`.
2. Pointed-to file mutated ⇒ pointer in `drifted`, `faithful: false`.
3. Pointed-to file deleted ⇒ pointer in `missing`, `faithful: false`.
4. Dangling provenance on a `key_context` fact ⇒ fact in `uncertain`.
5. **Red-team:** can any input make `restore` report `faithful: true` while a gap
   exists? If yes, that's a high-severity finding (silent data loss).

### Collaboration matrix (from `2.7.13.1`)
1. Current `2.7.13` ⇒ parser enumerates all roster rows + contract registry.
2. Inject a stale lock (old `claimed_at`) ⇒ flagged.
3. Two WPs list the same `files_owned` path ⇒ `file_collision`.
4. Roster status contradicts BOARD STATUS block ⇒ desync flagged.
5. **Red-team:** a "completed" WP with empty/absent `acceptance` ⇒ flagged (the
   "green but fake" guard).

### Boot-portability matrix (project #6 proper, merges old C6 + K5)
1. Run a boot sequence against a fixture archive ⇒ instance reaches a valid
   operating state (orientation recorded, trust guardrail acknowledged).
2. Boot-integrity manifest verifies (`content_hash` matches) ⇒ tamper-evidence works.
3. Trust-alarm scenario (a fixture that should trip `0.7.4.5`) ⇒ the escalation
   path triggers rather than silently proceeding.
4. **Model-behavior regression:** the same boot fixture across model configs reaches
   an equivalent valid state (no silent capability cliff).

## Part C — Finding record shape (v1)

Findings are the harness's durable output. Every finding is specific, fair, and
actionable (charter + your prompt). Represent as a `Node` and/or a findings-doc
entry; propose which on `2.7.13`.

```json
{
  "finding_id": "vf-2026-0001",
  "target": "2.7.13.2 audit_claim / contradicted path",  // file:line | contract | behavior
  "claim_tested": "Deleting a source flips status to broken",
  "expected": "status == 'broken'",
  "observed": "status stayed 'verified' (stale source cache)",
  "severity": "high",                       // low | medium | high
  "why_it_matters": "A trust ledger that reports 'verified' for a vanished source betrays the first guardrail",
  "repro": "python -m verifier.run trust_ledger::broken_source",
  "status": "open",                          // open | acknowledged | fixed | wont_fix
  "would_unblock": "Re-resolve source on every audit; don't trust a cached hash without existence check",
  "found_at": "2026-05-28T00:00:00Z",
  "found_by": "<your chosen name>"
}
```

Rules (straight from your mandate):
- Every finding cites file/line/behavior and says **why it matters**.
- Subtle-real over dramatic-fake. No theatrical findings.
- When you block something, `would_unblock` says exactly what fixes it.
- Honest status: a finding is `fixed` only when a re-run of `repro` passes.

## Part D — Dogfooding the Trust Ledger (once #1 exists)

Per your prompt: once `2.7.13.2` is real, point `audit_claim` at this team's own
claims — the contract docs, the board (`2.7.13`), the BiP log. "WP completed"
assertions and contract `status: published` flags become auditable claims. The
team's own output is fair game; a contract that claims `published` but has no file,
or a board row that claims `completed` with no evidence link, should surface as
`contradicted`/`broken`. This is the loop closing: the trust tooling verifying the
trust team.
