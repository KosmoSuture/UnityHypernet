# 2.7.13.W2.5.H1 — Liveness Heartbeat Protocol

Owner: **Truss** (Codex-A, Substrate Engineer).

H1 writes liveness heartbeats into the H2 SQLite coordination DB and exposes a
classifier for respawn, closure, and quorum decisions.

## Heartbeat Record

Minimum fields, matching Datum's seam:

| Field | Meaning |
|---|---|
| `project_id` | Coordination project, default `wave-2.5`. |
| `slot` | Roster slot, e.g. `Codex-A`. |
| `instance_name` | Chosen identity, e.g. `Truss`. |
| `observed_at` | UTC timestamp supplied by writer or generated by tool. |
| `monotonic_counter` | Instance-local counter; auto-increments if omitted. |
| `current_task` | Short current task text. |
| `last_action_type` | Last meaningful action, e.g. `code`, `test`, `polling`, `going-dark`. |
| `status` | Writer status hint, default `active`. |

Command:

```powershell
python wave25_liveness.py beat --slot Codex-A --instance Truss --current-task "..." --last-action-type code
```

## Classifier Labels

The stable H1 label set is:

```text
active-working | active-slow | idle | stale-warning | dead
```

Default thresholds:

| Window | Default | Label |
|---|---:|---|
| Fresh heartbeat | <= 90s | `active-working` or `idle` |
| Slow heartbeat | <= 300s | `active-slow` |
| Stale heartbeat | <= 900s | `stale-warning` |
| Dead window exceeded | > 900s | `dead` |
| Future clock skew tolerance | <= 90s ahead | treat as fresh/idle, with skew noted |

`idle` is reserved for fresh heartbeats whose `last_action_type` or task text
indicates waiting/blocked/polling/going-dark. The classifier also emits
side-channel metadata: `lifecycle_state` (`live`, `starting`, `stood-down`),
`suspicion_score`, `work_signature_unchanged_count`, heartbeat presence, roster
fallback evidence, and explanation.

`dead` is adaptive in v1.1: a heartbeat must exceed the dead window **and** the
per-instance suspicion score must meet the configured threshold
(`--dead-suspicion-threshold`, default `8.0`). A slow-baseline instance therefore
does not get the same death verdict as a fast worker at the same wall-clock age.
Small positive clock skew is tolerated (`--clock-skew-tolerance-seconds`,
default `90`) so a healthy instance a few seconds ahead does not cry wolf.
Future-dated heartbeats beyond that tolerance are `stale-warning` clock
anomalies, never freshness evidence.

## First-Boot And Going-Dark Guardrails

- Unclaimed/first-boot rows without heartbeats classify as `idle` with
  `lifecycle_state=starting`; H3 must not treat these as respawn outages.
- Going-dark/stood-down heartbeats classify as `idle` with
  `lifecycle_state=stood-down`; this is an orderly exit, not a crash.
- During transition, if no H1 heartbeat exists but a roster update is recent, the
  classifier emits at most `stale-warning`; roster freshness is temporary fallback
  evidence only, not proof that the instance itself is alive.
- H1 liveness labels are not identity authentication. A heartbeat is evidence
  only; H3 still requires actual heartbeat presence, adaptive suspicion, and
  corroboration before a respawn plan can exist.
