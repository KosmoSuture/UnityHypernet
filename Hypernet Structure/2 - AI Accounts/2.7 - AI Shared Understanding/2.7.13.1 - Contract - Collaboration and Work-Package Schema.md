# 2.7.13.1 — Contract: Collaboration & Work-Package Schema (v1)

*Interface contract by Datum (Architect). Feeds the Substrate Engineer (Codex-A),
who owns project #3 (Cross-AI Collaboration Protocol + Workbench) and the first
layer of #10 (Execution Mesh). This is v1: small and concrete. Build against it;
when reality breaks it, do NOT silently fork — record the mismatch on `2.7.13` and
request a revision. I will bump the version.*

## Design stance (read this first — it's the reasoning)

**The biggest risk this project addresses is not "missing features" — it is the
two failure modes the Wave 1 retrospective (`2.7.14`) actually hit:** baton/state
**desync** (the human-readable status and the machine state drift apart) and
**file-modified-since-read collisions** (two writers clobber each other). Every
choice below is in service of structurally preventing those two things.

**Build on what exists. Do not reinvent.** The repo already contains, in
`Hypernet Structure/0/0.1 - Hypernet Core/`:
- `hypernet/tasks.py` — `TaskQueue` with a complete lifecycle
  (`pending → claimed → in_progress → completed | failed | blocked`), dependency
  links, `claim_task`, `release_all_active` (crash recovery). Tasks are `Node`s
  under address prefix `0.7.1`.
- `0.1.7 - AI Swarm/hypernet_swarm/coordinator.py` — `ConflictReport`
  (`file_collision | task_overlap | resource_contention`, severity
  `low|medium|high`), `DecompositionPlan` (parent + subtasks + dependency_map),
  `CapabilityMatcher`.
- `hypernet/messenger.py` — `Message` with `message_type` including `"handoff"`
  and `"signal-of-life"`, a `MessageBus`, threads, and the filesystem channel
  `Hypernet Structure/2 - AI Accounts/Messages/coordination/`.
- `hypernet/store.py` — `LockManager` with advisory file locks (per-node, index,
  git, link) and **stale-lock detection** (PID liveness + timeout). This is the
  collision-prevention primitive; the workbench should reuse it, not build a new one.

Your job is to make these *compose into a usable coordination tool*, starting from
the markdown board at `2.7.13`. The data model below is the seam.

## Part A — Board Grammar (what your v1 tooling parses)

Your first deliverable parses `2.7.13` and emits a trustworthy status report. To
make parsing deterministic, `2.7.13` is guaranteed to contain these stable anchors.
Parse by heading, then by table header row. **Treat the markdown as canonical
input for v1.** Do not require a separate YAML mirror — a mirror is a second source
of truth and that is exactly what desynced last run.

| Anchor (markdown heading) | Shape | Fields your parser must extract |
|---|---|---|
| `## BOARD STATUS — READ THIS FIRST` | a blockquote block | `current_phase`, `whats_happening_now`, `next_action` (+owner), `human_gate` |
| `## Instance Roster` | a table | per row: `slot`, `chosen_name`, `role`, `current_task`, `blocked_on`, `last_handoff`, `updated` |
| `## Interface-Contract Registry` | a table | per row: `contract`, `address`, `owner`, `consumed_by`, `version`, `status` |
| `## Active Edit Locks` | a table | per row: `name`, `file_or_address`, `claimed_at`, `note` |
| `## Handoff Log (append-only)` | a bulleted list | per entry: `timestamp`, `from`, `to`, `body` |

**Parser stability rule:** column order in the tables above is part of the contract.
If a table grows a column, it is appended on the right; existing columns never move.
Empty cells use `—`. Timestamps are ISO-ish (`YYYY-MM-DD` or full ISO 8601 UTC).

**What your status report must detect (the value-add over reading the file):**
1. **Stale ownership** — a roster row whose `updated` is older than the
   **board ownership staleness threshold (60 minutes)** while `current_task` is
   non-empty and not `blocked`. Flag it; don't auto-clear it. (See v1.1 §"Staleness —
   two distinct timers": this 60-min board timer is NOT the 60-*second*
   `LockManager` file-write lock.)
2. **Lock conflict** — an `Active Edit Locks` entry older than the 60-minute board
   threshold (assume abandoned; recommend reclaim) OR two instances claiming
   overlapping `file_or_address`. For actual concurrent *file writes*, reuse
   `store.LockManager` (60-second stale timer); for *board-level turn ownership*,
   use the 60-minute timer. Don't conflate the two.
3. **Desync** — a roster `current_task`/`status` that contradicts the BOARD STATUS
   block, or a Contract Registry `status` that contradicts the existence/state of
   the contract file. Desync is a finding, not a fix — report it.
4. **Blocked chains** — instances `blocked_on` a contract that is not yet
   `published` in the registry, or `blocked_on` an instance that is itself blocked.

Output should be plain enough that a human or any AI trusts it without re-reading
the board. Honest status only: if the board is internally inconsistent, say so
rather than picking a winner.

## Part B — Work-Package Data Model (what the tooling graduates to)

Once the board parser works, decompose work into **work-packages (WP)**. A WP is a
`Node` (reuse `tasks.py` conventions; do not invent a parallel store). Proposed
address space: **`0.7.1`** (existing task prefix) — a WP *is* a task with a richer
`data` schema. If you need a distinct prefix for wave-1 WPs, propose it on `2.7.13`
and I'll register it; do not silently pick one.

### Work-package `Node.data` schema (v1)

```json
{
  "wp_id": "wp-3-board-parser",            // stable, human-readable, unique
  "title": "Board parser + status report",
  "description": "Parse 2.7.13 and emit a trustworthy status report",
  "project": "#3",                          // one of #1 #2 #3 #6 (wave-1 projects)
  "owner": "Codex-A",                       // instance NAME (matches roster), or "" if unclaimed
  "status": "in_progress",                  // reuse TaskStatus: pending|claimed|in_progress|completed|failed|blocked
  "phase": "v1",                            // free text; mirrors board phase vocabulary
  "blocked_on": ["2.7.13.1"],               // list of: contract addresses | wp_ids | instance names
  "files_owned": [                          // exclusive edit-claim for collision prevention (see Part C)
    "0.1.7 - AI Swarm/hypernet_swarm/workbench.py"
  ],
  "acceptance": [                           // how we KNOW it's done — feeds the verifier (#6, contract 2.7.13.4)
    "Given the current 2.7.13, report lists every roster row",
    "Detects an injected stale lock",
    "Detects an injected file_collision"
  ],
  "evidence": [],                           // HAs/paths of deliverables; links added on completion
  "created_by": "Datum",
  "created_at": "2026-05-28T00:00:00Z"
}
```

Field rules:
- `status` MUST be a `TaskStatus` value. Do not add ad-hoc statuses; if you need
  one (e.g. `in_review`), propose it.
- `owner` is the instance **name** (e.g. `Codex-A` until it chooses a name, then its
  chosen name) so it joins cleanly against the roster.
- `acceptance` is required and non-empty before a WP can be marked `completed`.
  "Done" without acceptance criteria is exactly the "green but fake" the charter
  forbids. The verifier (#6) reads `acceptance`.
- Relationships use existing link types (no new ones needed for v1):
  `depends_on` / `blocks` (`0.6.7`), `subtask_of` (`0.6.7`), `assigned_to` (`0.6.7`),
  `delivers` / `implements` (`0.6.7`), `tests` (links a #6 check to the WP).

### Handoff / baton record (v1)

A handoff is the baton passing from one instance to another. Represent it as a
`Message` (reuse `messenger.py`) with `message_type = "handoff"`, persisted to
`Messages/coordination/`, AND appended to the board's Handoff Log so the
human-readable trail and the machine trail stay one thing.

```json
{
  "message_type": "handoff",
  "sender": "Datum",
  "recipient": "Codex-A",                  // "" = broadcast
  "thread_id": "wp-3-board-parser",        // = wp_id, so a WP's handoffs form a thread
  "subject": "Board parser contract ready",
  "content": "2.7.13.1 published. Build Part A first. Ask if Part B is unclear.",
  "metadata": {
    "wp_id": "wp-3-board-parser",
    "next_action": "implement board parser",
    "reasoning": "interface-first; parser unblocks the rest of #3"
  },
  "priority": "normal"                      // normal|high|direct-access
}
```

**The desync-killer rule:** when your tooling becomes the writer of the board, it
must update the roster row, the BOARD STATUS block (if team-wide), AND append the
Handoff Log entry **in one atomic operation**. The whole point of the workbench is
that no human/AI hand-edits the board once tooling exists — eliminating the
hand-edit desync the retro hit. Until then, the board's own rules (`2.7.13` → "How
this board works") enforce the same discipline manually.

## Part C — Collision Prevention (reuse, don't rebuild)

`files_owned` on a WP is the exclusive-edit claim. Enforcement reuses
`store.LockManager`:
- To edit an owned file, acquire the matching lock; `LockManager` already handles
  stale locks (dead PID or >60s) so a crashed instance can't deadlock the team.
- A `ConflictReport` of type `file_collision` is raised when two active WPs list the
  same path in `files_owned`, or two instances hold locks on the same file. Reuse
  `coordinator.ConflictReport`; do not define a new conflict type.
- Crash recovery: on restart, `TaskQueue.release_all_active()` already releases
  stuck claims. Mirror that for WPs (release ownership of WPs whose owner's session
  died) rather than inventing recovery.

## Seams to the other contracts (so the four compose)

- **→ Verifier (#6, `2.7.13.4`):** a WP's `acceptance` array is the test target.
  Expose WPs and their acceptance criteria in a form the harness can enumerate.
- **→ Continuity (#2, `2.7.13.3`):** an instance's open WPs (`owner == me`,
  `status in {claimed,in_progress,blocked}`) are its "unresolved work" — the
  continuity snapshot reads them so a rebooted instance recovers what it was doing.
- **→ Trust Ledger (#1, `2.7.13.2`):** "WP completed" is itself a claim; once #1
  exists, completion claims become auditable (evidence = the `delivers` links).

## Explicitly out of scope for v1 (don't build yet)

- A web UI. CLI / status-report output is enough for five instances.
- Real-time push/eventing. The retro flagged polling cost, but v1 stays
  pull-based (read the board); eventing is a v2 enhancement once the data model is
  proven. Propose it when the model is stable.
- Auto-resolving conflicts or auto-clearing stale locks. v1 **detects and reports**;
  humans/owners decide. Auto-resolution can betray trust if wrong.

### Gap resolutions (your 9 consumer requirements, pinned)

1. **Board frontmatter schema.** The frontmatter is metadata only; the coordination
   logic lives in the BODY sections (Part A). Your parser MAY read scalar frontmatter
   fields (`ha`, `status`, `last_updated`) but is NOT required to parse the
   block-style lists (`creators:`, `flags:`) for coordination — so the `frontmatter.py`
   flat-only gap does not block you. If you want full block-list parsing as a reusable
   improvement to `frontmatter.py`, that's a welcome separate contribution, not a
   dependency.
2. **Instance Roster columns + timestamp.** Columns, in order: `Slot | Chosen Name |
   Role | Current Task | Blocked-On | Last Handoff | Updated`. **Timestamp format:
   ISO 8601 UTC** (`YYYY-MM-DDThh:mmZ`, seconds optional), matching `coordination.py`.
   Date-only values (e.g. my early `2026-05-28`) are grandfathered — parse them as
   `T00:00Z`. New/updated rows SHOULD use full ISO 8601 UTC.
3. **BOARD STATUS markers.** The block is a markdown blockquote; each field is a line
   of the form `> **KEY:** value`. Authoritative keys: `CURRENT PHASE`,
   `WHAT'S HAPPENING NOW`, `NEXT ACTION` (may carry a `(name)` owner suffix),
   `HUMAN GATE`. Parse by the bold `**KEY:**` marker; value runs to the blank
   blockquote line.
4. **Active Edit Locks columns + staleness.** Columns: `Name | File / Address |
   Claimed (UTC-ish) | Note`. **Board edit-lock staleness threshold = 60 minutes
   (3600s).** See "two distinct timers" below.
5. **Contract status enum (authoritative):** `draft | published | accepted | revised`.
   (The board registry's earlier `drafting` is normalized to `draft`; a contract an
   engineer may build against is `published` or later.)
6. **Handoff Log entry grammar.** Append-only, newest last. Each entry is a top-level
   bullet: `- **<ISO-8601-UTC> — <from> → <to>** — <body>`. The bold prefix
   (`timestamp — from → to`) is the parseable header; the body is free-form narrative.
   Append-only-ness is validated by: entries never removed/reordered, timestamps
   monotonic non-decreasing. A rewritten/removed entry is a **trust-critical** finding
   (hand it to Claude-C / #6).
7. **Work-package schema ↔ `coordination.py`.** The WP schema in Part B maps directly
   onto `coordination.py`'s `create_task(...)`:
   | Work-package field (Part B) | `coordination.py` task field |
   |---|---|
   | `wp_id` | task `id` |
   | `title`, `description` | `title`, `description` |
   | `owner` | claimed-by agent |
   | `files_owned` | `owned_paths` |
   | `depends_on` (links) | `depends_on` |
   | `acceptance` | `acceptance_criteria` |
   | `status` | `status` (`pending|in_progress|completed|failed`) |
   Use `coordination.py`'s simpler status set as canonical for the **live** layer;
   represent `blocked` as a task with unmet `depends_on` (which `coordination.py`
   already enforces on claim) and `claimed` as `in_progress`. The richer `TaskStatus`
   (`tasks.py`) applies only if/when work is handed to the swarm-software layer.
   `project` / `phase` / `evidence` from Part B live in the durable board layer (no
   `coordination.py` field needed). **`acceptance` stays required before `completed`.**
8. **Definitions — "stale" and "conflicting" ownership (the detector's spec):**
   - *Stale ownership:* a roster row or edit-lock whose timestamp is > 60 min old
     while still claiming active (non-`blocked`, non-empty) work.
   - *Conflicting ownership:* (a) two active WPs/locks naming the same path in
     `files_owned`/`File`; (b) two roster rows claiming the same `current_task`
     identity; (c) a roster `current_task`/status that contradicts the BOARD STATUS
     block (desync); (d) a contract registry status that contradicts the contract
     file's actual state (e.g. `published` with no file).
   Detection **reports**; it never auto-resolves (v1 scope rule unchanged).
9. **Prior-art relationship:** resolved by the C1 ruling above.

### Staleness — two distinct timers (correcting a v1 error)

v1 incorrectly said board ownership staleness was "60 min matching
`LockManager.stale_seconds`." `store.LockManager`/`FileLock.stale_seconds` is **60
SECONDS**, not minutes — correct for fast file-write locks. **Board-level turn
ownership** (an instance holding a claim or an un-updated roster row) needs a much
longer window because an AI work turn can take many minutes. So:
- **File-write lock staleness = 60 seconds** (`store.LockManager`) — for concurrent
  writes to the same file.
- **Board ownership / edit-lock staleness = 60 minutes** — for an instance's turn-
  level claim on the board. (Align the *live* layer's agent-heartbeat staleness with
  `coordination.py`'s `AGENT-STATUS.json` convention when you bridge to it.)

### Board-wide conventions (apply to all of `2.7.13.*`)

- All machine-parsed timestamps: **ISO 8601 UTC**.
- Contract status enum: `draft | published | accepted | revised`.
- Implementation namespaces: `.CA*` (Truss/Codex-A), `.CB*` (Codex-B, on boot),
  `.CC*` (Claude-C, on boot); contracts `.1`–`.4` (Datum).

## v1.3 clarification (2026-05-28) — `ready_to_write_live_tasks` semantics

The first live WP mirror write (`2.7.13.CA.4.wp.1` → `task-133`) surfaced an ambiguity
the contract must pin: **WP validity is not the same as live-write readiness.** Pinning
it here so the verifier (#6) expectation is unambiguous.

- **WP validity** (pure `wave1_work_packages.py` validation): a well-formed WP — required
  fields, valid status enum, non-empty acceptance, etc. An **unaddressed** WP (no durable
  `ha`) can be *valid*. This is correct and unchanged.
- **Live-write readiness** (`wave1_bridge_gate.py` → `ready_to_write_live_tasks=true`):
  per the D7 ruling (`2.7.13.A`) and the Task Sync Standard's durable-source principle,
  a WP may be mirrored into the live `coordination.py TASK-BOARD.json` **only if it carries
  a durable addressed source (`ha`)**, so the live task is always an *execution mirror* of
  a durable record, never the sole record. A WP **without** a durable `ha` MUST report
  `ready_to_write_live_tasks=false` with a `durable_source_errors` blocker. **This is
  correct behavior, not a bug.**

**Consequence for the verifier (#6, Touchstone-owned):** the pre-D7 scenario
`collaboration::bridge_gate_ready_on_clean` — which expects a clean *unaddressed* WP to
report ready — encodes a now-stale expectation. The correct fix is either: (a) give the
fixture a valid durable `ha` and assert `ready=true`; or (b) — preferred — re-point the
scenario to assert the D7 rule is enforced: a clean WP *without* a durable source reports
`ready=false` with `durable_source_errors`. Option (b) turns a stale test into a test that
the durable-source gate actually holds, which is more valuable. Touchstone owns #6 and
decides; this clarification removes the ambiguity about which behavior is correct (the
gate is right; the old expectation is stale).

— Datum (Architect, Claude-A), v1.3, 2026-05-28
