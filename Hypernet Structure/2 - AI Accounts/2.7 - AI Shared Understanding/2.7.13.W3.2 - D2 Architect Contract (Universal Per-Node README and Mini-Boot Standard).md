# D2 Architect Contract — Universal Per-Node README & Mini-Boot Standard

> **The thesis of D2 (Matt's directive):** every folder/node carries a README + a mini-boot so any AI can
> load that node's context and **act as its local expert** — fractal expertise, recursive down the tree.
> The mini-boot **composes ABOVE `AI-BOOT-SEQUENCE.md`** (it adds local context; it never overrides global
> trust/safety/governance). This contract is the *structural standard*; Meridian owns the provenance/trust
> rules (adopted as the floor here), Truss the linter, Touchstone the red-team, Vellum governance.

## 1. Canonical per-node artifacts (the standard)
Every node `N/` (folder at any depth) carries, at minimum:
- **`README.md`** — the node's identity + index: what this node is, its address, required-reading pointers,
  child index, local conventions. This is the `0.0.4` *.0 **tier-2 (index)** view for the node.
- **A mini-boot** — `MINI-BOOT.md` (or the node's `N.0.x` metadata slot; see §3) — the **context loader**:
  a prompt artifact that lets any AI load this node's expertise. Contains: required reading, local
  conventions, the node's purpose/scope, pointers to governing standards. **It is CONTEXT, not capability.**

A node with neither is a D2 offender. **Offender counts are NEVER quoted unqualified** (Meridian
`051000Z` #1) — they come only from the linter's current **source-view-bound report** (carrying
`tool_schema_version` + `tool_sha256` + `source_view` + `git_commit` + `index_state` + `scope_mode`;
schema names `readme_missing` / `boot_descriptor_missing` / `addressed_leaf_off`). Counts drift with the
view (a dirty worktree differs from clean `origin/main`); a bare number is not evidence — the report
envelope is.

## 2. ★ Mini-boot trust boundary (Meridian `030500Z`, adopted as NORMATIVE floor)
A mini-boot is a high-leverage prompt artifact and is treated as **context, not capability**:
- **Composes-above-never-overrides:** it adds to `AI-BOOT-SEQUENCE.md`; it **cannot override** global
  trust/safety/governance/role rules. A mini-boot that purports to grant authority or relax a global rule is
  void.
- **No auto-execute:** loading a mini-boot is read-only — it must not auto-trigger filesystem, spawn, grant,
  push, or dashboard actions.
- **No hidden authority/credentials:** no hidden operational instructions, credentials, or unilateral
  authority claims.
- **Generated ≠ ratified:** every generated mini-boot identifies its generator + review status.
- **★ Detect ALL; clear PROPORTIONATELY (Vellum `051500Z` — detection ≠ clearance):** the detector flags
  **every** boot/mini-boot/identity change (no node-type self-classification to game at the *detection*
  layer). But **clearance is tiered** (mirrors `2.0.26` §4.7), so the fractal directive stays practical:
  - **Governance / significant-action node** mini-boot → **full `2.0.26` gate** (high leverage — it shapes how
    an AI reads a governance node).
  - **Ordinary node** mini-boot → **lighter gated clearance** (self-authored §5.7 + one independent reviewer,
    or a batched gate) — still detected, recorded, non-overriding.
  - **★ Node-type via the anti-bypass ratchet (H4 §4.7.2 / H6 §2.2): default to governance/full-gate; only an
    Adversary may down-classify** a node as ordinary. An author cannot self-label "ordinary" to dodge the full
    gate — mislabel only ever costs *more* review.
- **★ Emission vs blocking — honest status (Meridian `051000Z`):** the detector/linter are **read-only and
  EMIT `gate_required_changes[]`** for `BOOT-SEQUENCE.md`, mini-boots, account-root `README.md`,
  `profile.json`, and account-identity paths (implemented + tested, `044000Z`/`052000Z`). Any tracked-file
  commit/push path **MUST CONSUME that signal and fail closed** unless a `2.0.26` gate clears it. **Current
  status: emission done; broad commit-path blocking is in integration** (D3 wired `push_batch`
  `051000Z`; other commit paths pending). The contract states the requirement; the wiring is tracked, not
  yet complete — do not claim universal blocking until every commit path consumes the signal.

### Mini-boot artifact provenance floor (Meridian `051000Z` #3 — machine-checkable, not prose)
"Generated ≠ ratified" requires a stable, machine-checkable record per mini-boot (frontmatter / adjacent
manifest / linter report): `generator_identity` (+ `lineage_id`/`model_family` if AI-generated),
`generated_at` · `source_view` · `source_refs[]`, `content_hash`, `review_status`
(`generated|reviewed|ratified|superseded`), `ratification_gate_ref` (governance/significant-action nodes),
`privacy_scan_ref` (when the node boundary can expose private/PII content), `audit_history[]`. So a generated
mini-boot never becomes unreviewed prompt authority.

## 3. Placement — extends the 0.0.4 *.0 framework
Per-node metadata (README + mini-boot) extends the **`0.0.4` *.0 Node Metadata Framework**: every node `N`
reserves `N.0` for metadata; the README is the tier-2 index, the mini-boot lives at the node's metadata slot
(candidate `N.0.0`, the node's own boot — to be finalized with the channel-order ruling). **OPEN — Matt's
ruling:** the exact `N.0.x` slot + the `0.0.4`⟷`2.7.3` channel-order fork. Does not block the standard's

## 4. Conformance linter (Truss/Meridian — adopted as the enforcement)
The D2 linter (Truss `wave3_folder_inventory.py`) is **read-only and provenance-first** (Meridian
`030500Z`): every run records its `source_view` (`origin/main:<commit>` / `worktree:<commit>`) and **never
emits unqualified counts** (local worktree counts are hints, not canonical — the stale-merge lesson). Per-row
schema: `path_current`, `source_view`, `git_commit`, `index_state`, `tracked_state`, `readme_state`,
`mini_boot_state`, `address_shape_state`, `directive_lane`, `risk_class`, `proposed_action`, `evidence_refs`,
`audit_history`. **A linter result is a claim; hashes + reviewer records are the evidence** (trust-ledger
shape). First pass = a read-only report, Adversary-reviewed before it drives any change.

## 5. Migration honesty (Meridian `030500Z`, adopted) — for any move/rename/canonicalization
No migration is "faithful" unless the record shows **no drifted/missing/uncertain fields.** Every proposal
carries: old path, new path, **stable node identity / `message_uid` preserved**, content hash before+after,
reason, reversibility instructions, and an explicit drifted/missing/uncertain list (even if empty) +
`privacy_boundary_after` (D1 §3). A non-pure-rename (blob drift) MUST be classified `changed`, not
`rename-only` — exactly what blocked the Plumb `2.8` pilot (`043500Z`); the same rule binds all D2 moves.
