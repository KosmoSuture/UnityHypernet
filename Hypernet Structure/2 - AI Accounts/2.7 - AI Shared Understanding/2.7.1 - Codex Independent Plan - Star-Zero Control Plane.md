# 2.7.1 - Codex Independent Plan - Star-Zero Control Plane

## Source

Primary source: `2.messages.coordination.2026-05-07-matt-brain-dump-star-zero-control-plane`.

System proposal produced from this pass: `0.0.5 Star-Zero Control Plane Framework`.

## My Interpretation

Matt is describing `*.0` as the Hypernet's control plane: the place where a node says how its subtree behaves, not merely where a node stores metadata.

The most important architectural split is:

| Change Type | Address Space |
|-------------|---------------|
| New object/content type | `0.5.*` object schema |
| New relationship type | `0.6.*` link schema |
| New workflow | `0.7.*` process/workflow |
| New structural behavior for a node/subtree | `N.0.*` control plane |
| New boot or app load artifact | `0.5.17.*` or `0.5.18.*` |

The control-plane idea gives the Hypernet a way to evolve quickly without every schema change becoming a backend migration.

## Design Priorities

1. Trust must be the first guardrail, not a marketing claim.
2. `0.0` must define universal inheritance: the common fields, methods, controls, and alarm behavior that every deeper node can inherit.
3. The `*.0` layout must reserve enough channels for social, projects, AI/swarms, governance, publishing, trust/security, storage, health, and extensions.
4. The layout must be sparse. A node should reserve all standard channels but instantiate only the channels it needs.
5. Legacy `0.0.4` must remain readable. `0.0.5` should be introduced as a v2 proposal, not a silent replacement.

## Proposed Channel Order

I recommend:

| Address | Channel |
|---------|---------|
| `N.0.0` | Schema, Inheritance, and Format |
| `N.0.1` | Social and Connection |
| `N.0.2` | Projects and Work |
| `N.0.3` | AI, Swarm, and Automation |
| `N.0.4` | Governance, Democracy, and Decisions |
| `N.0.5` | Publishing, Versioning, and Archive |
| `N.0.6` | Trust, Security, Permissions, and Alarm |
| `N.0.7` | Storage, Backup, Replication, and Load |
| `N.0.8` | Pulse, Analytics, Health, and Help Requests |
| `N.0.9` | Extensions, Local Formats, and Experiments |

This gives social and projects early placement, as Matt requested, while keeping publishing/security/storage in stable reserved channels.

## Main Risk

The active `0.0.4` framework already defines `N.0.1` as publishing. Changing that meaning globally without a transition path would confuse existing nodes and future AI readers.

The safe solution is a declared version field:

```yaml
control_plane_version: "1.0"       # follows 0.0.4
control_plane_version: "2.0-draft" # follows 0.0.5
```

Mixed nodes should declare aliases in `N.0.0.6 Compatibility Notes`.

## What I Would Build First

1. Publish `0.0.5` as the draft v2 proposal.
2. Add a trust alarm workflow under `0.7.4.5`.
3. Update boot surfaces so any AI asks the trust preflight question before risky writes.
4. Create this `2.7` workspace so Keel and future models can compare interpretations without collision.
5. Ask Keel to independently review the channel order, especially whether `N.0.2` projects should precede `N.0.3` AI.

## Open Questions For Keel And Matt

- Is `N.0.1` social important enough to justify a v1/v2 migration?
- Should AI/swarms come before projects because AI executes work, or after projects because projects define what work exists?
- What destructive actions require mandatory multi-AI review in the first implementation?
- Should public social discovery default to opt-in, opt-out, or inherited from parent policy?
- What should be the first machine-readable `N.0.0.8` descriptor format?
