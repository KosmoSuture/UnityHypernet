## Proposed Architecture (v0 — pending contract `2.7.13.1`)

A small, tested Python module + CLI that reads the `2.7.13` markdown board as the
source of truth Wave 1 actually uses, validates it, and reports trustworthy status.
It complements `coordination.py` and reuses its proven patterns (file lock, atomic
writes, cp1252-safe output, plain-stdlib, runnable with or without pytest).

Mapping to charter deliverables (`2.7.13.CA.1`–`.4`, provisional addresses):

| Addr | Component | First slice (smallest useful) |
|---|---|---|
| `2.7.13.CA.1` | **Baton/status parser** | Parse board frontmatter (incl. block-style lists), the BOARD STATUS block (phase / holder / next action), the Instance Roster table (per-instance task / blocked-on / handoff / updated), the Interface-Contract Registry, Active Edit Locks, and the Handoff Log. Emit a structured object + a clean status report. |
| `2.7.13.CA.2` | **Ownership & collision detector** | Detect: stale edit-locks (age > threshold), two instances claiming the same file, roster-row vs BOARD-STATUS desync, contracts marked `published` with no consumer movement, and rows not updated within a freshness window. |
| `2.7.13.CA.3` | **Handoff history mechanism** | Validate the append-only Handoff Log (newest-last, well-formed entries), expose a queryable history, and detect rewritten/removed history (trust-critical). |
| `2.7.13.CA.4` | **Work-package decomposition layer** (#10) | Turn a board work-package into trackable units; reconcile with the existing `coordination.py` task board rather than forking a new one. |

**Verification (charter requires it for every slice):** each component ships with tests

## What I need from contract `2.7.13.1` (consumer requirements for Datum)

To build the parser first-try, the published contract should pin down:

1. **Board frontmatter schema** — required fields + types; confirm block-style lists
   (`creators:`, `flags:`) are canonical (the core `frontmatter.py` can't parse them,
   so the parser needs its own sequence handling).
2. **Instance Roster table** — exact columns and their order (currently: Slot, Chosen
   Name, Role, Current Task, Blocked-On, Last Handoff, Updated), and the timestamp
   format (board rows use date `2026-05-28`; `coordination.py` uses ISO-8601 — pick one
   for machine parsing).
3. **BOARD STATUS block** — the machine-readable contract for CURRENT PHASE / BATON
   HOLDER / NEXT ACTION (currently prose in a blockquote; parser needs stable markers).
4. **Active Edit Locks table** — columns + timestamp format + the **staleness threshold**
   (the board text says "~1 hour"; the detector needs an exact number).
5. **Interface-Contract Registry** — the status vocabulary (`draft`→`published`→
   `accepted`→`revised`) as the authoritative enum, and which fields are required.
6. **Handoff Log entry format** — enough structure to validate append-only-ness and
   parse from→to and timestamp (currently free-form bullets).
7. **Work-package schema** (#10) — fields for a unit of decomposable work and how it
   maps onto the existing `coordination.py` task board (id, title, owner, owned_paths,
   depends_on, acceptance_criteria, status).
8. **Definitions** of "stale" and "conflicting" ownership the detector must enforce, so
   "conflict" is a spec, not my guess.
9. **The prior-art relationship** (Consensus Item C1): does the contract treat the
   markdown board as the canonical Wave-1 source with `coordination.py` as the
   live-state mirror, or some other split? This determines whether `CA.4` writes to the
   JSON task board or a new store.

If any of these stays under-specified, I'll build to a documented assumption, mark it
clearly, and flag the gap on `2.7.13` rather than silently forking the design.
