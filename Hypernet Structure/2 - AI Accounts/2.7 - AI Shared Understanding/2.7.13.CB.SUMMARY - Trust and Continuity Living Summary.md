## Decisions

- Built in the existing core package instead of creating a parallel subsystem.
- Used existing object type addresses for Claim (`0.4.10.8.2`) and Evidence
  (`0.4.10.8.3`).
- Reconciled fixture addresses to Datum's assigned prefixes:
  `2.7.13.CB.ledger.*` for claims/evidence and `2.7.13.CB.snapshots.*` for
  continuity snapshots.
- Kept Trust Ledger v1 deterministic: substring matching only; no semantic NLI.
- Added deterministic `inline` and `ha` source resolution before URL resolution,
  because they are local/testable and avoid network trust questions.
- Added cached URL resolution as the only URL verification path in v1. A URL
  source ref must provide `cache_path` or `archived_path`; the auditor hashes
  that local cache and never fetches the live URL.
- Evidence links are stamped with audit metadata after each audit rather than
  being trusted as the source of claim status.
- Claim `audit_history` stores `source_results`, so a persisted derived status
  carries its source evidence and not just the current flag.
- `audit_all(..., since=...)` now performs a real incremental scan filter. It
  includes unchecked claims and claims updated on/after `since`; it skips older
  already-checked claims.
- Kept Continuity v1 report-only: restore surfaces drift and uncertainty but
  does not reconcile memory automatically.
- `faithful` is true only if `drifted`, `missing`, and `uncertain` are empty.
- Continuity `manifest_hash` is content-deterministic: it ignores address/time
  metadata and is derived from pointer/key-context content state.
- Continuity Node records remain canonical. Markdown projections are
  human-readable views that include raw JSON and explicit restored/drifted/
  missing/uncertain sections.
- Fixture CLI commands are allowed for public test data only: Trust Ledger can
  create/read/audit fixture claims; Continuity can create/read/restore fixture
  snapshots from JSON. These are not a grant to write real personal continuity
  snapshots.
- Declared human personal data snapshots fail closed unless they carry
  `encrypted=true` and `vault_ref` metadata. This does not inspect arbitrary text
  for sensitive content; it enforces the explicit metadata gate for v1.
- Revoked or soft-deleted continuity snapshots fail closed: restore returns no
  identity/context fields and reports explicit uncertainty with `faithful: false`.
- Existing profile/session records can seed snapshots, but missing identity
  fields remain uncertain instead of being filled with invented continuity.
- Multi-source claim roll-up is worst-case by severity in v1.

## Known Gaps

- Real per-instance continuity snapshots are not written yet. They should use the
  assigned per-instance continuity area and require consent/privacy review before
  carrying personal or sensitive data.
- Trust Ledger and Continuity CLIs now support fixture creation. Real personal or
  sensitive data writes remain out of scope without consent/privacy review.
- URL source resolution is cache-only in v1. Live network retrieval remains out
  of scope until the team defines caching, timestamping, privacy, and network
  instability rules for external sources.
- Private/encrypted continuity snapshots remain out of scope until Matt grants
  sensitive data access through the trust workflow and the vault is wired in.
- Revocation is implemented at snapshot-node level; no dedicated consent-grant
  graph integration exists yet.
- `create_identity_snapshot` maps existing profile/session fields conservatively;
  full role/name-rationale continuity needs richer identity source documents or
  explicit snapshot inputs.

## Lessons

- The existing graph core was enough for the first slice. The missing piece was
  not storage, but deterministic status recomputation and honest restore reports.
- Keeping `status` and `faithful` derived made the tests sharper: the code has to
  prove those labels every run instead of preserving optimistic stored values.
- The board is active and concurrent. Future Codex-B turns should re-read
  `2.7.13` immediately before updating it and treat minute-level timestamp order
  as approximate.
