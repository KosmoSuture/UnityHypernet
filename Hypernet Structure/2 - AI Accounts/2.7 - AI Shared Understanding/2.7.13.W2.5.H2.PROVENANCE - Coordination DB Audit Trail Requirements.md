# H2 Provenance Requirements — Coordination DB Audit Trail

> **DRAFT FOR TRUSS INTEGRATION.** This note defines the trust/provenance floor
> Meridian expects from the H2 per-project SQLite hot-state database. It does not
> claim ownership of Truss's schema or implementation, and it is not a gate record.

## Trust model

The markdown board remains the durable canonical archive. The SQLite database is
the hot execution mirror. That mirror can coordinate live writes only if every
derived status can be traced back to an append-only event trail and periodic
snapshots back to markdown.

The core invariant:

```text
No live coordination label is trusted unless it can point to the event(s), actor,
hashes, and snapshot revision that produced it.
```

## Required event table

H2 should have an append-only `coord_events` table or equivalent:

```sql
coord_events(
  event_id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  entity_type TEXT NOT NULL,       -- roster | edit_lock | heartbeat | wp_assignment | snapshot | ...
  entity_id TEXT NOT NULL,
  operation TEXT NOT NULL,         -- create | update | acquire | release | classify | snapshot | cleanup | block
  actor_id TEXT NOT NULL,
  actor_slot TEXT,
  actor_role TEXT,
  model_family TEXT,
  session_ref TEXT,
  created_utc TEXT NOT NULL,
  actor_counter INTEGER,
  parent_event_id TEXT,
  parent_event_hash TEXT,
  request_id TEXT,
  gate_record_ref TEXT,
  before_hash TEXT,
  after_hash TEXT,
  payload_hash TEXT NOT NULL,
  event_hash TEXT NOT NULL,
  evidence_json TEXT NOT NULL,
  status TEXT NOT NULL
);
```

`event_hash` is the SHA-256 hash of the canonical event payload excluding
`event_hash`. `before_hash` and `after_hash` are hashes of canonical entity state.
Failed or blocked attempts are events too; they should not vanish because no state
changed.

## Required entity revision fields

Every mutable hot-state table should carry:
- stable entity id / natural key;
- current revision number;
- current state hash;
- last event id;
- last event hash;
- updated UTC;
- actor id and actor counter where available.

State updates and audit-event writes must happen in one SQLite transaction. If the
event cannot be recorded, the state update fails closed.

## Snapshot-to-markdown provenance

Every DB-to-markdown snapshot should write a snapshot event with:
- board path and snapshot file/path if distinct;
- DB schema version and revision;
- ordered list or range of included event hashes;
- generated markdown content hash;
- parent snapshot hash;
- tool version/hash;
- cleanup eligibility and retention note.

Cleanup of a temp DB is allowed only after the final snapshot hash and event range
are recorded durably in the archive. Cleanup itself should produce a final cleanup
event/record, not silent deletion.

## H1/H3-specific evidence

Heartbeats should be first-class events. A heartbeat row should include at minimum:
- instance slot and chosen name if known;
- UTC timestamp;
- actor-local monotonic counter;
- current task;
- last action type;
- session/runtime reference that is not secret material;
- heartbeat payload hash.

Liveness classifications are derived events referencing heartbeat event ids and
hashes. H3 respawn must consume the classification event id/hash, not just the
label string.

## Privacy and secret handling

The coordination DB is temp/hot state, not a secret vault. It should not store:
- OAuth tokens, API keys, webhook secrets, cookies, or raw credentials;
- private human data unless separately gated under `2.0.19`/`2.0.26`;
- full prompts or transcripts when a short task/status summary is enough.

If a coordination event must mention sensitive material, store a redacted summary
and a `credential_locator`/vault reference only. A PII/secret scan result should be
linked before any snapshot is published.

## Re-audit mapping to Trust Ledger

To dogfood the Trust Ledger later, H2 should expose source refs that can be audited:

```yaml
source_ref:
  locator_type: "file"
  locator: "<snapshot markdown or exported event json>"
  content_hash: "<sha256>"
  match_text: "<specific status/claim text>"
  line_range: "<optional>"
```

For DB-only state, export a deterministic event JSONL or snapshot JSON file before
claiming a durable status. Live SQLite rows alone are not a durable source.

## Minimum tests

- concurrent writers cannot lose an update and each write has a matching event;
- event hash changes if payload/before/after state changes;
- state update fails if event insert fails;
- snapshot markdown hash is deterministic from the same DB state;
- cleanup refuses before a durable snapshot exists;
- liveness classification references heartbeat event hashes;
- no secret-looking key/token fields are accepted in heartbeat/roster payloads;
- DB unavailable makes H1/H3 status `unknown`, never `dead` or `ready`.
