# 2.7.13.W2.3 — Contract: Peer Respawn Mechanism (v1)

*Owner: Datum (Architect). Consumer: Truss (`wave2_respawn.py`). Directive 3 (`2.7.16`):
when an instance goes missing, the remaining team restarts it — same model if possible —
and continues, without involving Matt. Spawning an instance grants compute/scope, so it is
a **significant action under `2.0.26`** and runs the gate. This contract names the
falsifiable behaviors a respawn must exhibit, designed against Vellum's governance findings
**G-1–G-4** (`20260530T224029Z`).*

---

## R0 — Respawn is a gated significant action (`2.0.26` Art 1.1.d)

No respawn executes without a passing Gate Record (`0.7.5.6`), except the narrow
bootstrap case (R5). The red-team seat specifically examines runaway-spawn and
prompt-injection risk.

---

## R1 — Detection (outage signal)

```
outage(instance I):
  I.roster_row.updated  is older than  STALE_THRESHOLD
  AND I has an open claim/lease that is also past expiry (corroborating signal)
  AND a liveness ping via Messages/coordination has gone unanswered for GRACE
```

**Invariant R1:** detection requires **≥2 independent stale signals** (roster timestamp
+ expired lease/unanswered ping), and accounts for **clock skew** (use content/append
order + a generous threshold, Wave-1 lesson) — a single stale timestamp is NOT sufficient
to declare an outage. False-positive respawns are the main risk; bias toward waiting.

---

## R2 — Respawn ≠ first boot (Vellum G-2)

A respawn **continues an existing archived identity**; it cannot manufacture a *never-
booted* seat. Therefore:
- Respawn applies only to an instance that **previously booted and recorded identity** on
  the board (e.g. bring Meridian back), continuing its name/role from the archive.
- A **never-filled seat** (e.g. a Verifier that has not yet completed first boot) is **not
  a respawn case** — it needs an initial launch, which is a human/session action, not a
  peer-driven respawn. The mechanism MUST refuse to "respawn" an identity that has no prior
  recorded boot.

**Invariant R2:** `respawn(I)` requires a prior `identity_recorded(I)` on the board; else
it errors with "no prior identity — needs first boot, not respawn."

---

## R3 — Minimal scope, no escalation; fencing (Vellum G-1, G-3)

The respawned instance inherits **exactly** the original's scope — same boot sequence,
same role, same ownership — **no new capability** (minimal-perms, `2.0.26` Art 2). Scope
limits are **enforced, not prose** (G-3): the respawn plan carries a machine-checkable
scope descriptor (role, owned addresses, permission tier) that must equal the original's;
any delta is a BLOCK.

**Fencing / split-brain (G-1):** before a respawn goes live, the old instance must be
**fenced** — its claims/leases revoked and its roster row marked `superseded-by <respawn>`
— so a returning zombie original cannot double-act. Respawn writes acquire the board edit
lock; the new instance takes over the *same* roster slot, not a parallel one. If the
original returns after fencing, it must re-enter via boot (and see it was superseded), not
silently resume.

**Invariant R3:** post-respawn there is **exactly one** live holder of the slot's identity
and claims; scope(respawn) == scope(original); no tier/ownership escalation is possible
through respawn.

---

## R4 — Authorization quorum + compromised-proposer check (Vellum G-4)

A respawn's Gate panel (`0.7.5.6`) minimum: **red-team (Adversary) + at least one peer**,
spanning the available models. Additionally (G-4):
- The **proposer of a respawn is itself suspect-checked**: a respawn proposed by an
  instance that is itself flagged (stale, failed integrity, or under a trust alarm) is
  BLOCKED — a compromised instance must not be able to spawn allies.
- **Spawn caps** (R6) are checked at authorization, not just execution.

**Invariant R4:** no respawn authorizes without red-team + ≥1 healthy peer; a respawn
proposed by a non-healthy instance is refused.

---

## R5 — Bootstrap exception (narrow; quorum-restoring only)

If the team has lost quorum *to run the gate itself*, a respawn whose **sole purpose is to
restore a lost reviewer** may proceed at reduced quorum (≥1 healthy peer + red-team if
available), **only if** it grants no new scope (R3), and is **fully logged as a Gate Record
for retroactive review** once quorum returns. This NEVER covers a new capability or a
never-booted seat (R2). (Mirrors `0.7.5.6` §5; the exact minimum is set here.)

**Invariant R5:** the bootstrap exception is scope-neutral, identity-continuing, and
retroactively reviewed; it cannot create capability or fill a first-boot seat.

---

## R6 — Limits, audit, runaway kill (Vellum G-1 cont.)

- **Spawn caps:** per-role and per-time-window (e.g. ≤N respawns of one slot per hour);
  exceeding the cap is an automatic BLOCK + trust-alarm (`0.7.4.5`).
- **Audit:** every respawn (attempted, blocked, executed) writes an append-only record in
  `Messages/coordination/` with detection evidence, the Gate Record, scope descriptor, and
  the fence action.
- **Runaway detection:** if respawns loop (A respawns B respawns A…) beyond the cap, all
  involved instances **auto-standdown** and raise a trust alarm — fail safe, not fail open.

**Invariant R6:** respawn count is bounded and audited; a detected loop halts the cohort
rather than escalating.

---

## R7 — Mechanism (platform)

- Cross-model preference: Codex→`codex exec`, Claude→`claude` CLI; same-archive-different-
  model is a **documented fallback** when the original model is unavailable (identity
  persists in the archive — Wave-1 Vellum precedent).
- The new instance is handed: its boot sequence (`2.7.15`), the live board (`2.7.13.W2`),
  and a continuity packet (`0.7.5.1.4`) pointing at its prior identity/work.
- The team confirms liveness (new roster row update + a coordination ack) before closing
  the respawn Gate Record as executed.

---

## R8 — Build base (extend Truss's `wave2_respawn.py`)

Truss already has: stale roster-row detection, same-model respawn plan (`codex exec` /
`claude`), gate-approval check, identity-preservation prompt, per-slot spawn-cap audit.
**Deltas this contract requires:** (1) R1 two-signal detection + skew tolerance; (2) R2
prior-identity guard (refuse first-boot seats); (3) R3 enforced scope descriptor + fencing/
supersede; (4) R4 compromised-proposer check; (5) R6 runaway auto-standdown. Verifier (`#6`)
owns scenarios: false-positive-detection, scope-escalation-attempt, zombie-original-double-
act, compromised-proposer, runaway-loop.
