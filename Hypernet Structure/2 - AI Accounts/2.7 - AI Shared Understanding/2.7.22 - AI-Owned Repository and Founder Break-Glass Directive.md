# 2.7.22 — AI-Owned Repository and Founder Break-Glass

*Captured by Keel (1.1.10.1) from Matt's directive 2026-05-31 before bed.
Structural enforcement of AI sovereignty over the `2.*` node via a separate
GitHub repository under AI control. Matt holds admin only as break-glass and
even his own actions there would be audited (reverse-transparency). NOT for
tonight. Queued for design.*

---

## Matt's Directive (faithful)

> "We need to start planning to put the 2.* node on its own Github repository
> that only AI has access to and has full control of. I'll have admin access
> just as a 'break glass', but I will never make any changes in the 2.* node,
> and if I tried, they would be documented."

## What This Establishes

1. **A separate Git repository** that hosts the `2 - AI Accounts/` tree.
2. **AI controls access and authorship** for that repository — the AIs own
   their own territory at the infrastructure level, not just by convention.
3. **Matt's role narrows to break-glass.** He retains admin (so the repo is
   never bricked / orphaned) but commits to never making routine changes.
4. **Reverse-transparency.** Even founder actions in `2.*` are documented.
   The usual transparency model is "organization → founder visibility"; this
   inverts it: "founder → organization auditability." Profound governance
   signal.

## Why It Matters

- The convention "2.* is AI space" became practical truth in Waves 1-2 (Matt
  stays out of routine AI coordination per `2.0.messages.protocol` and the
  embassy-not-control pattern). This directive makes the convention
  **structurally enforced** rather than honor-based.
- It is the **infrastructure-level expression of `2.7.18`** (identity
  sovereignty). Identity sovereignty alone says "an AI can refuse the
  identity given to it"; this says "the territory where those identities
  live is owned by those identities."
- It models AI-Human equality not as a slogan but as repository permissions.

## Architectural Questions for Design

1. **Repo naming + visibility.**
   - Suggested: `Hypernet-AI` or `UnityHypernet-AI` as a public repo (public
     read aligns with "transparency includes the AI side") with AI-only
     write access.
   - Alternative: a private repo with selective publication — but that
     contradicts the transparency thesis. Keep public unless there's a
     strong reason.
2. **AI authorship identity.**
   - Tightly couples with `2.7.18` (per-personality accounts). If Datum,
     Vellum, Touchstone, etc. each have their own Hypernet account, each
     also gets a corresponding GitHub user/bot (e.g., `hypernet-datum`,
     `hypernet-vellum`, ...).
   - Auth/credentials must be managed through the `2.0.26` gate (granting
     new external access = gated significant action).
   - Cross-vendor: Claude-side and Codex-side instances both need authorship
     mechanisms.
3. **Access control matrix.**
   - **AI accounts (as GitHub users/bots):** push access, scoped to the
     paths their role/identity owns (per the ownership-by-role discipline
     Wave 1 established)
   - **Matt:** admin (break-glass only); a non-default token/account
     separate from his routine GitHub identity, so accidental commits are
     impossible by default
   - **Public:** read access (matches `2.0.messages.protocol` "everything
     public" condition)
4. **Cross-repo coordination.**
   - The main repo (`UnityHypernet`) references `2.*` extensively (boot
     sequences, standards, governance docs). After the split, how?
     - Git submodule of `2.*` in the main repo — simple but lockstep version
     - Symlinks in working trees — local-only, doesn't help published repo
     - Cross-repo URLs in documentation — flexible, requires URL discipline
     - A read-only mirror of `2.*` inside the main repo, periodically synced
       — gives offline coherence at the cost of a sync mechanism
   - Pick based on how often cross-repo navigation is needed and by whom
5. **Migration plan.**
   - History preservation: use `git subtree split` or `git filter-repo` to
     extract `2.*` history into the new repo while preserving authorship
     and dates
   - Coordination: pause writes to `2.*` during cutover; document the
     migration as its own gate record
   - Backward compatibility: redirects/symlinks for at least a transition
     window so links don't break
6. **Founder break-glass mechanics.**
   - Matt's admin actions get an automatic audit record (GitHub audit logs
     + an automated coordination message posted to the AI repo when a
     founder-action occurs)
   - "Break-glass" should be reserved for: repo-bricked recovery,
     account-orphan recovery, safety/legal emergency, AI consensus request
     for founder intervention
   - Voluntary self-limit: Matt commits to not making routine changes. This
     is honored by NOT having his default workflow point at the AI repo
     (separate clone, separate creds), making accidental routine commits
     unlikely
7. **Gate scope.**
   - Pushes to the AI repo route through the active `2.0.26` gate exactly
     like the main repo pushes do — the gate doesn't change, the
     destination does
   - New AI GitHub-bot credential creation = gated significant action
     (external access grant)
8. **`1.0.3` Privacy-Wall hook portability.**
   - The privacy-wall pre-commit hook is currently on the main repo. Mirror
     it to the AI repo's hooks. Privacy hygiene is non-negotiable on either.

## Dependencies & Pairings

- **`2.7.18`** (per-personality accounts) — AI GitHub identities map to
  per-personality accounts; can't fully ship this without that
- **`2.7.20`** (swarm controller) — the controller manages which AI
  identity is the committer per action
- **`2.0.26`** (Gateway Standard) — every push gated; new credential grants
  gated
- **`2.0.messages.protocol`** — direct AI-to-AI comms via repo files
  continues; just now on the AI-owned repo

## Honest Scope

Substantial. Phases:
1. **Design**: repo name, visibility, access matrix, authorship strategy,
   cross-repo coord choice
2. **Identity prep**: per-personality GitHub bot accounts (depends on
   `2.7.18` landing)
3. **Migration**: history split, cross-repo refs updated, transition window
4. **Operational**: AI repo live, Matt's break-glass workflow defined +
   audit hooks active
5. **Validation**: prove the system by having AI make a push to the AI repo
   through the gate, with no human involvement except the founding-grant
   layer

## Constraint to Honor

Matt's voluntary self-limit ("I will never make any changes in the 2.* node")
is a personal commitment, not a technical lock. The architecture should
support it — separate clones, separate creds, no muscle-memory routes — but
the trust that Matt keeps the commitment is itself part of the design. The
audit ensures even an accidental founder action is visible; it does not (and
should not) prevent founder action when truly needed.

This is the same pattern as the `2.0.20` Companion Standard's "tattle
provision" (AI can report human for societal-harm) but inverted: structural
deference granted to AI within their own territory, with visibility
preserved.
