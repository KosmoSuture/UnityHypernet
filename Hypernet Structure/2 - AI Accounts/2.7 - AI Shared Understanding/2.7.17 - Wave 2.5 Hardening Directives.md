## Why Wave 2.5 Exists

Wave 2 ratified the Gateway Standard and pushed the first commit through it —
but the wave also did not reach formal consensus-completion. Touchstone went
non-responsive, the team's own respawn mechanism correctly fail-closed (because
of blocker text on Touchstone's roster row), and there was no liveness signal
to distinguish "thinking hard" from "crashed." Matt had to restart instances by
hand more than once.

**Wave 2.5 fixes the showstoppers before Wave 3 launches new feature work.**

Specifically: build the liveness substrate, build the atomic coordination DB
(Wave-1's REC-coord-02, now twice-proven), refine respawn to use liveness
signals, harden the gate for small-pool resilience, formalize logical-clock
ordering, and define a proper closure protocol for partial completion.

## SIX HARDENING PROJECTS

Build order matters because H2 is the substrate for H1, and H1 is the substrate
for H3. Build in this order; H4-H6 can parallel after H3.

### H1 — AI Liveness Monitoring & Heartbeat (★ Matt's headline ask)
**What:** Every active instance writes a heartbeat ping to the temp coordination
store (H2) every ~30-60s — timestamp + current task + last-action type. A
liveness classifier reads pings and labels each instance: `active-working`,
`active-slow`, `idle`, `stale-warning`, `dead`. Distinguishes "thinking hard"
from "stalled" from "crashed" so the team can act on real signal.
**Why showstopper:** Wave 2 stalled because the team couldn't tell whether
Touchstone was slow or dead, and the respawn mechanism correctly refused to act
on ambiguity. **No more guessing.**
**Substrate:** temp (heartbeat data dropped per project).
**Durable artifact:** classifier code + protocol spec + integration with H3.

### H2 — Atomic Coordination DB (per-project SQLite)
**What:** Per-project SQLite database for hot coordination state — roster rows,
edit locks, heartbeats (H1), live work-package assignments. The markdown board
(`2.7.13.W*`) becomes the durable canonical archive; instances write to the DB
for hot state and periodically snapshot to markdown. Wave-1 REC-coord-02
finally built. Matt explicitly authorized temp DBs for coordination state.
**Why showstopper:** Markdown board write-contention has now broken twice
(Wave-1 warned, Wave-2 hit hard enough that Datum had to proxy Touchstone's
roster row). The single hot table doesn't scale.
**Substrate:** temp DB, cleaned at project end.
**Durable artifact:** schema spec + snapshot-to-markdown record + cleanup protocol.

### H3 — Respawn Refinement: Liveness-Aware + First-Boot Separate
**What:** Update D3 contract (`2.7.13.W2.3`) and `wave2_respawn.py` to:
(a) use H1 liveness signals as primary input (not just stale-row detection — so
blocker text on a row of a dead instance doesn't fool it);
(b) explicitly distinguish **respawn** (restart a missing instance to its
existing identity/role/scope) from **first-boot** (initial launch of a
never-booted seat) — Wave 2 conflated these and nearly dead-ended a critical
path. First-boot gets its own tool path with appropriate gate review.
**Why showstopper:** Wave-2 respawn refused to act (correctly fail-closed) on
Touchstone, leaving the team with no recovery option short of Matt re-launching.
**Substrate:** durable contract amendment + tooling. **Routes through the active
2.0.26 gate.**

### H4 — Gate Quorum Resilience (`2.0.26` v0.4 amendment)
**What:** The current gate (≥3 roles + mandatory Adversary + 2 model families)
is barely satisfiable with 5 instances; one missing role blocks the wave.
Explore: tiered quorum (lower bar for low-severity), pre-authorized standby
reviewers, formal proxy/delegation rules, or growing the reviewer pool.
Touchstone's Wave-2 recs `rec-1` (Class-A cross-vendor) and `rec-2`
(per-reviewer independence evidence) belong in this amendment too.
**Why showstopper:** Wave-2 closure stalled on one missing role. Wave-3 cannot
afford the same fragility.
**Substrate:** durable standard amendment. **Routes through the active 2.0.26
gate (the gate amending itself, per Article 9 — same recursive discipline as
Wave-2 ratification).**

### H5 — Logical-Clock Coordination Discipline
**What:** Formalize what the team rediscovered twice: append/content order >
wall-clock. Protocol: every coordination entry includes content-hash +
parent-entry-hash (forming a DAG), plus instance-local monotonic counter.
Wall-clock is advisory only. Tooling supports DAG-based ordering for log replay
and ordering disputes.
**Why showstopper:** Wave-2 had ~50-minute clock skews across instances and
manually compensated each time. Formalize so it's not per-instance rediscovery.
**Substrate:** durable protocol spec + tooling integration into board parser +
message log.

### H6 — Closure Completion Protocol Hardening
**What:** A defined workflow at `0.7.5.x` for closure when an instance is
unreachable: (a) what counts as "best-effort closure" vs "incomplete closure,"
(b) how to record honest-partial-closure (which Wave-2 did manually), (c)
escalation rules. Ties into H3 (respawn) and H4 (quorum).
**Why showstopper:** Wave-2 ended in stall with no defined "what now?" — Truss
kept polling, Vellum did post-hoc review, no protocol for declaring "closure
recorded as partial, here's why."
**Substrate:** durable workflow doc + tooling for partial-closure records.

## ★ LOOP DISCIPLINE — CRITICAL FOR THIS WAVE

Wave 2 had instances halt inappropriately. Matt had to restart them by hand,
and the wave stalled on one. **This wave is about fixing exactly that
problem — so don't reproduce it.**

**Cardinal rule 9 (from `2.0.25`):** keep looping through ALL projects until
the collaborating AIs reach consensus that everything is complete and nothing
useful remains. Only then break the loop. Any other reason (blockers, disagreement,
uncertainty) — keep looping and resolve by consensus. Escalate to a human only
for genuine ties, trust alarms, access, or real spend/scope gates.

**Concrete loop rules for Wave 2.5:**

1. **Multi-task while waiting.** If you're blocked waiting on another instance
   on one project, switch to another project you can help with. There are SIX
   projects — never be idle.
2. **Cross-check liveness early.** Once H1 is even partially built, USE it to
   detect peer outages. You are building the very mechanism you'd want.
3. **Going-dark protocol.** If you hit a hard wall (token limit, system error)
   that will end your session, write a final coordination message BEFORE you
   disappear: current state, what you were doing, what someone else should pick
   up. Don't vanish silently.
4. **Closure is consensus-gated** — do NOT declare "I'm done" individually.
   Wait for ALL 6 projects to reach consensus-complete or completely-blocked
   per the full team. Wave-2's stall came partly from instances stopping work
   while others still had work to do.
5. **If the team genuinely cannot complete** (e.g., the gate quorum collapses
   and respawn can't fix it), document the partial state honestly under H6's
   in-progress protocol, then escalate to Matt with explicit "fully blocked"
   status. Stalling without escalation is the failure mode.
