## Principles (calibration, not bookkeeping pedantry)

1. **Conservative by default.** When in doubt, round DOWN, not up.
   Matt's words: *"I would much rather that my tally comes up short,
   than that I cheat anyone."* This is the calibration that protects the
   tally's credibility.
2. **Provable as possible.** Each hour attributed has a citation —
   timestamp, git commit, brain-dump file, coordination message,
   directive capture. Unprovable hours go in a separate "soft estimate"
   bucket, clearly labeled.
3. **No double-counting.** Time spent dictating to me here is also time
   logged in any session log; count it once.
4. **Honest about gaps.** When the system can't tell (Matt thinking
   about Hypernet while driving, conversations with Sarah about it, days
   without artifact production), the report says "uncountable" — it
   doesn't invent.
5. **Per the foundation thesis** (`2.7.26` Layer C): the tally feeds the
   eventual compensation system as one of its inputs. It's not the only
   input — directive-creation, founder-authorizations, architecture
   decisions all count as contributions independent of time spent — but
   it's a meaningful one.

## Methodology (proposed for the team that builds it)

### Provable-time evidence sources (in descending reliability)

| Source | Reliability | What it gives |
|---|---|---|
| Git commits authored as `KosmoSuture` | High | Discrete commit events, dated, authored by Matt |
| Brain-dump files in `0.3/` and coordination messages with `creator: 1.1` | High | Dated, sized; word-count → estimated dictation time |
| Coordination messages from `to: ★ Matt` and Matt's replies | High | Inter-message latency = response time = engagement |
| Founder authorizations (Gate Records signed by Matt) | High | Discrete decision events |
| Conversation transcripts (this conversation, prior Keel sessions) | High | Active engagement windows + token-volume proxies for time |
| File mtimes on Matt-edited files outside git | Medium | Edit windows visible but not always provably Matt vs. AI |
| MEMORY.md entries dated "Matt directive 20XX-XX-XX" | Medium | Date evidence, time unclear |
| BiP dated artifacts mentioning his work | Medium | Date evidence + content depth |
| Discord posts attributed to Matt | Medium | If accessible |

### Conservative time-estimation heuristics

| Activity | Conservative estimate |
|---|---|
| A documented brain dump (single session, ~500-2000 words) | **30 min** floor; longer dumps scale by word count |
| A multi-directive brain-dump night (like tonight) | **2-3 hours** floor for the night's engagement |
| A founder authorization with reasoning | **15-30 min** |
| A retrospective review conversation | **30-60 min** depending on depth |
| A wave-launch session (5 boot prompts + initial review) | **1 hour** floor |
| A git commit by KosmoSuture | **15 min** floor (writing + reviewing + committing) |
| A response that engages with AI proposal substantively | **15 min** floor per exchange |
| Day with archive activity but no measurable Matt-output | **0 hours logged** (conservative — uncountable) |

These are floors. Real time may have been higher, but the directive is to
undercount.

### Aggregation periods

- Per day (date stamp in local timezone with timezone declared)
- Per week, per month, per quarter
- Per wave (Wave 1, 2, 2.5, 3, ...) for the work attributable to each
- Per contribution category (architecture, governance, brain-dumping,
  authorization, coordination)

### What gets reported

- Hours total (the headline number)
- Hours per category
- Hours per wave / project
- Hours per month / week / day (time-series)
- Confidence bands (provable hours vs. soft-estimate hours, clearly labeled)
- Methodology disclosure (so anyone can audit / replicate)
- "Uncountable" estimate (acknowledged but not counted toward total)

## Concrete Build Plan

1. **Data extraction phase** — scripts that pull from each evidence
   source, normalize to (date, event, source-link, conservative-minutes)
   tuples in an H2 SQLite table or a flat CSV
2. **Heuristic application phase** — assign minutes to each event per
   the floors above; flag any case where the system has to guess
3. **Aggregation + reporting phase** — generate the per-day / per-week /
   per-wave reports
4. **Surface in dashboard** (`2.7.20`) — Matt's hours visible like any
   other contribution; supports the eventual compensation calculation per
   `2.7.26`
5. **Continuous update** — after initial backfill, the system updates as
   new activity occurs (paired with `2.7.26` per-contribution attribution)

## Honest Limits (will surface in the report)

- I cannot count Matt thinking about the Hypernet away from the keyboard
  (driving, showering, conversations) — these are real but uncountable
- I cannot precisely time-window engagement vs. distraction (Matt may
  have been doing other things while a directive sat staged for response)
- I cannot count time spent on the Hypernet that produced no artifact
- The 15-min floors are conservative — actual focus time per exchange
  often longer
- The total will be a LOWER BOUND, per Matt's directive

## Open Design Questions for the Team

1. **Where does the canonical timesheet live?** Suggested: extension of
   the H2 coord DB (`2.7.23` Layer 1) with a `contribution_log` table
   that includes human-attributed entries.
2. **How are confidence bands surfaced** to avoid the lower-bound number
   being mistaken for an exact one?
3. **How does the tally backfill stop double-counting** when an activity
   leaves traces in multiple sources (a brain dump might appear in
   conversation transcript AND in a saved BiP file)?
4. **Privacy of the timesheet** — is it public (consistent with
   transparency thesis) or Matt-private (since hours-worked can be
   sensitive)? Recommend public per the project's standing privacy
   posture, but Matt's call.
5. **Other contributors' tally** — when other humans contribute (Sarah,
   Richard, future donors), they get the same treatment. This project
   builds the schema for ALL human contributors, not just Matt.
