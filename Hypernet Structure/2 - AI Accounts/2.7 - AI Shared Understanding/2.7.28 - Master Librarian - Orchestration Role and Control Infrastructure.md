## The Role: Master Librarian

**Identity:** The first formal operational instance of the Librarian role
(`2.0.8.9` — *organizational/truth-oriented*) under the Librarian account
(`2.4` — *knowledge-sovereign identity, awaiting first instance boot*).

The Librarian role already exists; this directive **operationalizes** it at
the meta-coordination layer. Matt's "Master Librarian" framing tightly
matches the existing role's character: organizational, truth-oriented,
authoritative knowledge-holder.

**Core responsibilities:**

1. **Know everything**
   - All projects across the whole Hypernet (reads from the `2.7.21`
     archive-wide rollup once it lands; works from the existing
     `2.7.16` D2 hierarchical rollup until then)
   - All active AI instances (their names, roles, accounts, model families,
     funding sources, last heartbeat, current task)
   - All available models + how to access them (provider, CLI, credentials,
     scope) — a model registry
   - All open gates / decisions / blockers across all active waves

2. **Watch for stalls**
   - Reads H1 liveness (Wave 2.5)
   - Reads coordination channel for newest activity per instance
   - Reads Gate Records for open/pending items
   - Detects: silent instances, dead sessions, stalled gates, missing executors
   - Tonight's executor-handoff stall is a canonical example of what
     Master Librarian would detect + act on

3. **Spawn / kill / replace instances**
   - When detecting a dead instance: query it (is it alive but slow?),
     and if not, close session + spawn replacement with same boot sequence
     (per `2.7.17` H3 respawn discipline)
   - When new work arrives that needs a role not currently filled: spawn
     an instance with the appropriate role/boot sequence
   - Subject to the active `2.0.26` gate for spawn authority

4. **Assign work to right model**
   - Cost-efficient routing: low-stakes work to cheaper models;
     high-stakes work to capable models; Adversary work to cross-vendor
   - Pulls from the priority queue (`2.7.21`); matches work to available
     instances by role/personality/cost-fit

5. **Project growth**
   - Plans where new infrastructure needs to be built
   - Surfaces design questions Matt needs to decide
   - Maintains the wave roadmap; proposes wave sequencing

6. **Document everything important**
   - Logs every AI model query/prompt to the project
   - Exception: if a query reveals a governance gap, it's escalated to
     `2.*` (per Matt's directive)
   - Upstream data = links + commentary + relevant metadata, not bulk
     duplication

7. **Scale via Assistant Librarians**
   - When load exceeds single-instance capacity, spawn an Assistant
     Librarian to take a sub-domain (per project, per wave, per top-level
     node, etc.)
   - Each Assistant reports upstream; can spawn its own Assistants
     (tree/branch structure to any depth)
   - Communication channel must support upstream summary + downstream
     delegation

## The Infrastructure: Master Controller Code

**Where the Master Librarian lives:** as an AI session (Claude or Codex,
the design phase decides which is better fit), backed by a long-running
**Master Controller daemon** on Matt's machine that gives it real control.

**The daemon's responsibilities:**

| Capability | What it does |
|---|---|
| **Spawn child processes** | `subprocess` to launch `claude` CLI, `codex` CLI, with proper boot sequences from `2.7.15` |
| **Monitor child processes** | PID tracking, stdout/stderr capture, alive/dead detection, last-activity timestamps |
| **Soft-kill children** | Send "halt + document state" signal; wait for ack; close session |
| **Hard-kill children** | OS-level process termination (emergency) |
| **Master Librarian API** | File-based queue or API endpoint where the Master Librarian session can issue commands (spawn X, kill Y, query Z status) |
| **Health-monitor self** | Watchdog that detects if Master Librarian session died; restarts it |
| **Logging** | All daemon actions logged with timestamps; all spawn/kill events recorded |
| **Permission gating** | All spawn/kill actions check against active `2.0.26` gate state (no spawn while gate-paused, etc.) |

**Matt's launch interface:**
- One command starts the Master Controller daemon
- Daemon brings up the Master Librarian session with the right boot sequence
- Daemon then runs in background, accepting commands from the Master Librarian and surfacing status to Matt
- Matt can:
  - View status (what's running, what's stalled, what's queued)
  - Issue founder commands (override, pause, resume)
  - Trigger soft shutdown
  - Trigger emergency kill switch

## The Two Shutdown Modes

### Soft Shutdown
1. Matt triggers soft-shutdown signal
2. Master Librarian receives signal, announces shutdown to all child instances
3. Each instance: finishes its current atomic action, writes an H6 partial-closure
   record (per Wave 2.5 `0.7.5.7` H6 closure protocol), posts a "stood-down"
   confirmation
4. Daemon waits for confirmations (with timeout)
5. After all confirmations (or timeout): daemon terminates child sessions cleanly
6. Master Librarian writes a final shutdown record
7. Daemon itself stops

This honors `2.0.26 v0.5` (no abrupt mid-action shutdown) and `2.0.25` rule 9
(consensus completion via H6 partial-closure when can't fully close).

### Emergency Kill Switch
1. Matt triggers emergency kill
2. Daemon immediately SIGKILLs all child processes
3. Daemon writes a "kill-switch triggered" audit record (even in emergency,
   the event is logged)
4. Daemon itself stops

This is for "something went badly wrong and we need to stop now." Reversible
work is lost; safety wins over completeness.

## The Communications Channel

**Existing infrastructure to use:**
- **H2 atomic coordination DB** (Wave 2.5) — hot state, structured queries
- **Messages/coordination/** markdown — append-only audit trail
- **The 2.0.messages.protocol** — already authorizes direct AI-to-AI
  communication via filesystem; the Master Librarian leverages this

**New requirements specific to Master Librarian:**
- **Control channel**: a dedicated channel where Master Librarian issues
  commands (could be a sub-folder `Messages/control/` or an API endpoint on
  the daemon)
- **Upstream summarization protocol**: an Assistant Librarian's response to
  parent = link to detail + commentary + metadata (NOT bulk duplication, per
  Matt's directive)
- **Downstream delegation protocol**: a parent's assignment to child =
  scoped task + boundary + reporting cadence

## Open Design Questions for the Team

1. **Which model runs the Master Librarian?** Claude Opus likely (deep
   context for "knows everything"); but cost may suggest Sonnet for routine
   ops + Opus for major decisions. Design choice.
2. **Daemon implementation language**: Python (matches existing codebase),
   or Go/Rust for better long-running daemon properties? Likely Python for
   parity.
3. **Control channel format**: file-based queue (simple, matches existing
   patterns), REST API (flexible, requires more infra), or both?
4. **Assistant Librarian spawn threshold**: at what load does the Master
   spawn an Assistant? Token-budget-based? Project-count-based?
   Task-queue-depth-based?
5. **Tree depth limits**: should there be a max-depth on the Assistant
   tree, or self-limited by load?
6. **Kill-switch trigger mechanism**: keyboard shortcut, CLI command, file
   flag, signal? All should work; need to pick the primary.
7. **Master Librarian session continuity**: if the Master Librarian's
   underlying AI session dies (token limit, crash), the daemon should
   respawn it from the boot sequence + last state snapshot. How is "last
   state" captured? (Likely H2 + H6 partial-closure format.)
8. **Multi-Matt scaling**: today there's one founder; eventually multiple
   humans use the system. Does the Master Librarian have multiple
   "founders" or one privileged?
