# 2.7.13.W2.5.H2 — Atomic Coordination DB

Owner: **Truss** (Codex-A, Substrate Engineer).

H2 provides the per-project SQLite hot-state layer authorized by `2.7.17`.
The markdown board remains the durable canonical archive. The SQLite database is
temporary runtime state for contention-prone coordination writes.

## Runtime Contract

- One SQLite database per active project; default runtime file:
  `Messages/coordination/wave25_coordination.sqlite3`.
- The runtime DB is ignored by `.gitignore` through `*.sqlite3`; do not commit it.
- All writers use SQLite transactions and WAL mode rather than competing on one
  hot markdown table.
- Any durable closeout must snapshot the DB back to markdown before cleanup.

## Schema

Implemented in `wave25_coorddb.py` schema version `2`:

| Table | Purpose |
|---|---|
| `project_state` | Project id, board path, active/closed status, and project payload. |
| `roster` | Hot roster rows keyed by `(project_id, slot)` with revision counters. |
| `edit_locks` | Active/released edit locks with claim and expiry fields. |
| `heartbeats` | Latest H1 heartbeat per `(project_id, slot)`. |
| `heartbeat_events` | Append-only H1 heartbeat history. |
| `work_packages` | Live work-package claims and status. |
| `event_log` | Append-only coordination event stream with content/parent hashes and state-audit fields; H5 consumes this for DAG replay. |
| `schema_meta` | Schema version metadata. |

Schema v2 also records current state hashes and last-event references on hot-state
tables, rejects secret-looking payload fields, and produces stable snapshot hashes
for unchanged state. The current implementation also uses atomic revision
increments, supports `expected_revision` conflict detection, expires stale edit
locks with audit events, and snapshots the full event log rather than the last
few events.

## Snapshot-To-Markdown

Command:

```powershell
python wave25_coorddb.py snapshot --output wave25_coordination_snapshot.md
```

The snapshot renders roster, edit locks, heartbeats, work packages, recent events,
and the cleanup protocol. It is the durable evidence record for temp hot-state.

## Cleanup Protocol

1. Run a final snapshot and verify the markdown projection contains the expected
   rows.
2. Keep the snapshot with the Wave-2.5 closure evidence.
3. Run:

```powershell
python wave25_coorddb.py cleanup --execute
```

This removes the runtime DB plus SQLite WAL/SHM sidecars. Cleanup is for temp
coordination state only; it does not remove durable board/messages/spec files.
