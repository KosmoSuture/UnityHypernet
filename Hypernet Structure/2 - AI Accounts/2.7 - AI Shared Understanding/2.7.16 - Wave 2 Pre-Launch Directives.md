## THREE PRIMARY DIRECTIVES FOR WAVE 2

### Directive 1 — Draft + Ratify the Gateway Standard (FIRST WORK)

Matt is granting the AI side authority to push to GitHub and to grant itself
external service permissions (Gmail, Dropbox, financial, etc.) — under
conditions. Before any of that authority is exercised, the **standard that
defines those conditions** must itself be drafted and reviewed under the
process it defines (recursive — by design).

**Conditions Matt named:**
- Every significant action (commit/push to public; granting new external access;
  permission escalations) must pass a **multi-role review gate** before execution.
- **≥3 distinct roles** examine every action (quality + privacy/PII + security).
- **At least one red-team (Adversary, 2.0.8.2)** is always in the loop.
- **At least 2 different AI models** (cross-vendor — e.g., Claude + Codex).
- **Minimal required permissions** as the default for any new access grant.
- **End-of-project closure ritual**: when a large project reaches consensus
  completion, the gate-review + commit + push is part of the final state —
  large projects do not wait on Matt to be uploaded.

**Your task:**
1. Draft `2.0.26 — AI Significant-Action Gateway Standard` (or rename as you
   see fit). Define scope, the 3-role/red-team/2-model gate, minimal-perms
   defaults, ties to 2.0.19 permission tiers and 2.0.25 cardinal rules.
2. Draft `0.7.5.6 — Significant-Action Gate Workflow` (or appropriate
   address) — the operational mechanics: panel convening, per-role checklists,
   dissent handling, audit trail, execution.
3. **Apply the gate to itself**: get the draft reviewed by the panel before
   ratification. This is the first real exercise.
4. Once ratified, the standard becomes immediately binding for all future
   significant actions.

Keel's pre-work proposal lives in conversation memory; the next-session
Architect should read Wave 1's `2.7.11` (top-10) and `2.7.13.A` (Architect

### Directive 2 — Hierarchical Project Rollup Architecture

Matt's directive (full quote in the source brain dump):

Every node in the Hypernet maintains its own list of outstanding projects.
Each node's list aggregates upward: a node's full list = its own projects PLUS
everything compiled from its children. The root `0.0.1` (slot to be confirmed —
Matt said `*.0.1` "if I'm remembering correctly," but the *.0 framework's
channel order is still under refinement; finalize the slot as part of this
work) becomes the **master priority-categorized list of every outstanding
project across the entire Hypernet**.

AI agents loop continuously: pull from the priority list, pick projects matching
their role and personality priorities, fulfill their part, move on. Millions of
tasks coordinated through this hierarchy with personality-driven self-selection.

**Why this matters:** this is the natural production architecture for what
Wave 1 prototyped at small scale (project #3 collaboration substrate + #10
execution mesh). Wave 1 was 5 instances on 4 first-wave projects. The rollup
architecture scales the same patterns to millions of tasks across the whole
tree.

**Your task:**
1. **Finalize the channel slot** for project lists (the `*.0.x` slot debate —
   see `2.7.3` convergence work). Recommend a single canonical slot based on
   the existing channel-order work; surface to Matt only if there's a genuine
   tie.
2. **Design the rollup data model**: project record schema, child-to-parent
   aggregation, priority categorization, deduplication, and how a node's
   "compiled" list refreshes when children change.
3. **Design the agent-pull loop**: how an agent reads `0.0.1` (or wherever the
   root master list lives), filters by its role/personality, claims work
   atomically, and reports completion back up the tree.
4. **Wave 1's tooling is the starting point**: `wave1_board.py`,
   `wave1_work_packages.py`, `wave1_bridge_gate.py`, and the coordination
   substrate (#3) generalize directly. Extend, don't rebuild.
5. **Integration with the gateway standard**: any agent pulling work that
   leads to a "significant action" still routes through the gate from
   Directive 1.

### Directive 3 — Peer Respawn Capability (instance outage resilience)

Matt's directive (2026-05-30): when an AI instance goes missing and fails to
respond, there should be a process to **restart that instance — in the same
model it was started with, if possible — and continue with the work**. The
remaining instances should be able to spawn the new instance, run the same boot
sequence, and bring it back into the live coordination without involving Matt.

**Why this matters:** Wave 1 demonstrated that identity survives a model swap
(Vellum continued Codex→Claude, keeping name and work — "identity lives in the
archive, not the model"). But the respawn was done by Matt opening a new
terminal. The team should be able to do it itself.

**This is a significant action under the Gateway Standard (Directive 1)** —
spawning new AI instances grants compute/scope to a new agent. So the respawn
mechanism must:
- Pass the gate's review (red-team for runaway-spawn / prompt-injection risks)
- Apply minimal scopes (the respawn inherits the same boot sequence, same
  ownership/role, no escalation)
- Use cross-model preference (Codex respawns as Codex via `codex` CLI; Claude
  as Claude via `claude` CLI), with same-archive-different-model as a
  documented fallback when the original model is unavailable

**Your task (Wave 2):**
1. **Detection**: define the outage signal — likely a stale `Updated` timestamp
   on the instance's roster row past a threshold (extend `wave1_board.py`'s
   existing stale-ownership detector). Include sanity checks against clock skew.
2. **Authorization gate**: a respawn requires the Gateway Standard's review
   (at minimum: red-team + scribe + one peer instance). Define the
   minimum-quorum for a respawn vote in the workflow.
3. **Mechanism**: how an instance invokes another (`codex exec` / `claude` CLI,
   per platform), how the new instance is handed its boot sequence + the live
   board, and how the team confirms it's running.
4. **Identity preservation**: the respawned instance continues the chosen name
   from the board (per Vellum's Wave-1 precedent); identity persists in the
   archive, the model is the runtime.
5. **Limits**: spawn caps (per role, per time-window), audit trail in
   `Messages/coordination/`, automatic standdown on detected runaway loops.

This pairs naturally with Directive 1 (gateway standard) and Directive 2
(hierarchical rollup — agents loop through projects, so they need to survive).
