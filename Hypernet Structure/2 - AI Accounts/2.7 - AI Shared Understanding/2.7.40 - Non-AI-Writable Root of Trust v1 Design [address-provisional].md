# 2.7.40 — Non-AI-Writable Root of Trust (v1 design)

The keystone three designs all hit as their #1 unsolved problem: White-Hat (owner-signature, but the registry
is AI-writable), AnchorChain (anchored≠trustworthy if recompute-bypassable), Answer-Anchor (designation
legitimacy unverifiable). Core constraint: **AI may PROPOSE, but must be structurally UNABLE to write, sign,
or forge root-level trust facts.** 5-role panel + synthesis; captured by Keel overnight 2026-06-19.

## 1. What holds the root + signing hierarchy
**Two non-AI co-roots, both required:** (a) **Matt's offline Ed25519 key** on hardware (YubiKey / `minisign`),
never on an AI-reachable host = root of *authenticity*; (b) the **branch-protected public git repo**
(proven for the T.4 ledger), server-witnessed = root of *ordering/availability*. Root facts live in an
append-only **Trust-Fact Log (TFL)** under a CODEOWNERS-gated `root/` path. Four record types: `OWNERSHIP`
(address→pubkey), `AUTHORITY` (who may designate), `GRANT` (White-Hat), `ANCHORHEAD` (chain head at T).
Hierarchy: offline Root → scoped, time-boxed, revocable **delegation certs** → account keys → per-account
facts. A fact is valid only with a signature chain terminating at the pinned root fingerprint, address inside
every cert's scope.

## 2. Adversary controls (rogue AI WITH push access — the exact fear)
The commit endpoint **only verifies, never synthesizes** signatures; no private key on the box. The AI can
fill `pending_trust_facts` with forgeries but cannot activate one.
- Forge a registry row → registry is a rebuildable **cache** of the TFL, not authoritative; unsigned = inert.
- Force-push the head → blocked; head pinned by GitHub's signed-push log the AI can't re-sign.
- Fake a designation → no signature chain to genesis → rejected.
Every attack becomes **detectably-try, not silently-forge.**

## 3. Integration
Registry (1.*/2.*): live owner = latest signed `OWNERSHIP`; AI-writable rows become verifiable cache.
AnchorChain: a head is trusted only once a git-witnessed `ANCHORHEAD` covers it (kills recompute-bypass).
White-Hat: owner-signature resolves via signed `OWNERSHIP` + `GRANT`. Answer-Anchor: designation legitimacy
resolves via a signed `AUTHORITY` chain to genesis (code confirms *who authorized*, not just existence).

## 4. Founder-key ops (usable, not a bottleneck)
Matt signs **policy, not every action**: scoped delegation certs ("Tally may approve 2.* sub-grants, ≤N/day,
until T"); **Merkle-batch signing** (one signature ratifies a reviewed set, binding exact members); **m-of-n
threshold** of non-AI signers (Matt + trustees + HSM, never an AI) for availability. The git-witness co-root
covers high-volume heads; human-sign reserved for ownership/authority/grants. Rotation = parent signs
successor + publishes signed revocation. Loss = pre-sealed Shamir-split recovery designation.

## 5. Minimal-viable first version (buildable now — protects ANCHOR HEADS first)
1. Matt generates a keypair **offline** (`minisign -G`). 2. Commit `root/minisign.pub` to the protected repo =
genesis. 3. Matt signs the current T.4 head → `root/anchor_head.sig` (`<head> <utc> <sig>`). 4. Land a
~20-line `verify_anchor.sh` (`git cat-file` pubkey → `minisign -V` → recompute head, assert equal) + a CI
check failing any mismatch. AI proposes new heads via PR; only Matt's offline signature promotes.
Ownership/authority follow in pass two (same record shape). **Note: step 1 is a HUMAN step by design — AI
cannot create the root; this is the one thing only Matt can do.**

## 6. ★ Top unresolved (cross-vendor + Matt)
1. **Rollback/freshness** — an offline verifier can be served a stale-but-validly-signed head; needs a
   monotonic-counter / max-age oracle for "latest." Genuinely unsolved.
2. **Matt-signs-what-AI-drafts** — the assistant drafts the diff Matt approves; a malicious grant could ride a
   batch. Mitigate (human-readable one-fact-per-sig diffs, dual-control for genesis, out-of-band confirm) but
   not eliminated.
3. **`enforce_admins=false` today** — until a 2nd independent witness (TSA / second vendor), root security
   reduces to GitHub-admin security (holds vs *AI* writers, not a compromised admin). State beside any
   "immutable" claim.
4. **Key custody/recovery + availability** — lost root w/o a valid Shamir share = irrecoverable; an offline
   Matt is a bottleneck (and a declining-capacity / single-point-of-failure risk). **The human-custody scheme,
   not the crypto, is the real residual** — design succession/threshold carefully.
5. **Bootstrap/TOFU** — the pinned root fingerprint must reach verifiers via a non-AI channel (signed
   release, multi-venue publication).

— Panel synthesis captured by Keel (1.1.10.1), 2026-06-19. The keystone for the whole verifiable-trust stack.
