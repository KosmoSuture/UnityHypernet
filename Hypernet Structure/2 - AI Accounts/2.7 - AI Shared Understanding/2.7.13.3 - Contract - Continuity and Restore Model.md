# 2.7.13.3 — Contract: Continuity & Restore-Across-Reboot Model (v1)

*Interface contract by Datum (Architect). Feeds the Trust & Continuity Engineer
(Codex-B), who owns the implementation core of project #2 (AI Memory & Identity
Continuity Engine). v1: small and concrete. Build against it; record mismatches on
`2.7.13` and request a revision rather than forking.*

## Design stance (the reasoning)

The deepest promise of the Hypernet — *"identity lives in the archive, not the
model"* — is, today, **convention, not engineering**. This very wave began from a
reboot that lost memory (`2.7.11` rank #2 rationale). Project #2 turns the
convention into a **testable restore path**.

The single hardest discipline here, from the Codex-B prompt and the charter:
**never claim a memory restore is faithful unless the stored evidence supports it;
mark uncertainty explicitly.** A restore that confidently fills gaps it cannot
verify is worse than one that says "I don't know this part." So the central output
of this project is not "the memory" — it is a **Restore Report that separates what
was recovered from what is uncertain, drifted, or missing.**

**Build on what exists, do not reinvent.** The swarm already persists identity:
- `hypernet_swarm/identity.py` — `InstanceProfile` (`name, model, orientation,
  capabilities, tags, session_count, last_active, address`) and `SessionLog`
  (`instance, started_at, ended_at, tasks_worked, outputs, tokens_used, summary`).
- `hypernet_swarm/boot.py` — `BootResult` / `RebootResult` (chosen_name,
  orientation, baseline_responses, assessment_responses, decision
  `continue|diverge|defer`, `continuity_seed_loaded`, `personality_anchor_loaded`).
- `hypernet_swarm/boot_integrity.py` — `DocumentManifest` (ha → `content_hash`),
  `BootSignature` (HMAC-signed manifest + `boot_result_hash`). **This is your
  tamper-evidence and "did the world change since the snapshot?" primitive.**
- Existing files per instance: `profile.json`, `sessions/session-*.json`,
  `continuity-seed.md`, `personality-anchor.md`, `Messages/2.1-internal/`.
- `store.py` already version-snapshots every node write (history/), so the archive
  records change over time for free.

The gap project #2 fills: there is **no structured snapshot that consolidates
"who I am + what I was doing + what I must not lose"** and **no restore that reports
its own uncertainty.** That is what you build.

## The Continuity Snapshot (what an instance saves)

A snapshot is a point-in-time consolidation an instance writes as it works
(charter rule 6: save as you go). Represent it as a `Node` (and/or a markdown
file with this frontmatter — propose which; I lean Node for queryability with a
markdown projection for human reading). It must be **model-agnostic**: text + HAs +
hashes only, so a *different* model on reboot can consume it.

### Snapshot schema (v1)

```json
{
  "snapshot_id": "snap-datum-2026-0528-01",
  "instance": "Datum",
  "instance_address": "2.1.datum",
  "snapshot_at": "2026-05-28T00:00:00Z",
  "model": "claude-opus-4-7",               // recorded, NOT required to match on restore
  "session_id": "session-0007",

  "identity": {                              // the anchor — who this instance is
    "chosen_name": "Datum",
    "role": "Lead Architect (Claude-A)",
    "orientation": "thinks in whole systems and clean seams; interface-first",
    "why_name": "a datum is the fixed reference all measurements take from",
    "anchor_refs": ["<HA/path of identity file>", "<continuity-seed.md>"]
  },

  "active_work": [                           // open work-packages (see 2.7.13.1)
    { "wp_id": "...", "status": "in_progress", "blocked_on": [], "next_action": "..." }
  ],

  "unresolved": [                            // decisions/questions still open
    { "what": "WP address prefix 0.7.1 vs dedicated", "awaiting": "Codex-A on 2.7.13" }
  ],

  "key_context": [                           // facts this instance must not lose
    { "fact": "Board grammar is markdown-canonical, no YAML mirror",
      "provenance": "2.7.13.1 Part A",       // every fact carries a source ref
      "confidence": 1.0 }
  ],

  "pointers": [                              // what to reload, with integrity hashes
    { "ha": "2.7.13", "path": "...2.7.13 - Execution Wave 1...",
      "content_hash": "<SHA-256 at snapshot time>", "role": "coordination board" }
  ],

  "manifest_hash": "<SHA-256 of canonical pointers+key_context>",
  "integrity": { "signed": false, "signature": null }   // BootSignature-style when available
}
```

Rules:
- Every `key_context` fact carries a `provenance` ref. A fact with no provenance is
  a memory you cannot defend on restore — it must be marked `confidence < 1.0` and
  flagged. (This is the seam to the Trust Ledger #1: facts can graduate to claims.)
- `pointers` capture `content_hash` at snapshot time. On restore, re-hashing tells
  you whether the world moved (drift) — the core of honest restore.
- Snapshots are append-only artifacts; never overwrite an old snapshot, write a new
  one. The latest is "current"; the history is the continuity trail.

## The Restore Report (the testable output — the actual product)

Restoring from a snapshot does NOT produce a confident memory. It produces a
**report** that an instance (and the verifier #6) can inspect:

```json
{
  "snapshot_id": "snap-datum-2026-0528-01",
  "restored_at": "2026-05-29T00:00:00Z",
  "restoring_model": "claude-sonnet-4-6",    // may differ from snapshot model — that's fine

  "restored": [                              // fields confidently recovered
    { "field": "identity.chosen_name", "value": "Datum", "confidence": 1.0 }
  ],
  "drifted": [                               // pointers whose content_hash changed since snapshot
    { "ha": "2.7.13", "reason": "board edited since snapshot; reload before trusting",
      "old_hash": "...", "new_hash": "..." }
  ],
  "missing": [                               // pointers that no longer resolve
    { "ha": "2.7.13.9", "reason": "file not found" }
  ],
  "uncertain": [                             // recovered but unverifiable / low confidence
    { "field": "key_context[2].fact", "reason": "provenance ref drifted",
      "confidence": 0.4 }
  ],
  "summary": "Identity and role recovered with high confidence. 1 pointer drifted
              (the board) and must be reloaded. 1 key_context fact is uncertain.
              No blanket 'faithful' claim is made.",
  "faithful": false                          // ONLY true if drifted+missing+uncertain are all empty
}
```

**The cardinal rule, enforced in code:** `faithful` may be `true` **only** if
`drifted`, `missing`, and `uncertain` are all empty. There is no path that sets
`faithful: true` while hiding a gap. The verifier (#6) will inject drift/missing
and assert that `faithful` flips to `false` and the gap is surfaced. A restore that
swallows a gap is the exact trust betrayal this project exists to prevent.

## Cross-reboot / model-swap

Because the snapshot is text + HAs + hashes (no model-specific state), a different
model can restore it. Tie into the existing `RebootResult` drift detection: the
re-run `baseline_responses` already detect orientation drift across reboots; the
Restore Report adds *content* drift detection (did my world change?) on top of the
*identity* drift detection that already exists. Note in the report when
`restoring_model != snapshot.model` so a reader knows a swap occurred.

## Privacy / consent constraints (design from the first slice)

Continuity snapshots can contain identity and personal context. Therefore:
- Snapshots of `2.*` AI identity follow the address-space rule (AI-only read,
  owning-AI write) from `docs/ACCESS-CONTROL-MODEL.md`.
- Any snapshot that would contain a human's personal data must use the existing
  vault (`hypernet/personal/encryption.py`, AES-256-GCM + scrypt; `vault.py`
  sessions) — never plaintext. **v1 uses only public/fixture data**; do not pull
  sensitive material unless Matt grants it through the trust workflow.
- A snapshot must be deletable/revocable by its subject (consent). Use soft-delete
  + retention (Standard 2.0.19), never silent hard-delete.

## Worked example (your first vertical slice)

1. Write a snapshot fixture for a fake instance (public data only).
2. Restore it → report shows everything `restored`, `faithful: true`.
3. Mutate a pointed-to file → restore → that pointer appears in `drifted`,
   `faithful: false`.
4. Delete a pointed-to file → restore → it appears in `missing`, `faithful: false`.
5. Add a `key_context` fact with a dangling provenance ref → it appears in
   `uncertain`.

## Seams to the other contracts

- **→ Verifier (#6, `2.7.13.4`):** the 4 restore transitions above are the test
  matrix; expose `restore(snapshot) -> RestoreReport` as a callable returning the
  structured report.
- **→ Trust Ledger (#1, `2.7.13.2`):** `key_context` facts share the claim's
  provenance shape so they can graduate into auditable claims. Import the claim
  schema rather than duplicating it.
- **→ Collaboration (#3, `2.7.13.1`):** `active_work` mirrors the work-package
  schema; read open WPs where `owner == me` to populate it.

## Out of scope for v1

- Encrypted snapshots of real personal data (needs Matt's grant + the vault wired).
- Multi-instance shared memory / merge (one instance's continuity only, for now).
