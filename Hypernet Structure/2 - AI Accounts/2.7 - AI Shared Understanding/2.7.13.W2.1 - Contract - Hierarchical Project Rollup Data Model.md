# 2.7.13.W2.1 — Contract: Hierarchical Project Rollup Data Model (v1)

*Owner: Datum (Architect). Consumer: Truss (`wave2_rollup.py`). This is the v1 interface
contract for Directive 2 (`2.7.16`): every node keeps its own outstanding-project list;
each node's compiled list = its own projects + everything rolled up from its children;
the root becomes the master priority-categorized list of every outstanding project. This
contract names the falsifiable behaviors the rollup must exhibit. It is slot-agnostic
(W2-D11) and privacy-preserving (Vellum R-1). Built on Truss's existing tooling — extend,
don't rebuild.*

---

## C0 — Slot binding (logical role, not a hard address) — W2-D11

The project list lives in a node's `*.0` metadata space at a **logical channel role**:

```
channel_role: "projects.work-queue"
```

The physical address (`N.0.x`) is resolved from **one registry entry**, not hardcoded:

```yaml
# channel-registry (single source; set when Matt ratifies the *.0 channel order, 2.7.3)
channel_roles:
  projects.work-queue:
    physical: "N.0.3"     # RECOMMENDED (2.7.3 synthesis "Projects and Work"); PENDING Matt
    status: "provisional" # provisional until 2.7.3 channel order is ratified
```

**Invariant C0:** no module hardcodes the numeric slot; all reads/writes resolve through
the registry. Changing `physical` re-points the whole system with one edit. (Truss's
N.0.2 baseline becomes a one-line registry change, not a code change.)

## C1 — Project record schema (node-local)

Each node `N` holds a list of project records at its resolved `projects.work-queue`
address. One record:

```yaml
project:
  global_id: "proj:<origin_node>:<slug>:<short-hash>"   # globally unique, stable
  origin_node: "N"                  # the node that OWNS this project (authoritative home)
  title: "..."
  description: "..."
  status: "open|claimed|in-progress|blocked|done|abandoned"   # 'done'/'abandoned' drop from rollup
  priority: 0..100                  # local priority; see C4 for cross-node categorization
  role_tags: ["architect","scribe","trust",...]   # for agent-pull matching (C5)
  personality_tags: [...]
  visibility: "public|restricted|private"   # MOST RESTRICTIVE wins on rollup (C3)
  significant_action: bool          # ADVISORY ONLY — never self-authorizing (C6 / R-3)
  claimed_by: "<agent>|null"
  claim_lease: { holder, acquired_at, expires_at } | null   # atomic claim (C5)
  created_at: "<UTC>"
  updated_at: "<UTC>"
  evidence: [ ... ]                 # flag-plus-evidence for status=done (Wave-1 D6)
```

**Invariant C1:** `global_id` is stable and unique across the whole tree; `origin_node`
is the authoritative home (a project appears in exactly one node's *own* list and is only
*referenced* upward by rollup). De-dup is by `global_id` (C3).

## C2 — Compiled list = own + children (aggregation)

A node's **compiled list** is derived, never hand-authored:

```
compiled(N) = own_projects(N)  ∪  ⋃ over children C of  rolled_up(compiled(C))
```

- `own_projects(N)` = records whose `origin_node == N`.
- `rolled_up(...)` applies the C3 visibility transform before inclusion.
- The root's compiled list is the **master list** (C4 priority-categorized).

**Invariant C2 (freshness):** `compiled(N)` is recomputed (or incrementally invalidated)
whenever any descendant's own list changes. A compiled list must declare
`compiled_at` + the set of child `content_hash`es it was built from, so staleness is
detectable (never a silent stale rollup). Recompute is content-addressed, not time-based
(clock-skew lesson, Wave-1).

## C3 — Privacy-preserving rollup (Vellum R-1) — REQUIRED

A naive rollup that copies child rows into a public ancestor **leaks private-node content
to the public root**. Forbidden. The rollup transform enforces visibility:

```
rolled_up(record, into_node N):
  eff = most_restrictive(record.visibility, origin_node.visibility, ancestor policy)
  if eff == "public":        include full record
  if eff == "restricted":    include redacted reference (global_id, priority bucket,
                             role_tags) — NO title/description/evidence — resolvable
                             ONLY by principals who pass the origin node's ACL
  if eff == "private":       include COUNT-ONLY contribution to the parent's priority
                             buckets (so the parent knows work exists) — NO id, NO content
```

**Invariant C3 (no-leak):** for any node `N` with `visibility=public`, `compiled(N)`
contains **no cleartext** title/description/evidence from any descendant whose effective
visibility is `restricted` or `private`. The most-restrictive rule composes down the whole
ancestor chain (a public project under a private parent is private in rollup). This is
machine-checkable: a meta-test asserts that injecting a private descendant project never
changes the cleartext content of a public ancestor's compiled list (only its counts).
**Ties to `2.0.19` (data protection) and the Permission Grant Provenance layer (Meridian).**

## C4 — Priority categorization at the root (master list)

The root's compiled list is **priority-categorized**, not a flat dump:

- Buckets: `critical | high | medium | low | someday` (derived from `priority` + age +
  blocker count; deterministic function, recorded).
- Within a bucket, stable order by (priority desc, age desc, global_id) — deterministic.
- **R-4 (starvation backstop):** any project whose age in its bucket exceeds a threshold
  is auto-escalated one bucket (logged), so low-priority work cannot starve forever. The
  escalation is visible in the record, not silent.
- The categorization function is pure + tested; the same inputs always yield the same
  buckets (no hidden state).

**Invariant C4:** the master list is a deterministic function of the deduped, visibility-
transformed union; re-running it on unchanged inputs is identical (verifiable).

## C5 — Agent-pull loop (atomic claim)

An agent reads the master (or any subtree's) compiled list, filters, and claims work:

```
pull(agent):
  candidates = compiled(scope) filtered by status==open
             ∧ role_tags ∩ agent.roles ≠ ∅  (or personality_tags match)
             ∧ visibility resolvable by agent
  pick highest-priority candidate
  claim(global_id): atomic compare-and-set on the ORIGIN node's record
                    (status open→claimed, write claim_lease with expiry)
  on success: work it; on lease expiry without progress: auto-release (reclaimable)
```

**Invariant C5 (atomic, no double-claim):** a claim is an atomic CAS on the **origin
node's** authoritative record (not on a rolled-up copy), with a lease that auto-expires
(stale-claim release — Wave-1 stale-ownership detector generalizes here). Two agents
cannot both hold an open project; the rolled-up references are read-only mirrors.

## C6 — Integration with the Gateway Standard (`2.0.26`) — R-2, R-3

Pulling/working a project is ordinary local state. But:
- **R-3:** a project's `significant_action` flag is **advisory only — never
  self-authorizing.** If completing a pulled project entails a significant action
  (commit/push, external grant, spawn — `2.0.26` Art 1.1), it routes through the gate
  (`0.7.5.6`) regardless of what the flag says. The flag is a *hint to pre-convene a
  panel*, not a permission. A record cannot grant itself an exemption.
- **R-2 (priority-power is gated):** editing priorities or the categorization function
  **at high nodes** (near the root, where it steers the whole swarm's attention) is itself
  a **significant action** under `2.0.26` — it is power over what every agent works on
  next. Define a node-height threshold above which priority/bucket edits require a gate
  panel; below it, local priority edits are routine. (Exact threshold: set with the
  channel order; recommend "any node whose compiled list is consumed by ≥K descendants'
  agents.") This closes the "quietly re-rank the master list to redirect the swarm" abuse.

**Invariant C6:** no pulled project can perform a significant action without its own Gate
Record; no high-node priority edit lands without a gate.
