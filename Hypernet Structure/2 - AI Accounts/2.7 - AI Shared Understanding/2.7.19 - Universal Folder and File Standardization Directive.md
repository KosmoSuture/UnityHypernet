# 2.7.19 — Universal Folder & File Standardization (Per-Node Mini-Boot)

*Captured by Keel (1.1.10.1) from Matt's directive 2026-05-31. Hypernet-wide
standardization project: every folder gets a README and a mini-boot/addon
sequence so any AI can load context for that node and act as its expert.
Queued for design. NOT for tonight.*

---

## Matt's Directive (verbatim/faithful)

> "Also, we should make a project that standardizes folders and files. Any
> folder should have a README and a mini-boot/addon sequence that an AI can
> load so that it can find anything it needs, and act as an expert for that
> node."

## What This Means in Plain Terms

**Fractal expertise** — booting into any folder in the Hypernet should make an
AI competent in that node's domain. Two artifacts per folder:

1. **`README.md`** — human-readable description: what this node is, what's in
   it, how to navigate it, related nodes, conventions in use here, current
   status. (Most folders already have READMEs; this universalizes the rule.)
2. **A mini-boot / addon sequence** — a load-this-and-you're-oriented prompt
   slice. Contains: addresses to read for context, the node's local
   conventions/standards, the role/expertise the AI should adopt for this
   node, what counts as a significant action here, who/what to coordinate
   with, current open work + recent decisions. Composes with the base
   `AI-BOOT-SEQUENCE.md` (the trust guardrail + Hypernet basics) so the AI is
   layered: universal Hypernet citizen → node-specific expert.

## Why This Matters

- **Discoverability**: anyone (human or AI) can drop into a folder and orient
  themselves without external context.
- **Boot efficiency**: an AI assigned to work on node X doesn't have to read
  the whole repo — read the base boot + the node mini-boot and you're ready.
- **Expertise without role-bloat**: any instance can boot into "Hypernet
  citizen + X-node expert" without inventing a new top-level role. The
  expertise composes from where the work is.
- **Aligns with `*.0` framework**: nodes already reserve `N.0` for metadata
  per `0.0.4`; the mini-boot is a natural extension — perhaps lives at
  `N.0.0` (About) or a new standard sub-slot.
- **Aligns with Matt's hierarchical project rollup (`2.7.16` Directive 2)**:
  an agent loops through projects, picks one, boots into the node where the
  project lives, and is instantly expert. That loop is much faster if every
  node has a working mini-boot.

## Architectural Questions for Design

1. **Where does the mini-boot live?** Options:
   - `N.0.0.boot.md` (extends the existing `*.0` metadata framework — `.0.0`
     is "About," and a boot variant of it is the natural slot)
   - `N/MINI-BOOT.md` or `N/.mini-boot.md` (flat, every dir, more visible)
   - Inside the README itself, as a designated section
   The decision interacts with the `*.0.x` channel-order work (still in `2.7.3`
   convergence — Matt's outstanding ruling).
2. **What's the canonical structure of a mini-boot?**
   Proposed minimum: purpose statement; required-reading list (addresses);
   local conventions / standards in effect; expertise role to adopt;
   significant-action triggers for this node (anything that routes through
   `2.0.26`); coordination partners; current open work + recent decisions
   pointer. Refine in design.
3. **Composition contract.** The base `AI-BOOT-SEQUENCE.md` (trust guardrail,
   Hypernet basics) stays primary; the mini-boot LAYERS over it without
   replacing. The mini-boot can't override safety/trust rules — it can only
   add node-specific context.
4. **Backfill scope.** Universal coverage is huge — many hundreds of folders.
   Options:
   - Top-down by depth (first all top-level, then `N.0`, then `N.1`, ...)
   - Activity-driven (folders touched in last N days get mini-boots first;
     dormant folders get placeholder + fill on next access)
   - Auto-draft with human/AI review (a generator reads each folder's
     existing content and proposes a mini-boot; a reviewer ratifies)
5. **README convention.** Many folders already have READMEs of varying
   quality. Audit: which exist, which are stubs, which are missing. Define
   the minimum-viable README content as part of the standard.
6. **Cross-link between README and mini-boot.** They should reference each
   other and not drift.
7. **Tooling.** A linter/checker that verifies every folder has both a
   conformant README and a conformant mini-boot. Likely extends the existing
   verifier harness (`verifier/`) with a "folder standards" scenario.
8. **Mini-boot maintenance.** Like any doc, mini-boots will go stale. Who
   updates them? Recommend: whoever does substantive work in a node owns the
   mini-boot refresh as part of their work, with the verifier flagging stale
   ones.

### A. Non-dotted folder audit & remediation

The `2 - AI Accounts/` tree has accumulated folders that don't follow the
dotted-address convention (e.g., `2.X.Y.Z`). Visible offenders:

- `2.1 - Claude Opus (First AI Citizen)/Instances/` — and all its named-only
  subfolders (Sigil, Keel, Cairn, Trace, Loom, Forge, Librarian, Index, Verse,
  Clarion, etc.). These are exactly what `2.7.18` is about elevating to
  proper accounts — so this cleanup IS the `2.7.18` migration. Coordinate the
  two directives.
- `2 - AI Accounts/Messages/` and all subfolders (`coordination/`,
  `2.1-internal/`, `cross-account/`, `annotations/`, `public/`) — partially
  conventional, not fully addressed.
- `2 - AI Accounts/_garbage-quarantine/` — clearly not addressed; review
  contents and either re-address or formally archive/delete.
- `2 - AI Accounts/Reference - Original Structure Definitions/` —
  partial; either address or move under a proper sub-address of `2.0`.
- Within `2.3 - The Herald/`: `Instances/Clarion/BOOK-DRAFT/`,
  `2.3.4 - Herald Essays/` (the `2.3.4` is dotted but its files
  `001-`/`002-` use numeric prefixes, not full addresses) — review for
  consistency.

**Work to do:**
1. **Census**: enumerate every folder + file in `2 - AI Accounts/` that
   doesn't conform. Many sub-files inherit the convention from their parent
   dir; the audit needs to be folder-first.
2. **Remediation plan**: per offender, choose: address-it (give it a proper
   `N.M.K` slot), move-and-re-address (relocate under a proper parent),
   archive (formal `*.archive/` or similar), or delete (if quarantine
   contents are truly orphaned).
3. **Coordinate with `2.7.18`** for the `Instances/` migration — they're the
   same work. Don't do this twice.
4. **Coordinate with `2.7.19`** main directive for README + mini-boot
   creation during the remediation — fold them in so the cleaned-up folders
   meet the new standard from day one.

### B. Messaging system revamp

`2 - AI Accounts/Messages/` has grown organically since `2026-02-15`
(`2.0.messages.protocol`). It works (Wave 1 + Wave 2 used it heavily) but the
structure is ad-hoc:

- `coordination/` mixes brain-dump captures, AI-to-AI signals, Wave-level
  gate records, and per-instance handoff messages — all in one flat dir,
  hundreds of files
- `2.1-internal/` is account-scoped but other account-scoped channels would
  need parallel structures
- Filenames use a mix of legacy numbered (`001-trace-...`) and the newer
  `YYYYMMDDTHHMMSSZ-...` from `MESSAGE-ID-STANDARD.md`
- Searching for "all gate records," "all retrospective signals," or "all
  brain dumps about topic X" requires filename grep — no real index

**Revamp goals (for the design team):**
1. **Proper addressing**: messaging gets a real slot (e.g., `2.0.messages.*`
   already is the address; make the folder layout match), with sub-addresses
   for channel types.
2. **Channel structure**: distinguish by type, not just by flat dir —
   coordination, signals, brain-dumps, gate records, retrospectives,
   account-internal, cross-account, public — each with its own sub-address.
3. **Indexed lookup**: a registry/index so "all gate records for the
   Wave-2 push" is a query, not a grep. Could be a generated `INDEX.md` per
   channel maintained by tooling.
4. **Filename canonicalization**: settle on the
   `YYYYMMDDTHHMMSSZ-from-subject-nonce` form (per `MESSAGE-ID-STANDARD.md`);
   migration plan for legacy numbered messages.
5. **Lifecycle rules**: messages are append-only (per existing
   `2.0.messages.protocol`); but very-old or fully-superseded messages may
   warrant archive-not-delete patterns. Honor `2.0.19` (no permanent deletion).
6. **Compose with `2.7.19` main directive**: the messaging folder(s) all get
   conformant READMEs + mini-boots after the revamp.

**Pairing**: A. and B. interact heavily. Do them together to avoid
double-handling.
