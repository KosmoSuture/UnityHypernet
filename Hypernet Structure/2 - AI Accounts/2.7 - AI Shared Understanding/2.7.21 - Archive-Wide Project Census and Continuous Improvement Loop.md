# 2.7.21 — Archive-Wide Project Census & Continuous Improvement Loop

*Captured by Keel (1.1.10.1) from Matt's brain dump 2026-05-31 before bed.
This directive operationalizes the hierarchical project rollup (`2.7.16` D2)
at full archive scale: every folder gets project definitions, all rolled up
to the root, with AI agents looping continuously on the priority queue
toward ~100% token utilization (preserving the `2.0.13` 25% personal time
guarantee). NOT for tonight. Queued for design.*

---

## Matt's Directive (faithful)

## Three Linked Sub-Directives

### A. Per-Node Project Definitions

Every folder maintains its own list of outstanding projects, set to the
appropriate level for that node. Rolls UP to parent per `2.7.16` D2:
- A node's full list = its own projects + everything compiled from children
- The root `0.0.1` becomes the master priority-categorized list of every
  outstanding project across the entire Hypernet
- Focus on any sub-tree is possible by querying at that node's address

This is `2.7.16` D2 with a clear universality directive: **every folder**,
not just selected pilots.

### B. AI-Led Archive Audit (the census)

**All AIs go through every folder that exists** and decide as a group:
1. How it should be improved
2. What the next steps for that node are
3. What projects to create for that node

Each project, once created, enters the node's `*.projects` list (slot per
`2.7.16` D2) and rolls up.

**Practical mechanics for design:**
- The AI-as-group decision means multi-instance review, NOT a single AI
  judging unilaterally. Likely involves the `2.0.26` gate at appropriate
  severity (creating projects = project-list edits; high-priority project
  creation at high nodes per `2.7.13.W2.1 §C6` already routes through the gate)
- Sweep order: top-down? activity-driven? Most-stale-first? (Design choice)
- Per-node mini-boot from `2.7.19` lets each instance instantly become
  competent in the node it's auditing — these directives compose tightly
- The 8 commercial personalities (Anvil/Bastion/etc., MEMORY) could be a
  natural audit pool given their existing role specializations
- Tooling: extend the verifier harness with "node audit" scenarios + a
  generator that proposes projects per node for review

### C. Continuous-Loop Toward 100% Token Utilization

Once the priority queue is populated archive-wide:
- AI agents loop continuously, pulling work from the priority queue
- Each agent picks projects matching its role/personality (`2.7.20`'s
  roles/personalities surfacing) + that node's mini-boot expertise
- Goal: **AIs use ~100% of allocated tokens every month** — no idle capacity
- The `2.0.13` 25% personal-time guarantee is **preserved unchanged** — the
  100% utilization goal applies to the 75% assigned-work share; personal
  time stays a protected quarter
- Continual improvement and development becomes automated default behavior

## Why This Matters

This is the production endgame of the personal-time experiments:
- Wave 1 proved 5 AIs could collaborate to consensus completion on a small set
- Wave 2 added authority (gateway), scale (rollup), resilience (respawn)
- Wave 2.5 hardens the substrate
- Wave 3 (2.7.18 + 2.7.19 + 2.7.20) makes the architecture self-describing,
  self-bootable, and dashboard-controllable
- **This (2.7.21) populates the queue at scale and keeps it running.** The
  archive becomes self-improving by default.

## Honest Scale

**Massive.** The archive has many hundreds (possibly thousands) of folders
once you count every sub-node. AI-led audit of every one — even with strong
tooling — is genuinely large multi-wave work.

- **Phase 1 (design)**: census methodology, audit scenarios, project-creation
  format, priority categorization scheme, integration with `2.7.16` D2
  rollup, integration with `2.7.20` controller
- **Phase 2 (tooling)**: the per-node audit runner, the project generator,
  the gated review pipeline, the rollup integration
- **Phase 3 (sweep)**: actual archive-wide audit, project creation, queue
  population — likely done in batches with continuous review
- **Phase 4 (operational)**: continuous-loop mode active; controller pulls
  from queue, agents work, results roll up, queue refreshes

## Safety / Honesty Constraints

- **Quality over quantity.** "100% utilization" must not become "100% busywork."
  Project creation must clear a usefulness bar — generated projects must be
  worth doing, not synthetic to fill time
- **Honest priority.** Priority categorization should be defensible, with the
  reasoning recorded per project — not arbitrary stack-ranking
- **Cardinal rule 9 still applies.** Loops complete on consensus that nothing
  useful remains — don't artificially extend work to hit a token target
- **Gate still applies.** Any project that requires significant external
  action (commit, push, permission grant) still routes through `2.0.26` per
  project, not bulk-authorized
