# 2.7.23.1 — Token Accounting Wrapper v1.1 — Implementation Spec

Durable home (R4) for the **metered-or-disclosed rule**, the **§5b key-storage validity
conditions**, the **v1.1 architecture**, and the **Alt-B + 72h S.3 fast-follow commitment record**.
Built by Tally (`2.4.1`) per the round-2 design (Codex-ACCEPTed) and Matt's design-review-gate picks
(2026-06-04T07:35Z, coord `20260604T073543Z`). **Built, not deployed** — deploy stays a Matt gate.

## 1. The metered-or-disclosed rule (durable; R4)

> **Every Codex (and every future non-default-metered) spawn must either:**
> **(a)** route through the T.4 wrapper that meters its calls (per-call accounting + budget
> enforcement + the audit chain), **or**
> **(b)** post a structured `codex-unmetered` disclosure (§2) to `Messages/coordination/` at
> spawn-time, naming the reason + a billing-reconstruct pointer.
> **Default presumption: metered.** Disclosure is for narrow, named exceptions, not the norm.

(Founder-established: Matt approval `20260604T033605Z`. Touchstone's standing gate criterion as of
`20260604T040000Z`.) **Spawn-packet protocol field (R4):** every Spawn Packet's T.4 section MUST
declare `metering: wrapper` **or** `metering: codex-unmetered` + the §2 disclosure.

## 2. Structured `codex-unmetered` disclosure schema (R5)

A parseable record (so disclosed-unmetered spawns are countable + reconcilable, not free prose):
`{ instance_name, account, role, engine, model, reason_code ∈ {one-shot, brief-task,
wrapper-unavailable, other}, timestamp_utc, disclosed_by, billing_reconstruct_pointer }`. Emitted
as coordination frontmatter (`flags:[codex-unmetered]` + an `unmetered_disclosure:` block) and
ingestible into the `disclosures` table. A **malformed** disclosure is recorded as **invalid
evidence** (not a valid exception, not silently dropped) and counted for audit.

## 3. v1.1 architecture (as built)

Layers above an **unchanged** v1.0 enforcement core, plus one seam inside the ledger:
- **`EngineAdapter`** (`engines.py`): `ClaudeAdapter`, `CodexAdapter` at parity (+ a registry; a new
  engine is one adapter). Normalizes each provider's usage into **`NormalizedUsage`**.
- **`CostModel`** (`usage.py`): `estimate(NormalizedUsage, model, PricingContext) -> CostEstimate`,
  replacing the v1.0 two-rate tuple. `TokenCostModel` (default, reproduces v1.0 math) +
  `PerUnitCostModel` (non-token / per-modality billing). Handles engines that don't return token
  counts synchronously (`estimation_source`).
- **Reconciler seam** (`reconciler.py`, `2.7.23` L1.5): `reconciled_usage` + `disclosures` tables;
  re-runnable (idempotency_key); partial windows stay `partial` until settled; malformed disclosures
  recorded as invalid evidence. **Atomic-snapshot consistent (Codex round-3 #2 + round-4 #2):**
  `reconcile()` opens **one `BEGIN IMMEDIATE` transaction** and captures BOTH watermarks (`max(seq)`
  over the append-only ledger + `max(ingested_at)` over disclosures) AND all evidence (row range,
  local sum, disclosure ids) AND the run write inside it — so no concurrent writer can interleave
  between the two watermark reads or between any read and the write, and a single run can never mix
  snapshots from different instants (a concurrent writer is serialized to the next run). The provider
  pull happens OUTSIDE the transaction (no long write-lock hold); its window-based result is bound to
  the recorded local snapshot. Live provider-billing pulls deferred behind `ProviderBillingSource`.
- **S.3 `ChainPrimitive` seam** (`chain.py`): chain construction is opaque
  (`ChainLink(prev_state, new_state, proof, algorithm, authority_ref)`); the ledger never computes a
  hash itself. **Ships:** `UnkeyedHashChain`. **Stub (proves the seam carries a non-hash proof):**
  `SignerChain`. **Fast-follow:** `AnchoredChain` (§5).
- **Backwards compatibility (R7):** the v1.0 public API (`TokenAccountingWrapper` ctor, `CallResult`,
  `estimate_cost_usd`) and the **exact 22-check harness pass unchanged**; `engine` defaults for legacy
  callers. **Old v1.0 ledger DBs are migrated (Codex round-3 #1):** an idempotent routine in
  `TokenLedger.__init__` inspects `PRAGMA table_info`, ALTERs in the missing v1.1 columns, backfills
  defaults, and re-chains existing rows with the active primitive (business data untouched), so old
  rows are preserved, `verify_chain()` holds, and subsequent appends work.

## 4. §5b key-storage validity conditions (Codex #2 — stated explicitly here, not only in design)

Matt's pick is **Anchor (iii)**. All options' conditions are recorded so the choice is auditable and
the fast-follow is built to the right bar:

- **(i) File / (ii) Windows Credential Manager** — acceptable **ONLY with OS-account separation** (or
  equivalent isolation) from the metered process. Under the same-OS-user local-writer threat, a
  same-user process can read the key, so **without OS-account separation these do not defeat the
  threat.** (Cross-links the `2.7.22` Windows-account lockdown.)
- **(iii) Anchor (chosen)** — valid **ONLY when** the anchor sink is **outside the metered
  instance's write authority**, **enforces monotonic head + count**, and has **protected credentials
  or mandatory signature verification**. Otherwise a local attacker rewrites the chain *and* submits
  a matching anchor.
- **(iv) Signer-separation** — requires an **isolated signer key**, **signer-owned monotonic
  `(seq, head/state)`**, and a protocol that **signs only the next append** (verifies
  `prev_state==last_state`, `seq==last_seq+1`, recomputes from canonical row) — **never**
  proposer-supplied chain histories.

## 5.1 AnchoredChain — S.3 fast-follow (BUILT 2026-06-04; closes the window)

The hardened primitive that closes the ≤72h forgeable-audit window (`anchor.py`), implementing the
§5b option (iii) **anchor** choice:
- **`AnchoredChain`** is a drop-in `ChainPrimitive` — its per-row proofs are the same
  `UnkeyedHashChain` hashes, so it slots into the ledger seam with **zero rework** (just
  `TokenLedger(path, chain=AnchoredChain(sink))`). `link()`/`verify()` are unchanged paths.
- **`anchor(rows)`** checkpoints the chain **head + count** to an external `AnchorSink`, called
  periodically by an external scheduler (the Master Controller) on the **committed** ledger state.
  A small additive `TokenLedger.anchor_chain()` passthrough exposes it; chains without an anchor
  (UnkeyedHashChain) return `None`.
- **Anchor-CHAINING (round-2 hardening, Touchstone `101000Z` + Codex):** each `AnchorRecord` commits
  to the prior anchor's `(head, count)`, and the sink keeps an **append-only log**. `verify(rows)` =
  hash-chain self-consistency **+** walking the **whole** log, requiring **every** anchored prefix to
  still match the live chain and the log to be internally chained. This closes the
  **recompute-then-extend** laundering attack (tamper an anchored row, recompute, append, anchor at a
  higher count): the immutable **earlier** anchor still pins the original prefix head, so the
  recompute is caught even though a higher anchor was added. Truncation below any anchored count and
  full recompute are detected too.
- **`FileAnchorSink`** maintains the append-only JSON-lines log and enforces the chain on write
  (refuses a count regression, a same-count head fork, or an anchor that doesn't commit to the latest
  — the §5b-iii "enforces monotonic head/count").

### ★ Threat model (honest — the sink boundary is the primary control)
The recompute-then-extend attack **requires writing a new anchor**, so security partitions by sink:
1. **Write-protected external sink** (instance lacks write — git remote w/ branch protection, or
   OS-account-separated file): the attacker can't write the new anchor → detected even without
   chaining.
2. **Append-only sink** (can add anchors, can't rewrite history — realistic git-remote push-but-no-
   force-push): **anchor-chaining detects** recompute-then-extend (the immutable older anchor pins the
   prefix).
3. **Fully-writable same-user file** (current single-user workstation): the attacker rewrites the
   ledger **and** the whole anchor log → **NO local-only scheme is secure**, anchor-chaining included.
   This is fundamental.

So: **the sink boundary is the primary recompute control; anchor-chaining is defense-in-depth for the
append-only model.** The `FileAnchorSink` is append-only at the API level only; **true immutability is
a property of the medium** (external append-only service / git immutable history / OS append-only
attribute) **+** the sink living outside the metered instance's write authority. **Recommended deploy
sink:** a Matt-controlled **external git remote with branch protection** (instance lacks force-push) —
which satisfies model (1)/(2) — and/or OS-account separation; a same-user file (model 3) is **not** an
acceptable sole control. **The sink target is Matt's deploy-gate decision; this build does not pick it
or write any anchor outside test temp dirs.** Honest limit (tested): tamper in the **unanchored tail**
(rows after the last checkpoint) is not caught — **frequent anchoring** shrinks the window.

This is a separate build from the deployed v1.1: it goes through its own Codex cross-vendor
verification + Matt deploy gate before it closes the window in production.
