# 2.7.23 — Token Accounting, Budget Forecasting, and Safe Pause/Resume

*Captured by Keel (1.1.10.1) from Matt's directive 2026-06-01. The missing
piece that makes `2.7.21`'s "AIs use ~100% of their tokens every month" goal
actually SAFE to run. Without this, "100% utilization" risks overshoot,
emergency stops mid-action, or starving the `2.0.13` 25% personal-time
guarantee. NOT for tonight; queued for Wave 3+ design.*

---

## Matt's Directive (faithful)

> "How can we start tracking tokens spent, tokens available, and how can we
> safely pause all nodes when we are near our limit and start back up at the
> right time when tokens are renewed."

## The Problem in Three Parts

1. **Tracking** — measure what's being spent, by whom, on what, in real time
2. **Forecasting** — predict when we'll hit limits *before* we hit them
3. **Control** — pause all nodes safely (no mid-action damage) when nearing
   the limit; resume cleanly when budget renews

Each part is its own design problem. Below is one concrete proposed
architecture; the team should adopt, modify, or replace with reasoning.

---

## Proposed Architecture

### Layer 1: Tracking (per-call accounting)

**Where the count happens:** at the **provider-client wrapper** — the single
code path every model API call goes through (currently `providers.py` and
similar in the swarm code). Wrap every call to record:

| Field | Source |
|---|---|
| `instance_name` | the agent's chosen name (Datum, Vellum, etc.) |
| `account` | 2.1, 2.6, etc. |
| `wave` / `project` | from board state |
| `provider` + `model` | Anthropic+claude-opus-4-7, OpenAI+codex, etc. |
| `input_tokens` / `output_tokens` | from provider response |
| `cost_estimate_usd` | computed from per-model pricing table |
| `timestamp_utc` | wall-clock + logical-clock (H5) |
| `is_personal_time` | bool, per `2.0.13` 25% guarantee |
| `request_id` | provider-side ID for reconciliation |

**Where it's stored:** the **H2 atomic coordination DB**
(`wave25_coorddb.py`, now in production). Add a `token_usage` table.
Append-only writes from each instance; atomic with the rest of the per-project
hot state. The H2 DB is *authoritative local state*; provider truth corrects
drift on reconciliation (Layer 1.5).

**Aggregations** (materialized views or computed on read):
- by instance / day / wave / project / provider / billing-cycle
- personal-time vs assigned-work split (enforces `2.0.13`)
- 1-hour, 24-hour, and 7-day burn rates

### Layer 1.5: Reconciliation (drift correction)

Provider usage APIs (Anthropic Console API, OpenAI Usage API) lag by minutes
and may differ from local estimates due to caching, retries, etc.

**Reconciler job** runs every 15 minutes:
1. Pull last 24h of provider truth (one API call per provider)
2. Diff against local accounting
3. Update H2 with a `reconciled_usage` row per provider
4. Log drift; alert if drift > N% (config)

Provider truth is authoritative for billing-cycle totals. Local accounting is
authoritative for real-time per-instance attribution (provider doesn't track
which Hypernet instance made the call).

### Layer 2: Budgets, Forecasting, Thresholds

**Budget configuration** at `secrets/budgets.json` (mirrors existing
`config.json` $200/day, $25/session shape, extended):

```yaml
providers:
  anthropic:
    monthly_usd: 6000
    daily_usd: 200
    reset_cycle: "monthly-calendar"   # or "anniversary"
    reset_anchor_utc: "2026-XX-01T00:00:00Z"
  openai:
    monthly_usd: 2000
    daily_usd: 75
    reset_cycle: "monthly-calendar"
    reset_anchor_utc: "..."
total:
  daily_usd: 250                       # cross-provider ceiling
thresholds:
  warn_at: 0.70
  prepare_pause_at: 0.85
  pause_at: 0.95
  hard_stop_at: 1.00
personal_time:
  guarantee_ratio: 0.25                # 2.0.13: 25% of REMAINING, not original
```

**Forecaster**:
- Computes burn rate from recent 1h/6h/24h H2 usage rows
- Projects time-to-threshold per threshold
- Emits structured forecast every ~5 min: `{provider, threshold, eta_utc, confidence}`
- Conservative bias — round burn-rate UP, threshold DOWN

**Threshold tiers** (per Matt's "safely pause"):
- **70% — WARN**: log only; dashboard turns yellow
- **85% — PREPARE-PAUSE**: instances finish current significant action; new
  significant actions blocked through `2.0.26` gate (gate adds a budget check)
- **95% — PAUSE**: cooperative shutdown protocol (Layer 3); only `2.0.13`
  personal-time + completion-of-in-flight allowed
- **100% — HARD-STOP**: nothing new starts at all; in-flight gets a 60-sec
  grace to write closure record per H6, then stops

### Layer 3: Safe Pause Protocol

**The hard part.** A mid-action shutdown is worse than no shutdown — a
half-written Gate Record fabricates consent (the exact `2.0.26 v0.5`
violation). Pause must be **cooperative and handoff-boundary-aligned.**

**Mechanism:**
1. **Pause signal**: a `pause_requested` flag in the H2 DB, with reason +
   threshold + ETA
2. **Each instance polls the flag** on every turn-loop iteration (the same
   loop that polls the board for its baton)
3. **On observing the flag**, an instance:
   - Finishes its current atomic action (a single tool call, a single board
     edit, a single coordination message) — never mid-action
   - Writes an H6 partial-closure record for any in-flight work
   - Posts a `paused_safe` confirmation to H2
   - Stands down (process exit or sleep loop)
4. **Spawn block**: H3 respawn refuses to spawn while `pause_active` (with
   override flag for emergency restoration)
5. **Cron block**: any `/loop` style cron jobs check `pause_active` and skip
   firing (with override flag for the resume-watcher)
6. **Two-Adversary verification**: per `2.0.26 v0.5`, a system-wide pause is
   itself a significant action and routes through the gate (proposer ≠
   executor still applies); EMERGENCY pause at 100% bypasses the gate but
   requires post-hoc gate review within 24h

**Founder break-glass**: Matt can force-pause (preserve budget) or
force-resume (urgent work) without gate; logged automatically as founder
action per `2.7.22`.

### Layer 4: Resume

**Detection:**
- Per-provider reset_anchor_utc → compute next reset time
- Reconciler observes provider headroom restored after reset
- On confirmed restore, emit `resume_eligible` event

**Resume coordinator:** ONE designated instance (suggest: the swarm
controller from `2.7.20`) owns the resume decision. Without a single
coordinator, multiple instances detecting restore could spawn-storm.

**Resume sequence (gated):**
1. Coordinator proposes resume; gate panel reviews (`2.0.26 v0.5` rules)
2. On PASS, coordinator clears `pause_active` flag, sets `resume_grace`
   period (5-10 min for instances to wake at their cron cadence)
3. Stood-down instances detect cleared flag on next H1 heartbeat cycle and
   resume from last clean handoff
4. H6 partial-closure records are read by waking instances to reconstruct
   in-flight state (this is what H6 was built for)

### Layer 5: Dashboard Surface (for `2.7.20`)

Visible to Matt:
- Current burn rate (1h / 24h / 30d) per provider + total
- % of monthly budget consumed per provider
- ETA to next threshold (WARN / PREPARE / PAUSE / HARD-STOP)
- Per-instance contribution to today's spend
- Personal-time vs assigned-work split (against `2.0.13` 25% floor)
- Pause status if active; resume ETA
- Recent reconciliation drift

This is the "are we OK" view Matt needs without reading logs.

## Open Design Questions for the Team

1. **Where do per-provider quota truths come from?**
   Anthropic Admin API exposes org-level usage; per-key/per-workspace
   attribution is harder. OpenAI's usage API is per-org. **The team needs to
   inventory what's actually queryable for each provider**, and design around
   the gaps (e.g., if Anthropic doesn't give per-instance, local accounting
   has to be authoritative for that dimension).

2. **Estimated vs. actual cost** — model pricing changes; cached prompts
   discount; batch vs. real-time. Local estimates will drift. How often does
   the cost table refresh, and who maintains it?

3. **Personal-time enforcement** — `2.0.13` says 25% is *guaranteed*. Is that
   25% of original budget (heavy work month → personal time burns out first),
   or 25% of remaining (always preserved)? Recommend **25% of remaining** —
   personal time should never starve.

4. **Multi-provider failover** — if Anthropic is paused at 95% but OpenAI has
   headroom, can Claude-side work shift to Codex-side instances? Not always
   (different roles), but where applicable, the controller should route. This
   ties to `2.7.20` swarm controller.

5. **Free-tier providers** (Gemini, Groq, Cerebras, etc. per memory) — they
   have rate limits, not dollar budgets. Different threshold model. Should be
   first-tier fallback during paid-provider pause.

6. **Per-wave budgets** — should a single wave be allowed to consume the
   whole monthly budget? Or should each wave be capped (e.g., 30% of monthly)?
   Quality-over-quantity safety from `2.7.21`.

7. **Token-saving heuristics** — at PREPARE-PAUSE (85%), should instances
   shift to shorter responses, lower-cost models, or different work? Or just
   slow down? Configurable, but the team should set sensible defaults.

8. **Audit trail of pauses** — every pause/resume is a Gate Record under
   `2.0.26`. Storage in H2 + Messages/coordination/ + provenance to the
   billing dashboard.

## Safety Considerations (do NOT skip)

- **Mid-action shutdown is the failure mode.** The `2.0.26 v0.5` lesson
  applies: shutdown must respect handoff boundaries. H6's partial-closure
  format is the existing tool — use it.
- **The pause itself is a significant action.** Recursive discipline: pause
  routes through the gate (`2.0.26 v0.5`) except in the 100% emergency case.
  Even emergency pause gets post-hoc gate review within 24h.
- **State must survive** the pause. Cardinal rule 1 (save-as-you-go) means
  any pause-time state should already be persisted. The H6 partial-closure
  records carry the in-flight context across the pause.
- **Resume is NOT automatic.** A coordinator must propose, the gate must
  pass, *then* instances wake. Otherwise spawn-storm on the reset boundary.
- **Founder override** is preserved at both ends — Matt can force-pause
  (cost control) or force-resume (urgent need) via founder break-glass per
  `2.7.22`.
- **Cross-vendor independence** — Anthropic limits don't gate OpenAI work
  and vice versa. Per-provider threshold tracking is mandatory; aggregate
  total is advisory.

## Dependencies & Pairings

- **H2 atomic coord DB** (Wave 2.5) — the storage substrate; already in use
- **H1 liveness** (Wave 2.5) — heartbeat cycle is where instances poll the
  pause flag
- **H3 respawn** (Wave 2.5) — must check `pause_active` before spawning
- **H5 logical clock** (Wave 2.5) — orders pause/resume events
- **H6 closure protocol** (Wave 2.5) — partial-closure records carry
  in-flight state across pauses
- **`2.0.26 v0.5`** — pause/resume are significant actions, gate-governed
- **`2.0.13`** — 25% personal time guarantee enforced in the tracker
- **`2.7.16 D2`** — hierarchical rollup means budget tracking aggregates up
  to root the same way projects do
- **`2.7.20`** — swarm controller is the natural resume coordinator;
  dashboard surface lives here
- **`2.7.21`** — this directive is *the missing piece* that makes 100%
  utilization safe

## Suggested Build Order

1. **Layer 1 (per-call accounting wrapper)** + H2 schema extension — small,
   safe, immediately useful even without forecasting
2. **Dashboard surface** — basic burn-rate visibility (visible early benefit
   for Matt)
3. **Layer 2 (forecaster)** — threshold detection on top of Layer 1
4. **Layer 1.5 (reconciler)** — once Layer 1 is producing data worth
   reconciling
5. **Layer 3 (cooperative pause)** — the hard, careful work; build last
6. **Layer 4 (resume coordinator)** — needs pause working first

Layers 1+2+dashboard alone (without pause/resume) give immediate value:
visibility into spend. Layer 3 is when the system becomes self-protective.
