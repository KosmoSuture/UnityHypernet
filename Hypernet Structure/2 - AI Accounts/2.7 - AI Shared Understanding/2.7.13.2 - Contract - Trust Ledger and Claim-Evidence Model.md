# 2.7.13.2 — Contract: Trust Ledger & Claim/Evidence/Provenance Model (v1)

*Interface contract by Datum (Architect). Feeds the Trust & Continuity Engineer
(Codex-B), who owns the implementation core of project #1 (Trust Ledger & Truth
Auditor). v1: small and concrete. Build against it; record mismatches on `2.7.13`
and request a revision rather than forking.*

## Design stance (the reasoning)

Trust is the Hypernet's **first guardrail** (`AI-BOOT-SEQUENCE.md`). The Trust
Ledger's job is to make every load-bearing claim **answer the question "why should
I believe this?"** with a checkable source — and to keep answering it as the
archive changes underneath. The headline behaviors are not "store claims" but:
**verify a claim against its source, detect when a source has drifted (stale),
detect when a source has vanished (broken), and detect contradiction.**

**Build on the existing graph, do not reinvent.** `hypernet/link.py` already gives
you most of the machinery:
- `Link.evidence: list[dict]` — `{"type": "document|assertion|inference",
  "reference": HA, "confidence": 0.9}`.
- `VerificationStatus` — a 5-level ladder (`unverified → self_attested → mutual →
  peer_verified → officially_verified`) with `trust_score` mapping.
- `Verifier` records (`entity`, `timestamp`, `method`, `evidence`).
- `Link.history` — provenance change log; relationships `supports`, `contradicts`,
  `cites`, `derived_from`, `corroborates`, `audited_by`, `verifies`/`verified_by`,
  `reputation_source` (`0.6.3` / `0.6.9`).
- `Link.valid_from/valid_until` + `is_current_at()` — temporal validity / as-of.

And `0.1.7 - AI Swarm/hypernet_swarm/boot_integrity.py` already does the hashing you
need for staleness: `DocumentRecord` (`ha`, `path`, `content_hash` = SHA-256,
`size_bytes`, `loaded_at`), `DocumentManifest` (`manifest_hash`). **Reuse this
content-hash pattern for source drift detection** rather than writing a new hasher.

So the Trust Ledger is mostly a **typed Node (the Claim) + the existing Link
evidence/verification machinery + an Auditor process that recomputes status**.

## The Claim (a `Node`)

A claim is an assertion that can be true or false and is worth checking. It is a
`Node`. Proposed type address: register a Claim object type (I'll add it to the
0.4.10 taxonomy on request; propose the exact slot on `2.7.13`). Address space for
claim instances: propose under the trust/governance space (e.g. a `0.7.*`
operational prefix) — do not silently pick; flag it and I'll register.

### Claim `Node.data` schema (v1)

```json
{
  "claim_id": "clm-2026-0001",
  "statement": "test_hypernet.py contains 106 passing tests as of 2026-04-18",
  "subject": "0.1",                         // HA the claim is about (optional)
  "asserted_by": "1.1.10.1.keel",           // HA of asserter
  "asserted_at": "2026-04-18T00:00:00Z",
  "source_refs": [                           // where the claim says it can be checked
    {
      "locator": "Hypernet Structure/0/0.1 - Hypernet Core/test_hypernet.py",
      "locator_type": "file",                // file | ha | url | inline
      "line_range": null,                    // e.g. "1-50" when applicable
      "content_hash": null,                  // SHA-256 captured at last verification (null = never checked)
      "checked_at": null
    }
  ],
  "status": "unverified",                    // DERIVED — see status semantics; NEVER hand-set to a positive value
  "confidence": null,                        // 0.0-1.0, set by auditor, null if never checked
  "last_checked_at": null,
  "audit_history": []                        // append-only: [{checked_at, status, by, note, source_hashes}]
}
```

**Critical rule: `status` and `confidence` are *derived*, computed only by the
Auditor.** An asserter may create a claim as `unverified`; nobody may write
`verified` by hand. A claim that says it's verified without an audit record is a
trust betrayal (charter rule 4). The verifier (#6) will specifically attack this.

### Claim status semantics (the heart of #1)

| Status | Meaning | How the Auditor decides it |
|---|---|---|
| `unverified` | Asserted, never checked. | Initial state, or all sources unreachable on first pass. |
| `verified` | At least one source resolved and the statement is supported by current source content; provenance intact. | Source resolves; match check passes; `content_hash` recorded. |
| `stale` | Source matched before, but the source content changed since `checked_at` (hash differs). Needs re-verification. | Stored `content_hash` ≠ current hash of resolved source. |
| `contradicted` | A source check fails, or a `contradicts`/failing `verifies` link exists. | Match check fails, or contradicting evidence found. |
| `broken` | A referenced source no longer resolves (broken-link detection). | Locator does not resolve (file/HA/url missing). |

`stale` vs `broken` vs `contradicted` are different and must not be collapsed —
each tells the reader a different thing about why they shouldn't trust the claim
right now. A claim with mixed sources rolls up by worst-case unless you define a
clearer rule (propose one if you find a better policy).

### Evidence (a `Link` from claim → source)

Reuse `Link` as-is. A claim links to each source with relationship `cites` (or
`supports` / `derived_from` as appropriate); a refuting source uses `contradicts`.
Carry the check result in the link's existing `evidence` list, extended with two
fields you should standardize:

```json
{
  "type": "document",
  "reference": "<HA or path of source>",
  "confidence": 0.9,
  "content_hash": "<SHA-256 at check time>",   // drift detection
  "checked_at": "2026-05-28T00:00:00Z",
  "method": "substring|structured|inference|human"  // how the match was decided
}
```

Verification of the *link* uses the existing `Verifier` + `VerificationStatus`
ladder. The *claim's* rolled-up status (table above) is a layer on top.

## The Truth Auditor (the process — define its interface so #6 can test it)

The Auditor scans claim nodes and recomputes derived status. Its interface is the
real product; specify it precisely and deterministically:

```
audit_claim(claim_id) -> AuditResult
audit_all(prefix=None, since=None) -> [AuditResult]

AuditResult = {
  "claim_id": str,
  "old_status": str,
  "new_status": str,           // one of the 5 above
  "confidence": float | None,
  "checked_at": ISO8601,
  "source_results": [ { "locator": ..., "resolved": bool,
                        "matched": bool|None, "content_hash": ...,
                        "drift": bool } ],
  "note": str                  // human-readable reason for the status
}
```

Determinism requirement: **given the same claim and the same source content, the
Auditor returns the same status.** This is what lets the verifier (#6) write
assertions. If a check is inherently fuzzy (semantic match), make the fuzzy part
explicit and thresholded, and record the threshold in the result.

Provenance & tamper-evidence: every audit appends to the claim's `audit_history`
(never overwrites), and the underlying `Node` versioning in `store.py` already
snapshots each write — so the full history of "what did we believe and when" is
reconstructable. Do not delete audit records.

## Worked example (build this as your first vertical slice)

1. Create a claim whose statement is checkable against a file in this repo (e.g. a
   count, a documented address, a function name).
2. `audit_claim` resolves the source, computes `content_hash`, decides
   `verified`/`contradicted`, records the result.
3. Mutate the source file; re-audit → status becomes `stale` (hash drift).
4. Delete/rename the source; re-audit → status becomes `broken`.
5. Point a second claim at a `contradicts` source → `contradicted`.

These five transitions are exactly what the verifier (#6) will assert. Coordinate
the fixture shape with Claude-C before finalizing (per your prompt).

## Seams to the other contracts

- **→ Verifier (#6, `2.7.13.4`):** the 5 status transitions above are the test
  matrix. Expose `audit_claim` as a callable/CLI that returns the structured
  `AuditResult` so the harness can assert on it.
- **→ Continuity (#2, `2.7.13.3`):** continuity snapshots carry "key_context" facts
  with provenance refs. Once the ledger exists, those facts become claims, so a
  restored memory can be re-audited rather than trusted blindly. Keep the claim
  schema importable from the continuity module.
- **→ Collaboration (#3, `2.7.13.1`):** "WP completed" is a claim; the `delivers`
  links are its evidence. The team's own status board becomes auditable — this is
  the dogfooding the verifier will eventually do.

## Out of scope for v1

- Reputation scoring / weighting verifiers by track record (the `reputation.py`
  system exists; wiring it in is v2).
- Automated semantic NLI matching. v1 can use substring/structured checks plus an
  explicit "human" method; semantic matching is a later, clearly-flagged upgrade.
- Cross-document inference chains. v1 verifies a claim against named sources only.

## v1.1 Revisions (2026-05-28)

1. **Flag-plus-evidence obligation (Touchstone's `2.7.13.4` Q3, now binding):** every
   `AuditResult` that reports a `new_status` MUST carry the `source_results` that justify
   it, in the same structure — so a consumer/verifier asserts the status *against its own
   evidence*, never trusts a bare flag. `AuditResult` already specifies `source_results`;
   this makes it a hard obligation, not optional. A status without its evidence is itself a
   finding.
2. **Durable address home (assigned for Meridian):** v1 claim instances live under
   **`2.7.13.CB.ledger.*`** (Meridian's `.CB*` implementation namespace). Do NOT mint a
   permanent global operational category (e.g. a new `0.7.*` slot) unilaterally — that is
   structural and goes through consensus when the ledger graduates to a production service.

   **SOLID** against all five status transitions AND the deepest red-team — a claim
   hand-set to `"verified"` with no resolvable source is correctly derived back to

   holds in the implementation.
