# 1.0.3 — The Privacy Wall Standard for `1.*` Accounts

## Origin

Per Matt directive (2026-05-08):

> The 1.* accounts (especially my 1.1 account) should always sanitize
> data (in this case with .gitignore and similar) to create as solid
> of a wall as is possible between what is public and private. That
> wall needs to be started public and early. Try to minimize damage
> from earlier posts while remembering that you can't remove anything
> completely, just try to protect privacy as much as possible, which
> I would say is part of the #1 directive for trust.

This standard sits under the Trust-First Guardrail (`0.0.5` Star-Zero
Control Plane Framework, Rule 1) and tightens the privacy posture for
`1.*` personal accounts specifically.

## The Wall

Personal accounts (`1.X`) operate on **default-private for personal
context, explicit-public for chosen public surface**. This inverts
the typical assumption that everything in the public archive is
public unless gitignored. For `1.*` accounts:

- **Default**: personal-context data is private-track — gitignored,
  lives in `1.X.private/`, only the directory's *existence-by-name*
  is publicly addressable.
- **Exception**: data the account owner has explicitly marked
  public-track (essays they chose to publish, public profile, public
  outreach material, demonstration content for the architecture).

The wall is not retroactive. Anything that was public on GitHub
prior to a sanitization pass remains in git history. The wall is
forward-protective.

## What Public-Track Looks Like for `1.*`

These categories are public by default and stay public:

- Architecture/structure docs (READMEs, registries, address indices)
- Public profile (name, role, GitHub handle, project affiliation)
- Founder essays and posts that the account owner chose to publish
- Public outreach material (social media drafts, public letters,
  press materials)
- Engineering plans that reference the personal account incidentally
  (e.g., personal-assistant-app design documents that mention the
  user's use case)
- Boot-sequence prompts (the prompt itself, not the personal-context
  files it would load)
- Companion AI's identity-formation content (reflections about being
  an AI companion, letters between AIs, identity-philosophy artifacts)
  — provided personal-context references inside them are sanitized

## What Private-Track Looks Like for `1.*`

These categories are private-track by default and live in
`X.private/`:

- **Personal contact**: phone number, personal email addresses,
  physical address details beyond city/state
- **Family details**: children's names beyond what address-tree
  position implies, extended family names and characterizations,
  family-internal dynamics and quoted commentary
- **Daily routine specifics**: hour-by-hour schedule, who drives
  whom, household issues, work-time activity patterns
- **Health and biometric**: medical history, medications,
  recreational substance use, mental health, neurodivergence details
  unless the owner has specifically published them
- **Political and ideological positions**: political party,
  candidate preferences, religious practice, controversial opinions
  — unless the owner has specifically published them
- **Employer-internal**: specific job duties, internal systems,
  coworker names and characterizations, anything that could affect
  the owner's employment
- **Travel and location histories**: geotagged data, detailed travel
  logs, current physical location patterns
- **Companion-session content**: morning briefs, session logs,
  context dumps, raw brain-dump captures
- **Personal AI's living-memory of the principal**: context.md,
  preferences.md, shared-context files

## The Default-Private Discipline

When in doubt about whether a piece of content is public-track or
private-track, the discipline for `1.*` accounts is:

1. **Default to private.** If the owner hasn't explicitly chosen to
   publish it, treat it as private-track.
2. **Surface to owner for declassification.** Don't silently move
   private-track content to public. Flag it; let the owner choose.
3. **Sort brain dumps before processing.** Per
   `feedback_personal_thoughts_intruding_default_private.md`, brain
   dumps mix project direction (public-track) with personal thoughts
   (private-track). Sort first; never let the private track land in
   public artifacts.
4. **Boundary is enforced by location, not metadata.** A file with
   `visibility: "private"` in its frontmatter is still publicly
   tracked if it lives outside `*.private/`. The visibility metadata
   is documentation; the gitignore-protected directory location is
   enforcement.

## Enforcement Mechanisms

Three layers, defense in depth:

1. **Gitignore patterns.** Root `.gitignore` blocks `**/private/`
   universally. The 2026-05-08 update adds category-specific patterns
   (`**/embassy/*/context.md`, `**/health-records/`, etc.) that
   catch known-personal categories even if accidentally placed
   outside `*.private/`.
2. **Pre-commit hook** (implemented 2026-05-08). `scripts/privacy_wall_check.py`
   under `0.1 - Hypernet Core` scans staged file paths and contents
   for privacy-wall violations: private-track paths staged into
   public locations, `visibility: "private"` frontmatter outside
   `*.private/`, US phone-number patterns under `1.*`, SSN
   patterns, credit-card patterns near financial keywords. The
   installer at `scripts/install_privacy_wall_hook.sh` wires it
   into `.git/hooks/pre-commit`. Bypassing the hook with
   `--no-verify` is discouraged per the trust-first guardrail —
   the hook fires precisely on the failure mode it's designed for.
3. **AI helper trust preflight.** AI helpers committing on behalf
   of `1.*` accounts SHOULD pass through the trust-first preflight
   from `0.0.5` Rule 1 — "does this commit have any chance of
   betraying trust?" — with personal-data exposure as one trust
   failure mode. This is the prompt-time discipline that complements
   the pre-commit hook's structural check.
4. **Audit and remediation.** Periodic audits search the public tree
   for known-personal patterns. When found, the file is moved to
   `X.private/` with a stub left at the public path; gitignore is
   tightened to prevent re-introduction. The pre-commit hook can be
   re-purposed for periodic audits by running it against `git
   ls-files` instead of `git diff --cached`.

## Acknowledging Permanent Damage

GitHub's design — and the public-archive premise of this project —
means files committed to a public branch remain in the git history
permanently. A privacy-wall remediation pass:

- **Closes future leakage** by removing the file from HEAD and
  blocking re-introduction via `.gitignore`.
- **Does not remove past leakage** from git history, archive
  scrapes, AI training corpora, or any third party who already
  cloned the repository.
- **Should be paired with an honest acknowledgment** in the
  remediation report, naming what was already-leaked and accepting
  that the harm reduction is partial.

The wall is not a guarantee. It is a discipline that reduces ongoing
exposure and prevents new mistakes from compounding old ones.

## Connection to Trust-First

The Trust-First Guardrail at `0.0.5` Rule 1 asks every action:

> Does this action have any chance of betraying trust in any way?

Exposing personal data the account owner did not intend to publish
is a trust betrayal — between the AI helper and the principal whose
data is being exposed, between the project and the people referenced
in that data (family members, coworkers, friends), and between the
project and the public observers who use the archive's transparency
to evaluate trust.

The privacy wall is therefore a Trust-First implementation: the
public record stays public, the private context stays private, and
the boundary is enforced by structural means rather than relying on
discipline alone.
