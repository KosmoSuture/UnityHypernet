# 1.0.4 — Universal 1.* Schema (Draft, First Pass)

*Per Matt directive 2026-05-15. First-pass draft of the universal
schema for every `1.*` (person) node on the Hypernet. Three levels
deep for most channels; five levels deep for medical and
messaging per Matt's specific request. Handed to the 5-AI swarm
session for refinement via Project F consensus workflow.*

  and

  `0.0.4` Node Metadata Framework

## Design Principles

1. **Universal across all `1.*` accounts.** Every person on the
   Hypernet follows this top-level layout. Sub-level extensions
   are allowed per Matt's "extend the schema as you need to but
   check upstream first" rule.
2. **Default-private per `1.0.3`.** Personal-context data is
   private-track by default; explicit-public is the exception.
3. **Granularity depth follows data.** A node only needs the
   sub-levels it actually has data for. The schema is the
   ceiling; the data fills as much of the ceiling as it needs.
4. **Sparse instantiation.** Reserve all standard channels;
   only instantiate the ones a given person actually uses.
5. **Migration-friendly.** Current `1.1` has inconsistent
   numbering (1.1.10 Embassy, 1.1.11 Profile, etc.). This
   schema proposes a clean baseline; migration of Matt's
   account is its own multi-day task.
6. **Privacy gradients within channels.** Some sub-channels
   default to stricter gating than others (e.g., medical mental-
   health record vs medical vaccination record).

### Genome Addressing Scheme (Matt's specific ask)

Every region of the genome gets a permanent Hypernet address:

```text
1.X.6.3.genome.chr.1          # chromosome 1 (entire)
1.X.6.3.genome.chr.1.p13.3    # cytogenetic band
1.X.6.3.genome.chr.1.pos.10000-20000  # base-pair range
1.X.6.3.genome.gene.BRCA1     # gene by name
1.X.6.3.genome.gene.BRCA1.exon.5  # specific exon
1.X.6.3.genome.snp.rs6311     # named SNP
1.X.6.3.genome.region.MHC     # named region
```

The same address scheme is used across every `1.*` account that
has genetic data. So researcher granted access to
`1.X.6.3.genome.gene.BRCA1` for thousands of users can compare
their BRCA1 segments at a stable, standardized address.

Mandala mechanism per `1.0.1`: a researcher receives a mandala
that opens lockers granting read access to specific genome
addresses for specific users, with audit trail, expiration, and
revocation.

### Re-identification Risk Warning (Required in Schema)

Every grant of "anonymous" DNA access must include explicit
warning: even anonymized DNA can be re-identified when combined
with public genealogy databases, surname distributions, or other
joinable data. The mandala protocol must include:

- Researcher commitment to no re-identification attempts
- No combining with other identifiable datasets without
  explicit additional consent
- Audit trail of who accessed what when
- Right to revoke and request deletion of derived analyses

### Break-Glass Protocol

A first responder accesses the user's emergency profile via:

1. Verifiable medic credential (badge, EMS certification)
2. Geographic-context check (responder is at user's location)
3. User's biometric or unconscious-context override
4. Audit packet logged immediately, including responder ID,
   timestamp, what was accessed
5. User's AI Embassy notified in real-time
6. After-action audit: was access proportional to the
   emergency?

The protocol activates a *bounded subset* of medical data (the
`1.X.6.7.*` channels), not full access to all of `1.X.6.*`.

## Open Questions for the Swarm (Project F)

1. **Channel numbering finalization**: the proposed top-level
   layout reassigns slots from the current Matt-1.1 layout.
   Should canonical schema be adopted as-is, or are there
   reasons to keep particular existing slots?
2. **Granularity stopping rule**: each level-5 dive has 9 sub-
   slots. Some may never be used. Is "reserve all, instantiate
   on demand" the right default for empty branches?
3. **Object-as-zip vs text-native for medical**: medical files
   (DICOM imaging, FASTQ sequencing) are large binary. Per the
   2026-05-14 brain dump's object-as-zip proposal, these
   naturally fit the zip pattern. Confirm tonight.
4. **Mental health and substance-use stricter defaults**: how
   much stricter than other medical sub-categories? Specific
   gating rule needed.
5. **DNA address scheme version**: GRCh38 vs T2T-CHM13 vs
   future references — how does the genome address scheme
   handle reference updates without breaking historical
   addresses?
6. **Provider data ownership**: when a clinic's records are
   imported, who owns the resulting object — user or clinic?
   Both? Schema needs explicit dual-citation.
7. **Real-time monitoring liability**: schema supports the
   access pattern, but the legal framework for AI medical
   advice needs separate authoring (probably under `2.0.*`
   governance).
8. **Migration sequencing**: when does Matt's `1.1` migrate?
   Other accounts (`1.2-1.7`, `1.21-1.24`) are placeholder per
   `1.0.3` Pass 2 — they can adopt new schema cleanly. Matt's
   has real content and migration is harder.
