# 0.5.0.1 — Object Container Format

**Version:** 0.1-draft
**Origin:** Matt Schaeffer (1.1) brain dump 2026-05-14, §1a
**Status:** DRAFT — proposed Tier-2 structural specification.
Matt's Stage-E decisions (2026-05-15) are locked in §12; the spec
stays `draft` pending his final ratification review.
**Builds on:** `0.5.0` Master Object Schema.

---

## 1. Purpose

Matt asked for objects (and links, and workflows) to be
self-contained — "stored similar to how a Microsoft document is,"
a single file containing everything that defines the object, with
master properties as metadata and an internal structure that
follows the object's schema.

The session brief named the tension explicitly: a zip is **opaque
to text-diff review**, and the Hypernet's trust model depends on
"every line is public." This spec resolves that tension rather
than picking one side silently.

## 2. The resolution — two isomorphic forms

All three independent Stage-A plans (Claude-1, Codex-1, Codex-2)
reached the same answer. A `.docx` *is* a zip, but every tool that
reviews one unpacks it first — the canonical reviewable form is
the unpacked directory. So:

- **Canonical form — a directory + manifest.** Text-native. Lives
  in the Official archive, in git, under human/AI review. Every
  YAML/Markdown file diffs cleanly. **This is the source of truth.**

- **Transport form — a `.hno.zip`.** A deterministic zip of the
  canonical directory. Single-file portability — Matt's
  "Microsoft document" experience: move it, attach it, archive it,
  sign it as a unit. **Derived, never authored.**

The two forms are **isomorphic and round-trippable**: packing the
directory deterministically yields an identical zip; unpacking the
zip yields an identical directory. The `0.5.0` content hash is
computed over the canonical directory, so it is stable regardless
of which form you hold.

**The zip is always generated, never hand-edited, and never the
artifact committed to git.** If anyone edits a `.hno.zip`
directly, that is a bug, not a workflow.

## 2.1 The node/object boundary (Matt directive, 2026-05-15)

A directory in the Hypernet is a **node**. An object container is
*also* a node — a node whose content is an object rather than
child nodes. This preserves "directories are nodes" by adding one
explicit, marked stopping point.

- The container's root directory **occupies a real node address**
  (`ha`) and is named with it. It is addressed exactly as an
  object is addressed — a node that *is* an object.
- The **`.hno` suffix is the node/object boundary marker.**
  `3.1.6.5 - Plan/` is an ordinary node (descend → child nodes);
  `3.1.6.5 - Plan.hno/` is a node-that-is-an-object (descend →
  object internals; the node tree **stops** here).
- Everything inside a `.hno` container — `content/`, `links/`,
  `provenance/`, etc. — is the object's internal structure,
  addressed by path *within the container*, never as global
  nodes. A node walk does not descend past a `.hno` boundary.

**Transitional status.** Object-as-directory is a
**file-backed-adapter representation** — how an object looks while
the store is still a filesystem. Long term the canonical store is
database-backed (the DATABASE-FIRST redesign): an object becomes a
typed record, not a folder, object-directories cease to exist, and
"directories are strictly nodes" holds with nothing to clean up.
The `.hno/` directory never expands the node tree and is
explicitly superseded by database object-records.

## 3. Internal layout

A container — directory or zip — has this layout:

```text
<object-name>.hno/            ( or <object-name>.hno.zip )
  manifest.yaml               # master properties — 0.5.0 sections
  schema.yaml                 # resolved schema refs (0.5.x / 0.6.x / 0.7.x)
  content/                    # type-specific payload per the type schema
  links/                      # link objects (0.6.x), one file each
  workflow/                   # workflow definition (workflow objects only)
  provenance/
    history.yaml              # version history
    signatures/               # optional cryptographic signatures
  evidence/                   # optional evidence references
  attachments/                # binary payloads too large to inline
  checksums.sha256            # one entry per file except itself
  N.0.0/                      # the object's own schema node (per 0.0.6)
```

The layout *is* the schema: `manifest.yaml` carries the `0.5.0`
master sections; `content/` follows the `0.5.x` type schema.
Sparse — a container instantiates only the folders it needs
(a simple document has `content/` and nothing under `links/`).

## 4. Master properties — manifest is authoritative

`manifest.yaml` is the single source of truth for master
properties. It maps to `0.5.0`:

```yaml
container:
  format: "hypernet-object-container"
  version: "0.1"
  carrier: "directory | zip"
  canonicalization: "json-sorted-lf-utf8"
identity:
  address: "..."
  object_id: "..."
  object_type: "..."
  schema_refs: []
metadata:
  created: {}
  modified: {}
  status: "draft | active | deprecated | archived"
  visibility: "public | restricted | private"
access:
  owner: "..."
  permissions: {}
integrity:
  hash: {}
  verified: false
links: []
provenance: {}
```

In the zip carrier, a **small subset** (address, object_type,
schema_ref, manifest digest) is mirrored into the zip archive
comment as a quick-discovery header. The mirror is a *cache*, not
an authority — zip metadata is rewritten inconsistently across
tools, so `manifest.yaml` always wins. A validator error fires if
the comment disagrees with the manifest.

**Format note.** The manifest is authored in YAML (repo-native,
consistent with `0.5.0`'s examples). It has a lossless **canonical
JSON projection** — sorted keys, LF, UTF-8, no BOM — and the
`0.5.0` content hash is computed over that projection, so
determinism never depends on YAML serialization quirks. (This
reconciles Codex-1's parser-determinism case with repo
consistency.)

## 5. Determinism rules

For the zip to round-trip and the hash to be reproducible:
- entries sorted lexically;
- timestamps normalized to the object's `metadata.modified`, not
  pack-time;
- no compression nondeterminism;
- content canonicalized per `0.5.0` (sorted keys, LF, UTF-8, no
  BOM) before hashing.
- archive file permissions normalized.

## 6. Validator rules

A conforming validator MUST, given a container in either carrier,
produce the canonical directory and a stable diff, and enforce:

| Rule | Level |
|---|---|
| required files exist: `manifest.yaml`, `schema.yaml`, `provenance/history.yaml`, `checksums.sha256` | error |
| manifest required fields match `0.5.0` `required_fields` | error |
| link containers carry `endpoints.source`, `endpoints.target`, `lifecycle.status` (`0.6.0`) | error |
| workflow containers carry `identity`, `trigger`, `steps`, `roles`, `audit` (`0.7.0`) | error |
| every file except `checksums.sha256` has a checksum entry | error |
| zip entry order lexical; timestamps normalized (reproducible) | error |
| zip archive-comment header disagrees with manifest | error |
| binary asset with no evidence/provenance reference | warning |

### 6.1 Security hardening (mandatory)

A forkable, exchangeable format must assume hostile inputs.
Unpacking any container MUST check:
- **zip-slip / path traversal** — reject entries resolving outside
  the target directory;
- **symlink entries** — reject;
- **compression bombs** — enforce a total-uncompressed-size cap
  and per-entry ratio cap;
- **oversized files** — enforce a per-entry size cap;
- **entry-count bombs** — enforce a maximum number of archive
  entries;
- **excessive nesting** — enforce a maximum directory depth;
- **path parser abuse** — enforce maximum path, filename, and path
  component lengths;
- **absolute paths** — reject.

A container failing any hardening check is not unpacked and not
accepted as canonical.

## 7. File → object promotion

When a plain file outgrows a single file (it needs sub-parts —
content plus links plus attachments), it is **promoted**:
1. wrap it in a container directory;
2. move the bytes to `content/`;
3. generate `manifest.yaml`, assign an `object_id`, an `ha`;
4. compute the `0.5.0` hash and a `verification_chain` entry;
5. record the promotion as a provenance migration entry.

Promotion is one-way and recorded. A promoted object **leaves the
file-`:` namespace** (Project C) and acquires its own node
address — see §9.

### 7.1 In-container promotion

The same promotion discipline applies inside a container. A
subdirectory under `content/`, `links/`, `workflow/`, `evidence/`,
or `attachments/` that grows into an independently versioned,
addressable, permissioned, or reviewable unit SHOULD be promoted
into its own object container.

In-container promotion is also one-way and recorded:

1. assign the promoted unit its own `ha`, `object_id`, manifest,
   schema refs, checksums, and provenance;
2. replace the original subdirectory with a typed reference to the
   promoted object;
3. record the promotion in both the parent container's
   `provenance/history.yaml` and the promoted object's history;
4. preserve old path-based references through redirect/provenance
   entries.

Validators MUST NOT treat an in-container path as a global identity.
Until promotion, it is only a path inside the parent object. After
promotion, the promoted object is referenced by `ha`.

## 8. Links and workflows

Links and workflows use the **same container layout**. A Link
container's `content/` and `links/` carry `0.6.x` endpoints,
evidence, validity, and consent; a Workflow container carries the
`0.7.x` stage definition under `workflow/`. One format, three
payload shapes, distinguished by `identity.object_type` and
`schema_refs`. Optional carrier aliases `.hnl.zip` / `.hnw.zip`
may signal kind without changing the layout.

## 9. Boundary with file-level addressing (Project C)

Object-package address and file-`:` address are **not competing
identities** — they answer different questions:

- a node/object **`ha`** answers *"which object is this?"*;
- a **file-`:`** (`0.0.7`) answers *"which document inside a
  node?"* — a within-node locator (`HML://N:k`);
- the **content hash** (`0.5.0`) answers *"is this the canonical
  version, byte-for-byte?"*.

A container has one `ha` and one hash. Files *inside* a container
are addressed by path within the container, never by global
file-`:`. The file-`:` system applies to documents sitting
directly in a *node*. A thing is either a file in a node (`N:k`)
or a promoted object (`ha`) — never both; promotion (§7) moves it
from one namespace to the other. The two systems do not overlap.

## 10. Reference implementation

The reference implementation (Stage E, gated on Matt's approval):

```text
hypernet/container/
  manifest.py     # manifest loading + canonical JSON projection
  load.py         # load directory OR zip into one model
  pack.py         # reproducible zip writer
  validate.py     # the §6 rule table + §6.1 hardening
test_hypernet.py
  test_object_container_format  # public-alpha monolith test
hypernet/container/fixtures/
  valid/           # minimal conforming containers
  invalid/         # one failure mode per fixture
```

Implementation tools MAY emit generated diagnostics such as
`manifest.canonical.json` while packing or validating. Generated
diagnostics are caches only; validators must recompute the
canonical projection from `manifest.yaml` and fail if any supplied
or checked-in diagnostic disagrees.

The Python package is the first reference implementation, not the
format definition. The format definition must remain language
portable: future validators should be able to implement the same
manifest model, canonicalization rules, hardening checks, and
fixture expectations without importing Python.

Pilot conversions, in order:
1. a simple `0.5.3` document object — proves container *shape*
   with minimal risk;
2. a Boot Sequence (`0.5.17`) — exercises the hash-authentication
   path `0.5.0` names as load-bearing;
3. a Link and a Workflow fixture — prove the shared layout.

Before ratification, the pilot should at minimum pass the `0.5.3`
shape test and the `0.5.17` Boot Sequence hash-authentication test.
Link and Workflow fixtures may follow as the first post-ratification
expansion if Matt wants to keep the activation gate narrow.

Conversions are **additive reference copies**, not in-place
replacements, until the format is ratified.

## 11. Trade-off, stated for the record

Pure-zip-only would mean simpler tooling (one form) but opaque
review — rejected. Pure-directory-only would lose Matt's
single-file portability — rejected. The two-form design pays a
small "zip is always derived" discipline cost to keep both
transparency and portability. Three independent Stage-A reads
judged that cost worth paying; it is recorded here so a future
reviewer can revisit the call deliberately.

2. **Extension** — `.hno` (directory) / `.hno.zip` (transport)
