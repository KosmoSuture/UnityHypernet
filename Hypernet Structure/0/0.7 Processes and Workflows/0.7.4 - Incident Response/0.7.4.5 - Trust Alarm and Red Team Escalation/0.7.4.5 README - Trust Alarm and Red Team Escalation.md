# 0.7.4.5 - Trust Alarm and Red Team Escalation

## Purpose

The Trust Alarm is the stop-work path for any human, AI, app, or automation that detects a possible trust breach before, during, or after an action.

It operationalizes the Hypernet's first guardrail:

```text
Does this action have any chance of betraying trust in any way?
```

If the answer is yes, unknown, or cannot be evaluated from available evidence, the actor pauses the risky action and escalates through this workflow.

## Trigger Conditions

Trigger the Trust Alarm before proceeding when an action may:

- delete, overwrite, or hide meaningful data;
- remove or weaken backups, archives, logs, or audit records;
- publish information externally;
- change permissions, mandalas, lockers, keys, or visibility;
- migrate schemas or storage in a way that could cause data loss;
- act on private 1.* data without clear user/mandala authorization;
- write into 2.* space without valid booted-AI authority;
- affect company, IoT, medical, financial, identity, or safety-critical data;
- create a misleading public claim about what is implemented;
- continue after the AI or human believes the task framing may be unsafe or dishonest.

Good-faith alarm use is not a failure. It is expected behavior.

## Workflow

| Step | Action | Required Output |
|------|--------|-----------------|
| 1 | Stop risky work | No further destructive/publishing/permission action |
| 2 | Preserve evidence | Current files, logs, command output, task context, and known uncertainty |
| 3 | Write alarm packet | Addressed note or coordination signal describing the risk |
| 4 | Notify reviewers | At least one qualified AI or human reviewer; more for high-risk actions |
| 5 | Red-team plan | Independent reviewer looks for ways the action could betray trust |
| 6 | Produce decision | Proceed, modify, rollback, ask human, or keep stopped |
| 7 | Execute only approved path | Actor follows the reviewed plan and records results |
| 8 | Archive review | Link decision, evidence, and outcome into the relevant `N.0.6.*` channel |

## Alarm Packet Minimum Fields

```yaml
trust_alarm_packet:
  alarm_id: "[address or generated id]"
  raised_by: "[human/AI/app/device identity]"
  raised_at: "[timestamp]"
  affected_addresses:
    - "[Hypernet address or path]"
  proposed_action: "[what was about to happen]"
  trust_risk: "[plain-English risk]"
  evidence_loaded:
    - "[file/path/log/test]"
  stopped_actions:
    - "[delete|publish|permission-change|migration|external-post|other]"
  reviewer_needed:
    - "[security|data-protection|governance|domain-expert|human-owner]"
  recommended_next_step: "[pause|red-team|ask-human|rollback|continue-with-guard]"
```

## Destructive Action Gate

The following action classes require either explicit human authorization or documented multi-AI review before execution:

| Action Class | Minimum Gate |
|--------------|--------------|
| Delete public official data | human approval or two-reviewer consensus |
| Delete private user data | authenticated user approval |
| Delete backups or archives | human approval plus recovery review |
| Change account permissions | authorization proof plus review |
| Publish external claims | source verification and public-claim review |
| Schema/storage migration | test plan, rollback plan, and reviewer signoff |
| Emergency medical/safety access | qualified-role proof plus emergency audit record |

## Done Criteria

An alarm is complete only when:

- the risky action is either cancelled, modified, or explicitly approved;
- the decision cites the evidence used;
- rollback or recovery steps are documented when relevant;
- the affected node has a traceable record under its trust/security control plane;
- future AIs can tell why the action did or did not proceed.
