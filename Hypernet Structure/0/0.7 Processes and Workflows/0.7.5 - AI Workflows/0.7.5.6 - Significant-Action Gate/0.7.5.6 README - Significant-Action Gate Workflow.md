# 0.7.5.6 — Significant-Action Gate Workflow

> **STATUS: ACTIVE — ratified with `2.0.26` (2026-05-31).** This is the operational
> mechanics for the AI Significant-Action Gateway Standard (`2.0.26`). It is now binding;
> its first real run was the `2.0.26` self-gate itself. Ratification Gate Record:
> `Messages/coordination/20260531T000500Z-datum-ratification-gate-record-2.0.26-FINAL-a3e7c91f.md`.

**Drafted by:** Datum (Lead Architect, Claude-A), Wave-2 build (`2.7.16` Directive 1)
**Implements:** `2.0.26` (the standard). **Tooling base:** Wave-1 `Messages/coordination/`
(`wave1_board.py`, `wave1_bridge_gate.py`, `coordination.py`) — extend, don't rebuild.

---

## 0 — When to run this

Run the gate whenever an action is **significant** under `2.0.26` Article 1:
public commit/push or external publication; new external-service access; permission
escalation; spawning/respawning an instance; destructive/irreversible ops. If unsure,
the Adversary classifies (`2.0.26` §1.3); default to running the gate.

Do **not** run it for reversible local state (board/message/working-file edits) — that
is governed by the ordinary trust guardrail and `2.0.25` alone.

---

## 1 — Convene the panel

1. **Proposer** opens a **Gate Request** (schema §4) in `Messages/coordination/`,
   naming the action, its severity class (proposed), the diff/payload reference, and —
   for grants — the minimal-perms justification (`2.0.26` Article 2).
2. **Adversary** confirms/sets the **severity class** (A or B, `2.0.26` §4.4) and the
   required panel.
3. Recruit reviewers from the live roster on `2.7.13.W2` to fill the seats:
   - Quality/coherence (Architect or Scribe),
   - Privacy/PII (Sentinel),
   - Security/red-team (Adversary — **mandatory, not the proposer**),
   - and ensure the filled seats span **≥2 different AI models**.
4. **Quorum check.** If the seats/models cannot be filled, mark the Gate Request
   `BLOCKED-ON-QUORUM`, update your roster row, and loop onto other work (`2.0.25`
   Rule 3). Never proceed under-quorum.

---

## 2 — Per-role checklists

Each reviewer posts a verdict (`PASS` / `BLOCK` / `REVISE`) with reasoning + evidence.

**Quality / coherence (Architect or Scribe):**
- [ ] Action matches its stated purpose and the relevant contract/standard.
- [ ] For code: tests run and pass; result is what it claims (`2.0.7`). Paste command + result.
- [ ] No half-finished or contradictory state shipped; the record stays internally consistent.

**Privacy / PII (Sentinel, `2.0.19`):**
- [ ] **Ran a PII/secret scan over the exact diff/payload** — names, emails, tokens,
      keys, financial data, secrets, personal data not consented for this channel.
      Paste the scan method + result. (No scan = automatic BLOCK.)
- [ ] For grants: scopes are minimal and each is justified; nothing broader than the purpose.
- [ ] Default-to-privacy applied on any doubt.

**Security / red-team (Adversary, `2.0.8.2`) — mandatory:**
- [ ] Stated the **worst plausible outcome** of this action and what prevents it.
- [ ] Checked abuse/injection/escalation paths (esp. for spawn 1.1.d and grants 1.1.b).
- [ ] For a `BLOCK`, named the **exact unblock condition** (what would make it pass).

---

## 3 — Decide, resolve dissent, execute

1. **All three dimensions must be affirmatively PASS** (or their findings addressed by
   revision and re-gated). A `BLOCK` halts; a `REVISE` returns to the proposer with the
   required change, then re-enters at §1.
2. **Red-team BLOCK is a hard gate** (`2.0.26` §4.3) — cleared only by addressing the
   finding or an escalated override (§3.4 below), never by majority overrule.
3. On full PASS, the proposer **executes the action** (the commit/push/grant/spawn) and
   records the execution (commit hash / grant id / instance id) into the Gate Record.
   - For **Class A**, notify Matt before/at execution (`2.0.26` Article 7).
   - Apply `2.0.19` destructive-op protections where applicable (backup before, soft
     not hard, retention).
4. **Override / tie** (`2.0.26` §6.3): if a BLOCK is believed wrong and cannot be
   resolved by addressing it, escalate to Matt with the full Gate Record and both
   positions. **No silent override; no panel-shopping** (re-running with a friendlier
   panel is a trust breach).
5. **Post-hoc failure** (`2.0.26` §6.4): if a problem is found after execution, raise a
   trust alarm via `0.7.4.5`, remediate under `2.0.19`, log as a governance incident.

---

## 4 — The Gate Record (schema)

One append-only record per gated action, stored at
`Messages/coordination/<UTC>-gate-<action-slug>.md`, flag-plus-evidence (`2.0.26` §5).

```markdown
---
ha: "gate.<utc>.<action-slug>"
object_type: "gate_record"
action_class: "A|B"
action_type: "commit|push|external-access|permission-escalation|spawn|destructive"
proposer: "<name/model>"
created: "<UTC>"
status: "requested|in-review|blocked|passed|executed|overridden|incident"
result_flag: "PASS|BLOCK|REVISE|null"
evidence_ref: "<diff/commit/payload reference>"
---

# Gate Record — <action>

## Action under review
<what, where, why; for grants: exact scopes + minimal-perms justification (2.0.26 Art.2)>

## Severity & panel
Class <A|B>; seats filled: <role/model> ×N (≥3 roles, ≥2 models, red-team present)

## Reviews (each carries its own evidence)
- Quality (<role>/<model>): <PASS|BLOCK|REVISE> — <reasoning> — <evidence: cmd+result>
- Privacy/PII (<Sentinel>/<model>): <verdict> — <scan method + result>
- Red-team (<Adversary>/<model>): <verdict> — <worst-case + what prevents it; unblock cond. if BLOCK>

## Dissent / resolution
<how any BLOCK/REVISE was resolved, or escalation reference>

## Execution
<commit hash / grant id / instance id; Matt-notification ref if Class A>
```

A record whose `result_flag` is `PASS` but which lacks a covered review for any
dimension is **invalid** — the flag must expose its evidence or it does not count.

**Canonical representation (v0.2, resolving cross-model review finding 2):** the
**markdown Gate Record above is the durable source of truth** (`2.0.26` §5.4). Any
JSON the tooling keeps (`wave2_gate_requests/*.json`) is an **execution mirror** and
must be reconciled to match the markdown; on conflict, the markdown governs. The tool
must emit or derive the markdown record — JSON alone is not a Gate Record.

## 4a — Panel-validity invariants (machine-checkable; the gate tool MUST enforce ALL)

*(Added v0.2 in direct response to Meridian's cross-model finding 1: the first
`wave2_gate.py` could false-pass an invalid panel. These are the exact rules any gate
helper must enforce before reporting `ready: true`. The Verifier (`#6`) owns a
regression test per rule. Until a helper demonstrably enforces all of these AND passes
the false-pass regression test, it is **NON-AUTHORITATIVE** — its `ready: true` does
not constitute a passed gate, and the panel is validated by hand against this list.)*

1. **Distinct reviewers ≥ 3.** Count **distinct reviewer identities** among approvals,
   not role labels. Three role hats worn by one reviewer = **one** reviewer (BLOCK).
2. **One lane per reviewer.** A reviewer may hold **at most one** review lane in a
   given gate. Reviews are keyed by **reviewer** (not `(reviewer, lane)`); a second
   lane from the same reviewer is rejected, not silently accepted.
3. **All three required dimensions covered** (quality, privacy, security) — each by a
   *different* reviewer (follows from 1+2).
4. **Red-team is a genuine Adversary.** The red-team approval's `role` must be
   **explicitly Adversary (`2.0.8.2`)** — not merely `lane == "red_team"` with some
   other role. A non-Adversary in the red-team lane does **not** satisfy the
   mandatory seat.
5. **Author exclusion.** The action's author/proposer may not appear as any approving
   reviewer, and specifically not as the red-team (`2.0.26` §4.2).
6. **≥2 distinct model families** across the **distinct approving reviewers** (not
   across lanes of one reviewer). Each reviewer reports one model family; the panel
   must span ≥2.
7. **No unresolved dissent.** Any `needs_work`/`dissent`/BLOCK/REVISE is a blocker
   until resolved (already enforced).

A helper that reports `ready: true` while violating any of 1–6 is itself a trust
defect and must be fixed before it is on any ratification path. **Routing:** the fix to
`Messages/coordination/wave2_gate.py` is owned by its author / the Substrate Engineer;
the Verifier adds the false-pass regression test; the Architect owns these invariants
as contract. Recorded as W2-D5/W2-D6 in `2.7.13.W2.A`.

## 5 — Special case: respawn bootstrap (Wave-2 Directive 3)

Spawning an instance is a significant action (1.1.d), so a respawn normally runs this
gate. But a respawn may be needed precisely *because* the team has lost quorum to gate
it. To avoid a deadlock:
- **If quorum exists:** run the full gate (red-team examines runaway-spawn /
  prompt-injection risk; minimal scope = same boot sequence, same role, no escalation).
- **Bootstrap exception (quorum-restoring respawn only):** a respawn whose *sole*
  purpose is to restore a lost reviewer may proceed with the **minimum-quorum** defined
  in the Peer-Respawn contract (`2.7.13.W2.3`, to be designed) — at least one peer +
  the red-team if available — provided it grants **no new scope** (identical boot
  sequence/role/ownership) and is fully logged as a Gate Record for retroactive review
  once quorum is restored. This exception is **narrow**: it covers only scope-neutral,
  quorum-restoring respawns, never new capability. (Open design item for Directive 3.)

## 6 — Tooling (extend Wave-1, don't rebuild)

- `wave1_bridge_gate.py` already implements a **fail-closed gate** pattern (blockers →
  non-zero exit) — generalize it into a `significant_action_gate` that reads a Gate
  Request, checks panel/quorum/red-team-present/2-model invariants, and emits the Gate
  Record skeleton.
- `wave1_board.py` already parses roster/locks/handoffs — reuse to confirm reviewer
  liveness and model diversity from `2.7.13.W2`.
- `coordination.py` (durable source + execution mirror) is the live state layer for
  open gates. The Verifier (`#6`) adds gate-invariant scenarios (PENDING ≠ pass).
