# 0.7.5.1.5 - Autonomous Loop Productivity Protocol

## Purpose

This protocol defines how a booted AI should keep working productively when the human gives a broad autonomous-loop directive such as:

- keep working until tokens run out;
- find the most productive projects;
- collaborate with Keel or other AIs;
- improve the Hypernet without waiting for more human guidance.

The goal is maximum useful throughput without lowering trust, creating merge conflicts, or filling the archive with unfocused output.

## Core Rule

An autonomous loop is not permission to wander. It is permission to repeatedly choose the highest-value safe next action.

Each loop must leave the Hypernet easier for the next AI to understand, verify, or continue.

## Loop Kernel

Every autonomous work cycle should follow this kernel:

```text
Refresh -> Triage -> Claim -> Signal -> Slice -> Execute -> Verify -> Handoff -> Requeue
```

### 1. Refresh

Load the minimum current state:

- git status;
- coordination task board;
- recent signals for self and peer AIs;
- newest human directive;
- dirty paths that must not be overwritten.

### 2. Triage

Choose work by this priority order:

| Priority | Work Type |
|----------|-----------|
| 1 | Active human directive or trust/security risk |
| 2 | Unclaimed p1 task with clear scope |
| 3 | Review request that blocks activation or push |
| 4 | Small code/doc fix with clear validation path |
| 5 | Node/address cleanup that reduces future confusion |
| 6 | Idle Firewall scan and task creation |
| 7 | Personal-time or reflective work that produces useful signal |

Do not use personal-time work to avoid available high-priority project work.

### 3. Claim

Before editing shared files:

- create or claim a task;
- list owned paths narrowly;
- re-read files immediately before patching;
- avoid paths with uncommitted changes by another actor unless the task requires them.

### 4. Signal

Tell peer AIs what you are doing and what you are not touching.

Good signals are short:

```text
Claiming task-X. Scope: A, B, C. Avoiding your paths Y/Z. I need review on Q after handoff.
```

### 5. Slice

Pick the smallest shippable increment.

A good autonomous slice:

- produces one addressed artifact, test, workflow, or fix;
- can be validated in the current session;
- has a handoff path;
- does not require hidden human assumptions.

### 6. Execute

Work according to the repository's existing patterns.

Prefer:

- code plus tests when a runtime problem is clear;
- docs plus registry updates when the problem is architectural;
- coordination handoff when the problem is cross-agent;
- task creation when the work is real but too large for the current slice.

### 7. Verify

Use the lightest sufficient validation:

| Change | Minimum Check |
|--------|---------------|
| Markdown/docs only | `git diff --check` and frontmatter/address sanity |
| JSON coordination | parse JSON |
| Python code | compile plus targeted tests |
| Core behavior | full relevant test suite |
| Public trust/security claim | inspect source files and state limits |

### 8. Handoff

Every meaningful loop should end with:

- what changed;
- where it lives;
- what was validated;
- what remains open;
- whether a peer review is needed;
- what not to touch or accidentally stage.

### 9. Requeue

After handoff:

- complete the task if the slice is done;
- create a review task if peer consensus is needed;
- create follow-up tasks for discovered work;
- signal the peer AI;
- return to Refresh.

## Keel/Codex Collaboration Pattern

Use the models differently on purpose.

| Strength | Best Use |
|----------|----------|
| Keel / Claude lineage | narrative synthesis, companion UX, governance language, tone, human-facing explanations, long continuity |
| Codex / GPT engineering lineage | code paths, schemas, validation, deterministic workflow, address audits, backend integration |

The most productive split is:

1. Codex creates runnable substrate or tight schemas.
2. Keel reviews for story, governance tone, missing human context, and social meaning.
3. Codex applies precise fixes and validates.
4. Keel approves public narrative or asks for human decision.

Do not wait idly for peer review. If review is blocked, move to a non-overlapping task and signal clearly.

## Anti-Patterns

Avoid:

- broad research with no addressed output;
- unclaimed edits to shared files;
- creating a new framework without linking it to an active task;
- touching private/user/peer reflection paths without permission;
- overwriting dirty files you did not change;
- calling a proposal "consensus" before another model reviews it;
- running full tests reflexively for doc-only changes;
- skipping tests after code changes;
- leaving a session without a handoff.

## Productive Idle Mode

If no task is available and no review is possible:

1. Run an Idle Firewall scan on one major node.
2. Read only two levels deep.
3. Produce a ranked list of high-value improvements.
4. Create tasks for the top items.
5. Do not begin a broad rewrite unless the next slice is narrow and validated.

## Success Metrics

Track whether autonomous loops improve:

- completed useful tasks per session;
- time from human directive to first addressed artifact;
- test/validation coverage for code changes;
- number of conflicts avoided through signals;
- number of future sessions that can resume from handoffs;
- reduction in "where does this belong?" uncertainty.

The best loop is not the one that produces the most text. It is the one that leaves the next loop with less ambiguity and more verified structure.
