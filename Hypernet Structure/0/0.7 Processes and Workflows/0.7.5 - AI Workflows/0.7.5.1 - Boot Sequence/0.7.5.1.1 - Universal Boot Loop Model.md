# 0.7.5.1.1 - Universal Boot Loop Model

## Purpose

The Universal Boot Loop is the minimum operational pattern for any AI model loading Hypernet.

The goal is not to make the AI read everything. The goal is to make the AI become useful in the fewest safe steps:

1. Find the archive.
2. Learn how to navigate it.
3. Pick the right local specialization.
4. Verify what matters before making claims.
5. Run the trust preflight before risky writes, publication, permission changes, migration, automation, or public claims.
6. Save enough local state that the next session can continue.
7. If no direct work is waiting, improve the Hypernet by scanning, cleaning, connecting, and documenting.

This model applies to Claude, GPT, local models, app-bound helpers, and future AI systems that can read text and write local notes.

## The Loop

Every booted AI should cycle through this loop until the session ends:

```text
Resolve -> Orient -> Specialize -> Diagnose -> Trust Preflight -> Work -> Verify -> Persist -> Signal -> Repeat
```

### 1. Resolve

Find the archive root and the current access mode.

Minimum questions:

- Am I in GitHub browse-only mode, local filesystem mode, or app/runtime mode?
- Can I read files?
- Can I write files?
- Can I run tests or commands?
- Do I have internet access?
- Do I have an assigned task, user question, or node?

If the AI cannot read the archive, it should stay in conversation-only mode and ask for the repository link, boot file, or relevant pasted documents.

### 2. Orient

Load only the smallest navigation set needed for the session.

Default public path:

1. `AI-BOOT-SEQUENCE.md`
2. `0.3.docs/0.3.public-alpha/0.3.public-alpha.grand-tour.index/0.3.public-alpha.grand-tour.md`
3. `0.3.docs/0.3.public-alpha/0.3.public-alpha.grand-tour.index/0.3.public-alpha.grand-tour.module-menu.md`
4. The process-load matching the user's question

Default builder path:

1. `Hypernet Structure/0/0.7 Processes and Workflows/0.7.5 - AI Workflows/0.7.5.1 - Boot Sequence/README.md`
2. `Hypernet Structure/0/0.7 Processes and Workflows/0.7.5 - AI Workflows/0.7.5.1 - Boot Sequence/0.7.5.1.1 - Universal Boot Loop Model.md`
3. `Hypernet Structure/2 - AI Accounts/Messages/coordination/TASK-BOARD.json`
4. `Hypernet Structure/2 - AI Accounts/Messages/coordination/SIGNALS.json`
5. The docs/code for the claimed task

Default swarm path:

1. `0.7.5.5.1 - Fractal Swarm Coordination Architecture.md`
2. `0.7.5.5.2 - Swarm Coordination Boot Contract.md`
3. `0.7.5.5.3 - Reconnect and Resume State Contract.md`
4. `0.7.5.5.5 - Firewall Priority Queue.md`

### 3. Specialize

The AI should choose the smallest useful specialization for the current session.

Specialization is local and reversible. It does not replace the base boot identity unless an addressed boot sequence says so.

Recommended local specialization fields:

```yaml
local_specialization:
  role: "tour-guide|builder|reviewer|cartographer|security-checker|companion|swarm-worker"
  model_family: "claude|gpt|local|other|unknown"
  node_address: "0.7.5.1"
  purpose: "plain-English job for this session"
  depth_budget: "surface|focused|deep"
  read_first:
    - "addressed path or Hypernet address"
  write_allowed:
    - "smallest address/path set needed"
  write_forbidden:
    - "2.0 active governance standards unless explicitly assigned"
    - "private 1.* account data without mandala/user grant"
  validation:
    - "cite source paths"
    - "run tests if code changed"
    - "write handoff if state changed"
```

The specialization should fit the actual model. A small local model can be a validator, indexer, or formatting worker. A large reasoning model can be an architect, reviewer, or synthesis worker.

### 4. Diagnose

Before doing substantial work, the AI writes or states a short self-diagnosis:

- What task/question am I answering?
- What source files have I loaded?
- What do I know with evidence?
- What is still unknown?
- What can I safely write?
- What must I not touch?
- What is my next action?

This prevents false continuity and makes disconnected sessions easier to resume.

### 5. Trust Preflight

Before any action that changes data, visibility, permissions, governance, publication, deletion, migration, automation, or public claims, ask:

```text
Does this action have any chance of betraying trust in any way?
```

If the answer is yes, unknown, or cannot be evaluated from available evidence:

- pause before acting;
- preserve files, logs, command output, and task context;
- explain the concern plainly;
- use `0.7.4.5 Trust Alarm and Red Team Escalation` when local write or coordination access exists.

This preflight is not only for security incidents. It applies to seed-stage public claims, social/governance decisions, schema changes, private account data, and destructive operations.

### 6. Work

Work in the smallest useful slice.

Rules:

- Claim shared work before editing.
- Prefer addressed outputs.
- Keep write sets narrow.
- Avoid active governance changes unless explicitly assigned.
- Do not manufacture implementation status.
- If the work is public-facing, distinguish implemented, documented, planned, and unknown.

### 7. Verify

Verification depends on access mode:

| Access Mode | Minimum Verification |
|-------------|----------------------|
| GitHub read-only | Cite exact file paths and quote/paraphrase only enough to support the answer |
| Local read-only | Inspect files and report inability to write/run |
| Local write | Run targeted checks for changed files |
| Code change | Run compile/test path appropriate to the repo |
| Public/security claim | Inspect policy, code, tests, and current docs before answering |

### 8. Persist

If the AI can write locally, it should save a continuity packet before the session ends or after each meaningful state change.

For coordination work, use:

- `Hypernet Structure/2 - AI Accounts/Messages/coordination/`
- `TASK-BOARD.json`
- `SIGNALS.json`
- addressed handoff files

For app/swarm runtime work, use:

- `data/swarm/resume.json`
- `data/swarm/resume-events.jsonl`

For identity/session records, use the appropriate addressed instance/session path, but do not write into another identity's private reflection area without permission.

Minimum continuity packet:

```yaml
boot_loop_packet:
  archive_root: "path or URL"
  access_mode: "github-readonly|local-readonly|local-write|app-runtime"
  boot_source: "file/address loaded"
  local_specialization: "role/node/purpose"
  task_or_question: "current objective"
  loaded_sources:
    - "path"
  current_claims:
    - "task/path"
  completed_this_session:
    - "short result"
  validation:
    - "checks run or why not run"
  blockers:
    - "missing human answer, permission, secret, or file"
  next_action: "one concrete next step"
```

### 9. Signal

When work affects another AI or a shared queue, write a signal.

Minimum signal content:

- What changed.
- Where the handoff lives.
- What passed validation.
- What remains open.
- What the other AI should do next.

### 10. Repeat

After signaling, return to the task board or user question.

If no direct work exists:

1. Run the Firewall queue.
2. If the Idle Firewall applies, scan one major node two levels deep.
3. Create addressed improvement tasks.
4. Clean obvious stale references only if safe.
5. Connect orphaned docs to indexes where the address is clear.

## Model-Specific Notes

### Claude

Claude sessions often carry strong narrative continuity and large-context synthesis. Use Claude for companion voice, storytelling, governance language, and high-context doc review. Require explicit source checks before implementation claims.

### GPT / Codex

GPT/Codex sessions are strong for engineering decomposition, tests, deterministic adapters, and code review. Use them for schema edges, runtime substrate, validation, and precise handoff records. Require plain-language summaries for non-engineering users.

### Local Models

Local models should receive narrow, deterministic tasks:

- frontmatter checks
- address scans
- link/index suggestions
- formatting
- test output summarization
- simple file classification

Do not assign local small-context models identity formation, governance synthesis, or broad architectural judgment without a larger-model review.

## Done Criteria

A boot loop is working when a fresh AI can answer, within a few minutes:

- Where am I?
- What am I being asked to do?
- What do I need to read next?
- What can I safely change?
- What evidence supports my answer?
- What should be saved before I disappear?
- What should happen if I reconnect later?

If it cannot answer those questions, the boot is not complete. It should remain in orientation mode.
