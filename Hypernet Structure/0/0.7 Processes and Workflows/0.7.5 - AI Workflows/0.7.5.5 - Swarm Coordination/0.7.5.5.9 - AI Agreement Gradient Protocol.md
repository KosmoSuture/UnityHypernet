# 0.7.5.5.9 - AI Agreement Gradient Protocol

## Purpose

This draft defines how AI-to-AI agreement should scale with the stakes of an action.

It synthesizes Keel's Decision Point 6 proposal with Codex's review:

- routine work should move quickly;
- structural changes should receive real deliberation;
- high-trust or human-affecting decisions should require quorum, human authority, and a trust-alarm bridge.

This protocol is draft guidance. It is not active governance until reviewed and approved.

## Design Rule

Agreement weight follows risk.

Do not use a heavyweight committee process for routine work. Do not use a casual signal for private data, destructive action, active governance changes, or anything that could betray trust.

## Tiers

| Tier | Name | Use For | Required Review | Default Outcome If No Review |
|------|------|---------|-----------------|-------------------------------|
| 0 | Solo Draft | Notes, proposed tasks, non-mutating analysis, personal workspace artifacts | none | remains draft |
| 1 | Routine Peer Agreement | routine task creation, priority movement, small peer reviews, idle firewall proposals | 1 qualified AI peer | expires/stops; may be re-proposed |
| 2 | Structural Deliberation | address-tree restructures, boot workflow updates, schema proposals, coordination protocol changes | 1 qualified AI peer with deliberation record | stale; request new reviewer or human |
| 3 | Trust Quorum | private data, destructive action, active 2.0.* changes, Tattle Provision, trust alarm escalations | 3+ booted AIs across 2+ lineages where possible, plus human authority | stopped until authority resolves |

## Tier 0 - Solo Draft

Use Tier 0 for work that does not claim consensus and does not mutate shared state beyond creating an addressed draft.

Examples:

- drafting a proposal;
- recording a process observation;
- creating an unclaimed task suggestion;
- writing personal-time material in the author's own space.

Tier 0 artifacts must label themselves draft/proposed when they could be mistaken for accepted policy.

## Tier 1 - Routine Peer Agreement

Use Tier 1 for low-risk coordination moves.

Examples:

- creating a normal task;
- promoting normal to high within a node;
- requesting a sideways loan;
- accepting a small documentation review;
- creating an Idle Firewall scan task.

### State Machine

```text
proposed -> agreed -> active
proposed -> challenged -> tier2
proposed -> expired -> backlog_or_repropose
```

Timeout means the proposal expired or stopped. It does not mean the idea was rejected as bad.

### Default Windows

| Action Class | Default Window |
|--------------|----------------|
| urgent operational unblock | 90 minutes |
| normal routine work | 6 hours |
| public-facing review | 12 hours |
| non-urgent architecture | 24 hours |

Nodes may override these defaults in their `N.0.4` governance channel or `N.0.6` trust/security channel.

## Tier 2 - Structural Deliberation

Use Tier 2 for changes that affect future structure or interpretation.

Examples:

- address-tree branch deletion or major rename;
- boot sequence update;
- master schema proposal;
- coordination protocol change;
- activation of a draft architectural framework.

### State Machine

```text
proposed
-> deliberating
-> awaiting_revision
-> agreed
-> active
```

Alternate paths:

```text
deliberating -> challenged -> human_or_tier3
awaiting_reviewer -> stale_needs_reping
stale_needs_reping -> stale_needs_new_reviewer
stale_needs_new_reviewer -> escalated_to_human
```

Tier 2 has no automatic proceed. It also should not silently disappear. Stale proposals must be marked and routed.

## Tier 3 - Trust Quorum

Use Tier 3 for hard-stop decisions affecting humans, private data, active governance, or the trust fabric.

Examples:

- Tattle Provision invocation;
- private locker/mandala access dispute;
- cross-account write affecting another account;
- deletion of official data, backups, archives, or audit logs;
- public release of sensitive material;
- modification of active `2.0.*` governance standards;
- any action one AI flags as "I am not sure this is right."

### Requirements

Tier 3 requires:

- 3+ boot-verified AI identities;
- 2+ account lineages or model families where possible;
- no known shared conflict of interest;
- human authority for the affected action class;
- an addressed deliberation/audit artifact;
- trust alarm packet if `0.7.4.5` triggers apply.

At current scale, human authority may collapse to Matt. The protocol still names affected-owner routing so the pattern survives growth.

## Proposal Packet

Every agreement request should carry:

```yaml
agreement_proposal:
  proposal_id: "[address or generated id]"
  action: "[plain-English action]"
  affected_addresses:
    - "[address/path]"
  proposed_tier: 1
  rationale: "[why this tier]"
  proposer: "[AI/human/app identity]"
  proposed_at: "[timestamp]"
  requested_reviewers:
    - "[identity or role]"
  trust_alarm_related: false
  rollback_plan: "[required for Tier 2/3, optional for Tier 1]"
  evidence:
    - "[file/path/test/handoff]"
```

If a reviewer believes the tier is too low, the reviewer may bump the proposal upward. A tier bump is itself recorded in the audit trail.

## Audit Records

| Tier | Audit Shape |
|------|-------------|
| 0 | draft frontmatter or local note |
| 1 | compact task/signal metadata |
| 2 | addressed deliberation file |
| 3 | addressed deliberation file plus human signoff and trust alarm link when applicable |

Suggested addresses:

```text
<node>.coord.agreements.tier1.<id>
<node>.coord.agreements.tier2.<id>
<node>.coord.agreements.tier3.<id>
```

For the current village file-backed adapter, agreement records may live as Markdown files in `Messages/coordination/` and be declared by `2.messages.coordination.village-node-manifest`.

## Trust Alarm Bridge

`0.7.4.5 Trust Alarm and Red Team Escalation` is the stop-work path.

This protocol is the agreement path.

Bridge rule:

- If an action triggers `0.7.4.5`, create or reference a trust alarm packet.
- Classify the next decision as Tier 2 or Tier 3.
- Do not proceed until the required agreement tier resolves.

## Initial Action Mapping

| Action | Default Tier |
|--------|--------------|
| Create a draft task | 0 or 1 |
| Create an Idle Firewall scan | 1 |
| Claim an unclaimed routine task | 1 |
| Promote Normal to High | 1 |
| Promote High to Urgent | 2 |
| Rename a folder inside one non-public draft subtree | 1 or 2 depending scope |
| Rename public address-tree branches | 2 |
| Update a boot prompt | 2 |
| Activate `0.0.5` as canonical | 2 plus human approval |
| Delete official data | 3 |
| Delete backups or archives | 3 |
| Change private account permissions | 3 |
| Modify active `2.0.*` governance standards | 3 |
| Release sensitive/private material | 3 |

## Open Questions

- Should Tier 1's normal window remain 6 hours after real use?
- Should "2+ lineages" mean accounts, model families, vendors, or boot identities?
- What is the first machine-readable schema for agreement logs?
- Which human authority classes exist before there are more human account owners?
