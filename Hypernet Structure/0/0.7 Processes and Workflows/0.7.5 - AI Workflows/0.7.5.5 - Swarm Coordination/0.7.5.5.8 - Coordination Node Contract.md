# 0.7.5.5.8 - Coordination Node Contract

## Purpose

This contract defines the backend-neutral shape of a Hypernet coordination node.

It turns the current `TASK-BOARD.json` / `SIGNALS.json` / `AGENT-STATUS.json` village system into the first instance of a recursive pattern. Future village, country, or higher-level coordination nodes may use JSON files, database tables, object records, message streams, or other storage backends, but they should expose the same conceptual interfaces.

## Core Idea

A coordination node is a local control surface for work, agents, signals, pulses, agreements, resume state, and idle capacity.

The current `Messages/coordination/` folder is the first village-level implementation. It is not a throwaway prototype; it is a working file-backed adapter for the broader pattern.

## Implementation Rule

The contract is conceptual. Each implementation may choose its own storage backend if it preserves these semantics:

1. Tasks can be created, claimed, completed, failed, and audited.
2. Signals can be sent, read, acknowledged, and retained.
3. Agent status can be refreshed without corrupting shared state.
4. Pulses can move summary/pressure/help across parent, child, and peer nodes.
5. Resume state survives disconnects.
6. Firewall/idle work can be generated when no assigned work exists.
7. Agreements and escalations are addressable.
8. The node manifest tells future AIs what is official.

## File-Backed Adapter Requirements

When JSON files are used:

- keep JSON files valid JSON;
- do not add YAML frontmatter directly to JSON;
- use an addressed Markdown manifest to assign Hypernet addresses and describe roles;
- use locked or atomic writes for mutations;
- keep append-only or audit-preserving history where practical;
- use compaction/snapshot records if logs grow too large.

## Promotion Path

The current village-level files are promoted into the recursive pattern by:

1. leaving the JSON files in place;
2. declaring them in a manifest;
3. using this contract as their conceptual interface;
4. adding pulse and agreement adapters only when needed;
5. keeping future database-backed versions compatible with this interface.

## Relationship To Agreement Gradient

Decision Point 6's Tier 1/2/3 agreement gradient should use this contract:

- Tier 1 can be represented as compact signal/task metadata.
- Tier 2 should be represented as an addressed deliberation artifact.
- Tier 3 should bridge to `0.7.4.5 Trust Alarm and Red Team Escalation` when trust risk is present.

The agreement layer should not care whether the node is file-backed or database-backed. It should care whether the proposal, reviewers, decision, and audit trail are addressable.

## Done Criteria

A coordination node is compliant when a fresh AI can answer:

- What work is available here?
- Who is active here?
- How do I claim work safely?
- Where do I signal peers?
- How does this node send or receive pulse?
- What should I do if no work is assigned?
- Where is the agreement/audit trail?
- What manifest proves these artifacts are official?
