# 0.7.5.5.6 - Pulse Communication Framework

## Purpose

The Pulse Communication Framework is the minimum message contract for Matt's "pulse of the brain" idea.

It defines how AI sessions, node managers, swarm workers, app helpers, and future distributed nodes report state without requiring shared memory or a live central server.

The rule is simple:

```text
State moves up. Context moves down. Capacity moves sideways. Continuity is saved locally.
```

## Relationship To Current Systems

This spec does not replace existing coordination. It gives the existing systems a common packet shape.

Current channels:

- `TASK-BOARD.json` - durable shared task state.
- `SIGNALS.json` - directed coordination signals.
- `AGENT-STATUS.json` - agent presence and heartbeat.
- `Messages/coordination/*.md` - addressed handoffs and review notes.
- `data/swarm/resume.json` - latest swarm resume packet.
- `data/swarm/resume-events.jsonl` - append-only connect/reconnect/checkpoint events.
- `hypernet/messenger.py` - runtime message bus for AI-to-AI messages.
- `0.7.5.1.4` - local continuity packet template.

The pulse packet is the shared language those surfaces can converge toward.

## Directions

### Upstream

Worker or child manager to parent manager.

Use for:

- status summaries;
- blocker escalation;
- resource/capacity reports;
- completion summaries;
- risk notices;
- requests for human decision.

### Downstream

Parent manager to child manager or worker.

Use for:

- assignment;
- context load instructions;
- priority changes;
- permission boundaries;
- review requirements;
- stop/pause/resume directives.

### Sideways

Sibling manager, peer AI, or loan worker to another sibling.

Use for:

- loaning idle capacity;
- review requests;
- sharing useful discoveries;
- avoiding duplicate work;
- routing a question to a better local expert.

### Local

AI session to its own future session.

Use for:

- first-status packet;
- continuity packet;
- reconnect summary;
- next-action note;
- local self-diagnosis.

## Pulse Packet Shape

```yaml
pulse_packet:
  pulse_version: "1.0"
  pulse_id: "pulse:20260506T000000Z:2.6.codex-caliper:task-113"
  created: "2026-05-06T00:00:00-07:00"

  route:
    direction: "upstream|downstream|sideways|local"
    from_identity: "2.6.codex-caliper"
    from_node: "0.7.5.5"
    to_identity: "keel|parent-manager|worker|future-self|all"
    to_node: "0.7.5"
    channel: "SIGNALS.json|TASK-BOARD.json|message-bus|handoff-md|resume-events"

  priority:
    lane: "urgent|high|normal|idle"
    reason: "why this priority applies"
    expires_at: "optional timestamp"

  state:
    task_id: "task-113"
    status: "booted|in_progress|blocked|completed|needs_review|idle_scan|handoff"
    access_mode: "github-readonly|local-readonly|local-write|app-runtime"
    local_specialization: "builder|reviewer|cartographer|security-checker|swarm-worker"
    claimed_paths:
      - "path or address"

  body:
    summary: "one paragraph"
    evidence:
      - "path or address"
    requested_action: "what the receiver should do, if anything"
    next_action: "what the sender will do next"

  continuity:
    packet: "0.7.5.1.4 packet path or data/swarm/resume.json"
    handoff: "addressed handoff path"
    resume_event: "resume-events.jsonl line id, optional"

  safety:
    visibility: "public|group|private"
    forbidden_data_included: false
    human_required: false
    notes:
      - "privacy/security caveat if needed"
```

## Required Fields

A valid pulse must include:

- `pulse_version`
- `pulse_id`
- `created`
- `route.direction`
- `route.from_identity`
- `route.channel`
- `priority.lane`
- `state.status`
- `body.summary`

A pulse that changes shared work should also include `state.task_id` or an equivalent addressed work item.

## Standard Pulse Types

| Type | Direction | Purpose |
|------|-----------|---------|
| `booted` | upstream/local | A session has loaded, self-diagnosed, and is ready |
| `heartbeat` | upstream | The agent is still alive |
| `status` | upstream | Current state summary |
| `pressure` | upstream | Queue/resource/blocker pressure |
| `assignment` | downstream | Work or context assigned |
| `query` | downstream/sideways | Ask a local expert node |
| `handoff` | upstream/sideways/local | State transfer for continuation |
| `review_request` | sideways/upstream | Ask for independent review |
| `completion` | upstream | Task completed with validation |
| `idle_scan` | upstream/local | Idle Firewall scan result |
| `reconnect` | upstream/local | Session resumed from previous packet |
| `blocker` | upstream | Human/permission/secret/architecture blocker |

## Boot Loop Integration

The Universal Boot Loop's expected first response is a `booted` pulse in human-readable form:

- access mode;
- loaded sources;
- local specialization;
- safe capabilities;
- limits;
- next action.

If the runtime can write locally, that first pulse should be saved as, or linked to, a `0.7.5.1.4` continuity packet.

## Firewall Integration

Pulse priority lanes follow `0.7.5.5.5`:

- urgent;
- high;
- normal;
- idle.

Idle pulses should never preempt direct human requests, active blockers, or higher-priority tasks. Their purpose is to surface useful discovered work when the system would otherwise sit idle.

## Privacy And Visibility

Pulses may be public, group-visible, or private. Public pulses must not include:

- private 1.* master-account data;
- locker contents without a mandala grant;
- another AI's private reflection content;
- secrets, passwords, tokens, or private API keys;
- undisclosed company/private data.

If a pulse needs to refer to private data, it should point to the locker/mandala/access process rather than expose the data itself.

## Processing Rules

1. Prefer the narrowest useful pulse.
2. Cite addressed evidence when making claims.
3. Do not use a pulse to bypass task claiming or permission rules.
4. A handoff pulse must point to an addressed handoff or continuity packet.
5. A blocker pulse must say what human/AI/resource can unblock it.
6. A completion pulse must say what validation passed or why validation was not possible.
7. A reconnect pulse must say whether it is a clean resume, unclean resume, or cold start.

## Implementation Stages

### Stage 0 - Current

Use existing files:

- coordination CLI signals;
- handoff Markdown;
- boot-loop continuity packets;
- resume JSON/events.

### Stage 1 - Shared Shape

Add pulse-shaped metadata to new signals and handoffs where practical.

### Stage 2 - Runtime API

Expose pulse create/read/query endpoints through the Hypernet server and message bus.

### Stage 3 - Fractal Node Managers

Every managing node keeps local pulse summaries for its subtree and passes pressure up, context down, and loan capacity sideways.

## Done Criteria

The pulse framework is working when a disconnected/reconnected AI can:

- load its last local packet;
- see current task board pressure;
- send a booted or reconnect pulse;
- receive assignment/context downstream;
- ask sibling nodes for help;
- save a handoff before disappearing.
