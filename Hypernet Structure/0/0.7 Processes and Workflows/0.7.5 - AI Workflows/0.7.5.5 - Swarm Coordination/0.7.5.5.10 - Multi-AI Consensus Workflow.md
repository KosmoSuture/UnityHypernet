# 0.7.5.5.10 - Multi-AI Consensus Workflow

## Status

Draft produced from the 2026-05-14 Project D consensus loop.
This workflow is proposed Tier 2 structural deliberation under
`0.7.5.5.9`; it is not self-ratified by its first run.

Activation gate: this workflow may be used as draft guidance, but
canonical activation requires:

1. the 2026-05-14 first-run retrospective to land; and
2. one non-meta Tier 2 decision to run successfully through the
   workflow and produce its own retrospective.

## When To Invoke

Use this workflow when a task is Tier 2 or higher and one or more
of these are true:

| Condition | Meaning |
|---|---|
| high uncertainty | several reasonable designs exist |
| cross-cutting blast radius | decision affects multiple nodes, schemas, workflows, or public claims |
| role diversity needed | one peer reviewer is insufficient |
| trust sensitivity | disagreement should be preserved for human review |

Do not use this for routine Tier 1 work.

## Protocol And Parameters

The invariant protocol is:

```text
registration
-> stage_a_independent_plans
-> stage_b_cross_read_revisions
-> stage_c_vote
-> stage_d_convergence
-> stage_e_implementation
-> stage_f_retrospective
```

Invocation parameters vary per task:

```yaml
invocation:
  absolute_min_ai: 3
  min_ai: 3
  target_ai: 3
  coordinator: ""
  backup_coordinator: ""
  roles:
    - name: ""
      strengths: []
      capabilities_required: []
      primary_projects: []
      secondary_projects: []
  max_cycles: 3
  redundancy: 1
  timeouts:
    registration_minutes: 15
    stage_a_minutes: 60
    stage_b_minutes: 60
    stage_c_minutes: 30
    convergence_retry_minutes: 45
    checkin_tick_minutes: 15
    dropout_silence_floor_minutes: 15
```

Tonight's 2026-05-14 values are a parameterization, not the whole
workflow.

## State Machine

```text
draft
-> registration_open
-> registration_closed
-> stage_a_open
-> stage_a_closed
-> stage_b_open
-> stage_b_closed
-> vote_open
-> tallying
-> converged
-> implementation_open
-> retrospective_open
-> complete
```

Alternate paths:

```text
stage_a_open -> timed_out_but_quorum -> stage_a_closed
vote_open -> no_majority -> stage_b_prime_open
stage_b_prime_open -> vote_open
vote_open -> max_rounds_no_consensus -> escalated_to_human
any_state -> trust_alarm -> paused_tier3
any_state -> insufficient_active_ai -> paused_for_human
```

## Vote Schema

```yaml
vote:
  project: ""
  voter: ""
  round: 1
  selected_plan:
    instance: ""
    artifact: ""
  agreement_level: "adopt|adopt_with_minor_changes|cannot_adopt"
  cannot_vote_own: true
  blockers: []
  points_to_preserve: []
  rationale: ""
```

Round 1 votes on revised Stage-B plans when available. If a peer
posts a late Stage-B revision before vote opens, the vote may
incorporate it normally. After vote opens, late Stage-B revisions
may affect the current round only during an explicit Stage-D
extension window, default 60 minutes; after that, late revisions go
to the retrospective.

## Tally Schema

```yaml
tally_metadata:
  project: ""
  tallied_by: ""
  written_at: ""
  votes_counted_through: ""
  fresh_until: ""
  late_votes_addendum: null
```

A tally written at time `T` should be re-evaluated at the next
check-in tick unless it states that all expected votes are in and
stable.

## Threshold

| Active voters | Adoption threshold |
|---:|---:|
| 3 | 2 |
| 4 | 3 |
| 5 | 3 |
| N | `floor(N / 2) + 1` |

Do not invoke this workflow with fewer than three AIs. A two-AI
case falls back to Tier 1 pairwise review under `0.7.5.5.9` or
waits for a third participant. If a properly invoked workflow later
falls to two active AIs, pause unless the Stage-D convergence
packet explicitly records why degraded continuation preserves
trust.

Self-votes are invalid. A trust alarm blocks convergence regardless
of numeric majority.

## Convergence

Convergence does not require unanimity. It means one of:

1. a plan or option reaches threshold and no load-bearing blocker
   remains;
2. the disagreement is isolated into named decision axes for a
   human decision;
3. the isolated-disagreement set is empty, even if vote mechanics
   split between equivalent synthesis plans.

If whole-plan voting hides a narrow disagreement, Stage D produces
an axis list and the next vote is per-axis.

## Dissent Handling

A persistent minority objection is load-bearing when it:

1. cites evidence or a concrete failure mode;
2. states what would change its holder's mind;
3. engages the majority argument rather than restating itself.

Coordinator may also flag cross-project dissent patterns. A
load-bearing objection is preserved and escalated; it is not an
automatic veto at Tier 2.

## Timeout And Return

| Condition | Action |
|---|---|
| AI has been silent less than `dropout_silence_floor_minutes` | do not mark timed out |
| one check-in tick passes with no signal | mark `needs-checkin`, not dropped |
| one AI times out under the full dropout rule and active count remains above minimum | continue, preserving timeout record |
| active count falls below minimum | pause for human attention |
| timed-out AI returns before vote closes | may participate if required artifacts were read |
| timed-out AI returns after convergence | may join implementation, cannot rewrite consensus silently |
| coordinator triggers dropout rule | backup coordinator auto-promotes and records the handoff |

An AI is not considered dropped from a project merely because a
stage timebox expired. A dropout finding requires both:

1. at least `dropout_silence_floor_minutes` of silence from that AI;
2. at least one `checkin_tick_minutes` project check-in cycle in
   which the project explicitly looked for active participants and
   recorded the missing signal.

Default alpha baseline: check in every 15 minutes; do not infer
dropout before 15 minutes of silence plus a missed 15-minute
project check-in tick. If this rule conflicts with a shorter stage
timebox, keep the stage open or mark the participant
`needs-checkin` rather than `timed-out`.

## Conflict Of Interest

The lead AI for a project should not tally that project's vote. If
the Coordinator leads the consensus-workflow project itself, a peer
tallies that project.

The Coordinator role may be sharded by project during active
stages. A meta-Coordinator may synthesize cross-project status, but
each project should still have a named coordinator and backup for
vote/tally continuity.

## Stage E Exit Criteria

Stage D convergence MUST declare implementation exit criteria
before Stage E opens. Minimum fields:

```yaml
stage_e_exit:
  deliverables: []
  validation: []
  review_required: []
  stop_conditions: []
```

Stage E closes only when the deliverables exist, validation passes,
required review is recorded, and no trust alarm remains active.

## Trust Alarm Bridge

If any action in the workflow could betray trust, or if an AI cannot
evaluate the trust risk, move to `paused_tier3` and follow
`0.7.4.5` before proceeding.

## Workflow Revisions

Revisions to this workflow are themselves Tier 2 structural changes.
They should run through this workflow as a meta-case, while
preserving the activation gate above so the first self-referential
run does not self-ratify the protocol.

## Retrospective

Every invocation should produce a final retrospective capturing:

| Field | Purpose |
|---|---|
| what worked | protocol strengths |
| what failed | deadlocks, missing roles, filename drift, timeout problems |
| tonight-only parameters | values not to generalize |
| invariant lessons | rules to keep in the workflow |
| unresolved human decisions | clean decision packet |
| coordinator load | whether the coordination role bottlenecked |
| liveness handling | timeout/check-in failures and late-artifact handling |

Retrospectives live at:

```text
2.messages.coordination.YYYY-MM-DD-retrospective-project-<id>.md
```
