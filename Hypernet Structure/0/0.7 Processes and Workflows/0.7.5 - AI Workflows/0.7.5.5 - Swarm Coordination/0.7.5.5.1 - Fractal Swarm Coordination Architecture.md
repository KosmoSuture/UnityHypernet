# 0.7.5.5.1 - Fractal Swarm Coordination Architecture

## Purpose

This document turns Matt's 2026-05-05 fractal swarm brain dump into an engineering architecture. It treats the current single-server swarm as the seed case of a recursive pattern: every Hypernet node can eventually have a managing AI process, a local task/project queue, a communication pulse to parent and child nodes, and a load-balancing policy for workers that can help nearby nodes.

The design goal is not "one giant swarm." The goal is many small swarms that can coordinate through the address tree without losing local context.

## Core Claim

Every addressable Hypernet node may become a coordination cell.

A coordination cell has:

- A node address, such as `0`, `0.7`, `0.7.5`, or `3.1.8`.
- A manager identity responsible for that node and the addressed descendants assigned to it.
- A local queue of projects, jobs, requests, reviews, alerts, and idle-time exploration tasks.
- A pulse channel upward to its parent manager.
- A dispatch channel downward to child managers or terminal workers.
- A summary cache that lets a reconnecting AI quickly recover the state of the node.

This recurses. The same pattern works at `0`, `0.7`, `0.7.5`, `3.1`, `3.1.8`, or any future deeper address.

## Node Roles

### Root Manager

The root manager coordinates the whole Hypernet deployment. It should not try to know every detail. Its job is to know what major branches exist, which are overloaded, which are blocked, which need human attention, and which child managers are healthy.

### Branch Manager

A branch manager owns an addressed subtree. It is the expert for the knowledge and active work below that address. It reports summaries up and accepts queries, policies, and work directives down.

Examples:

- `0.7` manager: process and workflow expert.
- `0.7.5` manager: AI workflow expert.
- `0.7.5.5` manager: swarm coordination expert.
- `3.1.8` manager: Marketing and Outreach expert.

### Terminal Manager

A terminal manager handles a node with no official child manager below it. It still manages local documents, links, tasks, and quality checks, but it does not forward work further down unless the node grows enough to split.

Terminal status is not permanent. A terminal node can become a branch node when it gains children or workload.

### Loan Worker

A loan worker is an AI process temporarily assigned outside its home node. It keeps its identity and work history, but the receiving node defines the local task, context bundle, and write scope.

Loan workers must receive:

- A task address.
- A bounded write set.
- A local context bundle.
- A return condition.
- A handoff requirement.

## The Pulse

The pulse is the recursive communication contract.

### Upstream Pulse

Child managers send compact state upward:

- Active projects.
- Blockers.
- Pending human decisions.
- Capacity and idle workers.
- Failed or stale tasks.
- Recently completed work.
- New high-value project ideas.
- Integrity or security warnings.

Upstream messages should be summarized and address-linked. The parent should not receive raw chatter unless raw context is explicitly requested.

### Downstream Dispatch

Parent managers send targeted work downward:

- Queries against a subtree.
- Priority changes.
- Policy updates.
- New project definitions.
- Requests for local audit.
- Requests to loan workers upward or sideways.

Downstream messages must include enough address context for a child manager to decide whether it can act locally or must split/delegate further.

### Sideways Loaning

Sibling managers should not directly overwrite each other's queues. A loan request flows through the closest common parent:

1. Node A reports excess work or a skill gap.
2. Parent sees Node B has idle capacity or matching skill.
3. Parent offers a loan assignment to Node B.
4. Node B accepts, spawns or assigns a worker, and sends the worker to Node A's task context.
5. Node A receives the work output and writes the official handoff.
6. Node B records the contribution for reputation/economy accounting.

This prevents hidden cross-branch collisions.

## The `*.0` Pattern

Matt's point about the `*.0` node is important. The `*.0` document at each node should describe the default local format:

- What belongs under the node.
- How children are numbered.
- Which object/link types are expected.
- What local workflows exist.
- What manager responsibilities apply.
- Where task/project queues live.
- How local exceptions are documented.

Subnodes may extend or break the pattern, but the break must be addressed and explicit. The architecture should prefer "documented local exception" over "silent drift."

## Queue Model

Every coordination cell has four queue surfaces:

| Queue | Purpose |
|---|---|
| Urgent | Safety, data loss, failing tests, access breakage, user-blocking issues |
| High | Matt-directed priorities, active release work, architecture foundations |
| Normal | Planned improvements, cleanup, docs, ordinary feature work |
| Idle Firewall | Default behavior when no higher-priority task applies |

The Idle Firewall is not filler. It is the growth engine. When idle, a manager or worker walks the Hypernet by node, understands up to two levels deep, and proposes the highest-value improvements. Those proposals become Normal or High tasks after review.

## Reconnect Model

A reconnecting AI must not reconstruct the world from chat memory. It should load a node resume packet:

- Identity and role.
- Assigned node address.
- Parent and child managers.
- Active tasks.
- Last known work claims.
- Open signals.
- Recent handoffs.
- Local queue summary.
- Next scheduled heartbeat or required pulse.
- Known blockers and human-decision gates.

The resume packet is small enough to load quickly and precise enough to avoid duplicate work.

## Current Seed Mapping

The current Python swarm already has pieces of the seed:

- `hypernet_swarm/swarm.py`: single-node manager loop.
- `hypernet/tasks.py`: task lifecycle.
- `hypernet_swarm/coordinator.py`: decomposition, capability matching, conflict detection.
- `hypernet_swarm/heartbeat.py`: scheduled proactive outreach.
- `hypernet_swarm/identity.py`: identity and session log loading.
- `data/swarm/state.json`: single-node persistent state.
- `Messages/coordination/TASK-BOARD.json`: external agent coordination.
- `Messages/coordination/SIGNALS.json`: file-based pulse between agents.

The next step is not to replace these pieces. The next step is to make their boundaries explicit and recursive.

## Proposed Implementation Stages

### Stage 0 - Documented Contract

- Define fractal node manager responsibilities.
- Define swarm coordination boot/app-load contract.
- Define reconnect/resume checkpoint schema.
- Define the Idle Firewall queue contract.

### Stage 1 - Local Resume Substrate

- Persist an explicit `resume.json` next to `state.json`.
- Include workers, active tasks, suspended workers, queue counts, last pulse, and next required actions.
- Record connect/disconnect/reconnect events as JSON lines.
- Add tests around resume plan generation.

### Stage 2 - Node Manager Registry

- Define a local registry mapping node address -> manager identity -> state directory.
- Allow a manager to compute whether a node is branch or terminal.
- Allow queries for child manager status.

### Stage 3 - Pulse Router

- Add upstream summary messages and downstream dispatch messages as typed message objects.
- Route parent/child pulses through the existing message bus first.
- Later, support server-to-server federation.

### Stage 4 - Load Balancing and Loans

- Add queue pressure metrics per node.
- Add worker skill/capacity advertisements.
- Add loan request, acceptance, completion, and contribution accounting.

### Stage 5 - Multi-Server Federation

- Split subtrees across servers.
- Synchronize node manager summaries, not whole repositories.
- Use Git/file state as bootstrap and graph/index backends for scale.

## Non-Goals For This First Pass

- No global distributed scheduler yet.
- No automatic write access across node boundaries.
- No hidden background worker creation without visible budget and permission controls.
- No replacing the existing task queue until the recursive contract is tested locally.

## Consensus With Keel

Keel's decoded threads are directionally correct. The key point I would add is that "swarm coordination" should not be treated as a feature inside one running process. It should be treated as a repeatable node-local contract. The Python swarm is one implementation of that contract, not the contract itself.

That distinction matters because it lets Hypernet scale from one laptop to many servers without changing the mental model: address, manager, queue, pulse, resume packet, handoff.
