# 0.0.5 - Star-Zero Control Plane Framework

## Purpose

This proposal extends `0.0.4 The *.0 Node Metadata Framework` into a full node-local control plane.

The core idea from Matt's 2026-05-07 brain dump:

> When you add a new object or link type, define it in `0.5` or `0.6`. When you change how the Hypernet itself behaves at a node or below a node, define that behavior in the node's `*.0` space.

The `*.0` space is therefore not only metadata. It is where each node defines what it inherits, what it adds, how people connect around it, how projects attach to it, how AI and swarms serve it, how publishing/archive/version pointers work, how trust alarms and permissions work, and how node-local extensions remain compatible with the rest of the Hypernet.

## Foundational Rules

### Rule 1 - Trust First

The Hypernet strives for the highest level of trust possible.

Before any human or AI action that changes data, visibility, permissions, governance, publication, deletion, migration, or automated execution, the actor must ask:

```text
Does this action have any chance of betraying trust in any way?
```

If the answer is yes, unknown, or cannot be evaluated from available context, the actor must pause, document the concern, and use the trust alarm or review path appropriate to the risk.

### Rule 2 - Everything Has A Place

Everything official in the Hypernet has an address.

If it has no address, it may be scratch, draft, runtime state, or private local cache, but it is not an official Hypernet document or object.

### Rule 3 - Objects And Links Are Local Type Changes

New content kinds should normally be defined as object types under `0.5.*`, link types under `0.6.*`, flags under `0.8.*`, workflows under `0.7.*`, app loads under `0.5.18.*`, and boot sequences under `0.5.17.*`.

### Rule 4 - `*.0` Is Structural Behavior

If a change affects how a node or subtree behaves, inherits fields, controls publication, handles social interaction, hosts projects, reports pulse, delegates AI work, stores versions, escalates alarms, or defines local extensions, it belongs in `N.0.*`.

### Rule 5 - Inheritance Is Additive

A node inherits control-plane definitions from every ancestor:

```text
0.0 universal baseline
-> A.0 top-level category control plane
-> A.B.0 branch control plane
-> A.B.C.0 node control plane
-> A.B.C.D.0 deeper node control plane
```

Each level can add detail, narrow permissions, define local formats, or create local extensions. It should not silently contradict an ancestor. If it must diverge, the divergence is documented in that node's `N.0.0` schema/inheritance section.

## Compatibility With 0.0.4

`0.0.4` is active and defines a v1 metadata layout where `N.0.1` means Publishing and Distribution. Matt's 2026-05-07 brain dump strongly wants `N.0.1` to become Social and Connection and `N.0.2` to become Projects and Work.

This document is therefore a v2 proposal, not an immediate replacement. Existing v1 nodes remain valid. New v2 nodes should state `control_plane_version: "2.0-draft"` in `N.0.0`.

Recommended migration:

- Keep v1 meanings readable as legacy aliases.
- Move publishing/version/archive into v2 `N.0.5`.
- Move security/trust/alarm into v2 `N.0.6`.
- Move analytics/pulse/help requests into v2 `N.0.8`.
- Use `N.0.0` to state whether a node follows v1, v2, or a mixed transition.

## Feedback To Matt

Strong agreement:

- Treating `*.0` as the control plane is the right abstraction. It makes the database self-defining without requiring every new behavior to become code first.
- The distinction between "new data type" (`0.5`/`0.6`) and "new structural behavior" (`*.0`) should become a primary design rule.
- Social should be node-local. A "people reading the same book in a library" model is more Hypernet-native than a separate social network bolted on top.
- Project queues should be node-local and roll up pressure. This directly matches the swarm/fractal-manager work from `0.7.5.5`.
- Trust must be the hardest guardrail. The alarm button needs to be explicit, fast, and non-punitive when used in good faith.

Concerns:

- The `N.0.1` social proposal conflicts with the active `0.0.4` v1 layout where `N.0.1` means publishing. This is solvable, but it must be named as a migration, not silently changed.
- `*.0` nodes can become larger than content nodes. That is acceptable if `N.0.0` always provides a machine-readable index and large social/project/archive data can shard below the channel.
- A universal `*.0` layout should not force every node to instantiate every channel. The rule should be "reserved and addressable," not "physically present everywhere."
- Trust-first prompts are necessary but not sufficient. The destructive-action gate and trust alarm must be backed by workflow and tests.

Open questions:

- Should v2 `N.0.1` definitely be social, or should social be `N.0.4` to preserve more v1 compatibility?
- Should `N.0.2` be projects/work and `N.0.3` AI/swarms, or should AI come before projects?
- What is the minimum machine-readable control-plane index format for `N.0.0.8`?
- Which actions require mandatory multi-AI red-team review in v1: delete, backup deletion, permission change, publish, migration, external post, or all of those?
- Should node-local social discovery be opt-in, opt-out, or inherited from parent category?
